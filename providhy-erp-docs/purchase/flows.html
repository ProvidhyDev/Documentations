Business Flows (Traced)

At runtime the Purchase service is the purchase-side transaction engine of the ERP. It owns seven document types - requisition, purchase order, purchase invoice, purchase return, supplier payment, cheque (a flag on the supplier payment row) and expense entry - and every document lives the same lifecycle: draft, submitted_for_approval, approved, plus the escape hatches cancelled and rejected. A single status endpoint per document type drives all state changes; which transitions are legal is decided at request time by the tenant's approval-work configuration fetched from the Configuration service (BASIC flow with an approver role, or CUSTOM flow with compulsion checks), and the per-action permission (add_edit vs approve_cancel) is decided before that, by the IAM permission check. The stock ledger does not live here: approving or cancelling an invoice or return moves stock by calling the ProductManagement service over internal password-gated HTTP endpoints, and the accounting journal is posted by the Accounting service, called through Celery tasks (which in several places run synchronously in the request thread). Every state change emits an activity log through the Events service, with a notification on submit and reject; most transitions also emit a Kafka record through the Kafka producer service - the supplier payment and cheque endpoints are the exception and emit no Kafka at all.

Citations are relative to the service repo root at sha ad05cc9b47e36020b61ac46ed701781aeefbf7d3.

Requisition - status and cancel-submission

What happens: one POST endpoint moves a requisition through its whole lifecycle. The request body carries the target status (submitted_for_approval, approved or cancelled) and the tenant's approval-work configuration decides which shape the state machine has: in the BASIC flow the creator submits to a named approval_user and only that user can approve, the creator can self-approve a draft, and approved requisitions can be cancelled by anyone in the tenant; in the CUSTOM flow only approve (from draft or submitted) and cancel-of-approved are legal, each guarded by a compulsion check. Submit and approve re-validate every product against the ProductManagement service before touching the row. A second endpoint, cancel-submission, sends a submitted requisition back to draft either as a plain revert (creator only) or as a rejection (anyone else, with comment, rejected flag and an error notification). There is no journal, no stock and no Kafka on the Kafka side of things except the record events - the requisition is a paper document.

Trace (POST /api/purchase/requisition/status//)

  1. Auth: IAMAuthenticationBackendPurchase validates the token via IAM POST {IAM}api/token/verify/ (dashboard/auth_backends.py:25-58, 61-71); HasPermission then denies non-GET on an expired subscription, passes tenant_root, otherwise GETs {IAM}api/internal-check-permissions/ and requires feature PR1101 plus the action for the call (dashboard/auth_backends.py:102-134). initial() sets the action: anything other than submit requires approve_cancel (purchase/purchase_requisition/views.py:258-266).
  2. The row is fetched tenant-scoped, 400-style ValidationError when missing (views.py:268-277).
  3. Inside one atomic, the tenant's APPROVAL_WORK/FLOW configuration is fetched from the Configuration service; missing configuration is a 503 (views.py:280-317, dashboard/send_request.py:26-46, dashboard/helper.py:109).
  4. BASIC flow routing: submit only from draft; approve from submitted only when the caller is the approval_user, or from draft only when the caller is the entry_by, with the compulsion check (compulsion=true means "must be submitted first") on both approve branches; cancel from submitted only by the approval_user, or from approved by anyone (views.py:319-357, dashboard/helper.py:816-821).
  5. CUSTOM flow routing: approve from any state except cancelled, cancel only from approved; both go through the custom compulsion check (compulsion=true means "must be draft first") (views.py:300-317, dashboard/helper.py:824-829).
  6. Submit: every item's product is re-validated in one ProductManagement check-multiple call (views.py:360-372, dashboard/helper.py:525-529, dashboard/helper.py:138); the approval fields are set, the rejection fields cleared, row saved (views.py:374-382); then a BASIC notification to the approval_user, an activity log, and a Kafka record with the full KafkaPurchaseRequisitionSerializerForRecord payload (views.py:384-412, dashboard/custom_functions.py:30-52, 55-74, dashboard/kafka_function.py:47-79, purchase/purchase_requisition/serializers.py:325-349).
  7. Approve: same product re-validation; approved_by/date/time/comment set, rejection cleared, saved (views.py:418-442); activity log plus a Kafka approval record (views.py:444-464). No notification on approve.
  8. Cancel: related purchase orders that are approved or submitted block the cancel (views.py:470-490); otherwise cancelled_by/date/comment set, saved; activity log plus a minimal Kafka cancel message (id, unique_id, transaction_type) (views.py:491-524).

Trace (POST /api/purchase/requisition/cancel-submission//)

  1. Auth: same backend, feature PR1101, action pinned to VIEW even for POST (views.py:527-536) - the role rules are enforced in the body instead.
  2. Only a submitted row can be touched (views.py:556-567).
  3. Rejection branch (type=rejection, caller not the creator): status back to draft, rejected flag/comment/by/date set, approval fields cleared; activity log, an ERROR notification, and a Kafka record carrying the REJECTED status value (views.py:568-603).
  4. Revert branch (no type, caller is the creator): status back to draft, approval fields cleared; activity log and a Kafka record - which is also stamped with the REJECTED status value even though the HTTP answer says reverted (views.py:605-629).
  5. Any other combination (wrong user, wrong type, not submitted) is a 400 (views.py:631-642).

Side effects

  • Events service: notification on submit and rejection, activity log on every transition (dashboard/custom_functions.py:30-52, 55-74, dashboard/helper.py:105-106).
  • Kafka producer: full record on submit and approve, minimal id message on cancel and rejection (dashboard/kafka_function.py:47-79).
  • ProductManagement: product check-multiple on submit and approve (dashboard/helper.py:138).
  • Configuration: approval-work configuration read on every status call (dashboard/helper.py:109).
  • No journal, no stock movement, no supplier ledger change.

Order - status and cancel-submission

What happens: the purchase order follows the same lifecycle engine as the requisition, with two additions. First, an order can be created against an approved requisition, in which case every state transition re-runs the requisition quantity math - approving or cancelling must keep the requisition item's remaining counter and used_status consistent. Second, an order is the anchor document of the receiving chain: cancelling it is blocked while any GRN or purchase invoice against it is still approved or submitted. Approving an order that came from a requisition also consumes the requisition item's remaining quantity. No stock moves and no journal is posted from the order endpoints - stock-in happens later at invoice (or GRN) approval.

Trace (POST /api/purchase/order/status//)

  1. Auth: IAM + HasPermission, feature PR1102, approve_cancel for anything but submit (purchase/purchase_order/views.py:249-262).
  2. Tenant-scoped fetch (views.py:264-271); fiscal-year check on po_date is commented out (views.py:305).
  3. Configuration fetch, 503 when absent (views.py:298-340, dashboard/send_request.py:26-46).
  4. BASIC submit: when an order has a requisition, each item's quantity is validated against the requisition item's remaining (validation_check.py:31-46) and the requisition used_status is recomputed (validation_check.py:7-28); without a requisition, each product is validated via ProductManagement (views.py:414-482); approval fields set, rejection cleared, saved; notification to the approver, activity log, Kafka record with full payload (views.py:414-482).
  5. BASIC approve: from submitted by the approval_user, or from draft by the creator, with the compulsion check; the requisition quantity validation runs again before the approved fields are written; activity log and Kafka (views.py:484-554, 522-554).
  6. BASIC cancel: check_cancellation refuses the cancel when a GRN or a purchase invoice against the order is approved or submitted (views.py:273-296); from submitted the requisition quantities are rolled back before the cancel (views.py:555-564, 565-591); from approved the same rollback then the cancel; activity log and minimal Kafka message.
  7. CUSTOM flow: approve from any state except cancelled (compulsion checked), cancel only from approved (views.py:321-340).

Trace (POST /api/purchase/order/cancel-submission//)

  1. Auth: IAM + HasPermission, action pinned to VIEW (views.py:592-601).
  2. get_object is NOT tenant-scoped - it fetches the order by pk alone (views.py:603-608) - any authenticated user can address another tenant's order here (flagged).
  3. Rejection branch (non-creator, submitted): requisition quantities re-validated when the order has a requisition (views.py:610-616, 630-642); rejected flag/comment/by/date set, approval fields cleared, saved; activity log, ERROR notification, Kafka record stamped rejected (views.py:644-668).
  4. Revert branch (creator, no type): same requisition validation, status back to draft; activity log and a Kafka record also stamped rejected while the answer says reverted (views.py:670-695).
  5. Anything else is a 400 (views.py:696-703).

Side effects

  • Events service: notification on submit and rejection; activity log on every transition (dashboard/custom_functions.py:30-74).
  • Kafka: full record on submit and approve, minimal message on cancel and rejection (dashboard/kafka_function.py:47-79).
  • ProductManagement: product checks on submit and approve (dashboard/helper.py:513-529).
  • Configuration: approval-work config per call.
  • Requisition rows: remaining and used_status counters are mutated on submit, approve and cancel when the order is requisition-backed (purchase/purchase_order/validation_check.py:7-65).
  • No journal, no stock movement.

Invoice - status, cancel-submission and the quick payment

What happens: the purchase invoice is the heaviest document in the service. The catalog marks the whole v1 invoice family as superseded and lists only /v2/ as latest, but /v2/ exists for list and create only - the status, cancel-submission and delete views are the v1 classes, still registered and still the only implementation of the flow (flagged). Approving an invoice is a cross-service transaction: depending on the tenant's valuation configuration the stock is valued at this moment (new batches are created in ProductManagement and the stock-in call goes out), the linked purchase order's remaining-invoice counter is consumed, and - when the tenant has accounting automation configured - the accounting journal is posted by calling the Celery journal task directly in the request thread (not via .delay). Cancelling an approved invoice reverses the order counter and cancels the journal. An approved invoice can also be paid through the quick-payment path, which mints approved supplier payment rows from the payment_allocations JSON stored on the invoice row at create time.

Return - status, cancel-submission and the invoice ledger

What happens: the purchase return is the supplier-side mirror of the sales return - a credit note against an approved purchase invoice. The same lifecycle engine applies (BASIC or CUSTOM from the Configuration service), with two money-side side effects that set it apart from the order and requisition flows. First, approving or cancelling a return rewrites the referenced invoice's remaining_amount (minus the grand total on approve, plus on cancel) and emits an extra Kafka record stamped update_remaining on the purchase invoice. Second, approving a return - and cancelling an approved one - moves stock: the stock-out that returns goods to the supplier, but only when the tenant's PURCHASE_FLOW/FLOW valuation configuration names purchase_invoice; the call goes to the ProductManagement purchase-return manipulation endpoint, v1 or v2 by the row's revamped flag. When the tenant has a PURCHASE_FLOW/AUTOMATION configuration, the journal is posted by calling the Celery journal task directly in the request thread. Submit is deliberately quiet: product re-checks and quantity validation only - no stock, no journal, no ledger write.

Payment - status, cancel-submission, quick payment and the verified eSewa exclusion

What happens: the supplier payment is the money-out document - an advance to the supplier, a payment allocated to purchase invoices and expense entries, or a cheque (a flagged row of the same model, traced in its own section). The lifecycle engine is the usual BASIC/CUSTOM split, with one conspicuous difference from every other document in this service: no Kafka is emitted on any payment lifecycle transition - the only events are the notification on submit and the activity log on each transition. Approving with apply_advance deducts from the supplier's DR opening balance first and then FIFO from the advance_amount of earlier approved payments; the item allocations are validated against the invoice remaining amounts. The journal is posted asynchronously via the Celery .delay, unlike the invoice and return paths that call the task in the request thread. The quick-payment path bypasses the workflow entirely: it mints one APPROVED quick payment per allocation straight from the invoice or expense screen, each with its own journal queued on commit. Verified exclusion: the eSewa Payment-Service is not referenced anywhere in this service (grep for esewa, miniapp and federated over the whole source tree returns zero matches). The payment code is ledger-only: source_account is a bank or cash GL account with optional TDS and bank-charge legs, and payment_method is a display field (supplier_payment/models.py:15-47, supplier_payment/serializers.py:51-263). It is not a gateway to a payment provider and is not modeled as a path.

Cheque - record status and settlement status

What happens: a cheque is a SupplierPayment row flagged is_cheque - the BouncedCheques model in purchase/cheque/models.py:13 subclasses it for the bounced view. The status endpoint moves two state axes in one call: the record status (draft, submitted, approved, cancelled - the usual engine) and the settlement status of the cheque itself (pending, cleared, bounced, void, with an expired guard). The request may carry status, cheque_status or both - approve-and-clear is one call. Two notable behaviors: the endpoint only implements the BASIC flow - a tenant on the CUSTOM flow gets a 400 not-updated for every status call (views.py:1076-1088) - and, like plain payments, the cheque endpoints emit no Kafka at all. Approving a cheque that settles validates the allocations and queues the journal, but unlike plain supplier payments it performs no opening/advance deductions; it is cancelling a CLEARED cheque that restores the deductions.

Trace (POST /api/purchase/cheque/status//, view at purchase/cheque/views.py:625)

  1. Auth: IAM + HasPermission, feature PR1308 (the accounting cheques feature), approve_cancel for anything but submit (views.py:625-647, dashboard/choices.py:199).
  2. Request validation inside the atomic: at least one of status or cheque_status is required; both are checked against their choice lists; submit requires approval_user (views.py:999-1024).
  3. Settlement guards: no settlement change before the row is approved (views.py:1033-1037); no change once the cheque is expired (views.py:1039-1043, supplier_payment/models.py:134-136); settlement moves only out of pending (views.py:1045-1056).
  4. Configuration fetch (views.py:1058-1063); can_settle_cheque computed on the model (views.py:1072-1074, supplier_payment/models.py:159).
  5. BASIC settlement-first branch (views.py:832-849): an approved row can be marked bounced or void directly - bounced stores the bounce reason - without touching the record status.
  6. BASIC record routing: submit from draft (views.py:851-855, 726-756); approve from submitted by the approval_user, from draft by the creator, or an approved row cleared in the same call, all after the basic compulsion check (views.py:857-887); cancel from submitted by the approval_user or from approved by anyone (views.py:889-909).
  7. approved() (views.py:758-830): blocks approval when any allocated invoice is already fully paid (views.py:761-763, supplier_payment/models.py:153-157); when can_settle_cheque, validates the allocations and queues journal_creation_task.delay when the PURCHASE_FLOW/AUTOMATION configuration exists (views.py:765-790, purchase/purchase_invoice/tasks.py:40-71); record and settlement fields written (views.py:794-807); activity log only when the row was not already approved (views.py:809-816).
  8. cancelled() (views.py:911-949): when the cheque was cleared, restores the opening and LIFO advance deductions and re-validates the allocations (views.py:912-925, 951-997); cancelled fields written and deduction_from_opening zeroed; journal cancellation .delay when the journal flag is set (views.py:927-937); activity log (views.py:939-945).
  9. After a 200 result the row is saved a second time and the events fan out: an activity log per settlement change and, when a user other than the creator changed the approved row, a notification to the creator - success on cleared, warning on bounced or void (views.py:1080-1083, 656-704).
  10. CUSTOM flow: unhandled - the endpoint falls through to 400 not-updated for every transition (views.py:1085-1088).

Trace (POST /api/purchase/cheque/cancel-submission//, view at views.py:1092)

  1. Auth: IAM + HasPermission, feature PR1308, action pinned to VIEW (views.py:1092-1102).
  2. get_object is tenant-scoped and filtered to is_cheque rows - unlike the payment and return cancel-submission endpoints (views.py:1104-1111).
  3. Only a submitted row can be touched (views.py:1113-1126); fiscal-year check on cheque_date (1118).
  4. Rejection (type=rejection, non-creator): rejected fields; activity log; ERROR notification (views.py:1127-1156).
  5. Revert (no type, creator): back to draft with an activity log (views.py:1158-1175).
  6. Any other combination is a 400 (views.py:1177-1184). No Kafka.

Side effects

  • Events: notification on submit and rejection; activity log on submit, approve, cancel and every settlement change (views.py:738-752, 809-816, 939-945, 656-704).
  • Accounting: journal creation .delay at a settling approve when the automation config exists; journal cancellation .delay at cancel of a journaled cheque (views.py:782-790, 935-937).
  • Supplier ledger: no deductions at cheque approve; opening and LIFO advance restore only when cancelling a cleared cheque (views.py:912-925, 951-997).
  • Kafka: none.
  • The notf-issued-due-date route is an internal near-due list for the notification job and modify-cheque a shared-password bulk flag fix (views.py:485-548, temp_views.py).

Expense - the registry-driven lifecycle

What happens: the expense entry is the odd one out - a router-based ViewSet with a static, registry-driven state machine instead of the Configuration-service flow. Legal transitions are fixed: draft to submit or approve, submitted to approve, reject or cancel, approved to cancel (views.py:292-311), and a reject lands the row back on draft (views.py:546-547). The role rules live in the same registry: the creator submits and self-approves, the approval_user approves and rejects, and an approved expense can be cancelled by anyone unless a non-quick approved supplier payment is allocated on it (views.py:313-345). Approving an expense mints quick supplier payments from the payment_allocations stored on the row; cancelling voids them. The Kafka and journal work is scheduled on transaction commit, and the journal at approve is called synchronously in the request thread - with no automation-config gate, unlike the invoice and return paths.

Trace (POST /api/purchase/expense/status//, view at purchase/expense/views.py:431)

  1. Auth: IAM + HasPermission, feature PR1108; initial() maps POST status to approve_cancel for anything but submit, and create/edit/delete/cancel-submission to add_edit, GET to view (views.py:24-55).
  2. Tenant-scoped fetch (views.py:84-98, 432-438).
  3. validate_status_change: the status value check, the transition registry, the user registry, and the no-active-payment cancel block (views.py:281-345).
  4. handle_kafka is queued on commit: only supplier and customer entity types emit; approve sends the dual record via call_kafka_for_bill, submit and cancel send a single record (views.py:481-511, 442).
  5. handle_status_change: submit stores the approval_user (required); every branch writes status, comment, date and changed-by; reject maps to draft; approve mints the quick supplier payments via post_quick_supplier_payment_for_expense; cancel voids them via void_quick_supplier_payment (views.py:534-558, dashboard/custom_functions.py:380, 497).
  6. handle_post_status_change is queued on commit: the events fan-out - notification on submit, activity log on approve and cancel (views.py:456-479) - and the journals: journal_creation_task called synchronously at approve, journal_cancellation_task.delay at cancel (views.py:519-532, purchase/purchase_invoice/tasks.py).
  7. Response is 200 with id, unique_id and an updated message (views.py:446-454).

Trace (POST /api/purchase/expense/cancel-submission//, view at views.py:375)

  1. Auth: IAM + HasPermission, feature PR1108, action add_edit (views.py:35-55, 375-377).
  2. Only a submitted row can be touched (views.py:383-387).
  3. Rejection (type=rejection): status_changed_by and the comment are stored and an ERROR notification is sent (views.py:390-401).
  4. Revert (no type): the approval fields are cleared (views.py:402-406).
  5. Both branches set draft, save, write an activity log and emit the EXPENSE_ENTRY_REJECT_RECORD Kafka record (views.py:408-422) - a revert is reported as rejected to Kafka.

Trace (POST /api/purchase/expense/check-reference/, view at views.py:561)

Duplicate pre-flight: given an invoice_reference and an optional id, it reports whether another expense in the tenant already carries that reference - a check on the same row returns exists false (views.py:560-586).

Side effects

  • Kafka: on commit only; approve dual, submit/cancel single; suppressed for non supplier/customer entity types (views.py:481-511); reject record on both cancel-submission branches (views.py:417-422).
  • Accounting: journal creation at approve - synchronous, no automation-config gate; journal cancellation .delay at cancel (views.py:519-532, purchase/purchase_invoice/tasks.py:40-120).
  • Supplier payments: quick payments minted at approve from the stored allocations and voided at cancel (views.py:552-557, dashboard/custom_functions.py:380, 497).
  • Events: notification on submit and rejection; activity log on approve and cancel and on cancel-submission (views.py:456-479, 410-416).
  • Create validates attachment file types before saving (views.py:116-131, expense/utils.py).
