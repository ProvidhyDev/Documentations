Purchase . Expense

Expense entries: supplier/customer/account expense bills (with line items, TDS and opening payment allocations) that go through the same draft -> submit -> approve workflow as other purchase documents and are later settled by supplier payments. This app is a DRF viewset on a default router (all routes hang off the app root).

All routes below are relative to the service root; on the live service they sit under /api/purchase/expense/ (core/urls.py:38, router purchase/expense/urls.py:6-7). Source: purchase/expense/urls.py, views.py, serializers.py, models.py @ ad05cc9b.

Catalog note: the catalog lists 8 expense routes with paths rendered as /api/purchase/expense///... (triple slash) - a catalog path-normalization quirk; the real paths are the single-root paths below. The catalog's root row also advertises GET (list), but the viewset defines no list action, so a plain GET / is not functional (unverified at runtime).

Endpoint map

# Method Path Purpose Auth
1 POST / Create expense entry IAM + PR1108 ADD_EDIT
2 GET /search/ Filtered search (list screen) with party enrichment IAM + PR1108 VIEW
3 GET /detail// Expense detail IAM + PR1108 VIEW
4 POST/PUT/PATCH /detail// Update expense entry IAM + PR1108 ADD_EDIT
5 POST /delete// Delete draft expense IAM + PR1108 ADD_EDIT
6 POST /cancel-submission// Reject or revert a submitted expense IAM + PR1108 ADD_EDIT
7 POST /status// Status change (submit / approve / reject / cancel) IAM + PR1108 VIEW or APPROVE_CANCEL
8 POST /check-reference Invoice-reference duplicate check IAM + PR1108 VIEW

Routes: 7 catalog route paths (the catalog's 8th row is the malformed root row above). Feature PR1108 (AllFeatures.EXPENSE_ENTRY, dashboard/choices.py:181).

1. POST / - create

  • View: ExpenseEntryViewSet.create - purchase/expense/views.py:116 (router root, purchase/expense/urls.py:7).
  • Auth: IAMAuthenticationBackendPurchase (views.py:27-29) + HasPermission (applied per action by dashboard/auth_backends.py:74-134); POST create requires ADD_EDIT (views.py:37-52). required_feature_permission PR1108 (views.py:30).
  • Request (JSON/form-data): entry_date (required, serializers.py:52-55); with-bill entries also need invoice_date, invoice_reference, payment_terms (serializers.py:57-85, 190-196); entity_id + entity_type (supplier / customer / account); items (required for with-bill, each with account_id, vat - serializers.py:17-29, 182-188); tds_enabled/tds_type_id/tds_amount, tds_gl; description; payment_allocations (optional opening payments - serializers.py:159-180); files (image uploads, views.py:117-131).
  • Processing: no explicit transaction wrapper in the view; serialized by ExpenseEntryCreateSerializer (views.py:134-140, serializers.py:30-352): header totals computed and sanitized (calculate_summary + Configuration form-data sanitization - serializers.py:190-311), account/entity/payment-term validity fetched asynchronously from the Accounting and party services (network_validation, serializers.py:87-143, helper.task_runner), opening payment allocations validated against the remaining amount (serializers.py:159-180); fiscal year injected (views.py:133); tenant_id + entry_by set on save (views.py:140-142); uploaded files pushed to the Document service (views.py:143, dashboard/helper.py:212); unique_id generated with the EXP prefix (models.py:83-90).
  • Response: 201 { id, unique_id, message }; 400 with parsed serializer errors (views.py:135-139); 400 for invalid file types (views.py:127-131).

2. GET /search/ - filtered search

  • View: ExpenseEntryViewSet.search - views.py:153 (action url_path search, views.py:153-154).
  • Auth: IAM + VIEW (views.py:53-54).
  • Request (query): q, status (default draft, invalid status -> 400, views.py:209-212), supplier_ids / customer_ids (comma lists, views.py:206-207, 219-229), payment_status (views.py:208, 233-234).
  • Processing: tenant-scoped (views.py:230-232); q matches unique_id or invoice_reference (views.py:213-217); row visibility via helper.user_filter (views.py:159-161); supplier and customer names are gathered asynchronously from the party service and injected (views.py:162-197).
  • Response: 200 paginated ExpenseEntryListSerializer list (views.py:190-198, serializers.py:353-391).

3/4. GET / POST|PUT|PATCH /detail// - detail & update

  • View: ExpenseEntryViewSet.edit - views.py:237 (action url_path detail/, views.py:237-238).
  • Auth: IAM; GET -> VIEW, POST/PUT/PATCH -> ADD_EDIT (views.py:37-54).
  • GET: ExpenseEntryDetailSerializer (views.py:249-250, 275-279, serializers.py:417-609), 404 when missing (views.py:240-248).
  • POST/PUT/PATCH: ExpenseEntryCreateSerializer re-validation as in create (views.py:257-273); 400 on validation failure (views.py:262-266); 200 { id, unique_id, message } on success (views.py:268-273).

5. POST /delete// - delete

  • View: ExpenseEntryViewSet.remove_expense - views.py:347 (action url_path delete/, views.py:347-348).
  • Auth: IAM + ADD_EDIT (views.py:46-52).
  • Behavior: draft only (views.py:359-363); 404 when missing (views.py:350-358); 200 { id, unique_id, message } (views.py:364-370).

6. POST /cancel-submission// - reject or revert submission

  • View: ExpenseEntryViewSet.cancel_submission - views.py:372 (action url_path cancel-submission/, views.py:372-375).
  • Auth: IAM + ADD_EDIT (views.py:46-52).
  • Request (JSON): type (rejection to reject; omit to revert), comment.
  • Behavior: only while in submit_for_approval (views.py:383-387); rejection sets the rejected fields, ERROR notification (views.py:390-401); revert clears the approval fields (views.py:402-406); both end in draft (views.py:408-409); activity log (views.py:410-416); Kafka record type expense_entry_reject_record on both branches (views.py:417-422, dashboard/kafka_function.py, dashboard/choices.py:445).
  • Response: 200 { id, unique_id, message }; 404/400 for missing or wrong-status records.

7. POST /status// - status change

  • View: ExpenseEntryViewSet.status_change - views.py:430 (action url_path status/, views.py:430-431).
  • Auth: IAM; POST with status != submit_for_approval requires APPROVE_CANCEL, else VIEW (views.py:37-54).
  • Request (JSON): status (submit_for_approval / approved / rejected / cancelled), approval_user (required for submit), comment.
  • Guards: allowed transitions draft -> submit/approve, submit -> approve/reject/cancel, approved -> cancel (views.py:292-311); approve/reject/submit restricted to the creator or the approval_user (views.py:314-333); cancel blocked while an approved non-quick payment exists against the expense (views.py:335-345); rejected transitions land on draft (views.py:544-548).
  • Processing: atomic (views.py:432); on commit, Kafka record for supplier/customer expenses: approved -> call_kafka_for_bill (bill record), submit -> expense_entry_submit_for_approval_record, cancel -> expense_entry_cancel (views.py:442, 481-511, dashboard/choices.py:388-420); after commit: notification on submit, activity log on approve/cancel (views.py:451-453, 456-479), journal creation task on approve and journal cancellation task on cancel via Celery (views.py:519-532, tasks in purchase/purchase_invoice/tasks.py); approving with quick payments posts the quick supplier payments, cancelling voids them (views.py:552-557, custom_functions).
  • Response: 200 { id, unique_id, message }; 404/400 for missing or invalid transitions.

8. POST /check-reference - invoice-reference duplicate check

  • View: ExpenseEntryViewSet.check_invoice_reference - views.py:560 (action url_path check-reference, views.py:560-561).
  • Auth: IAM + VIEW (views.py:53-54).
  • Request (JSON): invoice_reference (required), id (optional - excludes the record itself).
  • Response: 200 { exists: bool }; 400 when invoice_reference is missing; 404 when the given id does not exist (views.py:562-586).
