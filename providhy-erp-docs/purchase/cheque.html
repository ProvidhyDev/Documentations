Purchase . Cheque

Issued cheques for supplier payments. A cheque is a SupplierPayment flagged is_cheque=True (unique_id prefix IC instead of SP, models.py:98-113 in supplier_payment) with an extra lifecycle on top of the normal payment workflow: pending -> cleared / bounced / void, with due-date and expiry tracking. The search screen merges locally issued cheques with cheques received by the Sales service (remote fetch), and a purchase cheque can be created by converting a sales cheque (delete in Sales + document transfer).

All routes below are relative to the service root; on the live service they sit under /api/purchase/cheque/ (core/urls.py:37). Source: purchase/cheque/urls.py, views.py, temp_views.py, serializers.py @ ad05cc9b.

Routes: 9 catalog routes. Feature PR1308 (AllFeatures.CHEQUES, dashboard/choices.py:199).

1. GET / - list by status

  • View: ChequeCreate - purchase/cheque/views.py:40 (route urls.py:7).
  • Auth: IAMAuthenticationBackendPurchase + HasPermission (views.py:39-44); GET requires VIEW (views.py:47-53).
  • Request (query): status (required - 404 UNKNOWN_STATUS if invalid, views.py:60-61).
  • Processing: SupplierPayment rows for the tenant and status (views.py:62-64), user_filter row visibility (views.py:65-67), CustomTransactionPagination (views.py:45, 68).
  • Response: 200 paginated ChequeListSerializer list (views.py:69-72, serializers.py).

2. POST / - create

  • View: ChequeCreate - views.py:40 (route urls.py:7).
  • Auth: IAM + HasPermission; POST requires ADD_EDIT (views.py:47-53).
  • Request (JSON): party (supplier JSON), cheque_number, amount, bank_account, cheque_date, cheque_status (required - views.py:107-116); optional items (allocations, JSON-string or list, views.py:133-137), files (image uploads), and the query param id - when present it is the Sales cheque id to convert (views.py:118-120).
  • Processing: one atomic transaction (views.py:139); fiscal-year check on cheque_date (views.py:127-129); fiscal year injected (views.py:130-131); serialized by ChequeSerializerWriteOnly (views.py:145-149, serializers.py) which creates the SupplierPayment with is_cheque=True.
    • New cheque: uploaded files pushed to the Document service (helper.upload_image, views.py:150-153, dashboard/helper.py:212).
    • Conversion (query id set): the old sales cheque is deleted from the Sales service (POST /api/sales/cheque/delete-internal// - views.py:74-87, dashboard/helper.py:123) and its documents are transferred via the Document service update-document-internal endpoint (views.py:89-103, dashboard/helper.py:152); the response then reports the converted cheque with cheque_type issued (views.py:167-175).
    • Activity log entry written with module ACCOUNTING (observed choice, views.py:158-165, custom.create_activity_log at dashboard/custom_functions.py:55).
  • Response: 201 { id, message } (+ data.cheque_type when converting); 400 with serializer errors (views.py:178-182).

3. GET /search/ - merged issued + received cheques

  • View: ChequeSearchView - views.py:383 (route urls.py:8).
  • Auth: IAM + HasPermission, action VIEW (views.py:383-391).
  • Request (query): q, status (required - 404 if invalid, views.py:433-435), filterset fields (ChequeFilterSet, views.py:389, applied at views.py:448).
  • Processing: local issued cheques (is_cheque=True) ordered by created for draft, else modified (views.py:437-446); remote received cheques are fetched from the Sales service list-internal endpoint (POST /api/sales/cheque/list-internal/ - views.py:393-426, dashboard/helper.py:122) and the two result sets are merged in sort order page by page (MergedChequeResultSet, views.py:314-379, 467-476); party name enrichment (views.py:477-480, dashboard/helper.py:1244-1248).
  • Response: 200 paginated merged list of ChequeListSerializer rows; remote fetch failures degrade to local-only results (views.py:419-423).

4/5. GET / POST /detail// - detail & update

  • View: ChequeRetrieveUpdate - views.py:185 (route urls.py:9-11).
  • Auth: IAM + HasPermission; GET -> VIEW, POST -> ADD_EDIT (views.py:185-199 range).
  • Behavior: tenant-scoped cheque lookup, read-only serializer for GET; update via the cheque write serializer for POST. Guard rules beyond tenant scoping - unverified here.

6. POST /status// - payment status and/or cheque status change

  • View: ChequeChangeStatusView - views.py:625 (route urls.py:10).
  • Auth: IAM + HasPermission; a POST whose status is not submit_for_approval requires APPROVE_CANCEL (views.py:639-647).
  • Request (JSON): status (payment status: submit_for_approval / approved / cancelled) and/or cheque_status (pending / cleared / bounced / void) - at least one required (views.py:1005-1006); approval_user required when submitting (views.py:1020-1024); bounced_reason when bouncing, cheque_status_comment optional.
  • Guards: cheque_status can only be changed while approved (views.py:1033-1037) and not after expiry (views.py:1039-1043); from an approved non-pending state only pending->other moves are allowed (views.py:1045-1056).
  • Processing: basic approval-work flow only (configuration fetched from the Configuration service, views.py:1058-1063, 1076-1088; a custom-title configuration yields 400 NOT_UPDATED).
    • submit_for_approval: approval fields saved, notification + activity log (views.py:726-756).
    • approve: blocked while the payment fully pays invoices that are already fully paid (views.py:761-763); when the payment settles (cleared) supplier opening-balance/advance deductions and allocation remaining amounts are applied (views.py:765-780, validation_check), and - when the tenant has an accounting-automation purchase-flow configuration - the journal creation Celery task is dispatched (views.py:782-790, tasks in purchase/purchase_invoice/tasks.py); approval fields saved (views.py:794-807); activity log on first approval (views.py:809-816).
    • cheque_status changes on an approved cheque: cleared / bounced (with bounce_reason) / void set with status date (views.py:834-849, 706-715).
    • cancel: from submit (by approval_user) or from approved (views.py:895-909); cleared cheques restore supplier opening/advance deductions LIFO (views.py:911-925, 951-997); journal cancellation task when a journal exists (views.py:935-936); activity log (views.py:939-945).
    • After any successful 200 the cheque is saved and, when approved, a cheque-status activity log plus a notification to the entry-by user (when a different user made the change) is sent (views.py:656-704, 1080-1083).
  • Response: 200 { message } (SUBMITTED / APPROVED / CLEARED / CANCELLED / status-updated variants, views.py:753-756, 827-829, 843-849, 946-949); 400 INVALID_* / NOT_UPDATED otherwise (views.py:868-893, 1085-1088).

7. POST /cancel-submission// - reject or revert submission

  • View: ChequeSubmissionCancel - views.py:1092 (route urls.py:12-16).
  • Auth: IAM + HasPermission; action VIEW (views.py:1093-1102).
  • Behavior: only while in submit_for_approval (views.py:1120-1126); rejection by a non-creator sets rejected fields, activity log REJECTION + ERROR notification (views.py:1127-1156); revert by the creator clears submit fields, activity log CANCEL_SUBMISSION (views.py:1158-1175); otherwise 400 INVALID_REQUEST (views.py:1177-1184). No journal effect, no Kafka.

8. POST /delete// - delete (IAM)

  • View: ChequeDeleteAPIView (base ChequeDeleteBaseAPIView) - views.py:592 (route urls.py:18).
  • Auth: IAM + HasPermission, action ADD_EDIT (views.py:592-599).
  • Behavior: deletes the cheque; base-class guard rules (e.g. approved/cleared cheques) - unverified beyond the range shown.

9. POST /delete-internal// - delete (internal)

  • View: ChequeDeleteInternalView (base ChequeDeleteBaseAPIView) - views.py:612 (route urls.py:19).
  • Auth: internal - InternalRequestPermission, shared password in the POST body (dashboard/auth_backends.py:137-148); no IAM classes.
  • Behavior: same base-class delete logic as the IAM path; called by other services (e.g. the Sales service when converting a sales cheque - see endpoint 2).

10. POST /notf-issued-due-date/ - due/issue date sweep

  • View: ChequeNearingDueIssueDateView - views.py:485 (route urls.py:24).
  • Auth: internal - InternalRequestPermission, shared password in the POST body.
  • Request (JSON): cheque_field (due_date or payment_date - views.py:491-501).
  • Behavior: finds pending cheques due within 7 days (due_date) or 2 days (payment_date), excluding a quiet window around 3-6 days for due dates (views.py:495-532); supplier existence checked per row (helper.supplier_check, dashboard/helper.py:314, views.py:534-538); per-cheque due/overdue notifications are sent (tail of the method - unverified beyond the range shown).
  • Response: 200 after processing (response shape - unverified here).

11. POST /modify-cheque/ - migration helper

  • View: ChangeChequeField - purchase/cheque/temp_views.py:9 (route urls.py:29).
  • Auth: internal - InternalRequestPermission, shared password in the POST body.
  • Request (JSON): tenant_id (optional scope).
  • Behavior: bulk-flags all payment rows that carry a cheque_number and cheque_status as is_cheque=True and clears payment_method (temp_views.py:16-33).
  • Response: 200 { detail: "N cheques modified!" }.
