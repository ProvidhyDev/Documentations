Purchase . Invoice

Purchase invoice entry against approved purchase orders (or independently), with TDS handling, additional costs and opening payment allocations. In f1-production the catalog marks every unversioned invoice route as superseded by the revamped v2 list/create endpoint, so only /v2/ is documented here; the full v1 lifecycle surface is listed at the bottom.

All routes below are relative to the service root; on the live service they sit under /api/purchase/invoice/ (core/urls.py:34). Source: purchase/purchase_invoice/urls.py, views.py, serializers.py, models.py @ ad05cc9b.

Endpoint map

# Method Path Purpose Auth
1 GET /v2/ List invoices for a status (list screen, revamped) IAM + PR1105 VIEW
2 POST /v2/ Create revamped purchase invoice IAM + PR1105 ADD_EDIT

Routes: 1 catalog route (serves both GET and POST). Feature PR1105 (AllFeatures.PURCHASE_INVOICE, dashboard/choices.py:178).

1. GET /v2/ - list by status

  • View: PurchaseInvoiceListCreateRevamped - purchase/purchase_invoice/views.py:125 (route urls.py:11-15).
  • Auth: IAMAuthenticationBackendPurchase + HasPermission (views.py:124-129); GET requires VIEW (views.py:131-137).
  • Request (query): status (required - 404 UNKNOWN_STATUS if not a known status, views.py:145-147).
  • Processing: tenant-scoped (views.py:148-150), row visibility via helper.user_filter (views.py:151-153, dashboard/helper.py:755), CustomTransactionPagination (views.py:139, 154).
  • Response: 200 paginated PurchaseInvoiceListSerializer list (views.py:155-158, serializers.py:321-394).

2. POST /v2/ - create revamped invoice

  • View: PurchaseInvoiceListCreateRevamped - views.py:125 (route urls.py:11-15).
  • Auth: IAM + HasPermission; POST requires ADD_EDIT (views.py:131-137).
  • Request (JSON): entry_date, invoice_date, payment_term, items (required - views.py:195-198); each item needs product_id, quantity, uom (views.py:200-201). Other header fields from the model: supplier (JSON), purchase_orders (approved order id, optional), payee, invoice_number, reference, narration, description, discount_amount, discount_percentage, tds_type_id, tds_amount, excise_duty, declaration_number, country, import_date, additional_cost (list), payment_allocations (list) - models.py:24-113. Form-data (non-JSON) bodies are accepted; the nested fields items, supplier, additional_cost, payment_allocations are parsed from their string form (views.py:163-177).
  • Processing: one atomic transaction (views.py:179).
    • Fiscal-year validation of entry_date (custom.validate_fiscal_year, views.py:181-182); fiscal year injected from the request (views.py:184-187).
    • Serialized by PurchaseInvoiceSerializerRevampedWriteOnly (views.py:202-204, serializers.py:1391-1778):
      • validate(): additional_cost rows must have debit and credit account both filled or both empty (serializers.py:1535-1543); each payment_allocations row needs a source_account entity_id and a total_allocated_amount (serializers.py:1545-1553); total allocated payments may not exceed the invoice remaining amount (TDS-adjusted) (serializers.py:1555-1561); payment dates are stamped server-side (serializers.py:1563-1564); a supplied invoice_number is checked for uniqueness in the tenant (helper.is_unique, serializers.py:1568-1576, dashboard/helper.py:282).
      • create(): header data sanitized through the Configuration service form-data endpoint (serializers.py:1583-1584, 1404-1437, dashboard/helper.py:108, dashboard/send_request.py:8); unique_id generated via the tenant unique-id configuration (helper.generate_unique_id, serializers.py:1587-1592, dashboard/helper.py:835); payment term validated (helper.payment_term_check, serializers.py:1595, dashboard/helper.py:478); revamped flag set to True (serializers.py:1601); header totals via helper.calculate_totals_revamped (serializers.py:1609-1618, dashboard/helper.py:1031); TDS handled - with tds_type_id the TDS amount is required, the tenant TDS-payable GL account is fetched from the Configuration service (GL_MAPPING / TDS_Payable, serializers.py:1680-1701, dashboard/helper.py:109) and amount_after_tds is computed (helper.calculate_tds, dashboard/helper.py:730); remaining_amount starts as amount_after_tds (serializers.py:1690-1717).
      • Line items: sanitized (serializers.py:1629-1631); each order_item reference must belong to the invoice's purchase order (serializers.py:1633-1644); per-item totals via helper.calculate_item_totals_revamped (serializers.py:1645-1651, dashboard/helper.py:1100); per-item product check against ProductManagement (serializers.py:1652, dashboard/helper.py:82) with batch-stock validation for batch-kept products (serializers.py:1492-1517, 1671-1673, PRODUCT_BATCH_CHECK_SERVICE_API); items created with return_count = quantity (serializers.py:1659-1674).
      • Additional costs: applied per item or to the whole invoice (product == all), with VAT allowed only on import invoices (serializers.py:1719-1761, 1676).
      • Opening payments (payment_allocations) are stored on the invoice's payments JSON field (serializers.py:1533, 1566; model field models.py:113).
    • After save, uploaded images are pushed to the Document service (helper.upload_image, views.py:208-210, dashboard/helper.py:212).
  • Response: 201 { id, message } (views.py:211-215); 400 with the serializer error message (views.py:217-220).
  • Side effects: Document service upload (images); no Kafka call in the revamped create path itself (the v1 create path and the status-change endpoints - superseded, see below - are where journal/Kafka calls live).

Frontend usage (apps-frontend @ production)

The cross-reference lists /api/purchase/invoice/v2/ among the latest routes NOT directly referenced from the frontend - while the frontend does reference the superseded v1 invoice routes (create, detail, status, search, delete). So in f1-production the revamped v2 endpoint is the documented latest surface, but the shipped frontend was observed talking to the v1 family; whether v1 routes are still routed in the live deployment is unverified from this snapshot (the catalog marks them superseded).

Superseded / legacy routes (not documented)

All unversioned invoice routes are marked superseded in the catalog (replaced by the revamped /v2/ family; only the v2 list/create route exists as latest):

  • /invoice/ - v1 list/create (PurchaseInvoiceListCreate, views.py:44).
  • /invoice/detail// - v1 detail/update (views.py:224).
  • /invoice/detail-no-perm// - v1 detail without feature check (views.py:548).
  • /invoice/delete// - v1 delete (views.py:579).
  • /invoice/status// - v1 status change incl. journal creation/cancellation tasks (views.py:623).
  • /invoice/cancel-submission// - v1 reject/revert (views.py:1317).
  • /invoice/search/ - v1 filtered search (views.py:1439).
  • /invoice/list/ - v1 flat list for accounting (views.py:1513).
  • /invoice/search/select/ - v1 approved picker (views.py:1592).
  • /invoice/approval-list/ - approved invoice list (views.py:1638).
  • /invoice/invoice-approval-list/ - approval list for notifications (views.py:1661).
  • /invoice/update-remaining-amount/ - remaining-amount update hook (views.py:1687).
  • /invoice/list-for-ageing/ - ageing list v1 (views.py:1722).
  • /invoice/list-for-ageing-v2/ - ageing list (views.py:1794).
  • /invoice/list-for-annex-report/ - annex report list (views.py:1869).
  • /invoice/detail-cheque/ - invoice detail for cheque entry (views.py:2043).
  • /invoice/list-internal/ - internal count/list (views.py:2064).

Scope anomaly: the revamped endpoint only exists for list/create; no revamped status/detail/delete/search routes exist in f1-production, so the v1 lifecycle views above remain the only implementation of those flows in this snapshot.
