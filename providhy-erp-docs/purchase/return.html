Purchase . Return

Purchase returns (goods returned to suppliers) against approved purchase invoices, with the same revamped create/list treatment as invoices. As with invoices, the catalog marks every unversioned return route as superseded by the revamped v2 endpoint, so only /v2/ is documented here.

All routes below are relative to the service root; on the live service they sit under /api/purchase/return/ (core/urls.py:35). Source: purchase/purchase_return/urls.py, views.py, serializers.py, models.py @ ad05cc9b.

Endpoint map

# Method Path Purpose Auth
1 GET /v2/ List returns for a status (list screen, revamped) IAM + PR1106 VIEW
2 POST /v2/ Create revamped purchase return IAM + PR1106 ADD_EDIT

Routes: 1 catalog route (serves both GET and POST). Feature PR1106 (AllFeatures.PURCHASE_RETURN, dashboard/choices.py:179).

1. GET /v2/ - list by status

  • View: PurchaseReturnListCreateRevamped - purchase/purchase_return/views.py:117 (route urls.py:9-11).
  • Auth: IAMAuthenticationBackendPurchase + HasPermission (views.py:116-121); GET requires VIEW (views.py:123-129).
  • Request (query): status (required - 404 UNKNOWN_STATUS if invalid, views.py:137-139).
  • Processing: tenant-scoped (views.py:140-142), row visibility via helper.user_filter (views.py:143-145), CustomTransactionPagination (views.py:131, 146).
  • Response: 200 paginated PurchaseReturnListSerializer list (views.py:147-150, serializers.py:152-235).

2. POST /v2/ - create revamped return

  • View: PurchaseReturnListCreateRevamped - views.py:117 (route urls.py:9-11).
  • Auth: IAM + HasPermission; POST requires ADD_EDIT (views.py:123-129).
  • Request (JSON): entry_date, return_date, items (required - views.py:182-186); each item needs product_id, quantity, uom, rate (views.py:183-186). Header fields from the model: purchase_invoice (approved invoice id - required by the serializer), supplier (JSON), title, description, reference, discount_percentage, discount_amount (models.py:12-58). Form-data bodies are accepted; nested fields items, supplier, convert are parsed from strings (views.py:154-164).
  • Processing: one atomic transaction (views.py:166).
    • Fiscal-year validation of entry_date (custom.validate_fiscal_year, views.py:167-168); fiscal year injected from the request (views.py:170-171).
    • Serialized by PurchaseReturnSerializerWriteOnlyRevamped (views.py:188-190, serializers.py:627-859):
      • validate(): the referenced purchase invoice must exist in the tenant and be approved (serializers.py:769-781); entry_date and return_date must not precede the invoice date (serializers.py:685-698); the return inherits the invoice's discount percentage, and when the invoice carried a discount amount it is re-derived pro-rata from the returned quantities (serializers.py:699-721).
      • create(): header data sanitized through the Configuration service form-data endpoint (serializers.py:786-788, 634-665, dashboard/helper.py:108, dashboard/send_request.py:8); unique_id generated via the tenant unique-id configuration (helper.generate_unique_id, serializers.py:793-798, dashboard/helper.py:835); revamped flag set True (serializers.py:803); header totals via helper.calculate_totals_revamped (serializers.py:804-820, dashboard/helper.py:1031).
      • Line items: sanitized (serializers.py:828-831); per-item totals via helper.calculate_item_totals_revamped (serializers.py:833-840, dashboard/helper.py:1100); per-item product check against ProductManagement with batch-stock validation for batch-kept products (serializers.py:738-767, 841-856); items created (serializers.py:857).
    • After save, uploaded images are pushed to the Document service (helper.upload_image, views.py:193-195, dashboard/helper.py:212).
  • Response: 201 { id, message } (views.py:196-200); 400 with the serializer error message (views.py:202-203).
  • Side effects: Document service upload (images); no Kafka call in the revamped create path itself (the v1 create and status-change endpoints - superseded below - carry the journal/Kafka calls).

Frontend usage (apps-frontend @ production)

No /api/purchase/return/ latest route appears in the fe_usage unused-latest list, i.e. the revamped /v2/ endpoint is referenced from the frontend (the superseded v1 routes are also referenced - a floor, not a ceiling).

Superseded / legacy routes (not documented)

All unversioned return routes are marked superseded in the catalog (replaced by the revamped /v2/ family; only the v2 list/create route exists as latest):

  • /return/ - v1 list/create (PurchaseReturnListCreate, views.py:39).
  • /return/detail// - v1 detail/update (views.py:207).
  • /return/detail-no-perm// - v1 detail without feature check (views.py:305).
  • /return/delete// - v1 delete (views.py:336).
  • /return/status// - v1 status change incl. journal creation/cancellation tasks (views.py:375).
  • /return/cancel-submission// - v1 reject/revert (views.py:882).
  • /return/search/ - v1 filtered search (views.py:996).
  • /return/list/ - v1 flat list for accounting (views.py:1058).
  • /return/search/select - v1 approved picker (views.py:1137).
  • /return/debug/redis/kafka/ - Redis/Kafka debug read (RedisKafkaDebugView, views.py:849).
  • /return/debug/redis/kafka/clear/ - Redis/Kafka debug clear (RedisKafkaDebugClearView, views.py:866).

Scope anomaly: as with invoices, the revamped endpoint only exists for list/create; no revamped status/detail/delete/search routes exist in f1-production, so the v1 lifecycle views above remain the only implementation of those flows in this snapshot.
