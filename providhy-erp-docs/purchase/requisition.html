Purchase . Requisition

Purchase requisition lifecycle: create -> submit for approval -> approve / reject / cancel. A requisition is an internal request to buy; purchase orders can be created against it and track usage per requisition item (used_status). Approval flows are tenant-configured (basic vs custom) by the Configuration service.

All routes below are relative to the service root; on the live service they sit under /api/purchase/requisition/ (core/urls.py:28). Source: purchase/purchase_requisition/urls.py, views.py, serializers.py, models.py @ ad05cc9b.

Routes: 9 catalog routes (the / route serves both GET and POST).

1. GET / - list by status

  • View: PurchaseRequisitionCreate - purchase/purchase_requisition/views.py:26 (route urls.py:6).
  • Auth: IAMAuthenticationBackendPurchase + HasPermission (views.py:25-29); GET requires action VIEW, set in initial() (views.py:31-36). Feature PR1101 (AllFeatures.PURCHASE_REQUISITION, dashboard/choices.py:174).
  • Request (query): status (required - 404 UNKNOWN_STATUS if not a known StatusChoices value, views.py:45-46).
  • Processing: tenant-scoped filter (views.py:47-49), row visibility via helper.user_filter (views.py:50-52, dashboard/helper.py:755), paginated with CustomTransactionPagination (views.py:38, 53).
  • Response: 200 paginated list of { id, unique_id, title, entry_date, due_date, status, entry_by } (PurchaseRequisitionListSerializer, serializers.py:104-115).

2. POST / - create

  • View: PurchaseRequisitionCreate - views.py:26 (route urls.py:6).
  • Auth: IAM + HasPermission; POST requires ADD_EDIT (views.py:31-36).
  • Request (JSON): entry_date (date, required), due_date (date, required), items (array, required) - views.py:60. Each item: product_id, uom, quantity (required, views.py:61-62); model fields also include conversion_rate, quantity_in_stock, remaining, description (models.py:64-90). title, description accepted (model fields, models.py:15-18).
  • Processing: fiscal year injected from the authenticated request, not the client (views.py:69-70); serialized by PurchaseRequisitionWriteOnlySerializer (views.py:74-80, serializers.py:146-249). Create path sanitizes header and line data through the Configuration service form-data sanitization endpoint (api/sanitization/form-data/ - serializers.py:153-200, dashboard/helper.py:108, dashboard/send_request.py:8), sets tenant_id + entry_by (serializers.py:226-227), then creates the items; the client-supplied quantity_in_stock is copied onto each item (serializers.py:238-248).
  • Response: 201 { id, message } (views.py:81-85); 400 { error: INCORRECT_DATA_FORMAT } on serializer failure (views.py:86-89).

3/4. GET / POST /detail// - detail & update

  • View: PurchaseRequisitionUpdate - views.py:93 (routes urls.py:7-11).
  • Auth: IAM + HasPermission; GET -> VIEW, POST -> ADD_EDIT (views.py:98-104).
  • GET: tenant-scoped lookup (views.py:106-110); user_filter row visibility (views.py:117-123); PurchaseRequisitionReadOnlySerializer (views.py:124-127, serializers.py:128-143) - approval_user is resolved to a username via helper.validate_approval_user, which calls the IAM service (serializers.py:136-143, dashboard/helper.py:800); 404 with a not-found error otherwise (views.py:129-132).
  • POST: same required fields as create (views.py:135-137); the update serializer replaces all items - existing items are deleted and re-created (serializers.py:251-284); sanitization calls as in create (serializers.py:255, 264). Observed quirk: serializer failure on update returns HTTP 200 with an error body (views.py:159-162).

5. GET /detail-no-perm// - detail without permission

  • View: PurchaseRequisitionDetailNoPerm - views.py:170 (route urls.py:12-16).
  • Auth: IAM only - no HasPermission feature check (views.py:170-171); any authenticated tenant user who knows the id can read it. Used so other purchase screens (orders, invoices) can embed the requisition header.
  • Same tenant scoping + user_filter + read-only serializer as endpoint 3 (views.py:173-199).

6. POST /delete// - delete

  • View: PurchaseRequisitionDelete - views.py:202 (route urls.py:17-21).
  • Auth: IAM + HasPermission, action ADD_EDIT (views.py:204-206).
  • Behavior: atomic delete; allowed only while status is draft AND the caller is the creator (views.py:214-222); items are deleted first (views.py:223). 200 { message } on success, 400 CANNOT_DELETED otherwise, 400 DATA_NOT_FOUND if the record is missing (views.py:225-249).

7. POST /status// - status change

  • View: PurchaseRequisitionStatusChange - views.py:253 (route urls.py:22-26).
  • Auth: IAM + HasPermission; a POST with status submit_for_approval keeps action VIEW, any other status requires APPROVE_CANCEL (views.py:258-266).
  • Request (JSON): status (submit_for_approval / approved / cancelled), plus flow fields: approval_user, comment, cancelled_comment (read from the body where used, views.py:442-450, 569).
  • Processing: whole endpoint is one atomic transaction (views.py:280). The tenant's approval-work configuration is fetched from the Configuration service (send_request.get_configuration, type approval_workflow, status workflow - views.py:287-292, dashboard/send_request.py:26, dashboard/helper.py:109); no configuration (or an unknown title) yields 503 SERVICE_UNAVAILABLE (views.py:337-340 range).
    • BASIC flow (views.py:293-299, 340 onward): draft -> submit_for_approval; submit -> approve (only by the approval_user); draft or submit -> cancel.
    • CUSTOM flow (views.py:300-336): approve only from non-cancelled states, gated by helper.check_for_custom_flow_compulsions (dashboard/helper.py:824); cancel only from approved.
  • Transition side effects (all within the same transaction):
    • submit_for_approval: per-item product validity checks against the ProductManagement service (helper.get_product_data, dashboard/helper.py:513, views.py:419-431); approval_user + submit fields saved (views.py:442-450); notification via custom.send_notification (dashboard/custom_functions.py:30, views.py:384-391); activity log via custom.create_activity_log (dashboard/custom_functions.py:55, views.py:392-398); Kafka record type purchase_requisition_submit_for_approval_record (views.py:399-412, dashboard/kafka_function.py:13-53, record type dashboard/choices.py:409).
    • approved: product validation batch (helper.product_validation, dashboard/helper.py:525, views.py:423-431); approval fields saved (views.py:433-442); activity log (views.py:444-450); Kafka purchase_requisition_approval_record (views.py:451-464, dashboard/choices.py:401). No notification call in the approved path.
    • cancelled: blocked while an approved or submitted purchase order references the requisition (views.py:470-481); per-item quantity roll-back validation (validation_check.requisition_quantity_validation_update, views.py:483-509 range); cancellation fields saved; activity log (views.py:504-510); Kafka purchase_requisition_cancel (views.py:512-519, dashboard/choices.py:381).
  • Response: 200 { message } per transition (SUBMITTED / APPROVED / CANCELLED); 400 INVALID_STATUS / INVALID_APPROVE_REQUEST for invalid transitions (views.py:336 range); ValidationError propagates as 400 for product or requisition guard failures.

8. POST /cancel-submission// - reject or revert submission

  • View: PurchaseRequisitionSubmissionRevert - views.py:528 (route urls.py:27-31).
  • Auth: IAM + HasPermission; action VIEW for POST (views.py:529-536).
  • Request (JSON): type (rejection to reject; omit for revert), comment (used on rejection).
  • Behavior: the record is reset to draft with approval_user and submit fields cleared (views.py:562-565). If the record is in submit_for_approval: type=rejection by someone other than the creator -> rejected (rejected fields set, views.py:568-573; activity log REJECTION views.py:575-581; notification ERROR views.py:582-589; Kafka purchase_requisition_reject_record views.py:590-595). No type by the creator -> reverted (activity log CANCEL_SUBMISSION views.py:609-615; Kafka record type purchase_requisition_reject_record again - the revert path reuses the reject record type, views.py:616-621). Other combinations: 400 INVALID_REQUEST (views.py:631-634). If the record is not in submit_for_approval: 400 (views.py:636-639).
  • Response: 200 { message: rejected | reverted }.

9. GET /search/ - filtered search

  • View: PurchaseRequisitionSearchView - views.py:646 (route urls.py:32-36).
  • Auth: IAM + HasPermission, action VIEW (views.py:647-655).
  • Request (query): q (free text), status (required - 404 if invalid, views.py:665-667), plus filterset fields (PurchaseRequisitionFilterSet, views.py:650, applied at views.py:670).
  • Processing: q matches unique_id, entry_date, due_date, entry_by (icontains, views.py:678-684); user_filter row visibility (views.py:671-677); CustomTransactionPagination (views.py:657).
  • Response: 200 paginated list, PurchaseRequisitionListSerializer (views.py:688-692).

10. GET /search/select/ - approved picker search

  • View: PurchaseRequisitionApprovedSearchView - views.py:695 (route urls.py:37-41).
  • Auth: IAM only - no feature-permission check (views.py:695-697), for pickers across modules.
  • Behavior: returns approved requisitions that ended before the current fiscal-year end date (views.py:705-710) and are not fully used (used_status != COMPLETE, views.py:713-715); q matches unique_id, entry_date, due_date, entry_by (views.py:719-725); light serializer returning id, unique_id, title (PurchaseApprovedRequisitionListSerializer, serializers.py:118-125).
  • Response: 200 paginated picker list.

11. GET /list/ - flat list for accounting

  • View: PurchaseRequisitionsForAccounting - views.py:736 (route urls.py:42-46).
  • Auth: internal - no IAM classes; gated by the shared internal password in the password query param (helper.validate_internal_pass, dashboard/helper.py; 400 on mismatch, views.py:737-738, 758-759).
  • Request (query): tenant_id (required by the filter), entry_date, from_date, to_date (entry_date range), entry_status (optional status filter, views.py:739-747).
  • Behavior: returns all non-draft requisitions ordered by entry_date (views.py:749-753); items are enriched with product name/unique_id via ProductManagement product-check calls (PurchaseRequisitionListForACCSerializer, serializers.py:287-322, dashboard/helper.py:82).
  • Response: 200 full (unpaginated) list; 400 when the password is wrong.

Frontend usage (apps-frontend @ production)

The cross-reference marks requisition /, /status/, /cancel-submission/, /search/, /search/select/ and /delete/ as referenced from the frontend, while /detail/, /detail-no-perm/ and /list/ are not directly referenced (detail-no-perm and list serve other modules). The fe_usage cross-reference is a floor, not a ceiling - endpoints reached via helpers or other services are not counted.
