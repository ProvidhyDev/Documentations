Business purpose

The procure-to-pay engine: a tenant's purchase team raises requisitions, converts them into purchase orders against suppliers (from ProjectMaster), receives goods, bills with purchase invoices, and pays suppliers by eSewa or cheque. Expenses run a parallel small lifecycle for non-purchase costs, and purchase returns handle goods sent back. Approved invoices post to the Accounting ledger via internal journal hooks; every transition emits events notifications/logs and a Kafka purchase_events record for reporting. (The GRN document family exists in the code but is not used in ProvidhyERP - excluded per scope.)

  FE->>P: supplier payment (eSewa or cheque)

Authentication model

Same per-view pattern as Sales: IAMAuthenticationBackendPurchase + HasPermission with feature permissions (PURCHASE_REQUISITION, PURCHASE_ORDER, PURCHASE_INVOICE, ...) and per-method actions (VIEW / ADD_EDIT / DELETE); approval workflows are tenant-configured (basic/custom) via the Configuration service; state transitions emit notifications, activity logs, and Kafka record types. A small set of internal (password-gated) routes feed other modules.

Scope exclusions (user-confirmed)

  • GRN (goods received note) + GRN-return + related deduction functions: not used in ProvidhyERP - not documented (paths listed in the catalog; excluded per scope).
  • Deduction-related functions: not used - not documented.
