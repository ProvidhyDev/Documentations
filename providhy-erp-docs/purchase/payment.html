Purchase . Payment

Supplier payments: pay approved purchase invoices and expense entries from a source account (cash/bank), keep supplier advances, issue cheques, and pay quickly from the invoice screen. Approving a payment fires a Celery task that creates the accounting journal (gated by the tenant's accounting-automation configuration); cancelling reverses it. Cheque-backed payments are flagged and tracked separately (is_cheque).

All routes below are relative to the service root; on the live service they sit under /api/purchase/payment/ (core/urls.py:36). Source: purchase/supplier_payment/urls.py, views.py, serializers.py, models.py @ ad05cc9b.

1. GET / - list by status

  • View: SupplierPaymentListCreate - purchase/supplier_payment/views.py:49 (route urls.py:6).
  • Auth: IAMAuthenticationBackendPurchase + HasPermission (views.py:48-53); GET requires VIEW (views.py:55-61).
  • Request (query): status (required - 404 UNKNOWN_STATUS if invalid, views.py:70-71).
  • Processing: tenant-scoped (views.py:72-74), helper.user_filter row visibility (views.py:75-77), CustomTransactionPagination (views.py:63, 78).
  • Response: 200 paginated SupplierPaymentListSerializer list (views.py:79-82, serializers.py:526-600).

2. POST / - create

  • View: SupplierPaymentListCreate - views.py:49 (route urls.py:6).
  • Auth: IAM + HasPermission; POST requires ADD_EDIT (views.py:55-61).
  • Request (JSON): supplier (JSON entity), source_account (account id), amount, payment_date (required - views.py:85-88); if bank_charge_applicable then bank_account + bank_amount (views.py:89-93); if tds_applicable then tds_account + tds_amount (views.py:94-98). Other model fields: payment_method, payment_reference_number, bank fields, tds fields, sorting_method, description, apply_advance, is_cheque, cheque fields (views.py, models.py:15-92); items (allocations: purchase_invoice or expense_entry id, allocated_amount, optional is_opening) - model fields models.py:131 onward.
  • Processing: one atomic transaction (views.py:108); fiscal-year check on payment_date (views.py:102-103); serialized by SupplierPaymentSerializerWriteOnly (views.py:110-114, serializers.py:51-263): header sanitized via the Configuration form-data endpoint (serializers.py:108-109, 58-85); TDS / bank-charge field rules enforced (serializers.py:117-121, 265-289); supplier entity data fetched from the party service (helper.get_entity_data, serializers.py:123-126, dashboard/helper.py:446); total allocations may not exceed the payment amount (serializers.py:137-141); per-item allocation checked against the reference invoice/expense remaining_amount or the supplier's credit opening balance (serializers.py:143-226); remaining (unallocated) amount becomes the advance when apply_advance is off (serializers.py:256-258), or the amount is validated against total available advances when apply_advance is on (serializers.py:229-255); total_allocated_amount saved (serializers.py:260-261).
  • Response: 201 { id, message } (views.py:115-119); 400 INCORRECT_DATA_FORMAT (views.py:120-123).
  • Side effects: none in the draft create (journal task fires on approval).

  • Behavior: atomic; allowed only while draft and by the creator (views.py:244-255); items deleted first (views.py:256); 200 / 400 CANNOT_DELETED / 400 DATA_NOT_FOUND (views.py:258-282).

6. POST /status// - status change

  • View: SupplierPaymentStatusChangeAPIView - views.py:547 (route urls.py:19-23).
  • Auth: IAM + HasPermission; submit_for_approval keeps VIEW, other statuses require APPROVE_CANCEL (views.py:553-561).
  • Request (JSON): status, approval_user, comment.
  • Processing: atomic (views.py:574); tenant approval-work configuration from the Configuration service (views.py:582-587, dashboard/send_request.py:26, dashboard/helper.py:109); missing configuration -> 503 (views.py:612). BASIC flow: draft -> submit; approve from submit (by approval_user) or from draft (by creator) (views.py:614-640); cancel from submit (by approval_user) or from approved (views.py:645-652). CUSTOM flow: approve from non-cancelled (helper.check_for_custom_flow_compulsions, dashboard/helper.py:824), cancel from approved (views.py:595-610).
    • submit: notification (custom.send_notification, dashboard/custom_functions.py:30, views.py:665-672) + activity log (custom.create_activity_log, dashboard/custom_functions.py:55, views.py:673-679). No Kafka.
    • approve: supplier entity data fetched (views.py:687-692); when apply_advance is set, the opening-credit-balance and previously-approved advances are deducted FIFO (views.py:697-740, helper.supplier_remaining_update, dashboard/helper.py:431); allocation remaining amounts re-validated (views.py:741-748, validation_check); approval fields saved (views.py:750-759); if the tenant has an accounting-automation purchase-flow configuration, the journal creation Celery task is dispatched (journal_creation_task.delay - views.py:761-769, tasks in purchase/purchase_invoice/tasks.py); activity log (views.py:771-777). No notification in the approved path.
    • cancel: advance deductions restored (LIFO, views.py:784-868 - restore_supplier_payments views.py:784-831), allocation validation (views.py:839-845), cancellation fields saved and deduction_from_opening reset (views.py:846-853); if a journal was created, journal_cancellation_task.delay (views.py:854-855); activity log (views.py:858-864).
  • Response: 200 { message }; 400 INVALID_STATUS / INVALID_APPROVE_REQUEST / INVALID_CANCEL_REQUEST (views.py:610, 635, 643, 652).

7. POST /cancel-submission// - reject or revert submission

  • View: SupplierPaymentSubmissionCancel - views.py:872 (route urls.py:24-28).
  • Auth: IAM + HasPermission; action VIEW (views.py:875-882).
  • Behavior: only while in submit_for_approval (views.py:900-906); rejection by a non-creator sets rejected fields, activity log REJECTION + ERROR notification (views.py:907-940); revert by the creator clears submit fields, activity log CANCEL_SUBMISSION (views.py:942-963); otherwise 400 INVALID_REQUEST (views.py:965-972). No Kafka, no journal effect.
  • Observed quirk: get_object looks the record up by pk only, no tenant scoping (views.py:884-891).

8. GET /search/ - filtered search

  • View: SupplierPaymentSearchView - views.py:286 (route urls.py:7).
  • Auth: IAM + HasPermission, action VIEW (views.py:287-297).
  • Request (query): q, status (required - 404 if invalid, views.py:333-335), filterset fields (SupplierPaymentFilterSet, views.py:292, applied at views.py:339).
  • Processing: excludes cheque records and quick payments (views.py:337-338); q matches unique_id, payment_date, entry_by (views.py:348-354); supplier name/unique_id and the source account name/unique_id are gathered asynchronously - supplier via SupplierDataGatherMixin, account via the Accounting service get-account-detail endpoint (views.py:301-325, 364-383, dashboard/helper.py:135).
  • Response: 200 paginated list with enrichment; source_account falls back to a dash when the lookup fails (views.py:372-383).

9. GET /supplier-invoice-list/ - payable list for a supplier

  • View: SupplierInvoiceList - views.py:389 (route urls.py:8-12).
  • Auth: IAM + HasPermission, action VIEW (views.py:388-399).
  • Request (query): supplier_id (required - 404 if missing, views.py:405-412), unique_id (optional), exclude_settled (bool), exclude_expense (bool).
  • Behavior: returns the supplier's approved invoices with remaining_amount > 0 (excluding fully paid unless exclude_settled) (views.py:414-433), plus the supplier's approved expense entries with remaining amount (views.py:434-451), and - when the supplier has a credit opening balance - an Opening Balance entry prepended (views.py:488-507); also returns a summary: pending_amount (invoices + expenses + opening), advance_amount (fetched from the Reporting service party-closing endpoint, views.py:517-533, dashboard/helper.py:155) and paid_amount (approved, cleared cheque payments, views.py:464-476).
  • Response: 200 { approved_invoice_list, invoice_data }.

10. POST /quick/frontend/ - quick payment

  • View: QuickSupplierPaymentCreateFrontend - views.py:979 (route urls.py:30-34).
  • Auth: IAM + HasPermission - but the required feature is PR1105 (PURCHASE_INVOICE), not the payment feature, and the action is VIEW even for POST (views.py:982-988). Observed quirk: this is effectively the invoice screen's pay action.
  • Request (JSON): payment_allocations (required - views.py:1035-1038; each row: source_account.entity_id, total_allocated_amount, optional payment_date), invoice_id or expense_entry (one required, views.py:1041-1042, 1001-1008).
  • Processing: one atomic transaction (views.py:1050); total allocated may not exceed the reference remaining amount (views.py:990-999, 1048); for each allocation a full SupplierPayment record is created already in APPROVED status with the creating user as approver and is_quick_payment=True (views.py:1057-1092, serializer create path with is_quick_payment context at views.py:1082-1093); the journal creation task is queued on commit (views.py:1095-1099); allocation remaining amounts re-validated (views.py:1111-1116); an activity log entry "Rs. X is paid against the invoice." is written on the reference record (views.py:1118-1125, ServiceType.PAYMENT).
  • Response: 200 { message: created }.
  • Side effects: accounting journal task (Celery) per payment; activity log. No notification, no Kafka.

11. POST /get-fetch-supplier-payments-internal/ - fetch by ids

  • View: FetchSupplierPaymentsInternal - views.py:1137 (route urls.py:42-46, marked "temporary url" in the source).
  • Auth: internal - InternalRequestPermission, shared password in the POST body (dashboard/auth_backends.py:137-148); no IAM classes.
  • Request (JSON): supplier_payment_ids (list of ids).
  • Behavior: returns the payments (no tenant filter - ids only, views.py:1141-1151) via SupplierPaymentBaseSerializer (serializers.py:22-28).

12. POST /quick-payment-check/ - quick-payment flag check

  • View: CheckQuickPaymentView - views.py:1154 (route urls.py:35-39).
  • Auth: internal - InternalRequestPermission, password in the POST body.
  • Request (JSON): tenant_id, supplier_payment_ids (both required, views.py:1160).
  • Response: 200 map of payment id -> is_quick_payment (views.py:1164-1172).

13. GET /get-supplier-advance/ - supplier advance summary

  • View: SupplierAdvanceSummaryAPIView - views.py:1175 (route urls.py:47-51).
  • Auth: internal - InternalRequestPermission, password in the query string.
  • Request (query): tenant_id (required by the filter), supplier_id (optional, comma-separated list, views.py:1208-1210).
  • Behavior: approved payments per supplier with effective_advance = advance_amount plus allocations to invoices that were later cancelled (views.py:1186-1230).
  • Response: 200 list of { id, payment_date, supplier id/name, effective_advance }.
