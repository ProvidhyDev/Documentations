Purchase . Order

Purchase order lifecycle: create (optionally from an approved requisition) -> submit for approval -> approve / reject / cancel. An approved order is the source document for receiving (GRN) and for purchase invoices; per-item usage counters (grn_count, invoice_count) track how much of each line has already been received or invoiced. Approval flows are tenant-configured (basic vs custom) by the Configuration service.

All routes below are relative to the service root; on the live service they sit under /api/purchase/order/ (core/urls.py:29). Source: purchase/purchase_order/urls.py, views.py, serializers.py, models.py @ ad05cc9b.

Routes: 10 catalog routes (the / route serves both GET and POST).

1. GET / - list by status

  • View: PurchaseOrderCreate - purchase/purchase_order/views.py:31 (route urls.py:6).
  • Auth: IAMAuthenticationBackendPurchase + HasPermission (views.py:30-34); GET requires VIEW (views.py:36-42). Feature PR1102 (AllFeatures.PURCHASE_ORDER, dashboard/choices.py:175).
  • Request (query): status (required - 404 UNKNOWN_STATUS if invalid, views.py:51-52).
  • Processing: tenant-scoped (views.py:53-55), row visibility via helper.user_filter (views.py:56-58), CustomTransactionPagination (views.py:44, 59).
  • Response: 200 paginated PurchaseOrderListSerializer list (views.py:60-63).

2. POST / - create

  • View: PurchaseOrderCreate - views.py:31 (route urls.py:6).
  • Auth: IAM + HasPermission; POST requires ADD_EDIT (views.py:36-42).
  • Request (JSON): po_date, validity_till, supplier, items (all required - views.py:68-70). Each item: product_id, quantity, uom, rate (required - views.py:71-72); other item model fields: conversion_rate, discount_percent, discount_amount, vat, description (models.py:101-149). Header fields: title, narration, description, payment_term, discount_percentage, discount_amount, requisition (id, optional) - models.py:17-33.
  • Processing: fiscal year injected from the request (views.py:77-78); serialized by PurchaseOrderSerializerWriteOnly (views.py:82-87, serializers.py:349-494). Create path: referenced requisition must exist and be approved (validate_requisition, serializers.py:416-426); header and line data are sanitized through the Configuration service form-data endpoint (api/sanitization/form-data/ - serializers.py:356-399, dashboard/helper.py:108, dashboard/send_request.py:8); tenant_id + entry_by set (serializers.py:439-440); header totals (vat_amount, vatable_amount, non_vatable_amount, grand_total, subtotal) computed by helper.calculate_totals (serializers.py:449-459, dashboard/helper.py:532); per-item totals via helper.calculate_item_totals (serializers.py:472-491, dashboard/helper.py:613); items created with invoice_count = grn_count = quantity (serializers.py:481-493). unique_id is generated on save with the PO prefix (models.py:83-94).
  • Response: 201 { id, message } (views.py:88-92); 400 { error: INCORRECT_DATA_FORMAT } (views.py:93-96).

3/4. GET / POST /detail// - detail & update

  • View: PurchaseOrderUpdate - views.py:100 (routes urls.py:7-11).
  • Auth: IAM + HasPermission; GET -> VIEW, POST -> ADD_EDIT (views.py:105-111).
  • GET: tenant-scoped (views.py:113-117), user_filter DETAIL visibility (views.py:119-129), PurchaseOrderSerializerReadOnly (views.py:130-133, serializers.py:220-301), 404 otherwise (views.py:134-138).
  • POST: same required fields as create (views.py:141-145); update() re-sanitizes the header, recomputes totals from the new items (serializers.py:496-521), rewrites header fields, then rebuilds line items (update_item_instances, serializers.py:533 onward).

5. GET /detail-no-perm// - detail without permission

  • View: PurchaseOrderDetailNoPerm - views.py:179 (route urls.py:12-16).
  • Auth: IAM only - no HasPermission check (views.py:179-180); for embedding order headers in other purchase screens (receiving, invoice entry).
  • Same scoping + user_filter + read-only serializer (views.py:182-207).

6. POST /delete// - delete

  • View: PurchaseOrderDelete - views.py:210 (route urls.py:17).
  • Auth: IAM + HasPermission, action ADD_EDIT (views.py:212-214).
  • Behavior: atomic; allowed only while draft and by the creator (views.py:222-230); items deleted first (views.py:231); 200 on success, 400 CANNOT_DELETED / DATA_NOT_FOUND otherwise (views.py:233-245).

7. POST /status// - status change

  • View: PurchaseOrderStatusChange - views.py:249 (route urls.py:18-22).
  • Auth: IAM + HasPermission; submit_for_approval keeps action VIEW, other statuses require APPROVE_CANCEL (views.py:254-262).
  • Request (JSON): status (submit_for_approval / approved / cancelled), approval_user and comment on submit, comment on approve/cancel.
  • Processing: one atomic transaction (views.py:299). Tenant approval-work configuration fetched from the Configuration service (views.py:307-312, dashboard/send_request.py:26, dashboard/helper.py:109); missing configuration yields 503 (views.py:338).
    • BASIC flow (views.py:313-319, 340-412): draft -> submit; approve from draft (only by the creator) or from submit (only by the approval_user, views.py:349-368); cancel from draft (by creator), from submit (by approval_user) or from approved, always with roll-back (views.py:381-412).
    • CUSTOM flow (views.py:321-336): approve from any non-cancelled state after helper.check_for_custom_flow_compulsions (dashboard/helper.py:824); cancel only from approved.
  • Guards: submit validates the referenced requisition is not cancelled (views.py:417-421), checks per-item requisition quantity and product existence (views.py:423-435, dashboard/helper.py:513); approve re-runs the quantity validation (views.py:502-518); cancel is blocked while an active GRN or an active purchase invoice references the order (check_cancellation, views.py:273-296 - the GRN guard is present even though the GRN feature is not used in ProvidhyERP).
  • Transition side effects: submit - notification (custom.send_notification, dashboard/custom_functions.py:30, views.py:451-458), activity log (custom.create_activity_log, dashboard/custom_functions.py:55, views.py:459-465), Kafka purchase_order_submit_for_approval_record (views.py:466-477, dashboard/choices.py:417). Approve - activity log (views.py:535-541), Kafka purchase_order_approval_record (views.py:542-553, dashboard/choices.py:405); no notification call. Cancel - activity log (views.py:574-580), Kafka purchase_order_cancel (views.py:581-588, dashboard/choices.py:385); no notification call.
  • Response: 200 { message } (SUBMITTED / APPROVED / CANCELLED); 400 INVALID_STATUS / INVALID_APPROVE_REQUEST / INVALID_CANCEL_REQUEST for bad transitions (views.py:336, 368, 408-412).

8. POST /cancel-submission// - reject or revert submission

  • View: PurchaseOrderSubmissionCancel - views.py:592 (route urls.py:23-27).
  • Auth: IAM + HasPermission; action VIEW for POST (views.py:593-601).
  • Request (JSON): type (rejection to reject; omit to revert), comment on rejection.
  • Behavior: only works while the order is in submit_for_approval (views.py:624-630). Rejection by someone other than the creator: requisition items re-validated (views.py:631-633), rejected fields saved (views.py:634-642), activity log REJECTION (views.py:644-650), ERROR notification (views.py:651-658), Kafka purchase_order_reject_record (views.py:659-664, dashboard/choices.py:433). Revert by the creator: requisition items re-validated (views.py:671-672), approval fields cleared (views.py:673-677), activity log CANCEL_SUBMISSION (views.py:679-685), Kafka record type purchase_order_reject_record reused (views.py:686-691). Other combinations: 400 INVALID_REQUEST (views.py:696-703).
  • Observed quirk: get_object looks the order up by pk only - no tenant_id scoping (views.py:603-608), unlike every other endpoint in this module.
  • Response: 200 { message: rejected | reverted }.

9. GET /search/ - filtered search

  • View: PurchaseOrderSearchView - views.py:707 (route urls.py:28).
  • Auth: IAM + HasPermission, action VIEW (views.py:709-717).
  • Request (query): q, status (required - 404 if invalid, views.py:727-729), filterset fields (PurchaseOrderFilterSet, views.py:712, applied at views.py:732).
  • Processing: q matches unique_id, po_date, validity_till (views.py:740-746); user_filter (views.py:733-739); supplier header data (name, unique_id) is gathered asynchronously through the SupplierDataGatherMixin and injected into each row (views.py:757-760, mixin in dashboard/mixins.py); serializer runs in v2 mode (views.py:751-755).
  • Response: 200 paginated PurchaseOrderListSerializer list with supplier enrichment.

10. GET /search/select/ - approved picker search

  • View: PurchaseOrderApprovedSearchView - views.py:765 (route urls.py:29-33).
  • Auth: IAM only - no feature-permission check (views.py:765-766).
  • Request (query): method (required - must be a PurcahseOrderSearchSelectParameter value, note the constant-name typo in source, views.py:772-777), q.
  • Behavior: approved orders only (views.py:779-783), excluding orders whose po_date is at/after the current fiscal-year end (views.py:784-786); with method=invoice, fully-invoiced orders (invoice_status COMPLETE) are excluded (views.py:787-791), otherwise fully-GRNed orders (grn_status COMPLETE) are excluded (views.py:792-796); q matches unique_id (views.py:798-804).
  • Response: 200 paginated PurchaseApprovedOrderListSerializer list (views.py:808-812, serializers.py:134-144).

11. GET /list/ - flat list for accounting

  • View: PurchaseOrderForAccounting - views.py:815 (route urls.py:34-38).
  • Auth: internal - shared password in the password query param (views.py:817, 400 on mismatch views.py:839-840).
  • Request (query): tenant_id, entry_date, from_date, to_date (po_date range), entry_status (optional, views.py:818-826).
  • Behavior: non-draft orders ordered by po_date (views.py:828-832); PurchaseOrderListForACCSerializer enriches items with supplier data (views.py:833-837, serializers.py:666-715).
  • Response: 200 full (unpaginated) list.

12. GET /report-po/search/select/ - approved orders by date range

  • View: PurchaseOrderFilterByDate - views.py:843 (route urls.py:39-43).
  • Auth: IAM only - no feature-permission check (views.py:843-845), used by report pickers.
  • Request (query): date_type (required - views.py:858-859; custom type also needs from_date/to_date, views.py:847-851), q. The date range is resolved server-side from the tenant's fiscal year via custom.date_mechanism_for_report (views.py:862-864, dashboard/custom_functions.py).
  • Behavior: approved orders whose po_date falls in the resolved range (views.py:865-869); q matches unique_id (views.py:870-877).
  • Response: 200 paginated PurchaseOrderForReportSerializer list (views.py:878-880, serializers.py:737-742).
