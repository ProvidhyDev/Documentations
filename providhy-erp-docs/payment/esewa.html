Payment . eSewa

eSewa payment-request lifecycle: another Providhy service creates a request (status requested), the wallet flow completes or fails it, the merchant side can cancel, and settlement is triggered for merchant-initiated completed payments.

Routes sit under /api/esewa/ on the live service. Source: esewa/urls.py, esewa/views.py, esewa/serializers.py, esewa/models.py @ 87a90b2c.

Payment request status (dashboard/choices.py:472-477): requested, completed, declined, failed, cancelled.

Endpoint map

# Method Path Purpose Auth
1 POST /esewa/payment/request/ Create payment request (optionally completed) internal
2 POST /esewa/payment/request/search/ Batch lookup of requests by payment id + tenant internal
3 POST /esewa/payment/request/cancel/ Cancel a requested payment (merchant side) federated (eSewa merchant)
4 POST /esewa/payment/request/pay/ Process/complete a requested payment internal
5 POST /esewa/payment/request/exists/ Check open requests for a customer internal
6 POST /esewa/payment/request/statistics/ Aggregate statistics (all tenants) internal
7 POST /esewa/tenant-data-deletion/ Delete tenant payment data internal

1. POST /esewa/payment/request/ - create

  • View: EsewaPaymentRequestAPIView - esewa/views.py:13 (internal auth, views.py:14).
  • Request (JSON): envelope { tenant_id, external_identifier, provider_code, initiator (default merchant), payment_request_data: {...} } (views.py:18-24). payment_request_data is serialized by EsewaPaymentRequestSerializer (serializers.py:16):
    • amount, customer, payment - model fields (serializers.py:29-40).
    • status - optional choice, defaults to requested (serializers.py:20-24).
    • transaction_id - optional; required when status is completed for customer-initiated flows (serializers.py:72-79); duplicates rejected (serializers.py:65-71).
    • payment_details - computed { tenant_id, paid_to } (serializers.py:44-48).
  • Processing: context (tenant_id, external_identifier, provider_code) is validated before create (serializers.py:50-57, 82-84). For a completed request created by the merchant initiator, transaction settlement is initiated via helpers.initiate_transaction_settlement (serializers.py:93-100).
  • Response: 200 with the serialized request on success (views.py:31); 400 with serializer errors (views.py:29). Wrapped in a transaction (views.py:16).
  • Note: the serializer defines execute_esewa_payment (serializers.py:104-124) which POSTs to the eSewa sandbox/payment URL with a dummy payload; it is not invoked from the create path (unverified whether it is used elsewhere).

2. POST /esewa/payment/request/search/ - batch lookup

  • View: EsewaPaymentRequestSearchView - esewa/views.py:75 (internal auth, views.py:76).
  • Request (JSON): { payment_id: [...], tenant_id: [...], method (a status value, or all / manual), provider_code, external_identifier } (views.py:112-118). Invalid method -> validation error (views.py:119-123).
  • Behavior: filters EsewaPaymentRequest by tenant_id__in and payment__in (views.py:94-99), returns a dict keyed by the payment id of the requested fields id, payment, unique_id, status, transaction_id, initiated_by (views.py:84-92); results filtered by status unless method is all/manual (views.py:136-140).
  • Response: 200 { <payment_id>: {request...}, ... }.

3. POST /esewa/payment/request/cancel/<payment_id>/ - merchant cancel

  • View: EsewaPaymentRequestCancelAPIView - esewa/views.py:34.
  • Auth: federated - extends generics.FederatedAuthenticationView (esewa/generics.py); requires user type ESEWA_MERCHANT, app scope ESEWA, feature PAYMENT_MANAGEMENT, action APPROVE_CANCEL (views.py:35-38). The eSewa merchant identity is exposed on request.external_identifier / request.provider_code.
  • Behavior: loads the request by payment id + authenticated tenant (views.py:41-45, 47-55; 404 if missing); forces status to cancelled through EsewaPaymentRequestPaySerializer with the external context (views.py:57-68).
  • Response: 200 { message: "Payment request cancelled successfully." } (views.py:69-72); 404 if not found; 400 on serializer errors.
  • Note: the serializer's validate_cancel_payment (serializers.py:176-179) enforces that only requested items can be cancelled - whether this check is wired into the cancel path is unverified (the view calls save() directly with a status payload).

4. POST /esewa/payment/request/pay/<payment_id>/ - process payment

  • View: EsewaPaymentRequestPayAPIView - esewa/views.py:175 (internal auth, views.py:176).
  • Request (JSON): the request body doubles as context: { external_identifier, connected_merchants: [...], description? } plus the serializer fields status, transaction_id (serializers.py:136-144, 192-203).
  • Behavior: locates the request by payment id + customer external_identifier + tenant in connected_merchants + status requested (views.py:179-190; 404 otherwise). Serializer validates: only requested items can be processed (serializers.py:154-158) and the merchant must be connected to the customer (serializers.py:161-165, 168-174).
  • Response: 200 with the updated serialized request (views.py:204); 404/400 otherwise.

5. POST /esewa/payment/request/exists/ - existence check

  • View: EsewaPaymentRequestExistsView - esewa/views.py:207 (internal auth, views.py:213).
  • Request (JSON): { customer_identifier } (views.py:216).
  • Behavior: counts open (requested) requests for the authenticated tenant + customer external identifier; sums their amounts (views.py:218-230).
  • Response: 200 { exists: bool, total_amount?: number }.

6. POST /esewa/payment/request/statistics/ - statistics

  • View: EsewaPaymentRequestStatisticsView - esewa/views.py:251 (internal auth, views.py:252).
  • Behavior: aggregates over ALL EsewaPaymentRequest rows (no tenant filter in the code, views.py:255): total count, total amount, failed count, requested (pending) count, completed count + completed amount (views.py:255-283).
  • Response: 200 { total_requests, total_amount, failed_requests, pending_payment_requests, completed_payment_requests, completed_payment_amount }.
  • Note: the all-tenants scope is what the code shows; whether callers rely on it is unverified.

7. POST /esewa/tenant-data-deletion/ - tenant data deletion

  • View: EsewaTenantDataDeletionAPIView - esewa/views.py:287 (internal auth, views.py:288).
  • Request (JSON): { remove_all: bool (default false) } (views.py:291).
  • Behavior: deletes EsewaPaymentRequest rows for the authenticated tenant, or ALL rows when remove_all is true (views.py:292-294).
  • Response: 200 { message: "Deleted N records for tenant T." }.
  • Warning: remove_all=true is a global delete across tenants - it is reachable by any internal caller (no extra guard in the code shown).

Frontend usage

None of the five ERP frontend apps reference these routes directly (fe_usage.json: 0 matches) - the eSewa API is consumed service-to-service (internal) and by the external eSewa merchant platform (federated cancel), which matches its auth design.
