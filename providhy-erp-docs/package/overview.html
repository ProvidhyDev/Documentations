ERP Project Package - Package Registry

The ERP-Project-Package service is the platform's package/module/contract registry: it defines the available ERP modules (sales, purchase, accounting, ...), packages that bundle modules, tenant contracts, agent (reseller) accounts, marketing campaigns with user ranges, and exposes the check endpoints every module service calls to verify a tenant's entitlements.

Repo: ERP-Project-Package @ branch f1-production, SHA 07d9c887.

Routes scanned: 41, all latest-version.

Apps: package, contract, campaign, agent_portal, plus 7 check endpoints.

Authentication model

  • cms-iam (CMSIAMAuthenticationBackend) - the management surface: package/module lists and status, contracts, campaigns, agents (explicit class lines in package/views.py, contract/views.py, campaign/views.py, agent_portal/views.py).

  • internal - the seven check-* endpoints (PackageCheck, ModuleCheck, ModuleContractCheck, PackageContractCheck, UserRangeCheck, UserRangeIdCheck, CMSCampaignCheck) are called by the 15 module services and the CMS platform to verify tenant entitlements; their bodies gate on tenant/module lookups rather than user JWTs (per-view auth lines unverified at def - treat as internal, confirm before relying on the call graph).

Every module service's auth backend (e.g. HasPermission in Sales/Purchase/Accounting) resolves whether a tenant's subscription/contract includes a feature before the IAM permission check passes - these are those endpoints.
