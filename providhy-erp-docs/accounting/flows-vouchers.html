Business Flows (Traced) - Vouchers & Ledger Posting

Deep trace of the Accounting money path: the four voucher families (journal, payment, receipt, contra) with their full create/submit/approve/reject/cancel/delete lifecycle, the shared bill-settlement flow, and the internal dashboard hooks through which Sales, Purchase, Inventory and payment modules post journals into the ledger. Every citation is verified against the f1-production source at SHA a60aaba3.

Citations are relative to the Accounting repo root. Shared building blocks used throughout:

  • IAMAuthenticationBackend (dashboard/auth_backends.py:21-57) - validates the tenant token by POST to IAM api/token/verify/ (dashboard/auth_backends.py:60-71), requires the ACCOUNTING service PR1300 in subscribed_services and email_verified (dashboard/auth_backends.py:41-42), returns user_id and tenant_id (dashboard/auth_backends.py:50-53), and puts the tenant's active fiscal year on request.fiscal_year (dashboard/auth_backends.py:48-49).
  • HasPermission (dashboard/auth_backends.py:74-107) - blocks non-GET when the subscription expired (dashboard/auth_backends.py:76-77), bypasses for tenant_root users (dashboard/auth_backends.py:79-80), otherwise fetches the user's feature/action grants from IAM api/internal-check-permissions/ (dashboard/auth_backends.py:83-85) and requires the view's required_feature_permission plus required_action_permission.
  • InternalRequestPermission (dashboard/auth_backends.py:110-121) - password in the POST body or GET query must equal the shared INTERNAL_PASS (dashboard/helpers.py:25, dashboard/helpers.py:225-228).
  • Fiscal-year guard - every voucher create/update calls custom.validate_fiscal_year (dashboard/custom_functions.py:535-555) which rejects entry dates outside the tenant's active Nepali fiscal year.
  • Balance rules - custom.check_debit_credit_settlement_for_line_items (dashboard/custom_functions.py:49-72) requires total debit equals total credit; custom.total_amount_calculation_of_line_items (dashboard/custom_functions.py:75-89) requires a positive sum for voucher amounts.
  • Sanitization - voucher and item payloads are round-tripped through the Configuration service sanitize endpoint before write (e.g. payment_voucher/serializers.py:276-306, dashboard/helpers.py:138).
  • Notifications and activity logs are emitted as Kafka records, not direct Events calls - the direct HTTP calls are commented out (dashboard/notification.py:22-23, dashboard/activity_log.py:31-32) and go through kafka.call_kafka_for_log_and_notification (dashboard/kafka_functions.py:41-59) with record types NOTIFICATION_RECORD and LOG_RECORD (dashboard/choices.py:344-345).

Voucher status state machine

All four voucher families share one status column (journal_voucher/models.py:100-104, choices StatusChoices dashboard/choices.py:62-67) and one rejection flag (journal_voucher/models.py:109-112). Bill settlements use the same statuses (journal_voucher/models.py:37).

stateDiagram-v2
    [*] --> draft
    draft --> submitted_for_approval
    draft --> [*] : delete
    submitted_for_approval --> draft
    submitted_for_approval --> approved
    submitted_for_approval --> cancelled
    approved --> cancelled
    approved --> [*]
    draft --> rejected_flag
    rejected_flag --> draft

Transitions and guards (journal family, same for payment/receipt/contra):

  • draft to submitted_for_approval - only the original entry_by can submit, and an approval_user id must be supplied (journal_voucher/views.py:320-330).
  • submitted_for_approval to draft - cancel-submission, only by the submitter (journal_voucher/views.py:626-635); or rejection: the approval user (or anyone other than the submitter) posts type rejection, which sets rejected, rejected_by, rejected_comment, rejected_date and keeps status draft-eligible (journal_voucher/views.py:606-625).
  • submitted_for_approval to approved - only the designated approval_user, not the submitter (journal_voucher/views.py:353-357).
  • submitted_for_approval or approved to cancelled - cancelled_by/cancelled_date set; a journal with additional cost (other_info.additional_cost) refuses cancellation (journal_voucher/views.py:279-281).
  • draft delete - only the original entry_by, items deleted first (journal_voucher/views.py:216-220).

The approval behavior is tenant-configured: the status endpoint fetches the tenant's approval-work configuration from the Configuration service (get_configuration, dashboard/send_requests.py:52-72; journal_voucher/views.py:260-265) and branches on its title (choices.ConfigTitle dashboard/choices.py:174-176).

Side effects on approval and cancel (journal family)

Approving writes: status/approved_by/approved_date (journal_voucher/views.py:358-365), an activity log record (journal_voucher/views.py:372, via dashboard/activity_log.py:67-103 to Kafka LOG_RECORD), and a Kafka approval record (journal_voucher/views.py:374-391, record type JOURNAL_VOUCHER_APPROVAL_RECORD dashboard/choices.py:346) whose payload is built by kafkaJournalVoucherItemReportingSerializer (journal_voucher/serializers.py:805-834) after pulling supplier/customer/employee names from Projectmaster (journal_voucher/views.py:457-529). Cancelling writes the cancelled fields plus a JOURNAL_VOUCHER_CANCEL Kafka record (journal_voucher/views.py:401-436). Submissions and rejections additionally send a notification record (journal_voucher/views.py:338-343, 613-618).

The Payment, Receipt and Contra families repeat the identical shape with their own Kafka record types (PAYMENT_VOUCHER_APPROVAL_RECORD/PAYMENT_VOUCHER_CANCEL dashboard/choices.py:348-349, RECEIPT_VOUCHER_APPROVAL_RECORD/RECEIPT_VOUCHER_CANCEL dashboard/choices.py:350-351, CONTRA_APPROVAL_RECORD/CONTRA_CANCEL dashboard/choices.py:352-353). Bill settlement approval additionally creates the linked JV (see Bill settlement section).

Bill settlement

Bill settlement settles a party bill against an opening/credit position. It reuses the voucher status machine (journal_voucher/models.py:37) but has one extra side effect: approval auto-creates the linked journal voucher and rewrites the party's remaining opening. All mutations run in one transaction (bill_pay_receive/views.py:226).

Trace (POST /api/bill-settlement/status/{pk}/)

  1. Auth: IAMAuthenticationBackend + BILL_PAYMENT_RECEIVE feature (bill_pay_receive/views.py:200-202); initial() picks the action permission by request status - submit requires VIEW, everything else APPROVE_CANCEL (bill_pay_receive/views.py:204-211).
  2. Load the tenant-scoped BillSettlement or 400 BILL_NOT_FOUND (bill_pay_receive/views.py:213-220).
  3. Fetch the tenant's approval-work configuration from the Configuration service (bill_pay_receive/views.py:231-236); no config = 503 SERVICE_UNAVAILABLE (bill_pay_receive/views.py:272).
  4. BASIC flow (bill_pay_receive/views.py:237-255): submit - only the original entry_by, only from draft, approval_user id required, sets approval/submit fields, sends notification + activity log (bill_pay_receive/views.py:288-309); approve - compulsion check then approval (bill_pay_receive/views.py:244-248); cancel - from SFA or approved (bill_pay_receive/views.py:250-253).
  5. CUSTOM flow (bill_pay_receive/views.py:257-270): no submit - approve goes directly, with the compulsion check requiring status DRAFT (bill_pay_receive/views.py:281-286); cancel as in BASIC.
  6. On approval (bill_pay_receive/views.py:311-340): basic-flow compulsion requires SFA when compulsion=true (bill_pay_receive/views.py:274-279); approver must be the designated approval_user when coming from SFA, or the original entry_by when approving a draft directly (bill_pay_receive/views.py:312-319); writes approved fields, then updates the entity's remain opening via custom.update_remain_opening_of_entity (bill_pay_receive/views.py:327-331) and creates the automated journal via bill_settlement_journal (bill_pay_receive/views.py:333-334), then an activity log (bill_pay_receive/views.py:336).
  7. On cancellation (bill_pay_receive/views.py:342-374): same guards mirrored, reverts the remain opening and cancels the linked journal via bill_settlement_journal_cancel (bill_pay_receive/views.py:361-368).

Journal hooks (internal, the money path)

The internal endpoints below are how every other module posts to the ledger. They share the same skeleton: validate tenant_id plus method plus the shared internal password, fetch the tenant's full supplier/customer/employee sets from ProjectMaster once, build O(1) lookups, collect all GL accounts in one query, then call journal.automated_journal.

POST /api/dashboard/create-journal/ (Sales, Purchase, stock adjustment)

JournalCreateForSalesPurchaseViewStockAdjustment.post (dashboard/views.py:712-763).

  1. Password gate: validate_internal_pass against the shared INTERNAL_PASS (dashboard/views.py:718-719).
  2. Entity fetch: all suppliers, customers, employees of the tenant from ProjectMaster (dashboard/views.py:619-646, 725).
  3. automated_journal dispatches on the method field to a per-transaction builder (dashboard/journal.py:242-293): purchase invoice, purchase return, sales invoice, sales return, supplier payment, customer payment, expense entry, stock adjustment, GRN and GRN-return (the GRN builders exist but the GRN document family is not used in ProvidhyERP). Cheque methods are folded into the payment builders by cheque_type (dashboard/journal.py:266-283).
  4. Each builder (e.g. expense_entry_journal dashboard/journal.py:326-372) reads the tenant's relevant automation configuration (e.g. PURCHASE_FLOW for the VAT account), creates the JournalVoucher already APPROVED with module_reference=True and the module feature stamped, and assembles the debit/credit items in the fixed JOURNAL_ITEM_ORDERING slot layout.
  5. Kafka: the items are serialized by kafkaJournalVoucherItemReportingSerializer and published with the record type mapped from the transaction kind - JOURNAL_VOUCHER_APPROVAL_RECORD for invoices/returns/expenses, PAYMENT_VOUCHER_APPROVAL_RECORD for supplier payments, RECEIPT_VOUCHER_APPROVAL_RECORD for customer payments (dashboard/journal.py:296-322).
  6. Failure semantics: any exception is swallowed - a PendingJournal row records the failure (tenant, unique_id, invoice id, type, amount, error) and the endpoint still returns 200 'Journal creation scheduled!' (dashboard/views.py:750-762). NotImplementedError returns 400 (dashboard/views.py:748-749). The caller's document approval is NOT rolled back.

POST /api/dashboard/cancel-journal/

JournalCancelForSalesPurchaseViewStockAdjustment.post (dashboard/views.py:766-782): same password gate, then journal.automated_cancel_journal(entry_id, method, tenant, user, approved_by) (dashboard/journal.py:3304) which cancels the JV the module document created (status cancelled, cancelled fields, cancel Kafka record). Called when a module document is cancelled after its journal posted.

POST /api/account-payable/supplier-create-journal/ and /api/account-receivable/customer-create-journal/

Same skeleton as create-journal (account_payable/views.py:116-164, account_receivable/views.py:119-167), but with a different failure contract: on exception they create the PendingJournal row and return 400 with the error (account_payable/views.py:153-163, account_receivable/views.py:156-166) instead of 200. Their cancel twins (account_payable/views.py:167-183, account_receivable/views.py:170-185) mirror cancel-journal.

PendingJournal

PendingJournal rows are the ledger's failure queue: one row per failed module journal, with the error message captured. The list route GET /api/dashboard/pending-journals/ (and by pk) exposes them for ops inspection (journal_voucher/views.py:853-867). No automatic retry worker exists in the Accounting repo - unverified whether an external job re-drives them.
