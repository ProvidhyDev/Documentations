Business Flows (Traced) - Ledger & Ops

Accounting is the general-ledger service of ProvidhyERP. This file covers the ledger and operations half of the service: chart-of-accounts structure changes, bank account management, the fiscal year close, the internal data-mutating ops routes, and the pending-journal dead-letter path. The voucher approval lifecycle (journal/payment/receipt/contra/bill-settlement status machines) and the module-facing create-journal/cancel-journal hooks are deep-traced in flows-vouchers.md; the tables below link out to it.

Runtime shape in one paragraph: every ledger line lives in a single JournalVoucher table whose jv_type column distinguishes journal, payment, receipt and contra vouchers (journal_voucher/models.py:56-210); the ChartOfAccount table is a hybrid tree where group=True rows are groups and account=True rows are accounts, linked through two parallel parent axes (parent for the direct parent, parent_type for the top-level account-type branch, chart_of_accounts/models.py); a BankAccount row is always paired 1:1 with a GL ChartOfAccount (the gl_mapping FK, bank/models.py:28-30, both FKs PROTECT). IAM-facing routes are tenant-scoped through request.auth (the tenant id returned by the IAM token check, dashboard/auth_backends.py:21-57); internal routes are gated by a single shared INTERNAL_PASS password compared in plain text (dashboard/helpers.py:25, 225-228). Fiscal close is computed outside Accounting (the caller does the carry-forward math) and applied locally as an idempotent bulk update (chart_of_accounts/views.py:1429-1475).

Auth and internal gates (how every trace below starts)

  • IAM routes - IAMAuthenticationBackend.authenticate (dashboard/auth_backends.py:21-57) takes the JWT from the accessToken cookie, the Authorization header, or the request body (dashboard/helpers.py:365-393) and POSTs it to the IAM backend api/token/verify/ (dashboard/auth_backends.py:60-71); a missing/failed verify is a 401, a dead IAM is a 503. It then requires ACCOUNTING in the user's subscribed_services and email_verified (lines 44-56), and loads the tenant's fiscal year into request context. HasPermission (dashboard/auth_backends.py:74-107) then enforces the view's required_feature_permission + required_action_permission with a live GET to IAM, unless the caller is a tenant_root (bypass) - and non-GET requests additionally require an unexpired subscription. Each view's initial() swaps the required action per HTTP method (e.g. GET-as-VIEW, POST-as-ADD_EDIT), e.g. bank/views.py:24-52.
  • Internal routes - InternalRequestPermission (dashboard/auth_backends.py:110-121) compares the password field (body for POST, query for GET) against PASSWORD = config("INTERNAL_PASS") (dashboard/helpers.py:25) with a plain string compare (dashboard/helpers.py:225-228). There is no per-caller identity: any service holding the shared password can call any internal route for any tenant.
  • Feature codes used in this file: CHART_OF_ACCOUNTS PR1301, BANK_ACCOUNT PR1305 (dashboard/choices.py:230, 234); actions add_edit/view/active_inactive/delete (dashboard/choices.py:319-325).
  • Side-effect plumbing shared by every traced route below: create_activity_log (dashboard/activity_log.py:11-33) posts to the internal Kafka-producer service when kafka_data=True, which writes the service_logs topic (dev_service_logs in development) via dashboard/async_func.py:90-119; failures are logged and swallowed (dashboard/kafka_functions.py:10-38).

Bank account operations - /api/bank-account/

What happens. A bank account is not one row: creating it writes the BankAccount master row and a paired GL ChartOfAccount (flagged bank=True) under the tenant's configured bank group, linked by gl_mapping (bank/serializers.py:39-103). Names pass through the Configuration service sanitizer and must be unique per tenant. Inactive-ing a bank mirrors the status onto its GL account so it disappears from voucher bank pickers, and deleting a bank that any voucher references does not fail cleanly - the PROTECT FK blows up into a generic 500 (bank/views.py:181-185).

Trace

  1. Auth - IAM + BANK_ACCOUNT (PR1305); initial() maps GET to view and POST to add_edit (bank/views.py:24-52).
  2. Create - POST /api/bank-account/ (bank/views.py:53-75): requires name, runs in one transaction, then BankAccountSerializer.create (bank/serializers.py:39-103):
    • posts the fields to the Configuration sanitizer (dashboard/helpers.py:49-51, bank/serializers.py:46-63); a failed call is a SANITIZE_ERROR 400;
    • checks tenant-wide name uniqueness on the sanitized name (bank/serializers.py:65-68);
    • creates the BankAccount row (bank/serializers.py:71);
    • reads the GL_MAPPING/BANK configuration for the BANK_GROUP id (bank/serializers.py:73-80); if the configuration is missing the request dies with 503 TemporaryServiceUnavailableError (bank/serializers.py:103);
    • creates the GL ChartOfAccount under the bank group with bank=True, copying the opening fields; its code_number is the last sibling's code plus the sibling interval, and a collision aborts with COA_LIMIT_EXCEED (bank/serializers.py:157-206, then 94-99).
  3. Side effect - the view writes a CREATION activity log to the service_logs Kafka topic (bank/views.py:77-84).
  4. Update - POST /detail/&lt;int:pk&gt;/ (bank/views.py:117-142): same sanitize + uniqueness path but excluding self (bank/serializers.py:105-155); once an opening was set, changing opening or opening_cr_dr is rejected with Opening cannot be edited! (bank/serializers.py:140-144); the linked COA's name/opening/opening_date/opening_cr_dr are force-synced (bank/serializers.py:148-153); an EDITION log carries the changed fields (bank/views.py:144-152).
  5. Delete - POST /delete/&lt;int:pk&gt;/ (bank/views.py:166-185): fetches the tenant's bank and calls instance.delete() directly. JournalVoucher.bank is a PROTECT FK (journal_voucher/models.py:18-20), so any voucher referencing the bank raises ProtectedError, which the bare except Exception converts into a 500 SERVER_EXCEPTION (bank/views.py:181-185). No usage pre-check, no cascade, no log entry.
  6. Status - POST /status/ (bank/views.py:207-242): bulk ids + active_status; per id it sets the bank status and the linked gl_mapping COA status in the same save sequence (bank/views.py:229-233), then an ACTIVE/INACTIVE log (bank/views.py:244-255).
  7. Import (internal) - POST /import/ (bank/views.py:357-378): password gate, then BankAccountMigrateCreationSerializer (bank/serializers.py:215-276) creates rows with migrated=True and links the GL COA exactly like the manual create; a REFERENCE log says Bank {name} migrated successfully (bank/serializers.py:331-340).

Side effects

  • Activity logs to Kafka service_logs for create/update/active/inactive/migrate (dashboard/activity_log.py:11-33).
  • Configuration reads on every create/import (GL_MAPPING/BANK) and a sanitize round-trip on every create/update.

Chart of accounts - structure changes - /api/chart-of-account/

What happens. The COA tree (ChartOfAccount rows with group=True/account=True, dual parent axes) is shaped three ways: by onboarding (register-coa seeds the platform default for a new tenant), by tenant users creating/renaming/re-homing/toggling accounts and groups under IAM, and by internal bulk routes used by other services. Account creation sanitizes the name, enforces tenant-wide uniqueness, and auto-assigns code_number as last-sibling-code + interval; group inactivation cascades to every descendant and to the GL accounts of any bank mapped inside the group. Delete is a hard delete with no usage check.

Trace - create an account

  1. Auth - IAM + CHART_OF_ACCOUNTS (PR1301); POST maps to add_edit (chart_of_accounts/views.py:57-86).
  2. Validate - POST /api/chart-of-account/ (chart_of_accounts/views.py:87-109): requires name + parent, one transaction.
  3. Sanitize - ChartOfAccountCreateSerializer.create posts name/opening/opening_date/description to the Configuration sanitizer (chart_of_accounts/serializers.py:194-213).
  4. Uniqueness - tenant-wide unique check on the sanitized name (chart_of_accounts/serializers.py:214-216).
  5. Code assignment - coa_addition -> chart_of_account (chart_of_accounts/serializers.py:144-192): the parent must belong to the tenant; the top-level branch (parent_type) is the parent itself when default_on, otherwise its parent; the code base is the last account=True child (on either tree axis) of that branch; new_code = base_code + interval; if new_code already exists for the tenant it is 400 COA_LIMIT_EXCEED (chart_of_accounts/serializers.py:187-190). account_type is inherited from the base child.
  6. Persist - the row is saved with account=True, the inherited account_type, the computed code_number/interval, and default_on taken from request context (chart_of_accounts/serializers.py:219-222); the view logs CREATION to service_logs (chart_of_accounts/views.py:111-118).

Trace - update an account

POST /detail/&lt;int:pk&gt;/ (chart_of_accounts/views.py:156-202) only edits name/parent/description - opening fields are not updatable (chart_of_accounts/serializers.py:225-232); bank-linked COAs are refused with BANK_COA_ERROR (chart_of_accounts/views.py:168-169). After sanitize + self-excluded uniqueness, re-homing under a different parent recomputes code_number on the new branch (chart_of_accounts/serializers.py:325-329); same parent keeps the code (chart_of_accounts/serializers.py:330-331). An EDITION log carries the diff (chart_of_accounts/views.py:181-202).

Trace - delete / status

  • Delete - POST /delete/&lt;int:pk&gt;/ (chart_of_accounts/views.py:213-229): instance.delete() with no check for vouchers referencing the account. Referencing journals are a PROTECT FK (journal_voucher/models.py:215), so a used account raises and the view's except returns 500 (chart_of_accounts/views.py:223-229); an unused one is gone.
  • Account status - POST /status/ (chart_of_accounts/views.py:253-287): bulk ids, validates active_status, refuses bank COAs (chart_of_accounts/views.py:274-275), sets the flag per id, ACTIVE/INACTIVE log (chart_of_accounts/views.py:289-300). No cascade - an inactive account simply stops appearing in pickers.
  • Group status - POST /group/status/ (chart_of_accounts/views.py:505-565): bulk ids; per group it sets the flag, cascades the same status to all children on both tree axes (chart_of_accounts/views.py:531-534, 567-569), then reads the GL_MAPPING/BANK configuration and, if the affected subtree contains the configured bank group, flips active_status on every bank_gl account inside it (chart_of_accounts/views.py:536-552, 571-600). Missing bank configuration is a 503 (chart_of_accounts/views.py:553-556).

Side effects

  • Activity logs to Kafka service_logs for every mutation above.
  • Configuration reads (GL_MAPPING/BANK) on group status change and bank-account status interplay; sanitize round-trips on create/update.
  • Group inactivation can silently deactivate bank GL accounts that sit under the group (cascade, chart_of_accounts/views.py:571-600).

Fiscal year close - /api/chart-of-account/get-opening-info/ + /api/chart-of-account/transfer-closing/

What happens. Fiscal close is split: the caller (an ops service; which one is unverified) fetches every active account's current opening fields, computes the carry-forward balances outside Accounting, and posts them back. Accounting then applies the new openings in one bulk update per tenant and stamps an ActionModel marker so the same tenant+year can never be closed twice. The balances that move are exactly the opening, opening_cr_dr and opening_date columns on ChartOfAccount rows - no journals are posted, no other service is written. Closed years are then read differently: when a request carries a fiscal year whose status is closed, the COA serializer replaces the stored openings with values fetched from the Reporting service's opening-history endpoint.

Trace

  1. Read the openings - POST /get-opening-info/ (chart_of_accounts/views.py:1375-1399, internal password): for the given tenant_id list it returns all account=True rows with active_status=active, selecting id/opening_cr_dr/opening/unique_id/opening_date/tenant_id/account_type/retain, grouped per tenant (chart_of_accounts/views.py:1380-1399). Inactive accounts are excluded, so a tenant that deactivated an account closes it out without an opening line.
  2. Apply the closing - POST /transfer-closing/ (chart_of_accounts/views.py:1402-1475, internal password), body {tenant_id: {fy_id, accounts: [{id, opening, opening_cr_dr, opening_date?}]}}, one transaction:
    • Idempotency guard - existing ActionModel rows with action_type=ACCOUNT_CLOSING for the given tenants+years are loaded first; any tenant already stamped is skipped entirely (chart_of_accounts/views.py:1435-1443).
    • Per-tenant update - update_opening_info re-filters the requested account ids against account=True and active_status=active again (chart_of_accounts/views.py:1405-1412); for each: opening is overwritten unconditionally (default 0), opening_cr_dr only when provided, and opening_date advances only if the incoming date is later than the current one (or the current is empty) (chart_of_accounts/views.py:1414-1425).
    • Persist - bulk_update of opening/opening_cr_dr/opening_date (batch 2000) (chart_of_accounts/views.py:1455-1459), then ActionModel(tenant_id, fy_id, ACCOUNT_CLOSING) rows bulk_created for the newly closed tenants (chart_of_accounts/views.py:1460-1471). An empty result set returns the message No accounts to update without writing markers (chart_of_accounts/views.py:1451-1454).
  3. Reading closed years - ChartOfAccountSerializer.to_representation (chart_of_accounts/serializers.py:60-88): when the request's fiscal year context has status closed (dashboard/choices.py:451), it calls the Reporting service api/dashboard/opening-history-detail/ with the shared password (chart_of_accounts/serializers.py:51-58, dashboard/helpers.py:190) and substitutes opening/opening_cr_dr/opening_date from the history record - so closed-year reports show the frozen openings, while the live columns keep serving the current year.
  4. Tagging vouchers - POST /api/dashboard/add-fiscal-year/ (dashboard/views.py:900-921, internal): takes a {tenant_id: fy} map and bulk-sets fiscal_year on every JournalVoucher row (loaded into memory, dashboard/views.py:905-910) and on ID rows with name=JV for the mapped tenants; a tenant missing from the map gets an empty fiscal_year string.

Side effects

  • Writes: ChartOfAccount.opening/opening_cr_dr/opening_date (active accounts only), ActionModel markers, and JournalVoucher.fiscal_year + ID.fiscal_year (add-fiscal-year).
  • Reads: Reporting opening-history-detail per COA detail render of a closed fiscal year.
  • No Kafka events and no activity logs on the close routes themselves.

Internal ops routes that mutate data

Short traces for the remaining data-mutating internal routes. All are gated by the shared INTERNAL_PASS password (class-level InternalRequestPermission or an in-body validate_internal_pass check) - none of them know which service is calling.

  • Register the default COA - POST /api/chart-of-account/register-coa/ (chart_of_accounts/views.py:742-765): manual password + tenant_id + data + response_account check (dashboard/custom_functions.py:30-46), then defaults.create_default_chart_of_accounts builds the platform standard tree for a new tenant (chart_of_accounts/views.py:752-754, dashboard/defaults.py:4) and returns {name: {id, name}} only for the requested response_account names. Onboarding seed; no activity log, no permission classes beyond the password check.
  • Bulk account management - POST/GET /api/chart-of-account/coa-new-account-management/ (chart_of_accounts/views.py:1503-1649): tenant_id may be all (resolved through the internal tenant list, chart_of_accounts/views.py:1506-1510) with optional start/end slicing; per tenant it finds the parent group by exact name, skips tenants without it, and for each missing account name re-uses the normal create serializer - sanitize, uniqueness, auto-code included (chart_of_accounts/views.py:1553-1583). entry_by is written as an empty string.   • Bulk create / validation / check-bulk - POST /bulk-create/ (chart_of_accounts/views.py:1206-1242+, InternalRequestPermission): pre-generates ID rows for the batch (chart_of_accounts/views.py:1210-1223) then runs ChartOfAccountBulkCreateSerializer (loop internals untraced); note a debug print in get_account_type_with_interval (chart_of_accounts/views.py:1239).   • COA/group visibility - POST /modify-coa-grp-acc-visibility/ (chart_of_accounts/views.py:1987-2031): bulk-sets show on accounts and groups matched by exact name+code_number pairs (optionally tenant-scoped) - this is how the platform hides standard accounts per tenant without deleting them.

  • Fix old payment vouchers - GET/POST /api/dashboard/fix-old-payment-vouchers/ (dashboard/views.py:1200-1498, InternalRequestPermission): finds JournalVoucher rows with jv_type journal/payment, a non-null supplier_payment_entry_id, NULL bank and status approved/cancelled (dashboard/views.py:1234-1247), fetches the supplier payments from the Purchase service (dashboard/views.py:1203-1216), then sets jv.bank to the CR item matching the payment's source_account, flips jv_type to payment and marks that item bank=True (dashboard/views.py:1261-1298). Pending journal - dead-letter handling

What happens. When a module service's journal hook fails, the failure is parked as a PendingJournal row (journal_voucher/models.py:249-264: tenant, unique_id, invoice_id, invoice_type, particular, amount, error_message). This is a dead letter, not a queue: no retry processor exists anywhere in this repository. The dashboard hook even converts the failure into a 200 so the module approval completes (dashboard/views.py:750-762), and the only ways to see or clear a row are the public untenant-scoped list endpoint, the Django admin, or the tenant deletion route.

Trace

  1. Producers - POST /api/dashboard/create-journal/: any exception inside automated_journal after the password gate creates the row and still returns 200 Journal creation scheduled! (dashboard/views.py:750-762). The AP/AR hooks instead return 400 after parking the row (account_payable/views.py:153-163; account_receivable/views.py:156-166, which dedupes with get_or_create on tenant+unique_id).
  2. Visibility - GET /api/journal-voucher/pending-journal-list/ and /pending-journal-list/<pk>/ (journal_voucher/views.py:853-867): no authentication classes, no tenant filter - one request lists every tenant's dead letters (the serializer strips error_message, journal_voucher/serializers.py:519-523); the admin site lists the same rows (journal_voucher/admin.py:95-111).
  3. Clearing - only tenant-data-deletion deletes them by raw SQL (dashboard/views.py:845-851); an operator can also delete rows through the admin. There is no endpoint that re-attempts journal creation from a pending row.

  D --> E["200 Journal creation scheduled to the module"]
  E --> F["row sits until manually inspected"]
