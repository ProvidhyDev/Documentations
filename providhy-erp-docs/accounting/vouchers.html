Accounting . Vouchers & Bill Settlement

The voucher family shares one lifecycle pattern: create -> submit for approval (tenant-configured basic/custom approval flow from the Configuration service) -> approve / reject / cancel, each step writing notification + activity log + Kafka record. All are IAM-authenticated with their feature permission; per-method action switching (VIEW/ADD_EDIT/DELETE) in initial() as in Sales/Purchase.

  • Create (1, POST): body = voucher header (date, narrative, fiscal year from request) + line items (account, debit/credit amounts); debit/credit balance validation enforced in the write serializer (unverified line-level here - the balance check is the standard of the serializer in journal_voucher/serializers.py).
  • Status change (4): same basic/custom dispatch as the sales module - fetches the tenant APPROVAL_WORK configuration from the Configuration service and routes to submit/approve/reject/cancel handlers with product-independent journal validation, notifications, activity log, and Kafka journal record types (views.py:228-566 region; handler internals partially verified - marked unverified where not read line-by-line).
  • Cancel-submission (5): reverts a submitted journal to draft with notification + activity log + Kafka events (views.py:567-660).
