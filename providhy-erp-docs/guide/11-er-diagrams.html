ER Diagrams

Database layout (verified): one PostgreSQL database per service - each settings.py reads its own DB_NAME config (e.g. Sales core/settings.py:99-105). There are no physical foreign keys between services: cross-service references are logical (shared ids like tenant_id, user_id, product id, account id passed between services over HTTP). Inside a service, items reference their headers with real FKs. Reporting reads its own replica database (reporting Reporting/settings.py:112, router settings.py:121) - it never points at module databases.

Per-service entities (verified model classes)

Model names below are the actual Django model classes in each service's models.py at the f1-production SHA (see each service overview). Fields are shown only where they anchor a cross-service reference; the full column lists live in the source.

Sales (25 models)

SalesQuotation(+Item), SalesOrder(+Item), DeliveryNote(+Item), DeliveryNoteReturn(+Item), SalesInvoice(+Item), SalesReturn(+Item), CustomerPayment(+Item), CreditLedger, CreditLedgerCustomer, CreditDispute, InventoryManipulation, FailedJournalCreation, InvoiceFailed, IRDConfiguration, SetupPanel, Source, TimeModel, ID. Header-item pairs are the document pattern; each header carries tenant_id, status, fiscal_year, approval state, and (when posted) the journal reference back to Accounting.

Purchase (20 models)

PurchaseRequisition(+Item), PurchaseOrder(+Item), PurchaseInvoice(+Item), PurchaseReturn(+Item), SupplierPayment(+Item), ExpenseEntry(+ExpenseLineItem), GoodsReceivedNote(+Item), GoodsReceivedNoteReturns(+Item), InvoiceAdditionalCost, FailedJournalCreation, TimeModel, ID. (GRN models exist but the GRN document family is out of scope in ProvidhyERP.)

Accounting (10 models)

ChartOfAccount, JournalVoucher(+Item), BillSettlement(+Item), BankAccount, PendingJournal, ActionModel, TimeModel, ID. The voucher family (journal/payment/receipt/contra) all sit on the JournalVoucher model with a voucher-type discriminator; BillSettlement ties settlements to party bills.

ProductManagement / Inventory (16 models)

Product, Variant, ProductVariant, ProductBatch, UOM, ProductUnitConversion, ProductCategory, Campaign, Inventory, BatchInventoryTotal, StockAdjustment(+Item), KafkaTest, ActionModel, TimeModel, ID. Product is the master; Inventory + BatchInventoryTotal are the ledger; StockAdjustment is the correction document.

ProjectMaster (10 models)

Customer, CustomerCategory, CustomerIdentityLink, Supplier, SupplierCategory, Employee, PaymentTerm, ActionModel, TimeModel, ID. Parties are referenced by id from Sales/Purchase documents (customer id, supplier id) - logical, not FK.

Reporting (22 models)

SalesTransactionView, PurchaseTransactionView, ProductTransactionView, AccountingTransactionView, TransactionLedgerView, TransactionLedgerFailure, ProductMaterializeView, ProfitAndLossReportView, TrialBalanceReportView, BalanceSheetReportView, InventoryValuationReport, InventoryValuationBatchReport, InventoryMonthlyClosing, SyncTracker, CustomerOpeningHistory, SupplierOpeningHistory, ProductOpeningHistory, AccountOpeningHistory, KafkaTestModel, ActionModel, TimeModel, ID.

TMS-Service (18 models)

Tenant, ChangedTenantID, Company, ExternalTenantLink, TenantPackage, TenantPackageModule, TenantContract, TenantCampaign, Subscription, SubscriptionLog, Payment, BillItem, RegistrationSource, ReleaseNote, ReleaseNoteViewLog, PendingData, TimeModel, ID.

events (13 models)

Notification, CMSNotification, NotificationChannel, NotificationPreference, ActivityLog, Export, EmailScheduler, CMSEmail, ExecutiveMail, BulkEmail, BulkEmailLog, FailedEmail, TimeModel, ID.

IAM-Backend (10 models)

CustomUser, CustomUserGroup, FeaturePermission, NewFeaturePermission, NewActionPermission, ExternalEntity, EntityActivity, APICongfigurationKey, TimeModel, ID. (ExternalEntity/EntityActivity hold the federated-identity mappings for the miniapp.)

Payment-Service (7 models)

EsewaPaymentRequest, CustomerPayment(+Item), SupplierPayment(+Item), TimeModel, ID - the payment-provider side of module payments.

Configuration-Service (20 models)

FiscalYear, FiscalYearHistory, TenantFiscalYear, DefaultServiceConfiguration, TenantServiceConfiguration, DefaultChartOfAccount, DefaultUOM, DefaultVariant, DefaultPaymentTerm, CostTerm, TDSType, Industry, Currency, TenantCurrency, Datepicker, TenantDatepicker, LoginSession, LengthParameter, TimeModel, ID.

ERP-Project-Package (10 models)

Package, PackageModule, Module, Contract, Agent, UserRange, PaymentPeriod, Campaign, TimeModel, ID - the entitlement master data.

Website-Service (12 models)

Blog, BlogCategory, MetaTag, Faq, ContactUs, Video, TermsAndConditions, Promotions, LeadGroup, GoogleAnalytics, TimeModel, ID.

Document-Service (5 models)

Document, DocumentManager, DocumentValidatation, TimeModel, ID.

Migration-Service

No models of its own (0) - it is stateless orchestration: it validates uploads and calls the target services' internal import endpoints (per-entity auth backends in Migration-Service auth_backends.py:75-92).

Kafka repos

No domain models - broker config (providhy-kafka), producer client library (Kafka-Producer), consumer command host (Kafka-Consumer; only a Django admin surface).
