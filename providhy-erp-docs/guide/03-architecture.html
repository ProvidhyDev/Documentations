Architecture Deep-Dive

This page is the structural deep-dive of the Providhy ERP platform: entry points, the two authentication chains, the tenant-registration cascade, the Kafka event backbone, data flow and state - plus the patterns and anti-patterns found in a full-architecture grill of the code. It complements the Platform Overview: that page says what the platform does; this page says how it is built and where the structural risk is.

Every file:line reference below was read from the f1-production commit listed under How to read this page (verified 2026-11-05). Severity tags (HIGH / MEDIUM / LOW) and the findings register at the bottom are the condensed output of that grill. CDXE-REBOOT is out of scope (not part of the Providhy ERP deployment).

All services are Django 5.0.3 + DRF + simplejwt with one Postgres database per service, one shared Redis (Celery broker + token revocation), and one Kafka cluster. Every container runs its entrypoint.sh: 4 Celery prefork workers (concurrency=1) + Celery beat + manage.py runserver as the web server (Sales entrypoint.sh:23). Running runserver in production containers is finding #13.

Reading the map: module services talk to each other only through internal HTTP hooks (journals into Accounting, notifications into events) and through Kafka for record events; IAM-Backend sits on every request; TMS is the tenant factory that Configuration, the Package Registry and the modules depend on at onboarding time.

Authentication: two chains

The platform has two user-facing authentication chains (ERP users and eSewa miniapp identities) plus one internal machine-to-machine scheme. All three are implemented per service - the same classes re-implemented in every module, which is where most of the structural risk is.

ERP chain (per request)

Every ERP request goes through two per-view classes in the module service: an IAMAuthenticationBackend* (authentication) and a HasPermission subclass (authorization). Sales copy as the reference implementation (Sales/dashboard/auth_backends.py):

Consequences: IAM-Backend is on the critical path of literally every ERP request (1-2 synchronous round-trips, no caching, no timeouts) - finding #1 (HIGH). Root users short-circuit the second call (line 93). Inside HasPermission the check is fail-closed (a view without declared required_feature_permission/required_action_permission returns False, lines 106-107), but there are no global DRF defaults: REST_FRAMEWORK is defined only in PROD/UAT and only sets the exception handler (Sales core/settings.py:141-144), so a view that declares no permission class is simply open - finding #11 (MEDIUM).

Federated chain (eSewa miniapp)

Miniapp identities are minted by IAM-Backend's external surface (api/external/: register, token, token/verify, token/refresh, is-registered, user-statistics, users, activities) with an HS256 JWT carrying custom claims (tenant_id, provider_code, user_type, tenant_root, subscribed_services, external_identifier, product_code, subscribed_date) and delivered as the miniAppAccessToken/miniAppRefreshToken cookies (IAM-Backend federated_identity/views.py:234-235):

sequenceDiagram
participant MA as eSewa miniapp
participant IAM as IAM-Backend
participant SVC as Module service
Note over MA,IAM: origin check on verify = TOTP on X-MINIAPP-TOKEN, skipped in UAT/DEV (utils.py:78-84)
MA->>SVC: request with miniAppAccessToken cookie
SVC->>IAM: POST /api/external/token/verify/ + X-MINIAPP-TOKEN (auth_backends.py:218-229)
IAM-->>SVC: Token is valid
SVC->>SVC: decode the same JWT locally with verify=False (line 192)
SVC-->>MA: 200 with raw int identities

The local decode trusts the remote verify (signature not re-checked, verify=False, line 192). A debug print of the full IAM response goes to stdout on every federated request (line 227) - finding #14 (LOW).

Internal service-to-service (INTERNAL_PASS)

Service-to-service calls authenticate with one static shared secret, INTERNAL_PASS (Sales dashboard/helper.py:29), sent in the POST body or the GET query string (auth_backends.py:147,152). Three weaknesses at once - finding #3 (HIGH):

  • the comparison is != (non-constant-time, helper.py:383-386);
  • on a failed check the attempted secret is printed to stdout (auth_backends.py:165) - which is the real secret whenever a caller typo'd it;
  • the same password rides along in plaintext in every internal payload (17 such payload sites in Sales/dashboard/helper.py alone).

Fix direction: per-service signed HMAC or mTLS, hmac.compare_digest, remove the print.

Tenant registration cascade

When a new eSewa user registers (and no tenant exists for the provider+identifier yet), four services are involved in one synchronous HTTP chain that creates the tenant end-to-end:

sequenceDiagram
participant ES as eSewa miniapp
participant IAM as IAM-Backend
participant TMS as TMS-Service
participant CFG as Configuration-Service
ES->>IAM: POST /api/external/register/ (AES-ECB payload)
IAM->>IAM: decrypt (utils.py:366) + exists-check (400 if known)

IAM-->>ES: cookies miniAppAccessToken / miniAppRefreshToken

Timeout inversion (finding #4, HIGH): the outer 60s budget can expire while the inner 120s hop is still running - IAM answers the user with an error while TMS/Configuration keep creating data (orphan-tenant risk). The code comment itself calls the 60s a stopgap.

[GOOD] The TMS step is idempotent (ExternalTenantLink per provider+external_identifier, select_for_update row lock, tenant_management/views.py:4771-4807), so retries are safe. The right fix is therefore an async 202 + outbox + reconciliation worker, not a bigger timeout.

[MEDIUM] The registration payload is "encrypted" with AES-ECB whose key is the first 32 characters of the client-supplied miniapp token sent in the same request (IAM utils.py:348-393, key = token[:32] at :393) - obfuscation, not encryption. Finding #5. Fix direction: per-provider asymmetric keys (or per-provider KMS-wrapped AES-256-GCM).

Event backbone (Kafka)

The platform is mid-migration of its Kafka contract. f1-production today runs the legacy generation - one raw topic per module with the action string inside the payload. The next-generation contract (9 topics + shared Actions constants) lives in the providhy_kafka package, which no f1 service has adopted yet. Both generations are verified below.

How a record event is published

Module services never touch Kafka directly. They POST to the kafka_producer sidecar (FastAPI + AIOKafkaProducer, kafka_producer/main.py:21,29; endpoint POST /v1/produce/, app/routes.py:13) with event_topic, event_type (used as the Kafka key) and value. Example, Sales (dashboard/kafka_function.py:8-27): topic sales_events, key "sales" (line 20), value {action, tenant_id, data}.

The action string comes from per-service ConsumerActionList classes - Sales ~15 values, Purchase 20, ProductManagement 20, Accounting 34 - each re-declared in its own choices.py, i.e. the action vocabulary is duplicated per service just like the auth backends.

Next-generation contract (providhy_kafka)

The shared package providhy_kafka (providhy-kafka @ development, 4015222) defines the intended contract in plain, Django-free classes (topics.py): 9 topics - invoice.events, return.events, order.events, delivery_note.events, drn.events, payment.events, activity_log.events, notification.events, email.events (with dev_ prefix in dev) - and 23 Actions constants (approval/cancel per record type plus activity_log_created, notification_created, email_created). Its docstring says producers and consumers should import from it so a rename happens in one place.

Verified by full-repo scan on 2026-11-05: zero f1 services import it and zero f1 code contains those topic strings, and it is not pinned in any requirements.txt. The migration to this contract has not started on f1 - findings #6/#7 (MEDIUM).

Data flow and state

The write path of a typical module record (invoice approval shown):

sequenceDiagram
participant FE as Frontend
participant SVC as Module service
participant A as Accounting
participant EV as events
participant KP as kafka_producer sidecar
participant K as Kafka
participant R as reporting
FE->>SVC: create + submit record (JWT)
SVC->>SVC: workflow approval, persist to own DB
SVC->>A: internal journal hook (HTTP, on approval)
SVC->>EV: notification + activity log (HTTP)
SVC->>KP: POST /v1/produce/ (record event)
KP->>K: publish to module topic
K->>R: consumer materializes transaction + ledger views
Note over R: reports read the warehouse + read replica only

Multi-tenancy: every table carries a tenant_id column; the request-scoped identity is the raw int tenant id returned by the auth backends (request.auth), and request.user is a raw user id int (finding #15, LOW). There is no Django multi-tenancy library and no DB-level row security - tenant isolation is enforced in query code.

Warehouse: reporting models wrap database views, e.g. db_table = "AccountingTransactionView" and "TransactionLedgerView" plus the report views (reporting/accounting/models.py:86,145,349,443,539; SalesTransactionView in reporting/sales). Reports never read a module database.

Replica: reporting runs a primary/replica router (Reporting/db_routers.py, settings.py:121) - reads go to a PostgreSQL streaming replica, writes and migrations to the master; a thread-local force_database override serves the "report from master" endpoints.

Redis / Celery: Redis holds the JWT jti revocation cache, locks and counters; Celery (per service, from entrypoint.sh) handles email and deferred postings.

Patterns and anti-patterns

What to keep

  • [GOOD] Fail-fast base classes: Sales/miniapp/generics.py:43-78 - FederatedAuthenticationView.__init_subclass__ crashes the app at import time unless a subclass declares feature + action permissions (also InternalAuthenticationView :89, FederatedSearchView :94).
  • [GOOD] Idempotent external registration in TMS: ExternalTenantLink + select_for_update (tenant_management/views.py:4771-4807).
  • [GOOD] The reporting primary/replica router isolates report reads from module writes (db_routers.py).
  • [GOOD] The providhy_kafka package idea: one source of truth for topic/action strings, importable without Django - it just has not been adopted on f1 yet.

What hurts

  • Per-request auth round-trips with no cache or timeout [HIGH #1]
  • 12 diverged auth_backends.py copies [HIGH #2]
  • Shared INTERNAL_PASS in body/query, non-constant-time compare, secret printed on failure [HIGH #3]
  • Sync 4-service registration cascade with inverted timeouts (60s outer < 120s inner) [HIGH #4]
  • AES-ECB with a client-derived key on the registration payload [MEDIUM #5]
  • Two Kafka contract generations; the next one unadopted on f1 [MEDIUM #6/#7]
  • events f1/uat divergence (kafka consumers exist only on uat) [MEDIUM #8]
  • Dual reporting ingestion paths [MEDIUM #9]
  • God files [MEDIUM #10] - table below
  • Fail-open DRF defaults (no global auth/permission classes) [MEDIUM #11]
  • Wrong env var for the payment URL in Sales [MEDIUM #12]
  • manage.py runserver as the container web server [MEDIUM #13]
  • Debug prints with PII/secrets [LOW #14]; raw-int user identity [LOW #15]

Direction of travel

A prototype of where the event side of the platform is heading exists in this codebase (the erp prototype repo, not deployed): CQRS + event sourcing + a transactional outbox - the Django service writes domain state and an OutboxEvent in one database transaction; an outbox_poller (asyncpg, FOR UPDATE SKIP LOCKED) ships the rows to Kafka; a FastAPI gateway serves the read model with Redis-based idempotency. Components: django_project, outbox_poller, read_model_consumer, consumer, saga_orchestrator, fastapi_gateway.

What that retires: the ad-hoc POST-to-sidecar publish step, the dual ingestion (findings #6, #9) and - combined with the 202 + outbox pattern - the synchronous registration cascade (finding #4). It does not fix the auth chain: that still needs the shared auth package plus token/permission caching (findings #1, #2).

Branch caveats

  • TMS: the local f1-production branch in the main checkout is behind origin/f1-production; this page traces the origin head (56f9576).
  • Accounting: the main checkout is parked on another branch (f1 is checked out in a sibling worktree); the trace used a worktree at f1 (a60aaba).
  • providhy_kafka: the package lives on its development branch (4015222); there is no f1 branch for it and no f1 service imports it.
  • events: see the branch note under Event backbone - its kafka consumers exist only on uat.
  • CDXE-REBOOT: out of scope for this page and this site (not part of the Providhy ERP deployment).
