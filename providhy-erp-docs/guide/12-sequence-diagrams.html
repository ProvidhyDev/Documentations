Sequence Diagrams

End-to-end cross-service sequences for the platform's major flows. Solid arrows are HTTP calls; dashed arrows are internal hooks, Kafka, or async work. Citations anchor each flow; see the per-service docs for the endpoint tables.

Tenant onboarding

sequenceDiagram
  participant CMS as CMS / PAM platform
  participant TMS as TMS-Service
  participant PKG as Package Registry
  participant IAM as IAM-Backend
  participant CFG as Configuration
  participant MOD as Module services
  CMS->>TMS: create tenant (internal, v2)
  TMS-->>CMS: tenant id
  CMS->>PKG: package + contract master data
  CMS->>TMS: assign TenantPackage + TenantContract
  TMS-->>PKG: entitlement state visible to checks
  CMS->>IAM: create users, groups, permissions
  CMS->>CFG: ensure-configuration (seed defaults)
  CFG-->>CMS: COA, UOM, FY, service config rows
  CMS->>TMS: company setup complete (tenant portal)
  MOD->>PKG: entitlement checks on first use
  MOD-->>CMS: modules live for the tenant

Anchors: TMS tenant_management/views.py:476 (internal tenant create), views.py:634 (CompanySetupView); Configuration ensure-configuration endpoints (configuration docs, service-configuration page); Package Registry check endpoints (package docs).

Authentication (every ERP request)

sequenceDiagram
  participant FE as Frontend
  participant SVC as Any service view
  participant BE as Service IAM backend
  participant IAM as IAM-Backend
  participant PKG as Package Registry
  FE->>SVC: request + Bearer JWT
  SVC->>BE: authenticate (per-view class)
  BE->>IAM: verify token
  IAM-->>BE: user + tenant
  BE->>PKG: check module/package/contract for tenant
  PKG-->>BE: entitled
  SVC->>SVC: HasPermission feature + action (per method)
  SVC-->>FE: 200 or 403

Anchors: CustomJWTAuthentication global only in IAM (IAM/IAM/settings.py:134-142); per-service backends e.g. IAMAuthenticationBackendSales (Sales), IAMAuthenticationReportBackend (reporting); HasPermission pattern (each service overview); Package Registry check endpoints (package docs).

Sales order to invoice to journal

sequenceDiagram
  participant FE as Frontend
  participant S as Sales
  participant CFG as Configuration
  participant PM as ProjectMaster
  participant PROD as ProductManagement
  participant A as Accounting
  participant EV as events
  participant K as Kafka
  FE->>PM: search / select customer
  FE->>PROD: product picker
  FE->>S: create sales order (from quotation)
  S->>CFG: tenant approval flow + fiscal year
  S->>S: submit for approval
  S->>EV: notification to approver + activity log
  FE->>S: approve order
  FE->>S: create delivery note against order
  S->>PROD: decrement stock (batch)
  S->>EV: delivery notification + log
  FE->>S: create invoice from delivery, approve
  S->>A: internal create-journal hook
  A-->>S: journal id
  S->>K: sales_events record
  K-->>S: (reporting consumes async)

Anchors: Sales docs (order/delivery/invoice pages); journal hook Sales dashboard/custom_functions (sales overview); Kafka topics (kafka docs); events create-notification (events docs).

Customer and supplier payments (eSewa)

Scope note (user-confirmed): Payment-Service is not used in ProvidhyERP. The diagram below is what this code path does in the platform; in ProvidhyERP, module payment endpoints record payments directly - see the traced flows pages (Sales/Purchase) for the live path.

sequenceDiagram
  participant FE as Frontend
  participant M as Sales or Purchase
  participant PAY as Payment-Service
  participant ES as eSewa (external)
  participant A as Accounting
  participant EV as events
  FE->>M: record customer or supplier payment
  M->>PAY: create EsewaPaymentRequest
  PAY->>ES: initiate eSewa payment
  ES-->>PAY: provider callback (async)
  PAY->>PAY: mark transaction success
  PAY->>M: settle module payment
  M->>A: payment side journal
  M->>EV: payment notification + log

Anchors: payment docs (payment-request routes, callback endpoints); Sales cheque page (cheque path); Purchase payment page.

Subscription payment (SaaS side)

sequenceDiagram
  participant CMS as CMS / PAM
  participant TMS as TMS-Service
  participant PKG as Package Registry
  participant ES as eSewa (external)
  CMS->>TMS: upgrade or renew module or package (get data, calculate)
  CMS->>TMS: pay
  TMS->>ES: eSewa charge (payment endpoints under api/payment)
  ES-->>TMS: provider callback
  TMS->>TMS: txn-status-internal flips status
  TMS->>PKG: update TenantContract and SubscriptionLog
  TMS-->>CMS: subscription live

Anchors: TMS payment page (module/package upgrade-renew-resubscribe routes, cms variants); TMS docs (Subscription, SubscriptionLog models).

Fiscal year close

sequenceDiagram
  participant CFG as Configuration
  participant IAM as IAM-Backend
  participant A as Accounting
  participant R as reporting
  participant MOD as Module services
  CFG->>CFG: create next fiscal year (FY engine)
  CFG->>MOD: update-tenant-fiscal-year (roll out to tenants)
  CFG->>IAM: sync fiscal year into IAM
  CFG->>A: add FY info to entries
  A->>A: get-opening-info for closing year
  A->>A: transfer-closing (balances forward)
  R->>R: record opening history per entity
  Note over MOD: old year locked, new year live

Anchors: Configuration dashboard page (15 FY-engine routes incl. update-tenant-fiscal-year, sync-fiscal-year-with-iam, add-fy-info-to-entries); Accounting dashboard (get-opening-info, transfer-closing); reporting opening-history models (ER page).

Bulk migration

sequenceDiagram
  participant OP as Ops or CMS
  participant MIG as Migration-Service
  participant TGT as Target service (internal)
  OP->>MIG: upload file for entity (validate phase)
  MIG->>MIG: GenericBulkValidationView (template + row errors)
  MIG-->>OP: validation report
  OP->>MIG: create (second phase)
  MIG->>TGT: per-entity internal import call (per-entity auth backend)
  TGT-->>MIG: created rows or errors
  MIG-->>OP: migration summary

Anchors: Migration docs (validate/create generic views, per-entity auth backends at auth_backends.py:75-92).
