Start Here

This site documents the Providhy multi-tenant ERP platform - the 16 backend services, every IAM-authenticated endpoint they expose, how they authenticate, how data moves between them, and the business flows they implement. Everything was traced from the f1-production source (the production handoff branch) in early November 2026; each service page names the exact commit SHA it was read from, and every processing claim carries a file:line citation into that commit.

How the site is organized

  1. Platform overview - what Providhy ERP is, who uses it, the architecture, the service map, and the key user journeys. Start here if you are new.
  2. User journeys - feature guides: the main business flows explained end-to-end in plain language (sales-to-cash, procure-to-pay, ledger, tenant onboarding, fiscal year, miniapp).
  3. Per-service documentation - one section per service in the sidebar (left). Each starts with an overview (purpose, auth model, functional map) followed by area pages with the endpoint tables.
  4. Cross-cutting reference - consolidated ER diagrams, end-to-end sequence diagrams, and the full one-line-per-endpoint API catalog.

Reading the endpoint docs

  • Auth labels: IAM (tenant-user JWT via the service's own IAM backend), cms-iam (CMS/PAM admin platform), internal (service-to-service, token or password-gated), federated (eSewa miniapp identity), public (no auth), basic (HTTP basic, ops).
  • Citations are file:line into the service repo at the SHA in the page frontmatter - open that file at that line to verify any claim.
  • unverified means the statement was inferred from structure (class name, path, sibling views) rather than read line-by-line. There are ~140 such markers in the whole set.
  • Latest version only: where a v1/v2/Revamped pair exists, only the newest route is documented; superseded routes are listed in the service overview's scope notes.
  • Excluded by scope (user decision): CDXE (not used in ProvidhyERP), Purchase GRN + GRN-return + related deductions, product variant/product-variant + deductions, transaction-linked journal hooks (one line each).
  • FE-usage numbers come from a static scan of apps-frontend's API_ENDPOINTS map and are a floor: helper-routed and miniapp calls are not counted.

Verified platform facts (from source)

  • One PostgreSQL database per service (each settings.py reads its own DB_NAME config; e.g. Sales core/settings.py:99-105). Reporting additionally reads a replica (reporting Reporting/settings.py:112) with a read router (settings.py:121) - reports never hit the module databases.
  • Kafka (kafka-crs:9092, SASL) carries record events on four topics (sales_events, purchase_events, inventory_events, accounting_events); reporting is the main consumer (reporting dashboard/management/commands/kafka_consumer.py).
  • Redis + Celery per service for async jobs (Sales core/settings.py:203-204).
  • IAM-Backend is the only service with a global DRF authentication class (CustomJWTAuthentication, IAM/IAM/settings.py:134-142) plus anonymous throttles; every other service authenticates per-view.
  • The eSewa miniapp reaches the platform through federated identity (FederatedIdentityAuthentication / MiniAppAuthentication), never with ERP user credentials.
