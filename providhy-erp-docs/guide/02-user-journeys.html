User Journeys

Feature-by-feature, in plain language. Each journey names the services involved and links to the endpoint docs. Sequence diagrams for the cross-service mechanics are in Sequence diagrams; entity details in ER diagrams.

Tenant onboarding

Actors: CMS/PAM operations staff, the new tenant's admin. Services: TMS, Package Registry, IAM-Backend, Configuration, every module.

  1. Register the tenant. CMS calls TMS's internal tenant-create (tenant_management/views.py:476, InternalRequestAuthentication) - the ERP frontend never creates tenants. v2 exists for the current flow (create-tenant/v2/).
  2. Attach entitlements. The CMS assigns a package (a bundle of modules) and records the contract in the Package Registry (ERP-Project-Package: package/module/contract apps). TMS mirrors the tenant-side views (TenantPackage, TenantContract, TenantPackageModule models; subscription log in SubscriptionLog).
  3. Create the people. IAM-Backend gets the tenant's users, groups, and feature/action permissions (the CMS admin surface - see IAM admin).
  4. Seed the configuration. Configuration-Service materializes the tenant's defaults from the platform defaults: chart of account (from DefaultChartOfAccount), UOM, variants, currency, datepicker, payment terms, and the service configuration rows (ensure-configuration endpoints - the workhorse called at onboarding).
  5. Open the fiscal year. Configuration creates the tenant's fiscal year (TenantFiscalYear); from this moment every module date resolves through get-fiscal-year-from-date.
  6. Complete in the app. The tenant's admin lands in the tenant portal and runs company-setup (TMS CompanySetupView, tenant_management/views.py:634) to finish onboarding (company profile, PAN, e-billing config). After this, entitlement checks (Package Registry check-* endpoints) pass for the modules in the package, and the tenant's staff can work. If the tenant's subscription lapses, the check endpoints fail and the modules lock the tenant out.

Sales-to-cash

Actor: tenant sales staff. Services: Sales, ProjectMaster (customer), Configuration (approval + fiscal year), Accounting (journals), events (notifications/logs), Kafka -> reporting.

  1. Quotation - the salesperson picks a customer (ProjectMaster customer search/select) and items (ProductManagement product picker) and raises a quotation. Approval follows the tenant's configured flow (basic: submit->approve; custom: multi-step) - the configuration comes from Configuration, not Sales.
  2. Sales order - created from the approved quotation; same approval pattern. The order is the commitment to deliver.
  3. Delivery note - issued against the order (quantities, batches); a delivery-note-return handles customer returns of delivered goods.
  4. Sales invoice - generated from the delivery; this is the billing event. On approval, Sales calls Accounting's internal create-journal hook (Sales dashboard/custom_functions -> Accounting /api/dashboard/create-journal/) so the ledger records the sale (debit receivable, credit sales). IRD e-billing tenants additionally get the invoice pushed to the IRD system (ebilling app - BillingInvoiceCreate).
  5. Payment - the customer pays; the live ProvidhyERP path records the payment through the Sales payment endpoints (the eSewa provider path via Payment-Service is not used in ProvidhyERP - user-confirmed) or by cheque (cheque app - its own approval + due-date flow). The payment posts its own journals (customer payment / receipt side).
  6. Returns - a sales return (credit note) runs the same lifecycle in reverse and cancels/adjusts the journals. Every transition: notification to the relevant users (events create-notification), activity log (events), and a Kafka record event that reporting materializes into SalesTransactionView - which is what the sales reports and the dashboard widgets read.

See Sales docs for all 10 areas, sequence: sales order to journal.

Procure-to-pay

Actor: tenant purchase staff. Services: Purchase, ProjectMaster (supplier), ProductManagement (items/batches), Accounting, events, Kafka -> reporting. Scope note: GRN + GRN-return + related deduction functions are not used in ProvidhyERP and are not documented (user decision).

  1. Purchase requisition - the request to buy; approved per tenant config.
  2. Purchase order - created from the requisition against a supplier; carries additional cost terms (ProjectMaster cost terms).
  3. Goods received - receipt of goods against the order (the live receipt flow in ProvidhyERP is the order-driven receive; the full GRN document family is excluded per scope).
  4. Purchase invoice - the supplier's bill, matched to the order/receipt; approval posts the ledger entries (debit purchases/expense, credit payable) via the internal journal hook.
  5. Supplier payment - pay the bill by eSewa (Payment-Service) or cheque (purchase-side cheque app); posts the payment side journals. Expenses (expense app) run a parallel small lifecycle for non-purchase costs.
  6. Purchase return - return goods to the supplier; same lifecycle in reverse. Same event pattern as sales: events notifications + logs, Kafka purchase_events -> reporting PurchaseTransactionView.

See Purchase docs, sequence: purchase cycle.

Stock and product master

Actor: warehouse/admin staff. Services: ProductManagement, Accounting, events, Kafka -> reporting.

  • Product master: products (with UOM, unit conversions, batches), categories, and campaigns. There is also a GraphQL surface for the product domain (the live /api/product/graphql/ has resolver-level permission checks, not endpoint auth - noted in the inventory docs).
  • Stock ledger: every stock movement (sales delivery, purchase receive, adjustment) is a ledger row with batch tracking; the ledger exposes reads and service-to-service verification/manipulation routes (password-gated internal protocol, documented in stock).
  • Stock adjustment: the only manual stock correction, in two generations (v1 + revamped v2 family) - it goes through approval, then posts to the ledger (stock adjustment journal) and emits events.
  • Excluded per scope: product variant/product-variant + deduction functions; GRN manipulation/return helpers.

See Inventory docs, sequence: stock adjustment.

Ledger and fiscal year

Actor: accountant. Services: Accounting, Configuration (fiscal year), ProjectMaster (parties), reporting.

  • Chart of accounts: tenant COA (seeded from platform defaults at onboarding, importable via Migration), with groups, bank accounts, fixed assets, TDS accounts. Reporting consumes the COA list via internal routes.
  • Vouchers: journal, payment, receipt, contra - all four share one lifecycle (create -> submit for approval -> approve/reject/cancel, with notifications, logs, Kafka accounting_events) and one balance rule (debit = credit). Bill settlement ties payments to bills.
  • Banks: bank accounts for the tenant's statements; contra entries move money between bank/cash.
  • Fiscal year: Configuration owns it. The yearly cycle: roll out the new FY to all tenants (update-tenant-fiscal-year), sync it into IAM, add FY info to entries, carry payment terms forward, then close the old year - closure locks transactions, and Accounting's get-opening-info / transfer-closing move closing balances into opening balances for the new year; reporting keeps the opening-history for audit.

See Accounting docs, Configuration dashboard, sequence: fiscal year close.

eSewa miniapp

Actors: merchant and customer inside the eSewa wallet app. Services: IAM-Backend (federated identity), then per-service miniapp endpoints.

The miniapp authenticates with federated identity - an eSewa user identity that IAM-Backend maps to the tenant's records - instead of an ERP login. Surfaces include: miniapp notifications (events, federated + internal), miniapp activity log (events), miniapp customer party management (ProjectMaster /api/miniapp/*), tenant config reads for the miniapp (Configuration /miniapp/ variants), subscription/tenant lookups for the miniapp (TMS tour-status/miniapp), and the merchant/customer credit, settlement and payment-request flows documented in the companion eSewa Miniapps docs.

Data migration

Actor: implementation/ops staff. Service: Migration-Service (plus each target service's internal import endpoints).

Moving a company's historical data (products, parties, COA, vouchers, ...) into a new tenant uses a strict two-phase pattern: validate (GenericBulkValidationView - file upload, template validation, per-row errors) then create (GenericBulkCreateView) - each entity has its own per-entity auth backend so a migration token can only touch its entity. The CMS variants (paths under /cms/) are the internal side. See Migration docs, sequence: bulk migration.

Subscriptions and billing (SaaS side)

Actors: CMS/PAM, the tenant. Services: TMS, Package Registry, eSewa.

The tenant's subscription (package + contract + modules) is managed in TMS's CMS surface: upgrade a module, upgrade/renew the package (each with get-data -> calculate -> pay -> log), grace periods, credit subscriptions, and the payment endpoints under /api/payment/ (module/package upgrade-renew-resubscribe, with /cms/ variants). Payments go to eSewa; the provider callback flips the transaction status (txn-status-internal) and the subscription records update. Release notes (TMS release-notes app) are how the platform communicates changes to tenants.

See TMS docs.
