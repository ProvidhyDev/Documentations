Business Flows (Traced)

At runtime ERP-ProjectMaster is the party master of the ERP. Every write path follows the same pipeline: an IAM token is verified remotely (subscription + feature/action permission), the payload is sent to the Configuration service for sanitization, a GL mapping is resolved from the Configuration service when the client did not provide one, the row is stored with a per-tenant unique id minted from the ID table, and - for parties with opening balances - a parties_opening event is pushed to a Kafka topic through the remote Kafka producer service. Party records (supplier, customer, employee) carry opening/remain_opening balances that the payment and reconciliation services read back over internal password-gated endpoints; the fiscal-year close rewrites those openings in bulk and marks the tenant + FY as closed with ActionModel rows. Reads fan out to Configuration, Accounting, Sales, Purchase, Reporting and PMS services on demand (payment-term check, synced-transaction counts, confirmation-letter eligibility, global search).

Supplier - create, update, status

What happens: creating a supplier validates name and supplier_type, resolves the default accounts-payable GL mapping from the Configuration service, sanitizes the payload there, enforces a unique name, mints a SUPn unique id, then notifies the events pipeline (activity log to the Events service, parties_opening event to Kafka via the producer service) whenever the party has an opening balance story. Updating re-runs the same pipeline with extra guards: inactive records are frozen, and for e-billing tenants the PAN is locked once the party has synced IRD transactions. Status toggling is a bulk operation that flips active_status for a list of ids and logs each flip.

Trace - status (POST /api/supplier/inactive/, supplier/views.py:495)

  1. Same auth, action ACTIVE_INACTIVE for POST (supplier/views.py:461-474).
  2. Body is {"id": [ids], "status": active|inactive}; each id is fetched tenant-scoped, flipped and saved inside one atomic block, each flip logged as ACTIVE or INACTIVE activity log (supplier/views.py:482-511).
  3. Error path: a missing id returns 404 mid-loop (supplier/views.py:512-515); because the block exits normally, ids earlier in the list are already committed - a partially applied bulk toggle.

Side effects

  • DB: Supplier row on the projectmaster database; unique id row in ID (dashboard/models.py:16-41).
  • Events service: activity log rows (CREATION / EDITION with old-new diff / ACTIVE / INACTIVE) via POST create-activity-log (dashboard/helper.py:80).
  • Kafka: master_events topic, event type master, action parties_opening, through the remote Kafka producer service (dashboard/kafka_function.py:7-38). No in-process Kafka producer exists in this repo.
  • Configuration service: sanitization (every write) and GL mapping read (create always, update only when gl_mapping is empty).
  • Self-call to payment-term check when a payment_term is submitted.
  • Reporting service: detail read only (opening history on closed FY, confirmation-letter eligibility).
  • No journal entries are written by this service; accounting bookkeeping happens in the downstream consumers of master_events.

Customer - create, update, status

What happens: the customer flow mirrors the supplier flow with customer-specific rules - a credit_limit that must be non-negative, the ACCOUNT_RECEIVABLE GL mapping, CUSn unique ids and an as_supplier cross-role flag. The same e-billing PAN lock applies. Responses differ in two ways: update returns 200 (supplier returns 201) and validation failures return the per-field serializer error message rather than a generic one.

Payment term - transfer-payment-term

What happens: a tenant-level seeding endpoint. For each tenant it matches the incoming credit-period definitions against existing payment terms by credit_period first and by title second; matches are renamed, marked default and reactivated, and unmatched definitions are created as new active terms with PT-prefixed unique ids. This is how new tenants get their standard payment terms and how a renamed credit period propagates.

Trace (POST /api/payment-term/transfer-payment-term/, payment_term/views.py:180)

  1. No IAM auth, no InternalRequestPermission declared - the view has no authentication_classes and no permission_classes (payment_term/views.py:180-183); the caller is the tenant-provisioning path, the auth situation is therefore unverified beyond the absence of any gate in this checkout.
  2. Required tenant_id (list) and data (credit_period -> definition map) (payment_term/views.py:195-199).
  3. Per tenant, existing terms are fetched with distinct credit_period, ordered by credit_period then -created (payment_term/views.py:204-220).
  4. Branch per tenant (payment_term/views.py:223-265): definitions whose credit_period matches an existing term reuse that term - title, default=True, active_status=ACTIVE applied (payment_term/views.py:225-236); definitions without a credit_period match are searched by title and, when found, the oldest non-active candidate is reactivated and marked default (payment_term/views.py:240-257); everything else is created active with a PTn unique id (payment_term/views.py:259-265, dashboard/models.py:24-41).
  5. Response 201 with created/updated counts (payment_term/views.py:267-273).

Side effects

  • DB: PaymentTerm rows created/updated plus PTn ID rows. No activity log is written by this endpoint.
  • No other service is called.

Supplier and Customer - bulk import pipeline

What happens: the two-phase import used by the in-app bulk import and the migration service. The frontend or migration service first validates single parties (check/), prefills existing parties by id (bulk-supplier/ / bulk-customer/ - readers, not writers), then validates a whole batch with raw SQL duplicate checks (bulk-validation/) which splits rows into valid_data and error_data, and finally bulk-add/ stores the valid rows with batch-issued unique ids, a tenant-wide GL mapping and one Kafka parties_opening event per row.

Trace (supplier shown, customer mirrors)

  1. check/ (supplier/views.py:528-557): internal password gate (supplier/views.py:537), single or many lookup by id, no writes.
  2. bulk-supplier/ (supplier/views.py:1040-1058): internal password gate (supplier/views.py:1050), returns the existing parties for the given id list serialized - import prefill.
  3. bulk-validation/ (supplier/views.py:1062-1130): InternalRequestPermission (supplier/views.py:1061-1062); raw SQL LOWER(name)/LOWER(pan_number) duplicate queries against the Supplier table (supplier/views.py:1079-1102); per row, duplicate name/PAN and invalid supplier_type or opening_cr_dr produce remarks; clean rows are normalized to lowercase (supplier/views.py:1103-1128); response splits error_data / valid_data (supplier/views.py:1129-1130). No writes.
  4. bulk-add/ (supplier/views.py:1134 onward): InternalRequestPermission (supplier/views.py:1133-1134); GL mapping resolved from Configuration for the whole batch and a 400 GL Mapping not found when absent (supplier/views.py:1143-1160); unique ids issued in one batch by reading Max(unique_id) from the ID table and bulk_create of the ID rows (supplier/views.py:1163-1177); Customer/Supplier rows bulk_created inside transaction.atomic with remain_opening mirrored from opening and today's date as opening_date (supplier/views.py:1180-1210); each created row then triggers call_kafka parties_opening in a per-row try/except (supplier/views.py:1213-1237); 200.
  5. Customer mirror: customer/views.py:1057-1143 - GL title ACCOUNT_RECEIVABLE (customer/views.py:1060-1071), CUS ids (customer/views.py:1073-1086), per-row Kafka (customer/views.py:1120-1138).
  6. The older migration import (import/) is a separate single-shot path: per-row name iexact duplicate check aborts the whole atomic batch with 400 (supplier/views.py:1011-1028, customer/views.py:933-951), GL mapping resolved row by row with a fallback chain through Accounting get-account-detail and then Configuration (supplier/views.py:959-996, customer/views.py:881-918). It writes no activity log and fires no Kafka.

Side effects

  • DB: batch of party rows + batch of ID rows.
  • Kafka: one parties_opening event per created row via the producer service.
  • Configuration: one GL mapping read per batch (bulk-add) or per row (import/).
  • Accounting: get-account-detail lookups on the import/ path only (dashboard/send_requests.py:62-67, dashboard/helper.py:87).

Dashboard - fiscal year opening update

What happens: the fiscal-year closing entry point, called internally with the shared password. For each tenant in parties_data it rewrites the opening triple (opening, remain_opening, opening_cr_dr, opening_date) of every listed supplier and customer, and stores SUPPLIER_CLOSING / CUSTOMER_CLOSING markers in ActionModel so a rerun for the same tenant + FY is a no-op. This is the source of truth the read serializers consult when the FY is CLOSED.

Trace (POST /api/dashboard/update-tenants-supplier-customer-opening-details/, dashboard/views.py:399)

  1. Gate: InternalRequestPermission - password in body for POST (dashboard/auth_backends.py:157-163); required parties_data + password (dashboard/views.py:400).
  2. Existing closing markers are fetched for all tenant + fy combinations up front, per action type (dashboard/views.py:405-415).
  3. Per tenant inside one atomic block (dashboard/views.py:416-427): the supplier block runs when the key is present and no SUPPLIER_CLOSING marker exists for that tenant + FY; _update_opening_details maps by row id, copies opening/remain_opening/cr_dr and only advances opening_date to a later date (dashboard/views.py:369-397).
  4. bulk_update of the opening fields for both models (dashboard/views.py:429-438).
  5. Missing ActionModel markers are bulk_created (dashboard/views.py:440-461); note the marker objects are built from the whole data_to_update, so a tenant + FY receives a marker even when its supplier list was empty (dashboard/views.py:440-448).
  6. Response 200 (dashboard/views.py:463-466).

Side effects

  • DB: Supplier/Customer opening fields; ActionModel rows (dashboard/models.py:56-66).
  • No Kafka, no Events log, no other service call.

  B -- ok --> C[collect tenant ids and fy ids]
