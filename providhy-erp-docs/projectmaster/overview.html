Business purpose

The party master of the ERP: customers, suppliers, employees, their categories, and payment terms - plus the dashboard feeds the frontend shows on every module screen. Every Sales and Purchase document references a party by id (customer id, supplier id) resolved through this service's search/select endpoints; nothing is duplicated into the module databases. It also hosts the eSewa miniapp's party surface (federated identity) and the APIKey search used by integrations.

ERP-ProjectMaster - Overview

ERP-ProjectMaster is the party master data service of ProvidhyERP. It owns supplier, customer, employee and payment-term records (plus their per-tenant categories), serves the cross-module dashboard and internal reporting / reconciliation endpoints, and exposes a customer API for the eSewa mini-app (provider code ESM). URLs are mounted at the core root: /api/dashboard/ (core/urls.py:8), /api/payment-term/ (core/urls.py:9), /api/supplier/ (core/urls.py:10), /api/employee/ (core/urls.py:11), /api/customer/ (core/urls.py:12), /api/miniapp/ (core/urls.py:13), plus prometheus metrics and static files (core/urls.py:14-15).

Catalog totals: 79 routes, all latest, 0 superseded.

Authentication model

  • IAM: token extracted from the accessToken cookie, the Authorization Bearer header, or a request-body field (dashboard/helper.py:361-390), then verified against IAM via POST api/token/verify/ (dashboard/auth_backends.py:108-120). Module backends add a subscription check: SUPPLIER_MASTER PR200 (dashboard/auth_backends.py:77-81), CUSTOMER_MASTER PR300 (dashboard/auth_backends.py:85-89), EMPLOYEE_MASTER PR400 (dashboard/auth_backends.py:93-97), PAYMENT_TERM PR500 (dashboard/auth_backends.py:101-105). The bare IAMAuthenticationBackend (dashboard/auth_backends.py:20-73) verifies the token without a subscription or feature check.
  • IAM with feature permission: HasPermission (dashboard/auth_backends.py:123-154) blocks POST when the subscription is expired, allows tenant_root users, otherwise fetches user permissions from IAM api/internal-check-permissions/ (dashboard/helper.py:71) and requires the view's required_feature_permission (feature_ID) and required_action_permission (actions). Feature codes: PR201 Supplier Creation (dashboard/choices.py:109), PR202 Supplier Category (dashboard/choices.py:110), PR301 Customer Creation (dashboard/choices.py:113), PR302 Customer Category (dashboard/choices.py:114), PR401 Employee Creation (dashboard/choices.py:117), PR501 Payment Term Creation (dashboard/choices.py:120). Actions: add_edit, view, active_inactive (dashboard/choices.py:269-273).
  • internal: InternalRequestPermission (dashboard/auth_backends.py:157-163) checks a password field against INTERNAL_PASS (dashboard/helper.py:33).
  • internal (view gate): several views set no permission class and instead call helper.validate_internal_pass on the request password themselves (dashboard/helper.py:125-128), answering 401 on mismatch.
  • public: no authentication classes, or AllowAny.
  • federated (mini-app): FederatedIdentityAuthentication (dashboard/auth_backends.py:166-203) reads the miniAppAccessToken, validates it with the external IAM while forwarding X-MINIAPP-TOKEN, then decodes claims (provider_code, user_type, external_identifier) without signature verification; HasFederatedEntityPermission (dashboard/auth_backends.py:222-229) additionally requires the view's required_user_type (ESM = Esewa Merchant, dashboard/choices.py:349-351).
  • API key (CDXE): APIKeyAuthentication (dashboard/cdxe_decorator.py:14-52) requires an X-API-Key header and tenant_id; the key is Fernet-decrypted with a per-tenant key fetched from IAM and must equal the tenant_id.

Shared processing patterns

  • Sanitization: master serializers POST the record to Configuration api/sanitization/form-data/ (dashboard/helper.py:83) and merge the sanitized values back (e.g. customer/serializers.py:172-225).
  • GL mapping: create/update resolve the default chart-of-accounts entry from Configuration api/service-configuration/tenant/expose/ (dashboard/helper.py:84) - account_payable_supplier (dashboard/choices.py:313) for suppliers, account_receivable (dashboard/choices.py:315) for customers, account_payable_employee (dashboard/choices.py:314) for employees.
  • Activity log: create_activity_log posts to Events api/activity_log/create-activity-log/ (dashboard/activity_log.py:13-31, dashboard/helper.py:80); edit_logs computes old/new field diffs (dashboard/activity_log.py:34-42).
  • Kafka: call_kafka posts to the Kafka producer v1/produce/ (dashboard/helper.py:117) with topic master_events (dev_master_events in development), event_type master, action parties_opening (dashboard/kafka_function.py:7-38).
  • Unique ids: minted from the dashboard.ID sequence model with prefixes SUP, CUS, EMP, PTM (e.g. customer/views.py:1102, supplier/views.py:1179, payment_term/views.py:296).
  • Uniqueness: helper.is_unique enforces tenant-scoped case-insensitive name uniqueness (dashboard/helper.py:150-170).
  • Required fields: helper.valid_required_data raises a FieldError listing missing fields (dashboard/helper.py:180-193).
  • Pagination: CustomTransactionPagination, page size 100, count query param, max 100 (dashboard/pagination.py:4-7).
  • Inactive records cannot be edited: views answer 400 with Inactive records cannot be edited (dashboard/helper.py:347).
  • Opening balances: remain_opening mirrors opening on create, and on update stays consistent with settled difference (new_remain = new_opening - (opening - remain_opening), raising when negative) (supplier/serializers.py:358-366, customer/serializers.py:362-374).
  • REST framework has no project-level override in this checkout (the REST_FRAMEWORK block is commented out, core/settings.py:92), so DRF defaults apply where no class sets authentication or permissions.
