Sales . Order

Sales order lifecycle: create -> submit for approval -> approve / reject / cancel -> (downstream) issue delivery notes and invoices against the approved order. Approval flows are tenant-configured (basic vs custom) by the Configuration service, and every state transition reserves/releases inventory through the Inventory service.

All routes below are relative to the service root; on the live service they sit under /api/sales/order/. Source: sales/sales_order/urls.py, views.py, serializers.py @ d07a3d4c.

1. POST /order/ - create

  • View: SalesOrderListCreate - sales/sales_order/views.py:30 (route urls.py:6).
  • Auth: IAMAuthenticationBackendSales + HasPermission (views.py:29-34); POST requires action ADD_EDIT, set in initial() (views.py:36-42).
  • Request (JSON):
    • items (array) - required (views.py:56-58); each item needs product_id, quantity, uom, rate, item_total (views.py:60-62).
    • order_date (date) - required (views.py:56-58).
    • customer (customer id) - required (views.py:56-58).
    • Optional model fields accepted by the write serializer (title, address, delivery_date, narration, document, description, amount, discount fields, vat fields, grand_total, subtotal, payment_term) - sales/sales_order/models.py:11-65; serializer excludes only modified/created/unique_id (sales/sales_order/serializers.py:371-377).
    • fiscal_year is injected from the authenticated request, not the client (views.py:68).
  • Processing: inside transaction.atomic (views.py:55); serialized by SalesOrderSerializerWriteOnly with tenant_id + user_id context (views.py:69-72). The serializer also runs text sanitize via the internal SANITIZE_URL service call on line items and main data (sales/sales_order/serializers.py:403-408, 411 onward).
  • Response: 201 { id, message } on success (views.py:76-82); 400 { error } with serializer errors (views.py:83-85).
  • Side effects: activity log only (custom.create_activity_log, views.py:44-51, 75). No kafka.call_kafka in the create path.

2/3. GET / POST /order/detail// - detail & update

  • View: SalesOrderUpdate - views.py:116 (routes urls.py:7-11).
  • Auth: IAM + HasPermission; GET -> VIEW, POST -> ADD_EDIT (views.py:117-127).
  • GET: loads the record scoped to the authenticated tenant (get_object, views.py:129-133); applies user-level row visibility via helper.user_filter (views.py:139-141); returns SalesOrderWithBatchSerializerReadOnly data, 404 with SALES_ORDER_NOT_FOUND otherwise (views.py:143-151).
  • POST: updates in place inside transaction.atomic (views.py:154); requires items, order_date, customer, delivery_date (views.py:163-166); rejects any order not in draft with a ValidationError (APPROVED_ENTRY_NO_UPDATE, views.py:176-177); saves via the write serializer (views.py:179-183); 200 { message, id } or 400 (views.py:182-193).

4. GET /order/detail-no-perm// - detail without permission

  • View: SalesOrderNoPerm - views.py:88 (route urls.py:12-16).
  • Auth: IAM only - no HasPermission feature check; any authenticated tenant user who knows the id can read it. Used so other sales screens (delivery notes, invoices) can embed an order header.
  • Same tenant scoping + user_filter + SalesOrderSerializerReadOnly as endpoint 2 (views.py:91-112); 404 otherwise (views.py:108-112).

5. POST /order/delete// - delete

  • View: SalesOrderDelete - views.py:196 (route urls.py:17).
  • Auth: IAM + HasPermission, action ADD_EDIT (views.py:197-200).
  • Behavior: inside transaction.atomic (views.py:211); deletable only when status is draft AND the record was entered by the current user (views.py:216); deletes line items then the record (views.py:217-218); 200 { message } (views.py:219-226). Any other status or a different entry_by returns 400 (views.py:227-232); missing record returns 400 (views.py:233-236).
  • Side effects: none - no activity log, notification, or Kafka in this path.

6. POST /order/status// - status change (approval workflow)

  • View: SalesOrderStatusChange - views.py:240 (route urls.py:18-22); entry point post() at views.py:412.
  • Auth: IAM + HasPermission; for POST with status != submit_for_approval the action is APPROVE_CANCEL, otherwise default VIEW (views.py:245-253).
  • Request: { status, comment?, approval_user? }.
  • Flow (views.py:412-436):
    1. transaction.atomic, tenant-scoped lookup (views.py:415-416).
    2. Loads the tenant's approval-work configuration from the Configuration service (send_requests.get_configuration, views.py:421-426).
    3. Title BASIC -> _handle_basic_flow; title CUSTOM -> _handle_custom_flow; anything else -> 503 TemporaryServiceUnavailableError (views.py:428-436).
  • Sub-actions (basic flow, _handle_basic_flow views.py:371-398):
    • Submit for approval (draft only, views.py:438-514): rejects self-approval (views.py:441-442); for orders created from a quotation, verifies the quotation is not cancelled (views.py:444-446), validates each line against quotation quantities (validation_check.quotation_quantity_validation, views.py:449) and runs validation_check.quotation_check (views.py:455); fetches stock-keeping method per product from the Inventory service (helper.get_product_data, views.py:450-452); reserves inventory by POST to helper.INVENTORY_MANIPULATION_API (self.inventory_instance, views.py:471, 668-686, password-gated payload); validates the approval user (helper.validate_approval_user, views.py:476-477); sets approval_user, submit_for_approval_date, comment, status and clears prior rejection fields (views.py:478-484); sends a notification (views.py:485-491), writes an activity log (views.py:492-498), emits Kafka record type SALES_ORDER_SUBMIT_FOR_APPROVAL_RECORD (views.py:499-510).
    • Approve (views.py:535-598): draft -> approved is self-approval, submitted -> approved requires the designated approval_user (views.py:320-346); enforces basic-flow compulsions (helper.check_for_basic_flow_compulsions, views.py:377); re-runs the inventory reservation (views.py:535-570), then approved_last_flow sets approved_by/date/comment/status/approved_date_time (views.py:572-581), writes the activity log and emits Kafka SALES_ORDER_APPROVAL_RECORD (views.py:582-598).
    • Cancel (views.py:600-666): approved -> cancelled (self) or submitted -> cancelled (other/approver) (views.py:348-369); cancel_check blocks the cancel when a linked Delivery note or Sales invoice is still active (approved/submitted) (views.py:289-312); cancelled_roll_back releases inventory via the same INVENTORY_MANIPULATION_API call (views.py:600-636), then cancelled() sets cancelled_by/date/comment (views.py:643-651), writes the activity log and emits Kafka SALES_ORDER_CANCEL (views.py:652-666).
  • Custom flow (views.py:400-410): only approve and cancel are handled (with check_for_custom_flow_compulsions, views.py:404); any other transition raises INVALID_STATUS (views.py:410).
  • Response: 200 { message } per outcome (e.g. "Sales Order entry submitted for approval", views.py:511-514); 400 on validation errors (views.py:268-271, 390-398).

7. POST /order/cancel-submission// - revert submission / reject

  • View: SalesOrderSubmissionCancel - views.py:690 (route urls.py:23-27); post() at views.py:707.
  • Auth: IAM + HasPermission (views.py:689-693); action fixed to VIEW (views.py:695-698).
  • Request: optional { type: "rejection", comment? } to record a rejection instead of a plain revert.
  • Behavior (views.py:707-796): allowed only while status is submitted_for_approval and the caller is the entry_by or the designated approval_user (views.py:714-717); releases the reserved inventory via INVENTORY_MANIPULATION_API (views.py:727-735); reverts status to draft and clears submit_for_approval_date (views.py:736-737). Two outcomes:
    • Rejection (type == "rejection" and caller is the approval_user, views.py:738-773): writes a rejection activity log + ERROR notification (views.py:741-757), sets rejected_comment/approval_user/rejected_by/rejected_date/rejected (views.py:758-763), emits Kafka SALES_ORDER_REJECT_RECORD (views.py:764-769).
    • Plain revert (entry_by reverts own submission, views.py:774-793): activity log (views.py:775-781), clears approval_user (views.py:782-783), also emits Kafka SALES_ORDER_REJECT_RECORD (views.py:784-789) - both branches reuse the same record type.
    • Otherwise 400 INVALID_REQUEST (views.py:794-796).

8. GET /order/list/ - internal list for other modules

  • View: SalesOrderListForAccounting - views.py:939 (route urls.py:28-30, route name invoice_return_acc).
  • Auth: not IAM - gated by the shared internal password in query param password (helper.validate_internal_pass, views.py:941); returns 400 on bad password (views.py:960-961).
  • Query params: tenant_id, from_date, to_date, optional entry_status (views.py:942-950).
  • Behavior: returns non-draft orders for the tenant in the date range, ordered by order_date, via SalesOrderListForACCSerializer (views.py:945-959). Consumed by accounting-side screens.

9. GET /order/search/ - list search

  • View: SalesOrderSearchView (FilteredAPIViewMixin, CustomerDataGatherMixin) - views.py:830 (route urls.py:31).
  • Auth: IAM + HasPermission; GET -> VIEW, POST -> ADD_EDIT (views.py:829-845).
  • Query params: q (free text over order_date, delivery_date, entry_by, unique_id - views.py:862-867), status (must be a valid StatusChoices value or the view raises 404, views.py:851-854), page/count plus filterset params (filterset_class SalesOrderFilterSet, views.py:837).
  • Processing: tenant-scoped queryset through the mixin, user-level row visibility via helper.user_filter (views.py:856-860), paginated with CustomTransactionPagination (views.py:848, 871); rows serialized by SalesOrderListSerializer (v2 context, views.py:873-877) with customer data gathered asynchronously and injected (views.py:880-883).
  • Response: paginated list (paginator.get_paginated_response, views.py:888).

10. GET /order/search/select/ - embedded select search

  • View: SalesOrderApprovedSearchView - views.py:891 (route urls.py:32-36).
  • Auth: IAM only - no HasPermission feature check (views.py:891-893), for use in pickers across modules.
  • Query params: q (matches unique_id, views.py:922-928), method (must be a valid OrderSearchSelectParameter value or 404, views.py:899-902).
  • Behavior: returns approved orders not yet fully consumed - excludes orders whose sales invoice is approved or delivery-note usage is complete (method delivery note, views.py:908-912) or whose delivery note is approved / invoice usage complete (other methods, views.py:913-918); paginated, serialized by SalesOrderSearchSelectSerializer (views.py:932-936).

Frontend usage (apps-frontend @ production)

apps-frontend drives this module from the sales service layer: create (POST /api/sales/order/), delete, status, cancel-submission, search and search/select are all confirmed referenced directly (fe_usage.json cross-reference, a floor - endpoints reached via helpers or miniapp are not counted). detail/, detail-no-perm/ and list/ are not directly referenced from the frontend (the no-perm variants serve other sales screens embedding the order header; list/ serves accounting).
