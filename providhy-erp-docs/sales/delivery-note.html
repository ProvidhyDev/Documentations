Sales . Delivery Note

Delivery notes record the physical issue of goods, either against an approved sales order or independently. Lifecycle: create -> submit for approval -> approve / reject / cancel, with inventory moved in the Inventory service at each transition. Approved delivery notes feed sales invoices and delivery-note returns.

All routes below are relative to the service root; on the live service they sit under /api/sales/delivery-note/. Source: sales/delivery_note/urls.py, views.py, serializers.py @ d07a3d4c.

Catalog note: the endpoint catalog flags every unversioned route of this app as superseded because the app contains a revamped create route (/delivery-note/v2/). Only the create endpoint actually has a versioned sibling; detail, status, delete, search and the import routes documented below are the only live implementations of their operations on f1-production (see Superseded section).

1. POST /delivery-note/v2/ - create (revamped)

  • View: DeliveryNoteListCreateRevamped - sales/delivery_note/views.py:91 (route urls.py:7). Replaces the superseded POST /delivery-note/ (DeliveryNoteListCreate, views.py:34).
  • Auth: IAMAuthenticationBackendSales + HasPermission (views.py:90-95); POST requires action ADD_EDIT (views.py:97-103). Feature DELIVERY_NOTE (views.py:94).
  • Request (JSON):
    • items (array) - required (views.py:107-109); each item needs product_id, uom (views.py:113-114).
    • entry_date (date) - required (views.py:107-109).
    • customer (customer id) - required (views.py:107-109).
    • sales_order (id, optional) - if given, must exist for the tenant and be approved (sales/delivery_note/serializers.py:697-706).
    • Other model fields (title, delivery_date, delivery_address, narration, document, vehicle_number, amount/discount/vat totals) - sales/delivery_note/models.py:12-65.
    • revamped flag defaults to true in the serializer (serializers.py:691); fiscal_year injected from the request (views.py:120).
  • Processing: transaction.atomic (views.py:106); DeliveryNoteSerializerWriteOnly2 with tenant/user context (views.py:121-128); serializer runs text sanitize via the internal SANITIZE_URL service for main data and line items (serializers.py:708-756) and looks up product data (serializers.py:758 onward).
  • Response: 201 { id, message } (views.py:131-137); 400 { error } on invalid data (views.py:138-141).
  • Side effects: none in the create path.

2/3. GET / POST /delivery-note/detail// - detail & update

  • View: DeliveryNoteRetrieveUpdate - views.py:176 (routes urls.py:8-12).
  • Auth: IAM + HasPermission; GET -> VIEW, POST -> ADD_EDIT (views.py:175-187).
  • GET: tenant-scoped lookup (views.py:189-193); user-level row visibility via helper.user_filter (views.py:200-206); DeliveryNoteSerializerReadOnly; with query param convert on legacy (non-revamped) records the items are re-shaped into line-item format (views.py:198, 211-214); 404 with DELIVERY_NOTE_NOT_FOUND otherwise (views.py:216-220).
  • POST: draft-only update (ValidationError APPROVED_ENTRY_NO_UPDATE, views.py:230-231); convert handling for legacy records (views.py:232-237); requires items, entry_date, customer and per-item product_id/uom (views.py:243-245); serializer chosen by the record's revamped flag - WriteOnly vs WriteOnly2 (views.py:251-258); 200 { message } or 400 (views.py:259-270).

4. GET /delivery-note/detail-no-perm// - detail without permission

  • View: DeliveryNoteRetrieveNoPerm - views.py:144 (route urls.py:13-17).
  • Auth: IAM only - no HasPermission feature check (views.py:144-145). Used so invoices/returns screens can embed the DN header.
  • Same tenant scoping + user_filter + read-only serializer (views.py:147-172); 404 otherwise (views.py:168-172).

5. POST /delivery-note/delete// - delete

  • View: DeliveryNoteDeleteAPIView - views.py:273 (route urls.py:18-22).
  • Auth: IAM + HasPermission, action ADD_EDIT (views.py:274-277).
  • Behavior: transaction.atomic (views.py:286); deletable only when status is draft and entry_by is the current user (views.py:294); deletes items then the record (views.py:295-296); 200 { message } (views.py:297-304); 400 "Delivery Note cannot be deleted!" otherwise (views.py:305-308); 400 not-found for missing record (views.py:309-313). No activity log or Kafka in this path.

6. POST /delivery-note/status// - status change (approval workflow)

  • View: DeliveryNoteStatusChangeAPIView - views.py:317 (route urls.py:23-27); entry point post() at views.py:364.
  • Auth: IAM + HasPermission; for POST with status != submit_for_approval the action is APPROVE_CANCEL (views.py:322-330).
  • Request: { status, comment?, approval_user? }.
  • Flow (views.py:364-444):
    1. transaction.atomic, tenant-scoped lookup (views.py:365-366).
    2. Loads the tenant's approval-work configuration from the Configuration service (send_requests.get_configuration, views.py:374-379).
    3. BASIC and CUSTOM branches dispatch inline (no separate flow methods):
      • Basic (views.py:380-425): draft -> submit_for_approval (views.py:381-387); approved requires either submitted -> approved by the designated approval_user (views.py:390-397) or draft -> approved by the entry_by (self-approval, views.py:398-405), each after helper.check_for_basic_flow_compulsions (views.py:392, 402); cancelled: submitted -> cancelled only by the approval_user (views.py:410-414) or approved -> cancelled (views.py:415-418), after cancel_check; else INVALID_STATUS (views.py:421-425).
      • Custom (views.py:426-443): approved from any status except cancelled, after helper.check_for_custom_flow_compulsions (views.py:427-434). The cancel branch (views.py:435-442) tests entry_status == CANCELLED AND entry_status == APPROVED simultaneously, which is never true - the custom-flow cancel is unreachable as written (anomaly). Falls through to INVALID_STATUS (views.py:443).
      • No/unknown configuration -> 503 TemporaryServiceUnavailableError (views.py:444).
  • Sub-actions:
    • Submit for approval (submitted_for_approval, views.py:631-717): for DNs against a sales order, the order must not be cancelled (views.py:634-636), each line is checked against order quantities (validation_check.order_quantity_validation, views.py:643) and validation_check.order_check runs (views.py:646); per-product stock-keeping from the Inventory service (helper.get_product_data, views.py:639-641); reserves inventory via DRN_MANIPULATION_API (legacy) or DRN_MANIPULATION_API_V2 (revamped records) (views.py:657-670, 736-757, password-gated); validates the approval user (helper.validate_approval_user, views.py:672-675); sets approval_user/submit fields/status, clears prior rejection (views.py:677-683); notification (views.py:684-690), activity log (views.py:691-697), Kafka record type DELIVERY_NOTE_SUBMIT_FOR_APPROVAL_RECORD (views.py:698-709).
    • Approve (handle_approval, views.py:446-462): draft -> approved also runs approved_if_draft, which repeats the order validation and inventory reservation (views.py:554-592); approved_last_flow sets approved_by/date/comment/status, writes the activity log and emits Kafka DELIVERY_NOTE_APPROVAL_RECORD (views.py:594-621).
    • Cancel (handle_cancellation, views.py:470-489): from submitted/approved it first rolls back inventory (cancelled_roll_back, views.py:491-526, same DRN manipulation API) then cancelled() sets cancelled fields, writes the activity log and emits Kafka DELIVERY_NOTE_CANCEL (views.py:528-552). cancel_check blocks when a linked delivery-note return or sales invoice is still active (views.py:339-362).
  • Response: 200 { message } per outcome; 400 on validation errors (views.py:407, 420, 422-425).

7. POST /delivery-note/cancel-submission// - revert submission / reject

  • View: DeliveryNoteSubmissionCancel - views.py:769 (route urls.py:33-37); post() at views.py:786.
  • Auth: IAM + HasPermission (views.py:768-772); action fixed to VIEW (views.py:774-777).
  • Request: optional { type: "rejection", comment? }.
  • Behavior (views.py:786-919): allowed only while status is submitted_for_approval and the caller is entry_by or the designated approval_user (views.py:796-799); releases the reserved inventory (order-referenced DNs re-validate quantities, views.py:801-823; independent DNs skip it, views.py:824-831; DRN_MANIPULATION_API / _V2, views.py:843-849); reverts to draft (views.py:850-851). Rejection branch (views.py:852-891): rejection activity log + ERROR notification, rejected fields, Kafka DELIVERY_NOTE_REJECT_RECORD. Plain revert branch (views.py:892-915): activity log, clears approval_user, also emits Kafka DELIVERY_NOTE_REJECT_RECORD (both branches reuse the same record type). Otherwise 400 INVALID_REQUEST (views.py:917-919).

8. GET /delivery-note/list/ - internal list for other modules

  • View: DeliveryNoteListForAccounting - views.py:1047 (route urls.py:28-32, route name invoice_return_acc).
  • Auth: not IAM - gated by the shared internal password (helper.validate_internal_pass, views.py:1049); 400 on bad password (views.py:1068-1069).
  • Query params: tenant_id, from_date, to_date, optional entry_status (views.py:1050-1058).
  • Behavior: non-draft DNs for the tenant in the entry_date range, ordered by entry_date, via DeliveryNoteListForACCSerializer (views.py:1059-1067).

9. GET /delivery-note/search/ - list search

  • View: DeliveryNoteSearchView (FilteredAPIViewMixin, CustomerDataGatherMixin) - views.py:943 (route urls.py:38-40).
  • Auth: IAM + HasPermission; GET -> VIEW, POST -> ADD_EDIT (views.py:942-958).
  • Query params: q (over entry_date, entry_by, unique_id - views.py:975-978), status (must be a valid StatusChoices value or 404, views.py:964-967), page/count plus filterset params (filterset_class DeliveryNoteFilterSet, views.py:950).
  • Processing: tenant scoping via the mixin + helper.user_filter (views.py:969-973); paginated with CustomTransactionPagination (views.py:961, 984); DeliveryNoteListSerializer (v2 context, views.py:986-990) with async customer-data gather (views.py:993-996).
  • Response: paginated list (views.py:1001).

10. GET /delivery-note/search/select/ - embedded select search

  • View: DeliveryNoteApprovedSearchView - views.py:1004 (route urls.py:41-45).
  • Auth: IAM only - no HasPermission feature check (views.py:1004-1005).
  • Query params: q (matches unique_id, views.py:1030-1034), method (must be a valid DeliveryNoteSearchSelectParameter value or 404, views.py:1013-1018).
  • Behavior: approved DNs of the tenant not fully consumed - excludes records whose note_return_status or invoice_status is complete (views.py:1020-1028); paginated, serialized by DeliveryNoteSearchSelectSerializer (views.py:1040-1044).

11. GET /delivery-note/report-dn/search/select/ - date-filtered DN picker

  • View: DeliveryNoteFilterByDate - views.py:1072 (route urls.py:48-52).
  • Auth: IAM only - no permission class (views.py:1072-1074).
  • Query params: date_type (required, views.py:1084-1088; custom ranges require from_date+to_date, views.py:1076-1080), from_date, to_date (resolved through the report date mechanism date_mechanism_for_report, views.py:1093-1095), q (unique_id, views.py:1102-1107).
  • Behavior: approved DNs of the tenant in the date range, serialized by DeliveryNoteSerializerForDRNReturn (views.py:1097-1115) - consumed by the delivery-note-return creation screen.

12/13. POST /delivery-note/import/ and /delivery-note/import/item/ - Excel import (migration)

  • Views: DeliveryImportView - views.py:1118 (route urls.py:46); DeliveryItemImportView - views.py:1257 (route urls.py:47).
  • Auth: no IAM classes - both gated by the shared internal password in the JSON body (helper.validate_internal_pass, views.py:1163, 1297).
  • Request: multipart with import_file (Excel) plus tenant_id; headers read from row 16, data rows from row 17 (views.py:1172-1209, 1306-1334).
  • Behavior: the header import creates delivery notes directly in approved status with migrated=True after a customer existence check against the customer service API (views.py:1224-1250); the item import groups rows by DN title and creates DeliveryNoteItem rows (batch-aware) after a product lookup via the product check service (views.py:1279-1294, 1340-1432). Both sanitize cell text through the internal SANITIZE_URL service first (views.py:1153-1158, 1271-1276).
  • Response: 200 { message } (views.py:1251-1254, 1433-1436).
  • Side effects: none beyond the created records (no Kafka).
