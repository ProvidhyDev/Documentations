Sales . Customer Payment

Customer payments record money received from customers: advance payments, payments allocated to specific approved invoices (items), and "quick payments" created inline against an invoice. The standard approval workflow applies, and approval deducts from the customer's opening balance and prior advances (FIFO); cancel restores them. Quick payments skip the workflow entirely and are created already approved.

All routes below are relative to the service root; on the live service they sit under /api/sales/payment/. Source: sales/customer_payment/urls.py, views.py, serializers.py @ d07a3d4c.

1/2. GET / POST /payment/ - list & create

  • View: CustomerPaymentListCreate - sales/customer_payment/views.py:42 (route urls.py:6).
  • Auth: IAMAuthenticationBackendSales + HasPermission (views.py:41-46); POST requires ADD_EDIT, GET VIEW (views.py:48-54). Feature CUSTOMER_PAYMENT.
  • GET: status query param is required and must be a valid status value or 404 (views.py:58-75); tenant-scoped, user-level row visibility (helper.user_filter, views.py:68-70), paginated, serialized by CustomerPaymentListSerializer.
  • POST Request (JSON):
    • customer (customer id) - required (views.py:78-81).
    • received_account (GL account id) - required (views.py:78-81).
    • amount (float) - required (views.py:78-81).
    • payment_date (date) - required; fiscal year validated against it (views.py:95-97).
    • bank_charge_applicable (bool) - when true, bank_account + bank_amount become required (views.py:83-87).
    • tds_applicable (bool) - when true, tds_account + tds_amount become required (views.py:89-93).
    • items (optional array of invoice allocations) - each with sales_invoice + allocated_amount (serializer context items_data, views.py:100-105).
    • fiscal_year injected from the request (views.py:102).
  • Processing: transaction.atomic (views.py:99); CustomerPaymentSerializerWriteOnly with tenant_id + user_id context (views.py:100-105).
  • Response: 201 { id, message } (views.py:108-114); 400 { error } on invalid data (views.py:115-118).
  • Side effects: none in the create path (no Kafka, no journal task).

3. GET /payment/search/ - list search

  • View: CustomerPaymentSearchView (FilteredAPIViewMixin, CustomerDataGatherMixin) - views.py:257 (route urls.py:7).
  • Auth: IAM + HasPermission, action VIEW (views.py:256-268).
  • Query params: q (over unique_id, payment_date, entry_by - views.py:320-326), status (required, invalid -> 404, views.py:303-306), page/count plus filterset params (filterset_class CustomerPaymentFilterSet, views.py:263).
  • Processing: excludes cheque rows (is_cheque) and quick payments (is_quick_payment) from the list (views.py:308-310); tenant scoping via the mixin + helper.user_filter (views.py:312-319); paginated with CustomTransactionPagination (views.py:299, 330); customer data and received GL-account data fetched in parallel (asyncio.gather over customer + GL_MAPPING_INFO_URL, views.py:272-296, 335-353).
  • Response: paginated list (views.py:355).

4. GET /payment/customer-invoice-list/ - payment screen data

  • View: CustomerInvoiceList - views.py:359 (route urls.py:8-12).
  • Auth: IAM + HasPermission, action VIEW (views.py:358-369).
  • Query params: customer_id (required, views.py:375), unique_id (optional, views.py:376), exclude_settled (bool, default false, views.py:377).
  • Behavior (views.py:371-468): lists the customer's approved invoices with remaining_amount > 0, excluding fully-paid bills unless exclude_settled (views.py:379-389); prepends an "Opening Balance" row when the customer has a remaining DR opening (views.py:421-437) or adds the remaining CR opening to the advance total (views.py:439-445); computes pending / advance / paid totals (views.py:403-410, 456-466) with the advance figure taken from the internal GET_PARTY_CLOSING_URL service call (views.py:446-455). Response: { approved_invoice_list, invoice_data: { pending_amount, advance_amount, paid_amount, customer_remaining_opening } }.

5/6. GET / POST /payment/detail// - detail & update

  • Auth: IAM + HasPermission; GET -> VIEW, POST -> ADD_EDIT (views.py:121-133).
  • GET: tenant-scoped lookup (views.py:135-139); user-level row visibility (views.py:145-151); CustomerPaymentSerializerReadOnly; 404 with CUSTOMER_PAYMENT_NOT_FOUND otherwise (views.py:156-160).

7. POST /payment/delete// - delete

  • View: CustomerPaymentDeleteAPIView - views.py:215 (route urls.py:16-18).
  • Auth: IAM + HasPermission, action ADD_EDIT (views.py:215-219).
  • Behavior: transaction.atomic (views.py:228); deletable only when status is draft and entry_by is the current user (views.py:231-234); deletes items then the record (views.py:235-236); 200 { message } (views.py:237-244); 400 "Customer Payment cannot be deleted!" otherwise (views.py:245-248); 400 not-found otherwise (views.py:249-253).

8. POST /payment/status// - status change (approval workflow)

  • View: CustomerPaymentStatusChangeAPIView - views.py:510 (route urls.py:19-23); entry point post() at views.py:533.
  • Auth: IAM + HasPermission; for POST with status != submit_for_approval the action is APPROVE_CANCEL (views.py:516-524).
  • Request: { status, comment?, approval_user? }.
  • Flow (views.py:533-574):
    1. transaction.atomic, tenant-scoped lookup, fiscal-year validation (views.py:534-542).
    2. Loads the tenant's approval-work configuration from the Configuration service (send_requests.get_configuration, views.py:544-549).
    3. BASIC -> handle_basic_flow (views.py:550-556); CUSTOM inline (views.py:557-572); anything else -> 503 (views.py:574).
  • Sub-actions (basic flow, views.py:576-614):
    • Submit for approval (draft only, views.py:616-649): sets approval fields, clears prior rejection fields (views.py:617-625); notification + activity log (views.py:627-641). No Kafka in this path.
    • Approve (views.py:651-747): from submitted (by approval_user) or from draft (self, views.py:585-597); when apply_advance is set, deducts from the customer's CR opening balance (updating the customer's remaining opening via helper.customer_remaining_update, views.py:664-680) and then from prior approved advances in FIFO order (views.py:682-702); validates line allocations against invoice remaining amounts (views.py:703-709); sets approved fields (views.py:711-720); if the tenant has a SALES_FLOW AUTOMATION configuration, queues the journal_creation_task celery task (views.py:722-730); activity log (views.py:732-738). No Kafka.
    • Cancel (views.py:802-841): from submitted (by approval_user) or approved (views.py:607-614); restores opening-balance and advance deductions in reverse (LIFO) order (restore_Customer_payments, views.py:749-800); re-validates allocations (views.py:808-814); sets cancelled fields (views.py:816-821); queues journal_cancellation_task if the payment had a journal (views.py:823-824); activity log (views.py:827-833). No Kafka.
  • Custom flow (views.py:561-572): approved from any status except cancelled, after check_for_custom_flow_compulsions (views.py:561-566); cancelled only from approved (views.py:567-571); else INVALID_STATUS (views.py:572).
  • Response: 200 { message } per outcome; 400 on validation errors (views.py:597, 614).

9. POST /payment/cancel-submission// - revert submission / reject

  • View: CustomerPaymentSubmissionCancel - views.py:845 (route urls.py:24-28); post() at views.py:864.
  • Auth: IAM + HasPermission (views.py:844-849); action fixed to VIEW (views.py:851-855).
  • Request: optional { type: "rejection", comment? }.
  • Behavior (views.py:864-945): only while submitted_for_approval; fiscal-year validation (views.py:871). Rejection branch (type == rejection and caller is not the entry_by, views.py:881-914): clears approval_user/submit fields, sets rejected fields, activity log + ERROR notification, 200 "rejected". Plain revert branch (no type and caller is entry_by, views.py:916-937): reverts to draft, activity log (CANCEL_SUBMISSION). Otherwise 400 INVALID_REQUEST (views.py:939-945). Note: get_object is not tenant-scoped here (views.py:857-862) - any authenticated user who knows the id reaches the status check (anomaly). No Kafka.

10. POST /payment/quick/frontend/ - quick payment

  • View: QuickCustomerPaymentCreateFrontend - views.py:952 (route urls.py:30-34).
  • Auth: IAM + HasPermission, action VIEW for both methods (views.py:951-961).
  • Request (JSON):
    • invoice_id (id) - required (views.py:979-982, 986-990).
    • payment_allocations (array) - required; each with received_account { entity_id }, payment_method, total_allocated_amount (views.py:994-1002).
  • Processing (views.py:978-1071): total allocations must not exceed the invoice's remaining_amount (views.py:963-972, 991); per allocation, a CustomerPayment is created already approved with is_quick_payment=True and a single item allocated to the invoice (views.py:994-1031); journal_creation_task is queued per payment on commit (views.py:1034-1038); allocations are validated against invoice remaining amounts afterwards (views.py:1045-1048); an activity log entry is written on the invoice ("Rs. X is received against the invoice", views.py:1055-1062).
  • Response: 200 { message } (views.py:1064-1071); 400 on serializer/validation errors (views.py:1040-1043).

11. POST /payment/quick-payment-check/ - quick-payment flag lookup (internal)

  • View: CheckQuickPaymentView - views.py:1095 (route urls.py:35-39).
  • Auth: internal - InternalRequestPermission (password in body, views.py:1096, dashboard/auth_backends.py:169-177).
  • Request: { tenant_id, customer_payment_ids (array) } - required (views.py:1099).
  • Behavior: returns a map of payment id -> is_quick_payment for the tenant (views.py:1100-1111).

12. POST /payment/get-fetch-customer-payments-internal/ - fetch by ids (internal)

  • View: FetchCustomerPaymentsInternal - views.py:1078 (route urls.py:41-45, marked "temporary url" in the source, views.py:40).
  • Auth: internal - InternalRequestPermission (views.py:1079).
  • Request: { customer_payment_ids (array) } (views.py:1082).
  • Behavior: returns the payments (CustomerPaymentBaseSerializer) - not tenant-scoped (views.py:1085-1092).

13. GET /payment/get-customer-advance/ - advance summary (internal)

  • View: CustomerAdvanceSummaryAPIView - views.py:1114 (route urls.py:46-50).
  • Auth: internal - InternalRequestPermission (password in query, views.py:1115).
  • Query params: tenant_id (required), customer_id (optional, comma-separated list, views.py:1118-1119, 1147-1149).
  • Behavior: approved payments annotated with the sum of allocations on cancelled invoices; effective_advance = advance_amount + cancelled_alloc_total, ordered by customer name then payment date (views.py:1131-1168).

14. GET /payment/customer-payment-info/ - due amount

  • View: CustomerPaymentInfoView - views.py:472 (route urls.py:51-55).
  • Auth: IAM + HasPermission, action VIEW (views.py:471-476).
  • Query params: customer_id - required (views.py:479-482).
  • Behavior: sums remaining_amount over the customer's approved invoices with remaining_amount > 0, excluding fully paid (views.py:485-497); response { due_amount } (views.py:499-506).
