Sales . Return

Sales returns are credit notes issued against an approved sales invoice (the only supported reference - the referenced invoice is required for quantity validation). Approving a return moves inventory back and debits the referenced invoice's remaining_amount; for e-billing tenants the credit note is also posted to IRD through an async retry task. Cancelling is a "void" with inventory rollback and remaining-amount credit-back.

All routes below are relative to the service root; on the live service they sit under /api/sales/return/. Source: sales/sales_return/urls.py, views.py, serializers.py @ d07a3d4c.

Catalog note: as with the other lifecycle apps, the catalog flags every unversioned route of this app as superseded because a revamped create route exists (/return/v2/); only the create endpoint has a versioned sibling, so the other routes below are the only live implementations (see Superseded section).

1. POST /return/v2/ - create (revamped)

  • View: SalesReturnListCreateRevamped - sales/sales_return/views.py:249 (route urls.py:7-11). Replaces the superseded POST /return/ (SalesReturnListCreate, views.py:42).
  • Auth: IAMAuthenticationBackendSales + HasPermission (views.py:249-253); POST requires action ADD_EDIT (views.py:255-261). Feature SALES_RETURN.
  • Request (JSON):
    • items (array) - required (views.py:358-361); each item needs product_id, quantity, uom, rate (views.py:364-367).
    • entry_date, return_date (dates) - required (views.py:358-361).
    • customer (customer id) - required (views.py:358-361).
    • sales_invoice (id) - the invoice being returned against; validated in the serializer (sales/sales_return/serializers.py - SalesReturnSerializerWriteOnlyRevamped).
    • draft (bool, optional) - default behavior creates a draft.
    • Other model fields (title, reference, description, tds_gl, vat fields, grand totals) - sales/sales_return/models.py; serializer excludes created/modified and defaults revamped=True (sales/sales_return/serializers.py); text sanitize via internal SANITIZE_URL.
  • Processing (views.py:352-473):
    • transaction.atomic; serializer with tenant/user + is_ebilling_user context; the reference invoice is validated in the serializer (views.py:372-378).
    • E-billing tenants, non-draft: blocks non-draft creation when e-billing is not subscribed (views.py:387-391); unique id generated from the unique-id service with entity RETURN (views.py:395-400); tenant PAN verified via TMS (views.py:392-394, TMS_PAN_INFO helper); reference invoice validated (views.py:404-418); inventory moved via SRETURN_INVENTORY_MANIPULATION_API (legacy) or _V2 (revamped) (views.py:301-309, 311-325); approved_last_flow sets approved fields (comment "bill return creation"), and if the tenant has a SALES_FLOW AUTOMATION configuration queues journal_creation_task (views.py:263-287); if IRDConfiguration.cbms is set, an InvoiceFailed row is created and the celery task retry_failed_sales_return is queued (countdown 3s), ebilling_status=POSTED (views.py:422-437); Kafka emitted with call_kafka_for_bill (dual payload: KafkaSalesReturnSerializer + KafkaSalesReturnSerializerForRecord, views.py:439-449).
    • Draft path: a unique id is still generated and the record is saved as draft (views.py:443-457).
  • Response: 201 { id, message } (views.py:458-467); 400 { error } - for revamped create the error body is the flattened serializer message string (views.py:469-473).
  • Side effects: as above (activity log on the approval path, journal task, IRD task, Kafka).

6. POST /return/status// - status change (approval workflow)

  • View: SalesReturnStatusChangeAPIView - views.py:771 (route urls.py:27-31); entry point post() at views.py:793.
  • Auth: IAM + HasPermission; for POST with status != submit_for_approval the action is APPROVE_CANCEL (views.py:776-784).
  • Request: { status, comment?, approval_user?, nepali_entry_date? }.
  • Flow (views.py:793-869):
    1. transaction.atomic, tenant-scoped lookup, fiscal-year validation (views.py:796-798).
    2. Loads the tenant's approval-work configuration from the Configuration service (send_requests.get_configuration, views.py:802-807).
    3. Basic (views.py:808-852): draft -> submit (views.py:809-815); approved from submitted (by approval_user) or from draft (self, entry_by match) - note both branches call helper.check_for_custom_flow_compulsions, a copy of the invoice code (views.py:817-835); void from submitted (by approval_user) or from approved (views.py:836-847); else INVALID_STATUS (views.py:848-852).
    4. Custom (views.py:853-868): approved from any status except cancelled, after check_for_custom_flow_compulsions (views.py:854-861); void from any status - blocked for e-billing tenants (views.py:862-867); else INVALID_STATUS (views.py:868).
    5. Unknown configuration -> 503 TemporaryServiceUnavailableError (views.py:869).
  • Sub-actions:
    • Submit for approval (submitted_for_approval, views.py:978-1033): reference invoice must not be cancelled (views.py:980-981); per-line invoice quantity validation + invoice_check (views.py:983-987); validates the approval user (views.py:989-992); sets approval fields (views.py:993-999); notification (views.py:1000-1006), activity log (views.py:1007-1013), Kafka SALES_RETURN_SUBMIT_FOR_APPROVAL_RECORD (views.py:1014-1025). No inventory move at submit.
    • Approve (handle_approval, views.py:1035-1063): e-billing tenants re-verify PAN via TMS first (views.py:1036-1044); reference invoice must be approved (views.py:1045-1046); draft -> approved runs approved_if_draft (quantity checks + approval_calc_part, views.py:1065-1073) then approved_last_flow; submitted -> approved runs approval_calc_part then approved_last_flow (views.py:1050-1052). approval_calc_part moves inventory via SRETURN_INVENTORY_MANIPULATION_API (legacy) or _V2 (revamped) with reference delivery_note/sales_order derived from the invoice and a both_deduction flag for draft records (views.py:1075-1088, 1227-1248). approved_last_flow (views.py:1090-1198): e-billing branch sets entry_date, Nepali date and a fresh unique id (entity RETURN), and if IRDConfiguration.cbms is set creates an InvoiceFailed row, queues retry_failed_sales_return (countdown 3s), sets ebilling_status=POSTED; if the IRD configuration is missing it calls the inventory REVERT API, records an InventoryManipulation row and an activity-log entry, then raises IRD_CONFIG_MISSING (views.py:1099-1142); otherwise writes the approval activity log (views.py:1144-1151); then updates the referenced invoice's remaining_amount (minus grand_total) and emits an extra Kafka event - status "update_remaining", record type SALES_INVOICE_APPROVAL_RECORD, transaction SALES_INVOICE (update_remaining_from_invoice, views.py:1153, 1200-1225); sets approved fields (views.py:1154-1162); queues journal_creation_task when a SALES_FLOW AUTOMATION configuration exists (views.py:1164-1171); emits Kafka with call_kafka_for_bill (dual payload, views.py:1179-1189).
    • Void (cancel) (handle_cancellation, views.py:877-897): draft -> void directly; submitted/approved -> cancelled_roll_back re-validates invoice state/quantities (views.py:899-908) then cancellation_calc_part reverses the inventory move (views.py:910-944) then cancelled() sets cancelled fields, queues journal_cancellation_task if the return had a journal (views.py:954-957), writes the activity log, credits back the invoice's remaining_amount plus an extra update_remaining Kafka event (views.py:959-976), and emits Kafka SALES_RETURN_CANCEL (views.py:967-976).
  • Response: 200 { message } per outcome; 400 on validation errors (views.py:835, 847, 849-852).

7. POST /return/cancel-submission// - revert submission / reject

  • View: SalesReturnSubmissionCancel - views.py:1293 (route urls.py:32-36); post() at views.py:1310.
  • Auth: IAM + HasPermission (views.py:1293-1296); action fixed to VIEW (views.py:1298-1301).
  • Request: optional { type: "rejection", comment? }.
  • Behavior (views.py:1310-1402): e-billing tenants rejected outright (views.py:1314-1315); fiscal-year validation (views.py:1318); allowed only while submitted_for_approval and the caller is entry_by or the approval_user (views.py:1320-1323); re-validates the reference invoice and line quantities (views.py:1324-1331); reverts to draft (views.py:1333-1334). Rejection branch (views.py:1335-1374): rejection activity log + ERROR notification, rejected fields, Kafka SALES_RETURN_REJECT_RECORD. Plain revert branch (views.py:1375-1398): activity log (CANCEL_SUBMISSION), clears approval_user, also emits Kafka SALES_RETURN_REJECT_RECORD (both branches reuse the same record type). Otherwise 400 INVALID_REQUEST (views.py:1400-1402).

8. GET / POST /return/list/ - internal list for accounting

  • View: SalesReturnListForAccounting - views.py:1405 (route urls.py:37-39, route name invoice_return_acc).
  • Auth: not IAM - gated by the shared internal password (helper.validate_internal_pass, views.py:1412, 1456); 400 on bad password.
  • GET: params tenant_id, from_date, to_date, optional id, type (journal) (views.py:1407-1440). Without id: approved returns in the entry_date range ordered by approved_date_time, journal=False when type=journal (views.py:1413-1432). With id: single approved journal=False return (views.py:1433-1445).
  • POST: params id, type, tenant_id (views.py:1452-1454); type=journal with id sets the return's journal flag to True (views.py:1456-1474); 400 otherwise (views.py:1476-1478).

9. GET /return/search/ - list search

  • View: SalesReturnSearchView (FilteredAPIViewMixin, CustomerDataGatherMixin) - views.py:1484 (route urls.py:40).
  • Auth: IAM + HasPermission; GET -> VIEW, POST -> ADD_EDIT (views.py:1483-1500).
  • Query params: q (over entry_date, return_date, entry_by, unique_id - views.py:1557-1563), status (required filter, views.py:1536-1539), tab, plus filterset params (filterset_class SalesReturnFilterSet, views.py:1491). For e-billing tenants the status maps to a status set and ird_sync_status (1/0) filters sync_with_ird (filter_lookup_for_ebilling, views.py:1508-1530), and the list serializer switches to BillSalesReturnListSerializer (views.py:1502-1506).
  • Processing: tenant scoping via the mixin (views.py:1543-1546); user-level row visibility for the draft tab (views.py:1548-1555); paginated with CustomTransactionPagination (views.py:1533, 1567); customer data gathered asynchronously and injected (views.py:1573-1578).
  • Response: paginated list (views.py:1579).

10. POST /return/print// - print credit note

  • View: PrintExportAPIView - views.py:1583 (route urls.py:41-43).
  • Auth: IAM + HasPermission, action EXPORT (views.py:1582-1591).
  • Behavior: only approved returns (views.py:1599-1603); stamps printed fields and increments print_count (views.py:1605-1610, 1631-1632); e-billing tenants log "Bill printed as Credit Note by " (first print) or "Copy of Original (n)" under the BILL_CREATION feature (views.py:1611-1621); others log a plain EXPORT activity (views.py:1623-1629). Response 200 { print_count } (views.py:1634-1636).

11. POST /return/retry// - retry IRD posting

  • View: RetryFailedInvoiceReturn - views.py:618 (route urls.py:44-48).
  • Auth: IAM + HasPermission, action APPROVE_CANCEL, feature SALES_RETURN (views.py:618-621).
  • Request: optional { nepali_entry_date }.
  • Behavior (views.py:629-656): blocks returns already synced with IRD or not approved (views.py:637-643); sets ebilling_status=POSTED (views.py:644-645); creates an InvoiceFailed row and queues the celery task retry_failed_sales_return with countdown 3s (views.py:646-652). Response 200 { message }.

12. GET / POST /return/fix-approved-datetime/ - temporary data fix

  • View: FixApprovedDatetimeAPIView - views.py:1644 (route urls.py:51-55, marked "Temporary url [ delete later ]" in the source, views.py:49-50).
  • Auth: internal - InternalRequestPermission (password in query/body, views.py:1645, dashboard/auth_backends.py:169-177).
  • Behavior: GET lists approved returns missing approved_date_time (views.py:1647-1654, 1664-1668); POST backfills approved_date_time as approved_date plus a random time between 10:00 and 17:00 (views.py:1656-1662, 1670-1683).
