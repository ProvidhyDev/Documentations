Business Flows (Traced)

At runtime the Sales service is a Django/DRF document manager with an approval engine on top. Every document (quotation, order, delivery note, delivery note return, invoice, return, customer payment, cheque) follows the same skeleton: a request is authenticated by IAMAuthenticationBackendSales (dashboard/auth_backends.py:19-51), which calls the IAM service /api/token/verify/ and only proceeds when the tenant is subscribed to SALES and the email is verified; HasPermission (dashboard/auth_backends.py:67-121) then enforces the per-view feature and action permission, with tenant-root bypass and an IAM internal-check-permissions call for non-GET writes. The status endpoints fetch the tenant approval-workflow configuration from the Configuration service (dashboard/send_requests.py get_configuration, URL dashboard/helper.py:162) and run either the basic flow (draft to submit to approve to cancel, self-approve allowed from draft) or the custom flow (any non-cancelled state can approve; cancel only from approved). Documents linked to inventory (order, delivery note, delivery note return, invoice, return) call the ProductManagement inventory manipulation API on every state move so reserved/issued stock follows the document lifecycle; invoices, returns, payments and cheques additionally post accounting journals through Celery tasks that call the Accounting service, and e-billing tenants push every approved bill to the IRD CBMS API (https://cbapi.ird.gov.np/api/bill, dashboard/helper.py:31) through a Celery retry task. Nothing in the payment endpoints touches an external payment provider - the eSewa Payment-Service path is not used in ProvidhyERP, payments are recorded locally and settled by journal posting.

Quotation - status change and cancel-submission

What happens: A draft quotation moves through the tenant's configured approval workflow. In the basic flow it must be submitted for approval (to someone else), then approved by that approver, or approved directly from draft by its creator; in the custom flow any non-cancelled state can be approved in one step. Approval and cancel only flip local state - no stock, no journal, no IRD - but every move writes an activity log, a notification and a Kafka record. A submitted quotation can be rejected (by the approver) or reverted to draft (by its creator), both of which re-emit the reject Kafka record.

Trace - POST /api/sales/quotation/status/

  1. Auth: IAMAuthenticationBackendSales verifies the JWT at IAM and requires the SALES subscription and verified email (dashboard/auth_backends.py:19-51). Permission: SALES_QUOTATION + VIEW, escalated to APPROVE_CANCEL when the requested status is not submit_for_approval (sales/sales_quotation/views.py:211-224, HasPermission at dashboard/auth_backends.py:67-121).
  2. Tenant-scoped fetch; 404-equivalent ValidationError when missing (views.py:226-231).
  3. The tenant approval-workflow configuration is fetched from the Configuration service (views.py:338-343, helper.CONFIGURATION_URL dashboard/helper.py:162). title basic routes to the basic flow, custom to the custom flow, and a missing configuration raises a 503 TemporaryServiceUnavailableError (views.py:344-352).
  4. Submit (basic, draft only): self-submission is rejected (views.py:356-357); every item product is validated through the PMS product check (views.py:358-370); the approval_user must exist in the tenant (views.py:372-373, helper.validate_approval_user); approval fields are set, prior rejected fields are cleared (custom.clear_rejected_fields, dashboard/custom_functions.py:187), and the row is saved (views.py:375-382).
  5. Approve (basic): allowed from submit_for_approval by the named approver, or from draft by the creator (views.py:239-252, 260-269); the basic-flow compulsion check runs first (views.py:295, helper.check_for_basic_flow_compulsions). Approve from submit additionally validates products (views.py:421-424). Approval fields, save, activity log, Kafka approval record (views.py:420-467; record SALES_QUOTATION_APPROVAL_RECORD views.py:453-467).
  6. Cancel (basic): only from approved, or from submit_for_approval by the named approver (views.py:254-258, 301-309); a linked sales order in submit or approved state blocks the move (views.py:274-287). Cancel fields, save, activity log, Kafka cancel record (views.py:469-516).
  7. Custom flow: approve from any non-cancelled state after the custom compulsion check (views.py:313-328), cancel only from approved.
  8. Error paths: wrong approver or state returns INVALID_APPROVE_REQUEST (views.py:299), INVALID_CANCEL_REQUEST (views.py:309), INVALID_STATUS (views.py:311), no configuration gives 503 (views.py:352).

Trace - POST /api/sales/quotation/cancel-submission/

  1. Only valid while in submit_for_approval (views.py:518-531).
  2. Rejection branch (request type rejection, caller is the approval_user): rejected fields are set, an ERROR notification and a rejection activity log are written, and the Kafka reject record is emitted (views.py:546-597).
  3. Revert branch (caller is the entry_by, no type): approval fields are cleared, CANCEL_SUBMISSION activity log, same Kafka reject record type (views.py:568-605).
  4. Any other caller/state returns 400 INVALID_REQUEST (views.py:607-609).

  • Activity log entries for submit, approve, cancel, rejection, revert - custom.create_activity_log (custom_functions.py:66; views.py:391, 443, 492, 546, 583)
  • Kafka records via call_kafka (dashboard/kafka_function.py:65): submit, approval, cancel, reject (views.py:403, 453, 501, 592)
  • PMS product validation HTTP call on submit (views.py:362-370)
  • No inventory, no journal, no IRD interaction

Order - status change and cancel-submission

What happens: A sales order behaves like a quotation but reserves stock in the ProductManagement service on every state move - submit reserves, approve converts the reservation into issued stock, cancel rolls it back, and cancel-submission releases it. Orders that reference a quotation additionally enforce that the quotation is not cancelled and that per-item quantities stay within the remaining quoted quantities. Cancel is blocked while a linked delivery note or invoice is live.

Trace - POST /api/sales/order/status/

  1. Auth and permission as in quotation, feature SALES_ORDER, action VIEW to APPROVE_CANCEL (sales/sales_order/views.py:240-258).
  2. Tenant-scoped fetch (views.py:259-266).
  3. Configuration fetch from the Configuration service; basic vs custom dispatch; 503 when missing (views.py:421-436, dashboard/helper.py:162).
  4. Submit (basic, draft only): self-submission rejected (views.py:441-442). When the order references a quotation: the quotation must not be cancelled, each item is checked against remaining quotation quantities, and the whole quotation is re-validated (views.py:444-455). A stock payload is built per item (product, primary quantity, batch flag - views.py:519-527) and posted to the PMS check-manipulation API with entry_status submit (views.py:464-474, helper.INVENTORY_MANIPULATION_API dashboard/helper.py:101); a 4xx from PMS raises the PMS error, 5xx raises service unavailable (views.py:668-686). Approval user validated (views.py:476-477); fields set, save, notification, activity log, Kafka submit record (views.py:478-510).
  5. Approve: same quotation guards and stock call with entry_status approved (views.py:535-570); then approval fields, save, activity log, Kafka approval record (views.py:572-598).
  6. Cancel: cancel_check blocks when a linked delivery note or sales invoice is in submit or approved state (views.py:289-312); from submit only the approver may cancel, from approved anyone with the action (views.py:348-369); stock rollback call with entry_status cancelled (views.py:600-636), then cancel fields, save, activity log, Kafka cancel record (views.py:643-666).
  7. Custom flow: approve from any state with custom compulsion check, cancel only from approved (views.py:400-410).
  8. Error paths: INVENTORY_NOT_FOUND when PMS returns 4xx or a JSON decode failure (views.py:673-686), INVALID_APPROVE_REQUEST (views.py:381), INVALID_CANCEL_REQUEST (views.py:390), INVALID_STATUS (views.py:396), 503 (views.py:436).

Trace - POST /api/sales/order/cancel-submission/

  1. Only while in submit_for_approval, and only by the creator or the approval_user (views.py:707-717).
  2. Stock reservation released by a PMS call with entry_status cancel_submission (views.py:727-735); referenced quotations are re-validated first (views.py:718-726, 816-826).
  3. Rejection branch: type rejection with the approver - rejected fields, rejection activity log and ERROR notification, Kafka reject record (views.py:738-773).
  4. Revert branch: creator without type - approval_user cleared, CANCEL_SUBMISSION activity log, same Kafka reject record (views.py:774-793).
  5. Otherwise 400 INVALID_REQUEST (views.py:794-796).

  • PMS inventory reservation, issue, release and cancel-submission release via check-manipulation (views.py:471, 565, 631, 733; helper.py:101)
  • Notification on submit (views.py:485-491), ERROR notification on rejection (views.py:749-757)
  • Activity logs for submit, approve, cancel, rejection, revert (views.py:492, 582, 652, 741, 775)
  • Kafka records submit, approval, cancel, reject (views.py:504, 592, 661, 764, 784)
  • Quotation quantity and validity checks against the referenced quotation (views.py:444-455, 816-826)
  • No journal, no IRD

Delivery note - status change and cancel-submission

What happens: A delivery note issues stock when it leaves draft. The same basic/custom approval engine applies, but every state move posts a stock payload that carries batch ids and a reference flag (order vs independent) to the PMS check-manipulation API, using the v2 endpoint for revamped notes. Cancellation is blocked while a linked delivery note return or sales invoice is live, and cancel from an active state rolls stock back before the status is saved.

Trace - POST /api/sales/delivery-note/status/

  1. Auth and permission as before, feature DELIVERY_NOTE (sales/delivery_note/views.py:317-330).
  2. Tenant-scoped fetch (views.py:332-337).
  3. Configuration fetch and dispatch; 503 when missing (views.py:374-380, 444, dashboard/helper.py:162).
  4. Basic flow in one branch per requested status: submit from draft (views.py:381-387), approve from submit by the approver or from draft by the creator after the basic compulsion check (views.py:389-407), cancel from submit by the approver or from approved (views.py:408-420).
  5. Stock call per item: product, batch_id, primary quantity, batch flag, plus reference order or independent (views.py:554-584 for approve, 631-670 for submit, 491-526 for cancel rollback). Revamped notes hit the v2 PMS endpoint, others the v1 endpoint (views.py:520-523; helper.DRN_MANIPULATION_API / DRN_MANIPULATION_API_V2, dashboard/helper.py:102-103).
  6. Order-referenced notes additionally validate the referenced sales order is not cancelled and that item quantities stay within the remaining order quantities (views.py:557-569, 634-646).
  7. Submit: approval user validated, fields set, save, notification, activity log, Kafka submit record (views.py:672-717).
  8. Approve: approval fields, save, activity log, Kafka approval record (views.py:594-629).
  9. Cancel: rollback stock call first when coming from an active state (views.py:470-489, 491-526), then cancel fields, save, activity log, Kafka cancel record (views.py:528-552).
  10. Custom flow: approve from any non-cancelled state after the custom compulsion check, cancel branch present (views.py:426-443).

Trace - POST /api/sales/delivery-note/cancel-submission/

  1. Only from submit_for_approval (views.py:769-800).
  2. Stock reservation released via PMS (views.py:844-849).

Cheque - create, status change, cancel-submission

What happens: A received cheque is a customer payment flagged as a cheque, with a second lifecycle on top of the record workflow: pending, cleared, bounced, void. Record status follows the usual approval flow, and approving a payable cheque posts the customer journal; marking it cleared settles the customer's opening/advance balances and queues the journal, while cancelling restores them. Cheque-level status moves are only allowed once the record is approved and never after expiry.

Trace - POST /api/sales/cheque/ (create)

  1. Auth and permission, feature CHEQUES (sales/cheque/views.py:38-101 region).
  2. The cheque is created as a CustomerPayment with is_cheque set; an activity log entry is written (views.py:102-176, activity at views.py:153).

Trace - POST /api/sales/cheque/status/

  1. Auth and permission, feature CHEQUES, action VIEW to APPROVE_CANCEL (sales/cheque/views.py:663-684 region).
  2. Tenant-scoped fetch; fiscal-year validity on the cheque date (views.py:1055-1056).
  3. Input guards: at least one of cheque_status or record status is required; both values must be valid; submitting requires an approval_user (views.py:1031-1053).
  4. Cheque-status guards: not before approval, not after expiry, and only from pending to another cheque state (views.py:1062-1085).
  5. Configuration fetch (views.py:1087-1092); only the basic flow is handled - a non-basic result falls through to 400 NOT_UPDATED (views.py:1105-1117).
  6. Record transitions: submit (notification and activity log), approve (customer balance deductions, journal creation task delayed when the cheque settles - views.py:698-843 region, journal at views.py:824), cancel (balance restoration, journal cancellation task when a journal exists - views.py:966-970 region).
  7. Cheque-state transitions: cleared, bounced with reason, void - validated by validate_set_cheque_status_fields (views.py:706-715 region), saved on the 200 result.
  8. After a successful 200 the row is saved and send_events_for_cheque writes a cheque-status activity log and a notification to the entry-by user when a different user made the change (views.py:656-704 region, 1109-1112).
  9. Error paths: 400 for the guard failures above and NOT_UPDATED when the flow does not match (views.py:1034-1117).

Trace - POST /api/sales/cheque/cancel-submission/

  1. Only from submit_for_approval (sales/cheque/views.py:1121-1160 region).
  2. Rejection by a non-creator: rejected fields, rejection activity log, ERROR notification (views.py:1158-1192).
  3. Revert by the creator: approval fields cleared, CANCEL_SUBMISSION activity log (views.py:1194-1215).
  4. Otherwise 400 INVALID_REQUEST (views.py:1217-1223).

Side effects

  • Journal creation on approval when the cheque settles (Celery delay, views.py:824; tasks.py:543-571) and cancellation on cancel (views.py:966-967; tasks.py:604-616)
  • Customer opening/advance balance deductions on settle, restoration on cancel (views.py:698-843 region, 966-970 region)
  • Activity logs and notifications for submit, approve, cancel, cheque-state changes, rejection, revert (views.py:698-800 region, 843, 970, 1170-1207)
  • No Kafka records, no IRD, no stock

Ebilling - billing invoice, billing return, retry, ird-config

What happens: The ebilling app is the e-invoicing front door for tenants subscribed to the E_BILLING service (every view carries the extra HasEbilling permission, dashboard/auth_backends.py:134-141). Creating a bill auto-approves it, issues stock, posts quick payments, emits the Kafka bill record and pushes the bill to the IRD CBMS API through the Celery retry task - the request itself never waits on IRD. The status endpoint only allows approving a draft into approved (which also posts to IRD); the cancel branch is unreachable because it raises before doing anything. The retry endpoint re-drives failed posts on demand.

Trace - POST /api/sales/billing/ (billing invoice create)

  1. Permission HasPermission plus HasEbilling (sales/ebilling/views.py:306-307 region for the status class, and the create class at views.py:48).
  2. Same required fields and serializer as the invoice v2 create (views.py:163-215).
  3. Draft mode: a plain draft bill is saved, no impacts, no unique id (views.py:222-230).
  4. Post-bill mode: the e-billing subscription is enforced (views.py:232-234); a unique bill number with the fiscal-year np name is generated (views.py:236-242).
  5. The bill is auto-approved in place: stock issued (post_bill, views.py:245, 120-162), approval flow with the SALES_FLOW automation config gating the journal task (approved_last_flow, views.py:246, 709), quick payments from allocations (views.py:248-250), Kafka bill record (views.py:252-265).
  6. The tenant PAN must be verified at TMS (views.py:267-275); the tenant must be eligible for bill posting, otherwise the created bill is returned with a cannot-post-to-IRD note and no marker (views.py:277-287).
  7. Otherwise an InvoiceFailed marker is created, ebilling_status posted, and the Celery task retry_failed_invoice runs without a countdown (views.py:288-295).

Trace - POST /api/sales/billing/status/

  1. Permission HasPermission plus HasEbilling (sales/ebilling/views.py:306-307).
  2. Configuration fetch; only basic or custom titles are accepted (views.py:339-350).
  3. Approve: only from draft by the creator, after the basic compulsion check (views.py:351-361). handle_approval re-validates the IRD configuration, creates the InvoiceFailed marker, schedules the Celery task with a countdown, sets ebilling_status posted, emits the Kafka bill record and runs the journal task when the automation config exists (views.py:561-720; IRD at views.py:644-674, Kafka at views.py:697, journal at views.py:709). A missing IRD configuration writes an activity log and fails (views.py:669-674).
  4. Cancel: the branch raises INVALID_CANCEL_REQUEST before any work - cancelled bills cannot be cancelled from this endpoint (views.py:362-363).
  5. Any other status raises the e-billing error (views.py:371-372); no configuration raises 503 (views.py:374).

Trace - POST /api/sales/billing/retry/

  1. Only an approved invoice that has not synced with IRD is accepted (sales/ebilling/views.py:868-947 region; guard at views.py:901-914).
  2. InvoiceFailed marker, ebilling_status posted, Celery task scheduled with a countdown (views.py:941-947).

Trace - POST /api/sales/billing/return/ and /status/ and /retry/

  1. The credit-note mirror of the billing invoice flow: create auto-approves and posts a credit note to IRD (sales/ebilling/views.py:958-1192; journal gate views.py:989-997, Kafka views.py:1140, IRD marker and celery task views.py:1166-1176).
  2. Status: approve from draft (views.py:1214-1260, 1262-1418), cancel branch unreachable (views.py:1214-1260 region mirrors the invoice), IRD post with retry task (views.py:1333-1373), journal (views.py:1396), Kafka (views.py:1401).
  3. Retry mirrors the invoice retry for credit notes (views.py:1610-1686; task sales/sales_invoice/tasks.py:222-356).

Side effects

  • Auto-approval: stock issue, journal task, quick payments, Kafka bill record (views.py:245-265, 958-1176)
  • IRD CBMS posting via Celery with InvoiceFailed bookkeeping and TMS PAN checks (views.py:267-295; tasks.py:60-131, 222-504)
  • Activity logs for the e-billing bill and credit-note variants (custom.create_activity_log_ebilling_bill / _return, custom_functions.py)
  • ird-config stores the tenant PAN, e-permit and IRD credentials (config_setup/views.py)
  • No local cancel path for bills, no stock release from these endpoints
