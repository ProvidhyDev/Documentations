Sales . Delivery Note Return

Delivery note returns (DNR) record goods returned by a customer against an approved delivery note. Lifecycle: create -> submit for approval -> approve / reject / cancel. Inventory moves (goods back into stock) happen at approval and are reversed at cancel, via the Inventory service.

All routes below are relative to the service root; on the live service they sit under /api/sales/delivery-note-return/. Source: sales/delivery_note_return/urls.py, views.py, serializers.py @ d07a3d4c.

Catalog note: as with delivery notes, the catalog flags every unversioned route of this app as superseded because a revamped create route exists (/delivery-note-return/v2/); only the create endpoint has a versioned sibling, so the other routes below are the only live implementations (see Superseded section).

1. POST /delivery-note-return/v2/ - create (revamped)

  • View: DeliveryNoteReturnListCreateRevamped - sales/delivery_note_return/views.py:84 (route urls.py:11-15). Replaces the superseded POST /delivery-note-return/ (DeliveryNoteReturnListCreate, views.py:29).
  • Auth: IAMAuthenticationBackendSales + HasPermission (views.py:83-88); POST requires action ADD_EDIT (views.py:90-96). Feature RETURNS_DELIVERY_NOTE (views.py:87).
  • Request (JSON):
    • items (array) - required (views.py:100-102); each item needs product_id, uom (views.py:106-107).
    • customer (customer id) - required (views.py:100-102).
    • entry_date (date) - required (views.py:100-102).
    • delivery_note (id) - the delivery note being returned against (validated in the serializer, sales/delivery_note_return/serializers.py - DRNSerializerWriteOnlyRevamped); other model fields per sales/delivery_note_return/models.py.
    • fiscal_year injected from the request (views.py:119); context carries tenant_id + user_id (views.py:113-117).
  • Processing: transaction.atomic (views.py:99); DRNSerializerWriteOnlyRevamped (views.py:120-122).
  • Response: 201 { id, message } (views.py:125-131); 400 { error } on invalid data (views.py:132-135).
  • Side effects: none in the create path.

2/3. GET / POST /delivery-note-return/detail// - detail & update

  • View: DeliveryNoteReturnRetrieveUpdate - views.py:170 (routes urls.py:16-20).
  • Auth: IAM + HasPermission; GET -> VIEW, POST -> ADD_EDIT (views.py:169-181).
  • GET: tenant-scoped lookup (views.py:183-187); user-level row visibility via helper.user_filter (views.py:193-199); DRNSerializerReadOnly; optional convert param reshapes legacy (non-revamped) items (views.py:200-208); 404 with DELIVERY_NOTE_RETURN_NOT_FOUND otherwise (views.py:210-214).
  • POST: draft-only (ValidationError APPROVED_ENTRY_NO_UPDATE, views.py:240-241); requires items, customer, entry_date and per-item product_id/uom (views.py:224-234); serializer chosen by the record's revamped flag (views.py:247-254); writes an edit log via custom.edit_logs before saving (views.py:257); 200 { message, id } or 400 with serializer errors (views.py:256-268).

4. GET /delivery-note-return/detail-no-perm// - detail without permission

  • View: DeliveryNoteReturnRetrieveNoPerm - views.py:138 (route urls.py:21-25).
  • Auth: IAM only - no HasPermission feature check (views.py:138-139).
  • Same tenant scoping + user_filter + DRNSerializerReadOnly (views.py:141-166); 404 otherwise (views.py:162-166).

5. POST /delivery-note-return/delete// - delete

  • View: DeliveryNoteReturnDeleteAPIView - views.py:271 (route urls.py:26-30).
  • Auth: IAM + HasPermission, action ADD_EDIT (views.py:272-275).
  • Behavior: transaction.atomic (views.py:285); deletable only when status is draft and entry_by is the current user (views.py:289); deletes items then the record (views.py:290-291); 200 { message } (views.py:292-299); 400 "Return Delivery Note cannot be deleted!" otherwise (views.py:300-303); 400 not-found otherwise (views.py:304-308). No activity log or Kafka in this path.

6. POST /delivery-note-return/status// - status change (approval workflow)

  • View: DeliveryNoteReturnStatusAPIView - views.py:312 (route urls.py:31-35); entry point post() at views.py:336.
  • Auth: IAM + HasPermission; for POST with status != submit_for_approval the action is APPROVE_CANCEL (views.py:317-325).
  • Request: { status, comment?, approval_user? }.
  • Flow (views.py:336-360):
    1. transaction.atomic, tenant-scoped lookup (views.py:337-338). Note: the lookup catches models.DeliveryNote.DoesNotExist although it queries DeliveryNoteReturn (views.py:333) - a copy-paste quirk.
    2. Loads the tenant's approval-work configuration from the Configuration service (send_requests.get_configuration, views.py:346-351).
    3. Title BASIC -> handle_basic_flow; title CUSTOM -> handle_custom_flow; anything else -> 503 (views.py:352-360).
  • Sub-actions (basic flow, views.py:362-385):
    • Submit for approval (draft only, submitted_for_approval, views.py:642-697): the referenced delivery note must not be cancelled (views.py:644-645); validates each line against the delivery-note quantities (validation_check.delivery_note_quantity_validation, views.py:646-647) and runs validation_check.delivery_note_check (views.py:648); validates the approval user (helper.validate_approval_user, views.py:650-653); sets approval_user/submit fields/status, clears prior rejection (views.py:655-661); notification (views.py:662-668), activity log (views.py:669-675), Kafka record type RETURNS_DELIVERY_SUBMIT_FOR_APPROVAL_RECORD (views.py:676-689). Unlike orders/DNs, no inventory reservation happens at submit.
    • Approve (handle_approval, views.py:458-475): draft -> approved is self-approval, submitted -> approved requires the designated approval_user (views.py:409-435, checked in handle_basic_flow views.py:368-373); draft approvals run approved_if_draft, which validates the DN state/quantities and moves inventory via INVENTORY_MANIPULATION_RDN_API (legacy) or _V2 (revamped), with order=True when the DN was order-referenced (views.py:548-576); submitted approvals run approved_inventory_manipulation (views.py:578-599); approved_last_flow sets approved fields, writes the activity log and emits Kafka RETURNS_DELIVERY_NOTE_APPROVAL_RECORD (views.py:601-640).
    • Cancel (handle_cancellation, views.py:477-494): only approved -> cancelled (views.py:437-450); cancelled_roll_back reverses the inventory move only when the record was approved (views.py:496-521, same RDN manipulation APIs), then cancelled() sets cancelled fields, writes the activity log and emits Kafka RETURNS_DELIVERY_NOTE_CANCEL (views.py:523-546).
  • Custom flow (views.py:387-401): only self-approval (draft -> approved) after check_for_custom_flow_compulsions (views.py:390-395) and self-cancellation of approved records (views.py:396-400); anything else raises INVALID_STATUS (views.py:401).
  • Response: 200 { message } per outcome; 400 on invalid transitions (views.py:381-385).

7. POST /delivery-note-return/cancel-submission// - revert submission / reject

  • View: DeliveryNoteReturnSubmissionCancel - views.py:754 (route urls.py:41-45); post() at views.py:773.
  • Auth: IAM + HasPermission (views.py:753-757); action fixed to VIEW (views.py:759-762).
  • Request: optional { type: "rejection", comment? }.
  • Behavior (views.py:773-856): allowed only while status is submitted_for_approval and the caller is entry_by or the approval_user (views.py:781-784); re-validates line quantities against the delivery note (note_ref_oreder, views.py:785, 858-863); reverts to draft (views.py:787-788). Rejection branch (views.py:789-828): rejection activity log + ERROR notification, rejected fields, Kafka RETURNS_DELIVERY_REJECT_RECORD. Plain revert branch (views.py:829-852): activity log, clears approval_user, also emits Kafka RETURNS_DELIVERY_REJECT_RECORD (both branches reuse the same record type). Otherwise 400 INVALID_REQUEST (views.py:854-856). No inventory call here because nothing was reserved at submit.

8. GET /delivery-note-return/list/ - internal list for other modules

  • View: DeliveryNoteReturnListForAccounting - views.py:928 (route urls.py:36-40, route name invoice_return_acc).
  • Auth: not IAM - gated by the shared internal password (helper.validate_internal_pass, views.py:930); 400 on bad password (views.py:949-950).
  • Query params: tenant_id, from_date, to_date, optional entry_status (views.py:931-939).
  • Behavior: non-draft DNRs for the tenant in the entry_date range, ordered by entry_date, via DeliveryNoteReturnListForACCSerializer (views.py:940-948).

9. GET /delivery-note-return/search/ - list search

  • View: DRNSearchView (FilteredAPIViewMixin, CustomerDataGatherMixin) - views.py:867 (route urls.py:46).
  • Auth: IAM + HasPermission; GET -> VIEW, POST -> ADD_EDIT (views.py:866-882).
  • Query params: q (over entry_date, entry_by, unique_id - views.py:898-903), status (must be a valid StatusChoices value or 404, views.py:888-891), page/count plus filterset params (filterset_class DeliveryNoteReturnFilterSet, views.py:874).
  • Processing: tenant scoping via the mixin + helper.user_filter (views.py:893-897); paginated with CustomTransactionPagination (views.py:885, 908); DeliveryNoteReturnListSerializer (v2 context, views.py:910-914) with async customer-data gather (views.py:917-920).
  • Response: paginated list (views.py:925).
