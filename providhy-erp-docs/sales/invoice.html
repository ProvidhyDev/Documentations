Sales . Invoice

Sales invoices (bills) are created against approved sales orders or delivery notes, or independently. For tenants subscribed to e-billing (Nepal IRD), creating a non-draft invoice auto-approves it and posts the bill to IRD via an async retry task; non-e-billing invoices follow the standard approval workflow. Cancelling an approved invoice is a "void" and is blocked when linked returns or approved payments exist.

All routes below are relative to the service root; on the live service they sit under /api/sales/invoice/. Source: sales/sales_invoice/urls.py, views.py, serializers.py, tasks.py @ d07a3d4c.

Catalog note: as with the other lifecycle apps, the catalog flags every unversioned route of this app as superseded because a revamped create route exists (/invoice/v2/); only the create endpoint has a versioned sibling, so the other routes below are the only live implementations (see Superseded section).

1. POST /invoice/v2/ - create (revamped)

  • View: SalesInvoiceListCreateRevamped - sales/sales_invoice/views.py:289 (route urls.py:7-11). Replaces the superseded POST /invoice/ (SalesInvoiceListCreate, views.py:43).
  • Auth: IAMAuthenticationBackendSales + HasPermission (views.py:289-293); POST requires action ADD_EDIT (views.py:295-301). Feature SALES_INVOICE.
  • Request (JSON):
    • customer (customer id) - required (views.py:420-428).
    • items (array) - required (views.py:420-428); each item needs product_id, quantity, uom, rate (views.py:431-434).
    • entry_date, invoice_date (dates) - required (views.py:420-428); fiscal year validated against entry_date (views.py:448-449).
    • sales_order / delivery_note (id, optional) - reference docs; payment_allocations (optional) - quick-payment allocations created at approval (views.py:511-512, 400-404); draft (bool, optional) - default behavior creates a draft.
    • Form-data bodies are supported: nested fields (items, customer, payment_allocations, draft) are JSON-decoded from strings (views.py:407-417).
    • Other model fields (title, reference, description, tds_gl, vat fields, grand totals) - sales/sales_invoice/models.py; serializer SalesInvoiceSerializerWriteOnlyRevamped excludes created/modified and defaults revamped=True (sales/sales_invoice/serializers.py:1043-1049); text sanitize via internal SANITIZE_URL (serializers.py:1059-1075 onward).
  • Processing (views.py:406-557):
    • transaction.atomic (views.py:419); serializer with tenant/user + is_ebilling_user context (views.py:436-445); saves the instance, then uploads any attached image (helper.upload_image, views.py:454-456).
    • E-billing tenants, non-draft (views.py:464-536): unique id generated from the unique-id service (views.py:468-471); tenant PAN verified against the TMS service (helper.TMS_PAN_INFO, views.py:473-479, 401 not verified -> EBILLING_NOT_VERIFIED); IRDConfiguration looked up - if cbms is set, an InvoiceFailed row is created, the celery task retry_failed_invoice is queued (countdown 3s) and ebilling_status=POSTED (views.py:481-504); referenced order/DN validated (post_bill, views.py:367-398, quantity checks + inventory approval via INVOICE_INVENTORY_MANIPULATION_API_V2, views.py:329-335); approved_last_flow sets approved fields, queues journal_creation_task when the tenant has a SALES_FLOW AUTOMATION configuration (views.py:337-365) and writes an activity log; quick customer payments are created from payment_allocations (views.py:510-512); Kafka is emitted with kafka.call_kafka_for_bill (dual payload: main + record serializers, views.py:514-528, record type per ConsumerActionList for SALES_INVOICE).
    • Non-draft, non-e-billing (views.py:464-462 guard is false): blocked with EBILL_ERROR_MESSAGE when e-billing is not subscribed (views.py:457-462).
    • Draft path (views.py:537-553): a unique id is still generated (with fiscal-year name part) and the record is returned as draft.
  • Response: 201 { id, message } - "Invoice created successfully as draft" for drafts (views.py:544-553); 400 { error } on invalid data (views.py:554-557).
  • Side effects: activity log, Kafka (call_kafka_for_bill), journal task, IRD posting task, quick payments - as above.

6. POST /invoice/status// - status change (approval workflow)

  • View: SalesInvoiceStatusChangeAPIView - views.py:756 (route urls.py:27-31); entry point post() at views.py:796.
  • Auth: IAM + HasPermission; for POST with status != submit_for_approval the action is APPROVE_CANCEL (views.py:761-769).
  • Request: { status, comment?, approval_user?, nepali_entry_date? }.
  • Flow (views.py:796-890):
    1. transaction.atomic, tenant-scoped lookup, fiscal-year validation (views.py:797-801).
    2. E-billing guard: if the tenant subscribes to e-billing, an IRDConfiguration with cbms must exist or the request fails (views.py:803-808). For e-billing tenants, submit and void are outright rejected with EBILL_ERROR_MESSAGE (views.py:824-825, 851-852) because e-billing invoices are approved at creation.
    3. Loads the tenant's approval-work configuration from the Configuration service (send_requests.get_configuration, views.py:813-818).
    4. BASIC (views.py:819-869): draft -> submit (views.py:820-828); approved from submitted (by approval_user) or from draft (self), after check_for_basic_flow_compulsions (views.py:830-848); void from submitted (by approval_user) or approved (views.py:850-864), after cancel_check; else INVALID_STATUS (views.py:865-869). CUSTOM (views.py:870-889): approved from any status except cancelled, after check_for_custom_flow_compulsions (views.py:871-878); void only from approved (views.py:879-888); else INVALID_STATUS (views.py:889).
    5. Unknown configuration -> 503 TemporaryServiceUnavailableError (views.py:890).
  • Sub-actions:
    • Submit for approval (submitted_for_approval, views.py:1068-1159): validates the referenced order/DN is not cancelled and checks line quantities (views.py:1070-1100); reserves/adjusts inventory via INVOICE_INVENTORY_MANIPULATION_API (order-referenced, independent) or _V2 (revamped) (views.py:1083-1111); validates the approval user (views.py:1113-1116); sets approval fields incl. nepali_entry_date, clears prior rejection (views.py:1118-1125); notification (views.py:1126-1132), activity log (views.py:1133-1139), Kafka SALES_INVOICE_SUBMIT_FOR_APPROVAL_RECORD (views.py:1140-1151).
    • Approve (handle_approval, views.py:1172-1201): e-billing tenants re-verify PAN via TMS first (views.py:1175-1183); draft -> approved runs approved_if_draft (order/DN validation, views.py:1203-1225) then approval_calc_part (inventory move, views.py:1227-1242); submitted -> approved runs approval_calc_part directly (views.py:1188-1190); approved_last_flow (views.py:1244-1347): for e-billing, generates the unique id, sets entry/invoice dates, and if cbms is configured creates an InvoiceFailed row, queues retry_failed_invoice (countdown 3s) and sets ebilling_status=POSTED - if IRDConfiguration is missing it attempts an inventory REVERT call, records an InventoryManipulation row and an activity-log entry before raising IRD_CONFIG_MISSING (views.py:1246-1293); otherwise writes the approval activity log (views.py:1294-1301); sets approved fields (views.py:1303-1311); emits Kafka with call_kafka_for_bill (dual payload, views.py:1318-1329); creates quick payments from payment_allocations (views.py:1331-1333, 1349-1353); queues journal_creation_task when the tenant has a SALES_FLOW AUTOMATION configuration (views.py:1334-1338).
    • Void (cancel) (handle_cancellation, views.py:900-924): blocked when an approved non-quick payment is linked (views.py:901-906); cancelled_roll_back re-validates the order/DN (views.py:926-948) and reverses the inventory move - for order/DN/independent branches with origin and both_addition flags (cancellation_calc_part, views.py:953-1032, API or _V2 by revamped flag); cancelled() sets cancelled fields, voids any quick customer payment (views.py:1044), writes the activity log and emits Kafka SALES_INVOICE_CANCEL (views.py:1049-1061), then queues journal_cancellation_task if the invoice had a journal (views.py:1063-1066). cancel_check blocks the void when an active sales return is linked (views.py:780-794).
  • Response: 200 { message } per outcome; 400 on validation errors (views.py:848, 864, 866-869).
