Sales Module

The Sales service owns the complete B2B sales cycle for every tenant: quotations, sales orders, delivery notes (with returns), sales invoices, returns, customer payments, cheque processing, and e-billing. It is one Django/DRF microservice; all routes are mounted under /api/sales/ on the live service.

Authentication & authorization model

Every IAM-facing view sets its own classes — there is no global DRF permission default in this service:

  • Authentication: IAMAuthenticationBackendSales (from dashboard/auth_backends.py) — validates the tenant token issued by the IAM service and exposes the tenant id on request.auth and the fiscal year on request.fiscal_year. Every record is scoped by tenant_id = request.auth.
  • Permission: HasPermission — checks the caller's feature permission (required_feature_permission, e.g. SALES_QUOTATION) and action permission (required_action_permission, e.g. VIEW / ADD_EDIT) granted by IAM for that tenant user. Many views switch the required action by HTTP method in initial() (GET → VIEW, POST → ADD_EDIT).
  • Internal endpoints: a small set (e.g. sales/quotation/list/, dashboard feeds) are not IAM-authenticated; they are gated by a shared internal password (query param password checked by helper.validate_internal_pass) and called by other Providhy services.
  • No-perm variants: some detail routes (e.g. detail-no-perm/) authenticate via IAM but skip the feature-permission check so other modules can embed the record (marked where present).

Citations use paths relative to the repo root, e.g. sales/sales_quotation/views.py:34.

Sales cycle

sequenceDiagram
    participant FE as ERP Frontend
    participant Q as Quotation
    participant O as Sales Order
    participant DN as Delivery Note
    participant INV as Invoice
    FE->>Q: create + submit
    Q->>Q: approval workflow (basic or custom flow)
    FE->>O: create from approved quotation
    O->>O: approval workflow
    FE->>DN: issue delivery against order
    DN->>INV: generate invoice from delivery
    INV->>INV: ird sync + payment

Approval behavior is tenant-configured: status-change endpoints fetch the tenant's approval-work configuration from the Configuration service (send_requests.get_configuration, title BASIC or CUSTOM) and dispatch accordingly (e.g. sales/sales_quotation/views.py:338). Every state transition writes a notification, an activity log, and a Kafka record (kafka.call_kafka) consumed by the reporting pipeline.

Cross-service calls made by this module

  • Configuration service — tenant approval-work flow, fiscal-year info.
  • Inventory (ProductManagement) — product validity checks (helper.product_validation).
  • IAM — approval-user validation (helper.validate_approval_user).
  • Kafka — transaction records for the reporting warehouse (ConsumerActionList record types per module).
