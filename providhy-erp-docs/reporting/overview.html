Business purpose

The reports and analytics layer - and the platform's answer to keeping reporting out of the way of transactions. It never reads a module database: module writes are mirrored to Kafka, consumed into reporting's own warehouse (transaction views + ledger + opening history), and served from there on a read replica (Reporting/Reporting/settings.py:112,121). It covers the full financial-reporting set (P&L, balance sheet, trial balance), inventory valuation and monthly closing, per-party transaction history, the frontend's dashboard widgets (analytics), and the Kafka ops surface.

Reporting . Overview

The Reporting service owns the read-side analytics of ProvidhyERP. A Kafka consumer ingests transaction records emitted by the sales, purchase, inventory and accounting services into materialized transaction views, and the HTTP API serves report screens (ledger, trial balance, valuation, ageing, VAT, TDS), dashboard widgets, warehouse / year-end closing operations, and internal reconciliation jobs. Reports are computed against a read-only PostgreSQL replica; the Kafka consumer and the sync jobs write to the master.

Source: Reporting/urls.py, Reporting/settings.py, dashboard/management/commands/kafka_consumer.py @ ec01f56b.

Authentication model

All IAM endpoints authenticate with IAMAuthenticationReportBackend (dashboard/auth_backends.py:13-31): it extracts the access token (header, cookie, or body - get_access_token in dashboard/helpers.py:576-605), validates it against the IAM service (POST api/token/verify/, validate_token_with_iam at dashboard/auth_backends.py:34-49), and returns the tuple (user_id, tenant_id). The tenant id from that tuple is the scoping key for every report (request.auth is used as tenant_id throughout the report views).

HasPermission (dashboard/auth_backends.py:52-79) is the feature/action gate used with the report views: a POST from a user whose subscription has expired is rejected; tenant-root users pass; otherwise the view must declare required_feature_permission and required_action_permission and one of the user's IAM permission sets must contain that feature id with that action. Each report view sets required_feature_permission dynamically from the report= query param in initial() (e.g. sales/views.py:25-65).

Other backends in dashboard/auth_backends.py:

  • APIKeyAuthentication (lines 95-110) - X-API-KEY header must equal the ESEWA_API_KEY setting; also reads X-EXTERNAL-IDENTIFIER into request.external_identifier. Used only by the CDXE inventory report.
  • FederatedIdentityAuthentication (lines 112-126) + HasExternalEntityPermission (129-134) - miniapp token validation; present in the module but no current route in this service uses it.
  • IAMUser (lines 144-157) + IsRoot (160-166) - Basic-authenticated user resolved via IAM with a root-user check; no current route uses them.
  • InternalRequestPermission (lines 169-189) - pure permission class: checks the password gate (validate_internal_pass, dashboard/helpers.py:363-367) from the body on POST or the query string on GET.
  • InternalRequestAuthentication (lines 192-207) - authentication class for the same password gate; used by /api/accounting/ageing-report/cms/ and /api/accounting/confirmation-eligibility-check/.

The shared internal password itself comes from the INTERNAL_PASS environment variable (PASSWORD constant, dashboard/helpers.py:36).

Internal (service-to-service) endpoints are marked internal in the endpoint maps below; they are gated by either the InternalRequestAuthentication / InternalRequestPermission classes or by an inline helpers.validate_internal_pass check inside the view.

Kafka consumption (internal ingestion)

Reporting is the main Kafka consumer of the platform. A long-running management command (not an HTTP route) polls the broker:

  • Command: dashboard/management/commands/kafka_consumer.py - group id reporting-consumer-group, auto.offset.reset earliest, bootstrap from KAFKA_BROKER_URL (kafka-crs:9092, Reporting/settings.py:199), SASL settings available in Reporting/settings.py:203-209, topics from the KAFKA_TOPICS env var (Reporting/settings.py:200; kafka_consumer.py:74-93).
  • Routing: the message key selects the handler - inventory, purchase, sales, accounting, master (route_message, kafka_consumer.py:106-118); the action field is matched against ConsumerActionList (dashboard/choices.py:644-821) with per-module action groups (kafka_consumer.py:120-300).
  • Effects: approved / cancelled / submitted / rejected records are materialized into the transaction views (SalesTransactionView, PurchaseTransactionView, ProductTransactionView, AccountingTransactionView) and the ledger via the ingestor functions in dashboard/kafka_data_ingestor.py (create_sales_transaction, create_purchase_transaction, create_product_transaction, create_accounting_transaction, plus cancel and reject variants); product creation/edition and new-batch records populate the product master materialized data.
  • Topic maintenance: a daily Celery beat task creates the four topics accounting_events, inventory_events, purchase_events, sales_events if missing (Reporting/celery.py:14-19; dashboard/tasks.py:23, 28-47). The in-process producer classes (KafkaProducerService, KafkaProducerServiceSASL - dashboard/producer.py:8-42) are used only by the kafka-test / kafka-topic-creation endpoints in warehouse.md.

Database layout

Read/write split via Reporting/db_routers.py: every ORM read goes to the replica database, every write and every migration goes to the default (master) database (PrimaryReplicaRouter, db_routers.py:47-69). The replica name comes from DB_REPLICA_NAME with a fallback to DB_NAME (Reporting/settings.py:98-112). A thread-local force_database context manager (db_routers.py:29-44) lets a code block pin its reads to the master - used by the kafka-test-from-master endpoint in warehouse.md. Report views therefore normally read replica data that the Kafka consumer wrote on the master; replication lag can make very recent transactions invisible (unverified: exact lag characteristics depend on the replica streaming setup).

Async processing

Celery with a Redis broker (Reporting/settings.py:172-175; broker redis:6379/1). Beat schedule: only the daily kafka topic creation task (Reporting/celery.py:14-19). A sync_single_tenant retryable task exists in dashboard/tasks.py:50-56 for per-tenant module sync (invoked programmatically; no beat entry references it - unverified).

Request flow

sequenceDiagram
    participant FE as Frontend
    participant RPT as Reporting API
    participant IAM as IAM service
    participant DB as PostgreSQL replica
    participant KAF as Kafka
    participant CONS as Kafka consumer command
    participant MAST as PostgreSQL master

    FE->>RPT: GET /api/sales/report/v2/ with token
    RPT->>IAM: api/token/verify/
    IAM-->>RPT: user_id + tenant_id + permissions
    RPT->>DB: query SalesTransactionView for tenant
    DB-->>RPT: rows
    RPT-->>FE: report payload

    Note over KAF: transaction services produce records
    KAF->>CONS: poll message with key and action
    CONS->>MAST: upsert SalesTransactionView and ledger rows
