Reporting . Warehouse

The dashboard app is the operational half of the reporting service: Kafka producer test endpoints, Django migration administration, year-end opening-history transfer, the reconciliation sync that rebuilds the materialized views from the source services, tenant data deletion, and the admin log viewer. Almost nothing here is called by the frontend - it is driven by the CMS/ops backends with the shared internal password (INTERNAL_PASS) or, for the two Kafka test endpoints and the history wipe, with no gate at all.

All routes below sit under /api/dashboard/ (dashboard/urls.py:7-75). Source: dashboard/views.py, dashboard/producer.py, Reporting/db_routers.py @ ec01f56b.

1. GET/POST /api/dashboard/ - ping

  • View: DashboardAPIView - dashboard/views.py:82 (route dashboard/urls.py:8).
  • Auth: public - no authentication classes.
  • Response: 200 { message } for both methods (dashboard/views.py:83-94).

2. GET /api/dashboard/choices/ - report choices

  • View: ReportingChoiceView - dashboard/views.py:97 (route dashboard/urls.py:9-14).
  • Auth: IAM only (dashboard/views.py:98) - no HasPermission feature check (no-perm variant); any authenticated tenant user can fetch the menu.
  • Processing: builds the report choice lists from the dashboard/choices.py enums - inventory, purchase, sales, accounting, tax, supplier, customer, financial position - excluding the GRN/GRN-return purchase reports (dashboard/views.py:103-106), the variant inventory valuation report (dashboard/views.py:110-112) and the GRIR classification accounting report (dashboard/views.py:101), plus month, report-date, status, annex and transaction-type choice lists (dashboard/views.py:136-187).
  • Response: 200 { reports, report_date_choices, status_choices, months, annex_report_choices, transaction_type_choices }.
  • Frontend usage: used by apps-frontend to render the report menus.

3. POST /api/dashboard/choices-internal/ - report name search

  • View: ReportingNameForGlobalSearch - dashboard/views.py:212 (route dashboard/urls.py:10-14).
  • Auth: internal - authentication_classes is empty and InternalRequestPermission gates the request by password (dashboard/views.py:213-214; permission class at dashboard/auth_backends.py:169-189).
  • Request (JSON): q (required, dashboard/views.py:235).
  • Processing: reuses the parent choice builder, scores each report label by partial match or SequenceMatcher similarity, keeps scores >= 0.4 and returns the top 5 (dashboard/views.py:217-258).
  • Response: 200 { report_name: [ { value, label, feature, of } ... ] }.
  • Frontend usage: not called by the frontend apps - CMS global search backend.

4. POST /api/dashboard/kafka-test/ - kafka test producer

  • View: KafkaProducerView - dashboard/views.py:261 (route dashboard/urls.py:15-20).
  • Auth: public - no authentication classes on the view (dashboard/views.py:261-276).
  • Request (JSON): message (optional, defaults to a canned string).
  • Processing: sends the message to the accounting_events topic with key accounting through KafkaProducerServiceSASL (dashboard/views.py:263-267; producer at dashboard/producer.py:23-42, SASL bootstrap from KAFKA_URL/KAFKA_SASL_CONFIG).
  • Response: 200 { message } on success, 500 { error } on producer failure.
  • Side effects: writes a message to the shared Kafka topic - the reporting consumer will pick it up and run its accounting handler.
  • Frontend usage: not called by the frontend apps - ops debugging.

5. POST /api/dashboard/kafka-topic-creation/ - topic producer

  • View: TopicProducerView - dashboard/views.py:279 (route dashboard/urls.py:16-20).
  • Auth: public - no authentication classes (dashboard/views.py:279-299).
  • Request (JSON): topic (required), data (optional).
  • Processing: produces a message to the named topic via KafkaProducerService (plain bootstrap, dashboard/views.py:289-290; producer at dashboard/producer.py:8-20). The endpoint name reflects its historical use of triggering topic creation; the actual topic-creation path is the daily beat task (Reporting/celery.py:14-19, dashboard/tasks.py:28-47).
  • Response: 200 { message } or 400/500.
  • Side effects: arbitrary topic production with no gate - ops endpoint.
  • Frontend usage: not called by the frontend apps.

6. POST /api/dashboard/delete-all-migrations/ - delete migrations by app

  • View: delete_migration - dashboard/views.py:303 (route dashboard/urls.py:21-23).
  • Auth: internal - password gate via helpers.validate_internal_pass (dashboard/views.py:311-314).
  • Request (JSON): app (required), password.
  • Processing: raw SQL DELETE FROM django_migrations WHERE app = %s (dashboard/views.py:323-330).
  • Response: 200 { status: success, message } / 400 / 500.
  • Side effects: unmarks all migrations for the app in the bookkeeping table (does not roll back schema).
  • Frontend usage: not called by the frontend apps - ops.

7. POST /api/dashboard/delete-all-table/ - drop table or view

  • View: delete_table_or_view - dashboard/views.py:348 (route dashboard/urls.py:24-28).
  • Auth: internal - password gate (dashboard/views.py:355-358).
  • Request (JSON): table_name (required), password.
  • Processing: looks up relkind in pg_class and drops a materialized view (kind m) or a table with CASCADE (dashboard/views.py:366-389).
  • Response: 200 / 404 (not found) / 500.
  • Side effects: destroys the named object in the reporting database - ops endpoint.
  • Frontend usage: not called by the frontend apps.

8. GET /api/dashboard/list-all-migrations/ - list migrations

  • View: list_migrations - dashboard/views.py:403 (route dashboard/urls.py:25-28).
  • Auth: internal - password gate in the query string (dashboard/views.py:408-412).
  • Query params: password, app (optional filter).
  • Response: 200 { status, count, data: [ { id, app, name, applied } ] } (dashboard/views.py:414-437).
  • Frontend usage: not called by the frontend apps - ops.

9. POST /api/dashboard/delete-migration-id/ - delete migration by id

  • View: delete_migration_by_id - dashboard/views.py:447 (route dashboard/urls.py:26-28).
  • Auth: internal - password gate (dashboard/views.py:451-455).
  • Request (JSON): id (required), password.
  • Response: 200 / 400 / 404 / 500 (dashboard/views.py:457-492).
  • Frontend usage: not called by the frontend apps - ops.

10. POST /api/dashboard/transfer-opening-history/ - year-end opening transfer

  • View: TransferOpeningHistoryAPIView - dashboard/views.py:495 (route dashboard/urls.py:29-33).
  • Auth: internal - password gate (dashboard/views.py:520-521).
  • Request (JSON): data - map of tenant_id -> { np_end_date } for the fiscal years to close; password.
  • Processing (dashboard/views.py:505-648):
    1. Fetches supplier/customer, product and account opening details for all tenants in parallel from the Project Master / PMS / Accounting services (APILinks GET_SUP_CUS_OPENING_URL, GET_PRODUCT_OPENING_URL, GET_ACCOUNT_OPENING_URL, dashboard/views.py:499-503, 537-545).
    2. Skips tenants that already have an ActionModel marker for the fiscal year (existing_action_tenants_by_type, dashboard/views.py:531-535) so the transfer is idempotent per tenant + FY.
    3. Bulk-creates SupplierOpeningHistory, CustomerOpeningHistory, ProductOpeningHistory, AccountOpeningHistory rows (batch size 1000, dashboard/views.py:616-631) plus ActionModel markers (dashboard/views.py:632-639).
    4. The closing-balance write-back calls to the master services are currently commented out (dashboard/views.py:577-614).
  • Response: 200 { message: "Balance processed successfully" }.
  • Side effects: writes opening history on the master database.
  • Frontend usage: not called by the frontend apps - fiscal-year close run by ops/CMS.

11. POST /api/dashboard/delete-history/ - delete all opening history

  • View: DeleteAll - dashboard/views.py:961 (route dashboard/urls.py:34-39).
  • Auth: public - no authentication classes (dashboard/views.py:961-967).
  • Processing: deletes every row of the four opening-history models (dashboard/views.py:963-966).
  • Response: 200 "success".
  • Side effects: wipes the whole opening-history store - dangerous ungated ops endpoint.
  • Frontend usage: not called by the frontend apps.

12. GET /api/dashboard/opening-history-detail/ - entity opening history

  • View: EntityHistoryAPIView - dashboard/views.py:970 (route dashboard/urls.py:35-39).
  • Auth: internal - password gate (dashboard/views.py:977-978).
  • Query params: tenant_id, entity_id, entity_type (supplier | customer | product | account), fy_id, password.
  • Processing: looks up the matching opening-history model and serializes it (supplier/customer single row, product/account lists - dashboard/views.py:988-1015; serializers in dashboard/serializers.py).
  • Response: 200 serialized history / 400 (unknown type or missing params).
  • Frontend usage: not called by the frontend apps.

13. POST /api/dashboard/sync-create-record/ - reconciliation sync

  • View: ReconcilationAPIView - dashboard/views.py:1018 (route dashboard/urls.py:40-44).
  • Auth: internal - password gate (dashboard/views.py:1026-1030).
  • Request (JSON): tenant_id (list; empty = all tenants via TMS TENANT_LIST_URL, dashboard/views.py:1031-1035), module_name (sales | purchase | inventory | accounting | master), password.
  • Processing (dashboard/views.py:1039-1186): for each tenant + module it collects the entry ids present in the reporting transaction views per transaction type (dashboard/views.py:1044-1062), calls the corresponding check-reconciliation endpoint of the source service (PRODUCT/SALES/PURCHASE/ACCOUNTING/MASTER_RECORDS_SYNC_URL, dashboard/views.py:1075-1183), then persists whatever the source returns: product adjustments + masterize rows, sales/purchase transaction rows, and for approved sales and purchase invoices + returns it rebuilds the product transaction rows FIFO-ordered by entry_date (dashboard/views.py:1105-1156).
  • Response: 200 { message: "Successfully synced" }; 400 with the error on failure (dashboard/views.py:1184-1188).
  • Side effects: writes transaction views and product materialized data on the master database.
  • Frontend usage: not called by the frontend apps - full resync job.

14. POST /api/dashboard/sync-create-record-v3/ - replay via remote producer

  • View: ReconcilationAPIViewV3 - dashboard/views.py:1366 (route dashboard/urls.py:45-49).
  • Auth: internal - password gate (dashboard/views.py:1371-1374).
  • Request (JSON): action, data, event_type, event_topic (all required, dashboard/views.py:1376-1378), tenant_id (optional; empty = all tenants via TMS, dashboard/views.py:1379-1383).
  • Processing: for each tenant it posts the event to the remote Kafka producer service (KAFKA_PRODUCER_URL, APILinks:360) so the reporting consumer re-ingests it (dashboard/views.py:1391-1408).
  • Response: 202 { message, tenant_count, : <status_code> ... }.
  • Side effects: produces Kafka events that the consumer will process.
  • Frontend usage: not called by the frontend apps - targeted resync job.

15. POST /api/dashboard/sync-accounting-report/ - rebuild accounting reports

  • View: ReconcilationAPIViewforAccounting - dashboard/views.py:1191 (route dashboard/urls.py:50-54).
  • Auth: internal - password gate (dashboard/views.py:1196-1199).
  • Request (JSON): tenant_id (list; empty = all tenants via TMS, dashboard/views.py:1200-1208), password.
  • Processing: per tenant, triggers the persisted trial balance, then P&L, then balance sheet report builders in that order (order matters - the balance sheet reads the persisted P&L net profit for retained earnings, dashboard/views.py:1209-1217).
  • Response: 202 { message: "Reconciliation started", tenant_count }.
  • Side effects: persists the three report views on the master database.
  • Frontend usage: not called by the frontend apps.

16. POST /api/dashboard/tenant-data-deletion/ - tenant data deletion

  • View: ReportTenantDataDeleteionAPIViewV2 - dashboard/views.py:1285 (route dashboard/urls.py:55-59).
  • Auth: internal - password gate (dashboard/views.py:1309-1312).
  • Request (JSON): tenant_id (list, required - dashboard/views.py:1323-1326), model_names (optional subset of the 19 allowed tables, dashboard/views.py:1286-1305, 1329-1343), password.
  • Processing: raw DELETE FROM WHERE tenant_id IN (...) inside a transaction for each selected table (dashboard/views.py:1345-1354).
  • Response: 200 { message, deleted_models, tenant_ids, summary } / 400.
  • Side effects: removes the tenant's reporting data (transaction views, opening history, valuation reports, persisted reports, sync tracker, IDs).
  • Frontend usage: not called by the frontend apps - tenant offboarding.

    • 17. GET /api/dashboard/log-viewer/ - log viewer

    • View: LogViewerAPIView - dashboard/views.py:1227 (route dashboard/urls.py:60-64).
    • Auth: BasicAuthentication + IsAdminUser (dashboard/views.py:1228-1229) - the admin/log-viewer bucket that the scope counts as public (no IAM, no internal password).
    • Query params: file_name (default app.log), limit (default 100), position (first | last), order (asc | desc).
    • Processing: lists the .log/.txt files in LOG_DIR and reads the requested slice (deque for the tail) (dashboard/views.py:1231-1274).
    • Response: HTML page rendered from logs/log_viewer.html; 404 JSON with the available file list when the file is missing.
    • Frontend usage: not called by the frontend apps - ops.

    18. GET /api/dashboard/get-party-closing-balance/ - party closing balance

    • View: GetPartyClosingBalanceAPIView - dashboard/views.py:1420 (route dashboard/urls.py:65-69).
    • Auth: internal - password gate (dashboard/views.py:1427-1430).
    • Query params: tenant_id, entity_id, entity_type (customer | supplier), password.
    • Processing: takes the last non-opening TransactionLedgerView row for the party and returns the balance only when the cr/dr side matches the entity type (customer = CR, supplier = DR, dashboard/views.py:1437-1461).
    • Response: 200 { entity_id, entity_type, advance_amount, pending_amount: 0, received_till: 0 }.
    • Frontend usage: not called by the frontend apps.

    19. GET /api/dashboard/kafka-test-from-master/ - read raw rows

    • View: KafkaTestModelFromMasterAPIView - dashboard/views.py:1474 (route dashboard/urls.py:70-74).
    • Auth: internal - password gate (dashboard/views.py:1499-1502).
    • Query params: model_name (one of 9 models, dashboard/views.py:1482-1492), db_type (master | replica, default replica), action, tenant_id, limit (default 100), password.
    • Processing: reads rows with the force_database override so master reads bypass the replica router (dashboard/views.py:1494-1546; context manager at Reporting/db_routers.py:29-44).
    • Response: 200 { count, results, db_type, limit }.
    • Frontend usage: not called by the frontend apps - replication-lag debugging.

    Frontend usage (apps-frontend @ production)

    Only /api/dashboard/choices/ is called by the frontend apps. All other dashboard-app routes are internal/ops or CMS callers. Floor, not a ceiling.
