Kafka Infrastructure (Consumer / Producer / Warehouse)

Business Flows (Traced)

This service is a read-only reporting warehouse (Django 5 + DRF) with seven apps mounted under /api/{dashboard,sales,purchase,inventory,accounting,system,analytics}/ (Reporting/urls.py:25-31). It never reads the module databases directly. The module services publish domain events to Kafka — the canonical topics are accounting_events, inventory_events, purchase_events, sales_events (listed in dashboard/tasks.py:23 and created by the daily 23:59 Celery beat job, Reporting/celery.py:14-19) — and a long-running kafka_consumer management command (group.id=reporting-consumer-group, auto.offset.reset=earliest, dashboard/management/commands/kafka_consumer.py:74-93) subscribes to whatever topics the KAFKA_TOPICS env var enumerates (kafka_consumer.py:90-92) and routes every message by its key — inventory / purchase / sales / accounting / master — into local tables. Events materialize into transaction views (SalesTransactionView, PurchaseTransactionView, AccountingTransactionView, ProductTransactionView) and product master rows (ProductMaterializeView), and each event triggers a delete-the-whole-fiscal-year + rebuild of the affected ledger — TransactionLedgerView for accounting (accounting/account_ledger.py:213-246) or the InventoryValuationReport FIFO ledger for stock (dashboard/kafka_data_ingestor.py:630-639). All report endpoints compute on the fly from those local tables, plus live COA/master fetches via APILinks, running on the read replica by default (Reporting/settings.py:112,121; forced master reads via force_database, Reporting/db_routers.py:29-44).

The practical consequence: the service's real transactional core is ingestion, not the HTTP surface. Of the 46 latest-version HTTP routes, 27 are READ, 14 are internal OPS endpoints, 4 are admin-triggered transactional flows (opening-history transfer + three sync endpoints), 1 (CDXE) belongs to the excluded miniapp domain, and 0 are plain CRUD/RECORD endpoints. The kafka_consumer command is a fifth transactional entry point and the only continuous write engine in the service.

Endpoint classification

Latest-version routes (46), classified. Class: READ = computes from local tables, no state change; RECORD = plain create/update of one business record (none exist); TRANSACTION = mutates warehouse state beyond a single row (ledger rebuilds, bulk history writes, sync); OPS = internal/admin utility, no business flow.

Kafka consumer ingestion (CMD kafka_consumer) — TRANSACTION

What happens. A standalone management command polls the subscribed topics one message at a time (kafka_consumer.py:49-71). Each JSON message is routed by its key to one of five handlers, which upsert the event into the module's local transaction view and then replay the affected ledger for the whole fiscal year from those rows. Cancellations and rejections are themselves events: they flip the transaction view's status (or delete the recorded row) and trigger the same full-year rebuild, so every ledger at any moment equals a deterministic replay of everything stored. There is no retry and no dead-letter queue: exceptions are recorded in the KafkaTestModel table and the loop continues, and with confluent-kafka's default auto-commit a failed message is not redelivered — it is lost until a sync endpoint replays it.

Failure behaviour

  • Handler exception → KafkaTestModel row {msg_key}_processing_error_{tenant_id} with the exception text (kafka_consumer.py:305-315); the loop continues. No retry, no DLQ; with auto-commit the offset has already advanced, so the event is lost until replayed via sync-create-record / sync-create-record-v3.
  • Non-EOF broker errors raise KafkaException and kill the process (kafka_consumer.py:95-103) — recovery is a supervisor restart from the last committed offset.
  • Unknown message key → warning + drop (kafka_consumer.py:118); unknown accounting action → fake "success" row (kafka_consumer.py:251).
  • create_sales_transaction has an update_remaining branch that dereferences the record without a None check (kafka_data_ingestor.py:338-340) — such a payload for an unknown invoice raises into handle_exception.
  • Rebuilds swallow nothing: accounting_ledger_report logs to KafkaTestModel then re-raises (accounting/account_ledger.py:476-491); the valuation cancel path raises RuntimeError with the traceback on lock failure (kafka_data_ingestor.py:769-772, 1141-1161).

Side effects

  • Rows written: ProductMaterializeView, ProductTransactionView, PurchaseTransactionView, SalesTransactionView, AccountingTransactionView, TransactionLedgerView (deleted then rebuilt per FY), InventoryValuationReport + InventoryValuationBatchReport (deleted then rebuilt per FY), KafkaTestModel (success + failure markers).
  • Advisory lock per (tenant, product) for valuation rebuilds (kafka_data_ingestor.py:621); the accounting rebuild's lock is commented out (accounting/account_ledger.py:206-212).
  • No Kafka produces, no HTTP side effects, no emitted events — the consumer writes only to its own database.
  • Cost: every event costs O(FY) work — a delete + full replay of that tenant's affected ledger.

Inventory - stock valuation (rebuild on every stock movement) — TRANSACTION

What happens. There is no incremental valuation. Whenever a stock movement lands (purchase invoice/return approval, sales invoice/return approval, stock adjustment approval or cancel), the consumer calls initiate_valuation_call / initiate_valuation_cancel_call (kafka_data_ingestor.py:1141-1161), which takes a per-(tenant, product) advisory lock, deletes every InventoryValuationReport / InventoryValuationBatchReport row for that product in the current fiscal year (:630-639), and rebuilds the entire FIFO ledger from scratch: opening + all approved ProductTransactionView rows. The HTTP endpoints /api/inventory/report/v3/ (and superseded /api/inventory/report/closing/) only read the rebuilt tables.

Trace

  1. Trigger — per product of the event: initiate_valuation_call(product_data_list) loops and calls inventory_valuation_report_consumer (kafka_data_ingestor.py:1141-1149); the cancel path calls inventory_valuation_report_on_cancel_consumer (:1152-1161, 749-815), which runs on the reporting DB alias (:764-768) and raises RuntimeError if the advisory lock cannot be acquired (:769-772). Any failure is wrapped in RuntimeError with a traceback (:1146-1160) and lands in KafkaTestModel via handle_exception.
  2. Delete FY rows — inventory_valuation_report_consumer (:604-662): inside transaction.atomic (:619), acquire_lock_in_transaction_safe(tenant_id, product_id) (:621); FY start computed from the event date (:627); deletes both valuation tables' rows with entry_date >= fy_start_date (:630-639).
  3. Opening — get_initial_product_data (:645, 701-716) seeds the starting closing qty/amount/rate, the qty_rate_stack, and the sale_data_stack from the previous ledger state; no monthly closing exists — the seed ultimately comes from get_product_wise_opening (inventory/ledger.py:57-89), which reads ProductOpeningHistory (written by transfer-opening-history at year end) plus the product master. Batch info is loaded separately when a batch ledger exists (kafka_data_ingestor.py:647-649, 718-747).
  4. Replay — _build_full_ledger_from_scratch (:817-959) → process_product_transactions (:960-1138): each approved transaction is converted to primary-unit qty/rate by product_transaction_conversion (inventory/ledger.py:92-187 — groups by entry_id, converts units, folds in discounts to an average rate :124-138), additional costs are applied (:190-224), then transactions are walked in date order feeding get_valuation_ledger (non-batch kafka_data_ingestor.py:999-1008, batch :1045-1054); the posted rate per line is final_total / qty (:984-996, 1030-1042).
  5. FIFO core — get_valuation_ledger (inventory/ledger.py:250-491):
    • Inward (purchase_invoice, sales_return, adjustment ADDITION; :288-301): purchases push (qty, rate) onto qty_rate_stack. A sales return does not take its own rate — it looks up the consuming invoice's recorded stack under the key {unique_id}_{entry_id} in sale_data_stack, walks it in reverse, and values the return at the original consumed rates (:302-344).
    • Outward (sales_invoice, purchase_return; :292-295, pop loop :437-467): FIFO pop from the stack; a sales invoice additionally records the consumed stack under its own key in sale_data_stack so a later return can reverse exactly those layers.
    • Adjustment DEDUCTION (:425-448): pops from the reversed stack (most recent layer first) — adjustments are valued LIFO.
    • Anything else (:476-485): a row is still written, with particular unknown and method none, and no quantity change.
    • Every row stores the running closing qty/amount/rate plus the surviving stacks, so the ledger is self-describing.
  6. Persist — bulk_create of the rebuilt InventoryValuationReport rows (kafka_data_ingestor.py:949) and InventoryValuationBatchReport rows (:953), plus a KafkaTestModel success marker (:956), all inside the same atomic block as the delete.

Dashboard - transfer-opening-history — TRANSACTION

What happens. Year-end operation: one POST pulls opening balances for the given tenant(s) from the four master services (supplier/customer openings, product openings, account openings), writes them into this service's four opening-history tables in a single transaction, and records ActionModel markers per (tenant, action type) for idempotency. The write-back of closing balances to the master services exists in code but is commented out — the masters are never told back. There is no monthly closing anywhere in the service; InventoryMonthlyClosing (inventory/models.py:192) is an orphan model.

Trace

  1. POST /api/dashboard/transfer-opening-history/ — dashboard/views.py:495-648. Shared internal PASSWORD check (:520-521); body is {tid: {np_end_date, ...}}.
  2. The whole handler runs inside transaction.atomic (:506).
  3. Idempotency: existing_action_tenants_by_type reads the ActionModel markers per action type (:531-535); a tenant already marked for a module is skipped for that module.
  4. Fetch: async_fetch_all_openings GETs GET_SUP_CUS_OPENING_URL, GET_PRODUCT_OPENING_URL, GET_ACCOUNT_OPENING_URL on the master services (:537-545).
  5. Per tenant: supplier/customer opening-history rows (:547-571; the closing-balance write-back is commented at :577-580), product opening (:582-589; write-back commented :591-593), account opening (:595-605; write-back commented :607-614).
  6. Persist: four bulk_create(..., batch_size=1000) into the four *OpeningHistory tables (:616-631); ActionModel markers bulk-created per tenant/action type (:632-639; the final write-back block :640-650 is also commented).
  7. Returns 200 with counts (:645-648).

Dashboard - sync tracker ops (sync-create-record / sync-create-record-v3 / sync-accounting-report) — TRANSACTION

What happens. Three internal, password-protected endpoints that repair the warehouse. sync-create-record takes known entry IDs, asks each module's own sync endpoint to resend the full payloads, and stores them with the same save helpers the consumer path uses. sync-create-record-v3 re-publishes raw events to a remote Kafka producer service so the normal consumer path replays them. sync-accounting-report rebuilds the persisted TB/P&L/BS snapshot tables. The first two stamp SyncTracker rows (per-tenant last sync time); the third returns 202 immediately after starting the per-tenant rebuilds.

Trace — sync-create-record (POST /api/dashboard/sync-create-record/)

  1. dashboard/views.py:1018-1188. Internal password check (:1026-1030); no tenant in the body → enumerate all tenants from TENANT_LIST_URL (:1031-1035).
  2. Payload build: known entry IDs per module plus product IDs — build_payload_for_tenant (dashboard/sync_data.py:175-207) produces {password, tid: {txn_type: [entry_ids], product: [product_ids]}}.
  3. Per module: POST to the module's own records-sync URL (e.g. PRODUCT_RECORDS_SYNC_URL, dashboard/views.py:1077-1079; sales/purchase/accounting analogous), then store the response with save_product_transactions / save_product_materialize / save_sales_transactions / save_purchase_transactions / save_accounting_transactions (dashboard/sync_data.py:20-164) — the same upserts the consumer would have done, so the ledger/valuation rebuild semantics are identical.
  4. create_sync_tracker_record stamps SyncTracker(tenant, service, last_sync_time) (dashboard/sync_data.py:166-172).
  5. Any module error → 400 (dashboard/views.py:1187-1188).
  • Bug: the existing-ID dedupe inside every save_* helper is not scoped by tenant (dashboard/sync_data.py:47-51, 72-74, 99-103, 127-131) — if two tenants share an entry id, the second tenant's rows are skipped as "already synced".

Trace — sync-create-record-v3 (POST /api/dashboard/sync-create-record-v3/)

  1. dashboard/views.py:1366-1417. Password (:1371-1374); requires action / data / event_type / event_topic (:1376-1378); all-tenant fallback via TENANT_LIST_URL (:1379-1383).
  2. Per tenant: POST {action, data, tenant_id} to APILinks.KAFKA_PRODUCER_URL using a requests.Session (:1399-1403) — the producer re-publishes onto Kafka and the normal consumer picks the event up, so all consumer side effects (ledgers, valuation, markers) apply.
  3. Returns 202 with per-tenant HTTP status codes (:1410-1417).

Trace — sync-accounting-report (POST /api/dashboard/sync-accounting-report/)

  1. dashboard/views.py:1191-1224. Password (:1196-1199); all tenants when none given (:1200-1208).
  2. Per tenant, rebuild the persisted reports in fixed order — trial balance → profit & loss → balance sheet (:1215-1217, calls trigger_persisted_trial_balance_report accounting/trial_balance_ledger.py:510, trigger_persisted_pl_report accounting/profit_loss_ledger.py:425, trigger_persisted_balance_sheet_report accounting/balance_sheet_ledger.py:421). The order is required because the BS reads the persisted P&L net profit for retained earnings (comment :1210-1214; _persisted_pl_net_profit, accounting/balance_sheet_ledger.py:49-64).
  3. Each trigger collects all of the tenant's ledger entry dates, dedupes the fiscal years, and rebuilds each FY (full rebuild vs incremental per the key (tenant, date_type, fiscal_year, parent_id, child_id) — accounting/trial_balance_ledger.py:253-291; P&L profit_loss_ledger.py:379-424; BS balance_sheet_ledger.py:141-180). Each trigger runs in a nested savepoint and logs errors to KafkaTestModel instead of failing the batch (accounting/trial_balance_ledger.py:555-557, 574-586).
  4. Key fact: the per-transaction triggers that would keep these snapshots fresh are commented out in the live ingestion path (accounting/account_ledger.py:470-474). The only live call sites are these three lines — so the persisted TB/P&L/BS snapshots are stale until someone calls this endpoint.
  5. Returns 202 "Reconciliation started" (:1218-1224).

Trial balance — how the query is assembled

Entry: GET /api/accounting/report/v3/?report=trial_balance → trial_balance_report_v3 (accounting/report_v3.py:385-585).

  1. The chart of accounts is fetched live per tenant (custom.get_coa_accounting, report_v3.py:405); AR and AP are pinned to GL codes 11601 and 21901 (:408-409).
  2. Ledger rows: TransactionLedgerView filtered by tenant with entry_date cast to a date field (:433-435).
  3. Opening: for YEARLY/FY the opening is the last ledger row before the FY start (or the sum of rows flagged opening), falling back to the COA opening; for TODAY/DAYS/CUSTOM it is the last row before from_date (:455-508).
  4. In-range movements are summed to the closing per account, signed by the account's natural dr/cr (:511-530).
  5. GL 12501 override: the row is renamed "Opening Inventory", its opening is taken from the product opening (get_product_opening) and its transaction totals are zeroed (:549-564).
  6. AR/AP party entries are appended from the party ledgers (:576+).

Everything is computed on request from TransactionLedgerView; the persisted TrialBalanceReportView rows are a separate snapshot maintained only by sync-accounting-report.

Profit & loss — how the query is assembled

Entry: ?report=profit_loss → profit_and_loss_report_v3 (accounting/report_v3.py:1378-1511).

  1. COA filtered to income/expense accounts only (:1399-1405); each account's latest balance up to to_date comes from get_opening_of_ledger_balance (accounting/profit_loss_ledger.py:503-576) and is sign-adjusted by the account's natural dr/cr (report_v3.py:1424-1428).
  2. Fixed COA-code buckets: Sales 42300, Direct income 41000, Purchases 51600, Direct expenses 51000, Indirect income 42000, Indirect expense 51300 (report_v3.py:1460-1494).
  3. COGS = opening inventory (get_product_opening) + purchases + direct expenses − closing inventory (from the valuation tables via get_tenant_product_closing, report_v3.py:1467-1471) — assembled at :1472-1485.
  4. Gross profit = sales − COGS (:1488-1490); net = gross + indirect income − indirect expense (:1500-1504). With internal=True the function returns only the net profit (:1505-1506) — that is the value the balance sheet plugs into retained earnings.

Balance sheet — how the query is assembled

Entry: ?report=balance_sheet → balance_sheet_report_v3 (accounting/report_v3.py:1157-1315).

  1. COA filtered to asset/liabilities/equity accounts (:1181-1196); the product closing (valuation) is fetched once up front (:1204).
  2. Per account: latest ledger balance up to to_date, signed by natural dr/cr (:1225-1240), with two overrides — GL 12501 becomes "Closing Inventory" valued from the valuation closing (:1209-1211), and a retained-earnings equity account gets the period's net profit by calling profit_and_loss_report_v3(internal=True, product_closing=...) (:1212-1224).
  3. Accounts are grouped under their COA subgroups, then aggregated into main groups (:1244-1297).
  4. Balancing: diff = assets − (liabilities + equity) is added back as a "Difference in Opening Balance" line so the sheet always balances (:1302-1313).

Sales book — how the query is assembled

Entry: GET /api/sales/report/v2/?report=sales_book → view dispatch (sales/views.py:128-141) → sales_invoice_v2 (sales/report_v2.py:323-449).

  1. Base filters: transaction_type=sales_invoice, status (default approved), date range, customer — customer=all removes the filter (report_v2.py:326-337; date mechanics in sales/views.py:104-117).
  2. Row projection is an explicit field list over SalesTransactionView, ordered by entry date desc (report_v2.py:340-367); per row the customer detail is resolved by helper and zero amounts are returned as null (:371-417).
  3. Direct-JV sales rows are appended from the ledger and the whole list re-sorted by date (:419-430).
  4. Totals (grand, taxable, non-taxable, VAT, discount, export) are aggregated in the DB via qs.aggregate (:433-447).
  5. Pagination is optional — paginate_if_required returns a paginated response when requested (sales/views.py:266-270).
