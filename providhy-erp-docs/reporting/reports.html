Reporting . Reports

The report screens of the platform: one endpoint per module that renders a menu of report types selected by the report= query param, backed by the Kafka-materialized transaction views. Date ranges follow the shared date mechanism (custom.date_mechanism_for_report / date_mechanism_for_report_v2 in dashboard/custom_functions.py:53, 110) against the tenant's Nepali fiscal year; pagination is CustomTransactionPagination (page size 100, count param - dashboard/pagination.py:4-7).

All routes below are relative to the service root. Source: sales/, purchase/, inventory/, accounting/, system/ url + view modules @ ec01f56b.

1. GET /api/sales/report/v2/ - sales reports

  • View: SalesBookReportRevampedAPIView - sales/views.py:20 (route sales/urls.py:7-11).
  • Auth: IAM + HasPermission (sales/views.py:19-23); the feature is switched per report type in initial() - sales/views.py:25-65 (SALES_QUOTATION_REPORT, SALES_ORDER_REPORT, DELIVERY_NOTE_REPORT, RETURNS_DELIVERY_NOTE_REPORT, SALES_BOOK_REPORT, SALES_RETURN_REPORT, SALES_REGISTER_REPORT, SALES_RETURN_REGISTER_REPORT, MATERIALISED_VIEW_REPORT); action VIEW.
  • Query params: report (required; dispatch at sales/views.py:128-264), date_type, month, from_date, to_date, fy_from_date, fy_to_date, customer (default all), status (default approved), dn, page, count.
  • Validation: register reports force date_type to CUSTOM and require month + from/to (sales/views.py:101-102, 289-304); CUSTOM date_type requires from_date + to_date (sales/views.py:306-310); unknown status or report -> 404.
  • Processing: date bounds via custom.date_mechanism_for_report_v2 + convert_date_to_filterable_format (sales/views.py:312-333), then dispatch to the sales/report_v2.py functions: sales_invoice_v2 (called at sales/views.py:133), sales_return_v2 (:147), sales_quotation_v2 (:161), sales_order_v2 (:175), delivery_note_v2 (:189), delivery_note_return_v2 (:203), materialized_view_report_v2 (:218), sales_book_register_v2 (:233, fiscal-year bounds fy_from/fy_to), sales_return_register_v2 (:251). The per-report aggregation internals live in sales/report_v2.py (unverified beyond the call sites).
  • Response: 200 with the report payload; list-shaped results are paginated when the client asks (pagination.paginate_if_required, dashboard/pagination.py:16-36; sales/views.py:266-270).
  • Side effects: none (read-only replica queries).
  • Frontend usage: used by apps-frontend (sales report screen).

4. POST /api/inventory/cdxe/ - CDXE inventory report

  • Frontend usage: not called by the frontend apps - it is the eSewa/CDXE integration endpoint.

9. GET /api/accounting/vat-summary-report/v2/ - VAT summary

  • View: VatSummaryReportAPIViewV2 - accounting/views.py:573 (route accounting/urls.py:27-31).

  • Processing: the requested range is split into fiscal months (get_fiscal_months, accounting/views.py:966+); per month the sales VAT register (sales_reports.sales_book_register_vat_v2) and sales return VAT register plus purchase / purchase return / expense VAT registers are computed (calculate_monthly_data, accounting/views.py:622-694); a running carry-forward of the credit balance is applied month by month (accounting/views.py:843-904).
  • Response: 200 with monthly sales and purchase VAT tables pivoted by fiscal month plus prev-month credit, monthly VAT and payable-balance series (accounting/views.py:906-955).
  • Frontend usage: used by apps-frontend (VAT summary screen).

14. GET /api/accounting/bill-ageing/<party_type>/ - bill ageing

  • View: BillAgeingReport - accounting/views.py:1618 (route accounting/urls.py:57-61, party_type path param).
  • Auth: IAM + HasPermission (accounting/views.py:1617-1619); initial() binds the model and feature per party (accounting/views.py:1626-1660): supplier -> SUPPLIER_BILL_AGEING with PurchaseTransactionView (purchase_invoice + expense_entry) and SalesTransactionView as the secondary model; customer -> CUSTOMER_BILL_AGEING mirrored.
  • Query params: date_type (default yearly), from_date, to_date, due_date, supplier_ids or customer_ids (csv, accounting/views.py:1770-1782).
  • Processing: approved invoices within the range annotated with paid_amount and payment_status (query_invoices, accounting/views.py:1662-1716); approved returns are mapped back to their invoices (get_return_amounts, accounting/views.py:1718-1750); the primary and secondary invoice sets are unioned (accounting/views.py:1784-1818); payment terms are fetched from the Project Master (checked_payment_term, accounting/views.py:1761) and party names via helpers.party_check (accounting/views.py:1832); per row due_date, overdue_days, return-adjusted remaining/paid amounts and final payment status are computed (accounting/views.py:1836-1911).
  • Response: 200 paginated items + totals (total_grand_total, total_paid_amount, total_remaining, total_return_amount, accounting/views.py:1913-1922).
  • Frontend usage: not called by the frontend apps.
