IAM Backend

The IAM-Backend is the identity and access-management service: it issues and verifies the JWT tokens that every other Providhy service relies on (via its per-service IAMAuthenticationBackend* classes), manages tenant users, groups, feature/action permissions, onboarding, and the federated external-identity surface (eSewa merchants, miniapp identities, CMS platform).

Repo: IAM-Backend @ branch f1-production, SHA 0f7c15f7. Routes on f1-production: 82, under /api/ (plus a few admin maintenance routes outside /api/). Source: IAM/urls.py (config), heimer_auth/views.py, federated_identity/views.py, federated_identity/auth_backends.py, IAM/settings.py @ 0f7c15f7.

Why this service matters for the whole ERP

Every other module authenticates requests by validating the JWT this service mints. The token carries tenant_id, user_id, email_verified, subscription_expired, subscribed_services, tenant_root, user_permissions, fiscal year - which is exactly what the per-module IAMAuthenticationBackend* classes decode and check (e.g. Sales: sales/sales/dashboard auth backends). So: IAM-Backend is the root of the entire authorization model documented across this site.

Global auth settings (IAM/settings.py:134-149)

  • DEFAULT_AUTHENTICATION_CLASSES: heimer_auth.auth_backends.CustomJWTAuthentication (a simplejwt-based bearer auth, settings.py:139-142) - applies to every view that does not override authentication_classes.
  • Throttling: anon 3/sec, user 5/sec (settings.py:135-138).
  • No DEFAULT_PERMISSION_CLASSES - so a view that sets no permission_classes is still JWT-authenticated but has no global feature-permission gate; admin-type views then rely on in-code checks (tenant-root, etc.). Where a view sets required_feature_permission + required_action_permission (e.g. GroupManageView, heimer_auth/views.py:716-727) it is enforced through the HasPermission permission (heimer_auth/auth_backends.py:75).
  • Explicit exceptions: internal routes (InternalRequestAuthentication, heimer_auth/auth_backends.py:104), cms routes (CMSIAMAuthenticationBackend, heimer_auth/auth_backends.py:39), federated routes (FederatedIdentityAuthentication, federated_identity/auth_backends.py:10), public routes (authentication_classes = [], e.g. heimer_auth/activate_account.py:55, 167, 311, 383, 460), log viewer (BasicAuthentication, heimer_auth/views.py:4014).

  • POST /delete-all-migrations/, /delete-all-table/, /list-all-migrations/, /delete-migration-id/ - admin maintenance views in heimer_auth (auth: unverified - no class shown at definition; treat as ops-only, confirm before use).

  • POST /api/external/clear-cache/ - ClearRedisCacheView, authentication_classes = [] (federated_identity/utils.py:397-398) - unauthenticated cache reset; noted for completeness.

Frontend usage

apps-frontend + iam-frontend reference 6/82 latest IAM routes directly (token, refresh, logout, profile-type flows); most other endpoints are consumed by the other 15 services via internal auth or are admin-surface. The cross-reference count is a floor - every module's auth backend calls token/verify indirectly.
