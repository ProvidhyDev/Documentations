ProductManagement . Stock Adjustment

Stock additions and deductions with an approval workflow (draft -> submitted -> approved / cancelled / rejected). The StockAdjustment model (db_table StockAddition) holds items (StockAdjustmentItem); approving a deduction commits stock out of the ledger, approving an addition commits stock in. Two generations of the workflow endpoints coexist (v1 and the revamped v2); the revamped views are the live ones and the v1 handlers are kept registered. The status change is the only adjustment operation that touches the stock ledger, and it raises a Kafka event on approve/cancel.

All routes below are relative to /api/inventory/ except where noted; Source: inventory/urls.py, inventory/views.py, inventory/serializers.py @ edd7d596.

Catalog note: the catalog marks the v1 adjustment routes (detail, status, cancel-submission, delete, list, search) as superseded and lists a commented-out v2 router registration as /api/inventory//adjustment/v2/{id}, but every route in the map above is live in inventory/urls.py:7 and :185-244. They are documented here as one version family; see report for the discrepancy.

1. GET/POST /adjustment/ (v1)

  • View: StockAdjustmentViewset (ViewSet) registered on the DefaultRouter - inventory/urls.py:7, views.py:286.
  • Auth: IAM + HasPermission, feature PR1001 STOCK_ADJUSTMENT; GET -> view, POST -> add_edit (views.py:287-297).
  • GET: params status (required, 404 UNKNOWN_STATUS, views.py:301-305) and adjustment_type; user-scoped listing (helper.user_filter) of StockAdjustment rows, paginated StockAdjustmentListSerializer (views.py:299-317).
  • POST: deduction type requires reason (views.py:322-328); optional convert flag reshapes line items (InventoryItemConverter, views.py:332-337); per-item required-field validation incl. new-batch batch_number (views.py:339-348); StockAdjustmentSerializerWriteOnly creates the header + items (views.py:351-368); 201 { id, unique_id }.
  • The viewset defines no detail methods, so the catalog's /api/inventory/adjustment/{id} detail route (all six methods) does not actually resolve - flag.

2. GET/POST /adjustment/v2/ (latest)

  • View: StockAdjustmentViewset2 - inventory/views.py:375 (route urls.py:186-188).
  • Auth: IAM + HasPermission + EbillingBlockPermission (ebilling tenants blocked, views.py:537), PR1001; GET -> view, POST -> add_edit (views.py:376-395).
  • GET: same listing contract as route 1 (views.py:396-440).
  • POST: revamped create - items may carry a single batch_info object; revamped rows are created via StockAdjustmentSerializerWriteOnly2 and the header is flagged revamped (views.py:441-470); deduction still requires reason.
  • Response: 201 { id, unique_id, message }.

3. GET/POST /adjustment/detail//

  • View: StockAdjustment - inventory/views.py:589 (route urls.py:189-193).
  • Auth: IAM + HasPermission + EbillingBlockPermission (views.py:588), PR1001; GET -> view, POST -> add_edit (views.py:590-608).
  • GET: tenant-scoped row with detail user-filter (views.py:610-615); StockAdjustmentSerializerReadonly; when ?convert=true and the row is not revamped, items are reshaped to line-item format (views.py:616-630); 404 ADJUSTMENT_NOT_FOUND (views.py:594-601).
  • POST: update allowed only in draft (serializer enforces); required-field validation differs for revamped vs classic rows (views.py:648-677); saves via StockAdjustmentSerializerWriteOnly2 for revamped rows else WriteOnly (views.py:687-697); 200 { id, unique_id, message }.

4. POST /adjustment/status// (v1)

  • View: StockAdjustmentStatusAlter - inventory/views.py:957 (route urls.py:194-198).
  • Auth: IAM + HasPermission, PR1001; submit keeps add_edit, every other status change requires approve_cancel (views.py:985-992).
  • Request: { status: submit_for_approval | approved | cancelled }.
  • Processing: the tenant's APPROVAL_WORK / FLOW configuration decides basic vs custom flow - 503 when absent (views.py:1088-1108); submit (draft -> submitted) holds stock - available decremented per item and batch total, AVAILABLE_NEGATIVE guard, hold recomputed (views.py:1121-1175), per-product stock_keeping resolved via the self product check endpoint (views.py:1110-1119); approve (draft = self-approve, submitted = approve by the approval_user - views.py:1000-1026) commits the movement - deduction: total (and available) decremented, addition: both incremented (deduction_condition + addition/deduction cases, views.py:1293-1406, 1407-1471); cancel reverts the movement per prior status (views.py:1472-1633).
  • Side effects: activity log (custom.create_activity_log -> Events, views.py:1201, 1436, 1609) and Kafka adjustment event on approve/cancel (self.call_kafka, views.py:1459, 1621, 1634-1647).
  • Response: 200; 400 on invalid status / negative stock / not authorized for the action.

5. POST /adjustment/status/v2// (latest)

  • View: StockAdjustmentStatusAlter2 - inventory/views.py:1663 (route urls.py:199-203).
  • Auth: same as route 4 (views.py:1664-1699).
  • Processing: same state machine as route 4 over revamped rows - identical method structure (post dispatch views.py:1789-1816, submit cases views.py:1829-1909, deduction_condition views.py:2114, approved views.py:2130-2196, cancelled views.py:2197-2368); stock movements use the revamped item shape (single batch per item).
  • Side effects: activity log (views.py:1910, 2161, 2344) and Kafka (views.py:2184, 2356, 2369-2382).

6. POST /adjustment/cancel-submission// (v1)

  • View: StockAdjustmentSubmissionRevert - inventory/views.py:2398 (route urls.py:204-208).
  • Auth: IAMAuthenticationBackendInventory (views.py:2399); no permission class - authorization is enforced in the body: only the creator or the approval_user of a submitted row may act (views.py:2426-2429).
  • Request: { type?: rejection, comment? }.
  • Processing: deduction items only - the held stock is released (available restored per batch and on the BatchInventoryTotal, inventory_calc_revert, views.py:2430-2460, 2520-2523); the row returns to draft with approval_date cleared (views.py:2461-2462). With type=rejection by the approval_user: rejection activity log + notification (custom.send_notification -> Events), rejected flag/comment/by/date set (views.py:2463-2488); otherwise a cancel-submission activity log and approval_user cleared (views.py:2499-2512).
  • Response: 200 message; 400 when the row is not submitted or the caller lacks the role (views.py:2513-2518).

7. POST /adjustment/cancel-submission/v2// (latest)

  • View: StockAdjustmentSubmissionRevertRevamped - inventory/views.py:2527 (route urls.py:209-213).
  • Auth: IAM + EbillingBlockPermission (views.py:2526-2528); same in-body role check (views.py:2555-2558).
  • Processing: revamped single-batch variant of route 6 - releases the held quantity on the item's batch row and the batch total (views.py:2559-2587), then the identical rejection / cancel-submission branches (views.py:2590-2639).
  • Response: 200 message; 400 otherwise (views.py:2640-2645).

8. POST /adjustment/delete//

  • View: StockAdjustmentDelete - inventory/views.py:2654 (route urls.py:214-218).
  • Auth: IAM + HasPermission + EbillingBlockPermission; anomaly: the required feature is SALES_ORDER add_edit instead of STOCK_ADJUSTMENT (views.py:2656-2658).
  • Request: none beyond the pk.
  • Processing: only draft rows created by the caller can be deleted - items and header removed in one atomic (views.py:2669-2681).
  • Response: 200 { message }; 400 otherwise (views.py:2682-2685).

9. GET /adjustment/list/

  • View: StockAdjustmentForAccounting - inventory/views.py:712 (route urls.py:219-223).
  • Auth: IAM + HasPermission, PR1001, view (views.py:712-730).
  • Request: ?username.
  • Processing: submitted (SUBMIT_FOR_APPROVAL) adjustments of the tenant, user-filtered, serialized with StockAdjustmentListSerializer (views.py:736-748) - consumed by the Accounting service for the adjustment ledger view.
  • Response: 200 list.

10. GET /approval-list/

  • View: StockAdjustmentApprovedList - inventory/views.py:730 (route urls.py:224-228).
  • Auth: internal - password in query via validate_internal_pass (views.py:730-735); no IAM.
  • Request: ?password, ?tenant_id, ?username.
  • Response: 200 list of that tenant's submitted adjustments for the approval screen of other modules (same serializer as route 9, views.py:737-748).

11. GET /adjustment/search/

  • View: AdjustmentSearchView - inventory/views.py:538 (route urls.py:229-244, incl. a <str:version>/ suffix that the catalog flattens to /api/inventory/<str:version>/).
  • Auth: IAM + HasPermission, PR1001; GET -> view (views.py:539-550).
  • Request: status (required, 404 otherwise, views.py:560-562), q over reason / entry_date / entry_by / unique_id (views.py:571-577), plus the FilteredAPIViewMixin filter set - StockAdjustmentFilterSetV2 when the request version is v2 (views.py:552-554, 543).
  • Processing: tenant-scoped (via the filter set) StockAdjustment rows, user-filtered, paginated StockAdjustmentListSerializer (views.py:556-585).
  • Response: 200 paginated list.

12. POST /api/dashboard/add-fiscal-year/

  • View: AddFiscalYearStockAdjustmentApiView - inventory/views.py:5969, mounted under the dashboard app (dashboard/urls.py:26-30; import at dashboard/urls.py:4).
  • Auth: InternalRequestPermission (views.py:5970).
  • Request: { data: { tenant_id: fiscal_year, ... } }.
  • Processing: stamps the fiscal year onto every StockAdjustment row of the listed tenants (bulk_update, batch 1000, views.py:5973-5982) and onto the STA id-ledger rows (views.py:5984-5991) - called by the fiscal-year closing flow of other services.
  • Response: 200 { message }.

Side effects (all endpoints)

  • Activity log via the Events service (POST {EVENTS}api/activity_log/create-activity-log/) on create, update, submit, approve, cancel, reject, cancel-submission (custom.create_activity_log).
  • User notification on rejection via the Events service (custom.send_notification, views.py:2474-2482, 2601-2609).
  • Kafka events (adjustment created / approved / cancelled) via the producer connection (self.call_kafka, views.py:1459, 1621, 1634-1647 and the v2 twins).
  • Stock-ledger mutations only on status change (and on cancel-submission for deductions) - see stock.md for the ledger model.
  • Per-product stock_keeping lookups via the self product check endpoint (PRODUCT_CHECK_SERVICE_API, views.py:1110-1119, 2410-2419, 2539-2548).
  • Approval flow configuration from the Configuration service (APPROVAL_WORK / FLOW, views.py:1088-1093).

Frontend usage (apps-frontend @ production)

Per fe_usage.json, none of the adjustment routes are referenced by the frontend scan (all in unusedLatest) - the scan floor does not cover this module; the adjustment screens are served by the ERP app through these endpoints (see report).

Superseded / legacy routes (not documented)

  • The v1 status, cancel-submission and router-list routes (map rows 1, 4, 6) remain live but are superseded in practice by their revamped twins (rows 2, 5, 7); they are documented above for the catalog's sake rather than as separate legacy entries.
  • No adjustment route is removed from the catalog's superseded list without a live twin - see the catalog note under the endpoint map.
