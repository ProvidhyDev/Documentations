Business Flows (Traced)

At runtime ProductManagement is both a user-facing master service and the stock engine of the ERP. ERP users create and edit products (with UOM, categories, batches, campaigns) through IAM-authenticated endpoints, and correct stock manually through the stock-adjustment document, which runs a configurable approval workflow (basic vs custom flow, self-approval vs designated approver) and moves the stock ledger when it is approved. The Sales and Purchase services are the other main writers: they hold, commit, release and reverse stock for orders, delivery notes, invoices, returns and GRNs through an internal password-gated protocol of verification and manipulation endpoints, all operating on the same two ledger structures - Inventory rows (per product, or per product+batch) and one BatchInventoryTotal row per batch-managed product. Every state change leaves a trail: activity logs and notifications go to the events service, product and adjustment lifecycle events go to Kafka through an internal producer endpoint, and stock-adjustment approval/cancellation additionally queues a dev-only Celery task that posts the adjustment journal to Accounting.

Product creation - POST /api/product/v2/

What happens: creating a product is a cross-service flow. The view reads the tenant's batch-serial configuration from the Configuration service (the request fails with 503 if it is missing), computes the required-field set from the product type (goods need UOM and category; services may not manage inventory; independent-stock goods need an expiry date when the expiry compulsion is on), enforces a unique product name per tenant, sanitizes the payload through Configuration, optionally verifies a preferred supplier through a self-call, persists the product together with any secondary unit conversions and a ProductVariant row, and - for goods that manage stock - seeds the stock ledger by calling its own inventory create endpoint with the opening quantity. Finally it publishes a product_creation Kafka event and writes a CREATION activity log.

  1. Auth: IAMAuthenticationBackendProduct (product/views.py:746, dashboard/auth_backends.py:23-51) - IAM token must include the PRODUCT_MASTER service PR900 and email-verified status; HasPermission (dashboard/auth_backends.py:98-130) with required_feature_permission PR901 PRODUCT_CREATION (product/views.py:747) and required_action_permission switched in initial() - POST to add_edit, GET to view (product/views.py:761-766). The v2 handler carries the same gate (product/views.py:1100-1121).
  2. Configuration gate: get_configuration for PRODUCT_FLOW / BATCH_AND_SERIAL (product/views.py:1133-1143) - 503 CONFIGURATION_NOT_FOUND when absent; the title and compulsion are read (product/views.py:1145-1148).
  3. Type-driven validation: goods add uom and product_category to required fields (product/views.py:1154-1156); service with manage_inventory true is rejected (product/views.py:1158-1162); independent-stock goods with expiry compulsion true need expiry_date (product/views.py:1164-1170); fixed-asset normalization runs before required-field validation (product/views.py:1173); empty-string reorder_quantity is rejected and negative values rejected (product/views.py:1175-1180); helper.valid_required_data enforces the rest (product/views.py:1181, dashboard/helper.py:358).

  5. Uniqueness: is_unique on name scoped to the tenant, case-insensitive (product/views.py:1236, dashboard/helper.py:196-219).

  9. The superseded v1 handler POST /api/product/ (product/views.py:745-1097) is structurally identical but has no expiry-configuration gate, no sellable/manage_inventory boolean handling and its GET implementation is fully commented out (product/views.py:768-883), so GET on the v1 route returns 405.

Product update - POST /api/product/detail/<int:pk>/

What happens: the detail endpoint serves GET (view permission) and POST (add_edit). An update is tenant-scoped, re-reads the same batch-serial configuration, sanitizes the payload, fills any empty GL mapping from the tenant's accounting-automation configuration, replaces the ProductVariant link set when variants are passed, and publishes a product_edition Kafka event. GL ids, UOM and the non-editable fields are stripped from the update payload, so the update is partial by construction.

Trace

  1. Auth and dispatch: same backend and feature as creation; initial() switches POST to add_edit (product/views.py:1533-1538, 1468-1472).
  2. Lookup: product fetched with select_related for category, subcategory, uom and campaign, scoped to request.auth (product/views.py:1474-1480); missing product yields 404 on GET and 400 INVALID_OBJECT on POST (product/views.py:1549-1551, 1671-1674).
  3. Configuration and expiry: BATCH_AND_SERIAL configuration read again; with expiry compulsion true a missing expiry_date fails (product/views.py:1558-1575).
  4. Sanitize: ProductSerializer.update posts to SANITIZE_URL and re-injects asset_category from context (product/serializers.py:1061-1064).
  5. GL completion: product_gl_addition_creation - fixed assets take the asset category as expense GL and clear income and inventory GL; otherwise empty expense/inventory/income GL slots are filled from the PRODUCT_FLOW AUTOMATION configuration titles PRODUCT_EXPENSE, PRODUCT_INVENTORY, PRODUCT_INCOME or SERVICE_* (dashboard/custom_functions.py:74-113).
  6. Variant sync: when product_variant is passed, the single ProductVariant row for the product is get_or_create'd and its variant multi-value set is cleared then re-set (product/serializers.py:1093-1102). Note the secondary_units sync block is commented out, so detail updates never touch ProductUnitConversion rows (product/serializers.py:1074-1091).
  7. Edit log: changed fields are diffed via edit_logs for the activity log; GL fields are excluded from the diff (product/views.py:1509-1518).
  8. Events and response: call_kafka PRODUCT_EDITION (product/views.py:1659-1665); 200 with the serialized product (product/views.py:1670).

Side effects

  • Product row updated; ProductVariant and its variant links replaced when passed (product/serializers.py:1093-1102).
  • GL mapping fields possibly filled from configuration (dashboard/custom_functions.py:74-113).
  • Kafka product_edition event (product/views.py:1659-1665).
  • Activity log EDITION with field diffs (product/views.py:1482-1490).

Stock adjustment - the lifecycle

The stock-adjustment document is the manual correction path for the stock ledger. The revamped v2 family is the live one (POST /api/inventory/adjustment/v2/ create, POST /api/inventory/adjustment/status/v2// status, POST /api/inventory/adjustment/cancel-submission/v2// revert; inventory/urls.py:185-245); the v1 status and cancel-submission routes are still routed but superseded (see Superseded routes). Adjustment is either an ADDITION (stock in, e.g. found goods) or a DEDUCTION (stock out, e.g. damaged goods), and DEDUCTION additionally requires a reason. Two stock-keeping methods matter: BATCH products write both the per-batch Inventory row and the BatchInventoryTotal rollup; independent products write the Inventory row only. The approver model differs from Accounting: approval is SELF (the creator, from DRAFT) or OTHER (the designated approval_user, from SUBMIT_FOR_APPROVAL).

Trace (create - POST /api/inventory/adjustment/v2/)

  1. Auth: IAMAuthenticationBackendInventory + STOCK_ADJUSTMENT feature; POST requires ADD_EDIT action, GET VIEW (inventory/views.py:376-386).
  2. Fiscal-year guard on entry_date (inventory/views.py:415); e-billing tenants must pass a reference (inventory/views.py:416-417).
  3. Item validation: every item needs product_id, quantity, rate; batch items need batch_number for new batches (inventory/views.py:438-442).
  4. StockAdjustmentSerializerWriteOnly2 validates and creates the StockAdjustment + items as DRAFT (inventory/views.py:450-459); nothing moves in the stock ledger at create time.

Trace (status - POST /api/inventory/adjustment/status/v2//)

StockAdjustmentStatusAlter2 (inventory/views.py:1663). initial() picks the action permission: submit requires ADD_EDIT, all other transitions APPROVE_CANCEL (inventory/views.py:1691-1698).

  1. Load the tenant-scoped adjustment (inventory/views.py:1668-1675), fiscal-year guard (inventory/views.py:1793).
  2. Fetch the tenant approval-work configuration (inventory/views.py:1796-1801); no config = 503 (inventory/views.py:1816).
  3. BASIC flow (inventory/views.py:1760-1777): submit - creator only, from draft, requires approval_user id; approve - SELF (draft, creator) or OTHER (SFA, approval_user); cancel - from approved or from SFA (approval_user); anything else 400 INVALID_STATUS.
  4. CUSTOM flow (inventory/views.py:1779-1787): no submit; approve directly from draft (compulsion check when compulsion=true, inventory/views.py:1684-1689) or cancel.
  5. On submit, DEDUCTION entries HOLD stock: per item, the batch case moves primary_quantity from available to hold on both the Inventory row and the BatchInventoryTotal row (inventory/views.py:1829-1858); the independent case does the same on the Inventory row and also reduces its amount (inventory/views.py:1860-1876). ADDITION entries hold nothing. The hold makes the stock unavailable to concurrent sales while the document awaits approval. Negative available is rejected (inventory/views.py:1841-1842).
  6. On approve, stock is finally committed: DEDUCTION - from draft the draft-case writers reduce available and total permanently (inventory/views.py:1949-1990, 2114-2126); from SFA the approval-case writers convert the hold into a permanent total reduction (inventory/views.py:2114-2126). ADDITION increases total and available (inventory/views.py:1942-1946, 2139-2150).
  7. On cancel, the move is reversed: cancelling an APPROVED adjustment restores the total and available quantities (inventory/views.py:2197-2240); cancelling from SFA only releases the hold (available restored, hold recomputed) because the total was never touched (inventory/views.py:2240-2280).
  8. Side effects on approve: activity log (inventory/views.py:2161-2167), a Kafka approval payload (inventory/views.py:2180-2186), and - only when the tenant has a PRODUCT_FLOW automation config AND the service runs with DEVELOPMENT enabled - a Celery journal_creation_task that posts the adjustment journal to Accounting (inventory/views.py:2169-2178).
  9. Notification/activity log on submit (inventory/views.py:1902-1916).

Trace (cancel-submission / rejection - POST /api/inventory/adjustment/cancel-submission/v2//)

StockAdjustmentSubmissionRevertRevamped (inventory/views.py:2527). Only while in SFA, and only by the creator or the designated approval_user (inventory/views.py:2555-2558). For DEDUCTION it releases the hold (batch: Inventory + BatchInventoryTotal, independent: Inventory; inventory/views.py:2559-2587). With body type=rejection by the approval_user, the document stays draft but is flagged rejected with rejected fields, a rejection activity log and an ERROR notification (inventory/views.py:2590-2615).

Trace (delete - POST /api/inventory/adjustment/delete//)

StockAdjustmentDelete (inventory/views.py:2654): draft only and only by the creator (inventory/views.py:2673-2675); items and the document are deleted in one transaction. Note the permission is checked against the SALES_ORDER feature, not STOCK_ADJUSTMENT (inventory/views.py:2657) - a copy-paste quirk, so the effective gate depends on which feature the tenant granted.

Stock API - internal verify/manipulation protocol

Sales and Purchase move stock through this service via two password-gated endpoint families (shared INTERNAL_PASS, no IAM): verification endpoints that only check availability, and manipulation endpoints that move quantities between available and hold (and on final document commit, out of total). The live set (inventory/urls.py): purchase-verification, sales-verification, quantity-verification (delivery-note ready check), note-return-verification, sales-invoice-verification, sales-return-verification; and the manipulators: check-manipulation (sales order), drn-manipulation (delivery note), note-return-manupulation, sales-invoice-manupulation, sales-invoice-manupulation-revert, sales-return-manupulation, sales-return-manupulation-revert, purchase-invoice-manipulation, purchase-return-manipulation, grn-manipulation, grn-return-manipulation - most with the v2/revamped route superseding the v1 path.

Trace (sales order submit - verification then hold)

  1. Sales calls POST /api/inventory/quantity-verification/ with password, tenant_id, entry_status and items; DeliveryInvoiceVerification (inventory/views.py:2784) checks per item: for submit the quantity must fit in available_quantity, for approve it must fit in total_quantity; batch items are checked on each per-batch Inventory row plus the BatchInventoryTotal rollup (inventory/views.py:2785-2853). Read-only - it never writes.
  2. Sales then calls POST /api/inventory/check-manipulation/; SalesOrderInventoryCheckManipulation (inventory/views.py:2856) loads the tenant negative-inventory config (inventory/views.py:2859-2861), and for submit/approve subtracts the quantity from available_quantity and recomputes hold_quantity = total - available on the Inventory row or the BatchInventoryTotal row for batch items (inventory/views.py:2868-2906).
  3. A negative available is rejected unless the tenant has the negative-inventory config enabled (inventory/views.py:2882-2886, 2897-2901).
  4. On cancel_submission or cancelled the mirrored branch restores the quantities via inventory_ins_increment (inventory/views.py:2908-2929).
  5. DeliveryNoteManipulation (inventory/views.py:2940) is the same hold/release pattern for delivery-note documents.

Campaign management

Campaigns are product discount/pricing records (type + value with from/to dates) referenced by products.

  • Update POST /api/product/campaign/detail// - IAM + PRODUCT_CAMPAIGN, POST requires ADD_EDIT; blocked for inactive campaigns (product/views.py:2714-2718); requires name, from_date, to_date, type, non-empty value; saves through the serializer and writes an EDITION activity log with the diff (product/views.py:2707-2733).
  • Bulk status POST /api/product/campaign/inactive/ - IAM + PRODUCT_CAMPAIGN, POST requires ACTIVE_INACTIVE; flips active_status for a list of ids, activity log per row, and returns 404 mid-loop on a missing id - the whole transaction rolls back, so it is all-or-nothing (product/views.py:2770-2800).
