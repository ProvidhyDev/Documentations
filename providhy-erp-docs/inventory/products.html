ProductManagement . Products

Product master (with product batches), unit-of-measurement (UOM) master, and the GraphQL endpoint of the product app. Products carry the GL account mapping (expense / income / inventory GL), the stock model (independent vs batch), campaign linkage, and secondary unit conversions. Categories are documented separately (categories.md); campaigns in campaign.md. Variant and product-variant routes exist in the same app but the feature is not used in ProvidhyERP - they are listed in overview.md under Not used and not documented here.

All routes below are relative to /api/product/ unless noted; Source: product/urls.py, product/views.py, product/serializers.py, product/schema.py @ edd7d596.

1. POST /graphql/

  • View: csrf_exempt graphene_django GraphQLView mounted directly at product/urls.py:9 with the schema from product/schema.py (no APIView subclass).
  • Auth: none at the endpoint. The schema's two resolvers (product, all_products) are decorated with has_permission(ServiceChoices.PRODUCT_MASTER, ActionChoices.VIEW) (schema.py:37-55); all fields of Product, ProductCategory, UOM, Campaign are exposed (fields = all).
  • A CustomGraphQLView class implementing APIKeyAuthentication exists (views.py:4725-4737) but is not referenced by any URL - dead code. The root-level /graphql/ mount the catalog lists is commented out (core/urls.py:11), so /api/product/graphql/ is the only live GraphQL endpoint.

8. POST / (v1 create, legacy)

  • View: ProductListCreate - product/views.py:745 (route urls.py:39). The GET handler is commented out (views.py:768-814); the view is create-only.
  • Auth: IAM + HasPermission, feature PR901 PRODUCT_CREATION; POST -> add_edit (views.py:746-748, 761-766).
  • Request: full product payload; expiry configuration is fetched from the Configuration service (PRODUCT_FLOW / BATCH_AND_SERIAL) - 503 CONFIGURATION_NOT_FOUND when absent. Goods require uom + product_category; services must not manage inventory; independent stock keeping plus expiry compulsion requires expiry_date (pattern shared with v2, views.py:1150-1170).
  • Processing: ProductSerializer.create (serializers.py:1054-1059); a supplier-existence check against the Projectmaster service is attempted but the response is compared with if supplier_response == 204, i.e. a Response object is compared to an integer - the condition is always false and the branch raises SOMETHING_WENT_WRONG, so this v1 create path is effectively dead/broken (views.py:1059-1063); activity log and Kafka product-creation event on success.
  • Status: superseded by route 9 in practice; documented here because the route is still registered.

  • Processing: streams all products of the tenant in chunks as NDJSON lines via ProductUomSerializer (id, uom, secondary_units, serializers.py:2056-2067) (views.py:5053-5058).
  • Response: 200 streaming application/json body.

33. POST /uom-import/

  • View: ProductUnitImportValidationCreation - product/views.py:5061 (route urls.py:211-215).
  • Auth: InternalRequestPermission.
  • Request: { tenant_id, data: [rows with name, item_code, uom, secondary_unit, conversion_rate, remarks] } with rows for one product continuing under a blank name (views.py:5139-5158); query create=true switches from validation to creation.
  • Processing (create): for each matched product, missing UOMs are created and ProductUnitConversion rows are bulk_created (views.py:5068-5101).
  • Processing (validate): products not found are returned in error_data with a remark, the rest in valid_data, both reshaped into the single-unit migration format (views.py:5160-5215).
  • Response: 200 { valid_data, error_data } or { message: "Created" }.

34. POST /change-case/

  • View: ProductChangeCase - product/views.py:5218 (route urls.py:226).
  • Auth: InternalRequestPermission.
  • Request: { fields: [field names], case: upper|lower (400 otherwise, views.py:5246-5250), tenant_id } (views.py:5222).
  • Processing: single bulk .update() applying Lower/Upper to the named product fields for the tenant (views.py:5232-5244).
  • Response: 200 { message, updated_rows }.

35. GET /duplicate-batch/

  • View: CheckForDuplicateBatch - product/views.py:5455 (route urls.py:227).
  • Auth: IAMAuthenticationBackendProduct only (no-perm) (views.py:5456).
  • Request: ?batch_number.
  • Response: 400 { error: "Product 'X' already has this batch number!" } when any batch of a tenant product carries the number (views.py:5460-5470), else 200 empty - used as a pre-flight check by document screens.

36. POST /deduplicate-unique-id/

  • View: ProductUniqueIdDeduplicateView - product/views.py:5257 (route urls.py:228-232).
  • Auth: InternalRequestPermission.
  • Request: { tenant_id? (scope), dry_run, batch_size (default 2000, views.py:5297-5307) }.
  • Processing: finds (tenant_id, unique_id) groups with more than one product (views.py:5309-5318); keeps the oldest row and renumbers the rest from the higher of the PRD ID-ledger max and the max number found on Product rows (views.py:5339-5373); dry_run reports without writing (views.py:5431-5432); otherwise one atomic bulk_create of new ID-ledger rows plus bulk_update of the products, 409 on a concurrent-update IntegrityError (views.py:5434-5450).
  • Response: 200 { message, tenants_affected, duplicate_groups, products_reassigned, dry_run, reassignments }.

37. POST /product-batch/check-multiple/

  • View: ProductBatchCheckMultiple - product/views.py:2878 (route urls.py:60-64).
  • Auth: InternalRequestPermission (views.py:2879).
  • Request: { batch_ids: [ids], tenant_id }.
  • Response: 200 map { batch_id: { unique_id, batch_number, expiry_date } } via ProductBatchMinimalSerializer (views.py:2890-2899).

38. POST /product-batch/check/

  • View: ProductBatchCheck - product/views.py:2965 (route urls.py:134-136).
  • Auth: the class sets permisson_classes = [AllowAny] - a misspelling DRF ignores (views.py:2966), so the effective gate is the body password check (views.py:2971), else 401.
  • Request: { password, tenant_id, product_id, batch_id: [ { id?, ...rate/quantity/return_count/... } ], inventory_data?: bool }.
  • Processing: for each entry with a known id, re-fetches the batch under the product and, when inventory_data is set, fetches available/total quantity from the self inventory quantity endpoint (views.py:2979-3011); unknown ids are passed through (views.py:3022-3023).
  • Response: 200 merged batch list; 204 when a batch does not exist (views.py:3027-3028).

39. POST /product-batch/detail/

  • View: ProductBatchAddUpdate - product/views.py:2383 (route urls.py:124-128).
  • Auth: IAM + HasPermission, PR901; POST -> add_edit (views.py:2384-2387, 2418-2423).
  • Request: batch payload { product, batch_number, manufacture_date?, expiry_date?, product_life? } (ProductBatchSerializer).
  • Processing: the tenant's expiry configuration must exist (503 CONFIGURATION_NOT_FOUND otherwise, views.py:2439-2461); ProductBatchSerializer sanitizes via the Configuration service and enforces batch-number uniqueness per tenant (serializers.py:473-516); batch-scoped activity log (views.py:2389-2398).
  • Response: 200 with the saved batch data.

40. GET /product-batch/search/select/<product_id>/

  • View: ProductBatchSearchSelectAPIView - product/views.py:4766 (route urls.py:129-133).
  • Auth: IAM + HasPermission, PR901; GET -> view (views.py:4767-4770).
  • Request: path product_id; q over batch_number / expiry_date / manufacture_date / unique_id (views.py:4784-4788).
  • Processing: ProductBatchSearchSerializer appends available/total quantity per batch via the self inventory quantity endpoint (serializers.py:1131-1155).
  • Response: 200 paginated list.

41. POST /product-batch/create-endpoint/

  • View: BatchCreateEndpoint - product/views.py:3059 (route urls.py:137-141).
  • Auth: no class; body password must equal the shared password (views.py:3061-3062), else 401.
  • Request: { password, tenant_id, entry_by, method, quantity, product_id, batch_number, ...batch fields, fiscal_year? }.
  • Processing: reuses an existing batch with the same number when it belongs to the same product (400 otherwise, views.py:3084-3111); new batches go through ProductBatchSerializer (sanitize + uniqueness, serializers.py:498-516); for new batches only, inventory is seeded by POSTing to the self create-endpoint (INVENTORY_CREATE_ENDPOINT -> self /api/inventory/create-endpoint/, views.py:3131-3138); Kafka NEW_BATCH_CREATION event for new batches (views.py:3152-3158).
  • Response: 200 { batch_id, batch_number, expiry_date, product_life, unique_id }.

42. POST /product-batch-line-item/

  • View: ProductBatchForLineItem - product/views.py:4797 (route urls.py:119-123).
  • Auth: InternalRequestPermission (views.py:4798).
  • Request: { product_id }.
  • Response: 200 list of the product's batches with available/total quantity (ProductBatchSearchSerializer, views.py:4803-4807) - for document line-item batch pickers in other services.

Side effects (all endpoints)

  • Activity log via the Events service (POST {EVENTS}api/activity_log/create-activity-log/, helper.py:100) for UOM / product / batch create, update, active-inactive.
  • Sanitization via the Configuration service (POST {CONFIGURATION}api/sanitization/form-data/, helper.py:102) on every UOM, product and product-batch create/update; a failed sanitize aborts the write (SANITIZE_ERROR).
  • Accounting GL-mapping check (helper.GL_MAPPING_SERVICE_CHECK) on product reads (per product, serializers.py:843) and in the migration import (views.py:3912).
  • Self inventory calls: quantity reads through helper.query_inventory_data -> self /api/inventory/inventory-data/ (helper.py:82, INVENTORY_API points back at this service) and INVENTORY_DATA_QUANITY_SERVICE_API -> self /api/inventory/inventory/data/ (helper.py:83); inventory seeding through self /api/inventory/create-endpoint/ and /api/inventory/bulk-create/ (helper.py:59, :67).
  • Kafka events via the producer connection (PRODUCER_CONNECTION_URL) on product create/update and new batch creation (call_kafka, views.py:1660-1665, 3152-3158; serializers.py:2009).
  • Cross-service reads: Sales and Purchase recent-transaction endpoints for the timeline (helper.py:113-115); Accounting fixed-asset accounts in the list screen (views.py:3297-3304).

Frontend usage (apps-frontend @ production)

Per fe_usage.json, the product-area routes referenced by the frontend scan are: /uom/, /uom/search/, /uom/search/select/, /search/, /detail//, /list/, /recent-transactions/v2//, /duplicate-batch/, /product-batch/detail/. This is a floor, not a ceiling; every other route on this page is marked unused by the scan (mostly internal S2S endpoints consumed by other services).

Superseded / legacy routes (not documented)

  • GET /api/product/recent-transactions/<int:pk>/ (v1, ProductRecentTransaction - views.py:4864) - superseded by the cursor-paginated v2 (route 30); the internal variant (route 31) still subclasses the v1 handler.
