ProductManagement . Dashboard

Shared infrastructure routes of the ProductManagement service, mounted at /api/dashboard/: static choice lists, the ERP home-dashboard widgets, tenant data deletion, fiscal-year closing / opening-balance operations, and the Kafka reconciliation endpoint. The service has no warehouse or transfer module and no miniapp app - the SITESPEC pages for warehouse and miniapp do not apply; the only transfer-related endpoint is the fiscal-year transfer closing endpoint below (transfer-closing/), and there is no stock transfer flow in this service.

Source: dashboard/urls.py, dashboard/views.py @ edd7d596.

Endpoint map

# Method Path Purpose Auth
1 GET /system-choices/ Static choice lists for forms AllowAny (no auth)
2 GET /analytics/ Home dashboard widgets (counts, reorder, expiring) IAM + PRODUCT_MASTER (no-perm)
3 GET /approval-list/ Pending adjustment approvals for the user IAM + PRODUCT_MASTER (no-perm)
4 POST /tenant-data-deletion/ Delete all data of tenant(s) internal
5 POST /set-variant-path/ Rebuild variant tree paths internal (excluded feature)
6 POST /opening-info/ Opening balances per tenant internal
7 POST /transfer-closing/ Fiscal-year closing: rewrite opening balances internal
8 POST /check-reconciliation/ Resend unsynced products / adjustments internal
9 POST /add-fiscal-year/ Stamp fiscal year onto adjustments internal - documented in adjustment.md (route 12)

1. GET /system-choices/

  • View: ProductChoiceView - dashboard/views.py:51 (route urls.py:9).
  • Auth: AllowAny - no authentication, no permission check (views.py:50-51); returns only static choice labels.
  • Response: 200 dict of value/label lists - valuation_method, active_status, stock_keeping_method, adjustment_type, reason, entry_status, campaign_type, product_type, vat_choices (views.py:53-98) - consumed by every form in the module.

2. GET /analytics/

  • View: DashboardView - dashboard/views.py:102 (route urls.py:10).
  • Auth: IAMAuthenticationBackendProduct only - no HasPermission (views.py:103).
  • Processing: active product count and in-window active campaign count (views.py:148-156); up to 5 products with reorder_quantity > 0 whose available quantity (self inventory-data call, views.py:111-121) has fallen to or below the reorder level (ProductAnalytics, views.py:141-143); up to 5 products with batches expiring within 90 days (ProductAnalyticsBatch, views.py:132-146).
  • Response: 200 { count: { product, campaign }, reorder_products, expiring_products }.

3. GET /approval-list/

  • View: StockAdjustmentApprovedListDashboard - dashboard/views.py:169 (route urls.py:11-15).
  • Auth: IAMAuthenticationBackendProduct only (views.py:170).
  • Processing: the tenant's submitted adjustments, split into addition / deduction, user-filtered to what this user may act on, capped at 5 each (views.py:172-204).
  • Response: 200 { addition_adjustments, deduction_adjustments } - the approval widget of the ERP home screen.

4. POST /tenant-data-deletion/

  • View: DeleteTenantDataAPIView - dashboard/views.py:215 (route urls.py:16-20).
  • Auth: InternalRequestPermission (views.py:214).
  • Request: { tenant_id: id | [ids] } - 400 when missing (views.py:231-235).
  • Processing: inside one transaction, deletes in batches of 20000 - BatchInventoryTotal, ProductVariant, ProductBatch, Inventory (views.py:240-283), then Product and ProductUnitConversion (views.py:285-298), then UOM (with raw-SQL deletes of ProductCategory and Variant - views.py:216-228, 300-354), Campaign, the ID ledger and all StockAdjustment rows + items (views.py:309-354).
  • Flag: tenant-wide destructive operation, internal-gated - used by the offboarding / tenant-reset flow.

5. POST /set-variant-path/

  • View: ApplyVariantPathView - dashboard/views.py:371 (route urls.py:21-25).
  • Auth: InternalRequestPermission (views.py:370).
  • Processing: recursively rebuilds the path attribute of every Variant tree (root variants first, views.py:372-389).
  • Note: variant is an excluded feature in ProvidhyERP - see overview.md Not used; listed here for route completeness.

6. POST /opening-info/

  • View: ProductOpeningInfoAPIView - dashboard/views.py:392 (route urls.py:31-35).
  • Auth: InternalRequestPermission (views.py:393).
  • Request: { tenant_id: [ids] } - 404 when no products exist for the tenants (views.py:442-454).
  • Processing: serializes all products with ProductOpeningSerializer (product + batches + secondary units), then overlays opening figures from the Inventory rows - opening_quantity/date/rate/amount per product or per batch depending on stock keeping (views.py:395-440).
  • Response: 200 map { tenant_id: [opening rows] } - consumed by the accounting side of fiscal-year opening.

7. POST /transfer-closing/

  • View: TransferClosingProductAPIView - dashboard/views.py:466 (route urls.py:36-40).
  • Auth: InternalRequestPermission (views.py:467).
  • Request: { product_data: { tenant_id: { fy_id, products: [ { product_id, batch_id?, opening_date, opening_quantity, amount } ] } } } (views.py:469-478).
  • Processing: for tenants without an existing PRODUCT_CLOSING action for that fiscal year (ActionModel idempotency marker, views.py:479-487), rewrites the Inventory opening figures - keeping the latest opening_date (views.py:485-509) - then bulk_updates Inventory (opening_quantity, amount, opening_date) and creates the ActionModel markers (views.py:511-527).
  • Response: 200 { message: "Success updating!" }.

8. POST /check-reconciliation/

  • View: InventoryCheckReportReconcileAPIView - dashboard/views.py:545 (route urls.py:41-45).
  • Auth: InternalRequestPermission (views.py:546).
  • Request: { tenant_id: { last_sync_date?, product?: [ids already synced], adjustment?: [ids already synced] } }.
  • Processing: per tenant, returns up to 500 Product rows (KakfaProductReadSerializer) and 500 approved StockAdjustment rows (KafkaStockAdjustmentSerializer) not yet in the caller's synced id sets, with adjustments ordered FIFO from last_sync_date (views.py:563-653) - lets an external Kafka consumer reconcile its product/adjustment streams.
  • Response: 200 { tenant_id: { product: [...], adjustment: [...] } }.

9. POST /add-fiscal-year/

  • Documented in adjustment.md (route 12) - the view (AddFiscalYearStockAdjustmentApiView, inventory/views.py:5969) is mounted here via dashboard/urls.py:26-30.

Side effects (all endpoints)

  • Route 4 is the only writer (destructive); routes 6-8 read the stock/product/adjustment models; route 7 writes Inventory opening figures and ActionModel markers.
  • Route 2 reads stock figures through the self inventory-data endpoint (helper.query_inventory_data).
  • No journals, notifications or Kafka events are raised by the dashboard app itself (route 8 only serves the reconciliation data; the actual publishing is done by the external consumer).

Frontend usage (apps-frontend @ production)

Per fe_usage.json, /system-choices/ and /analytics/ are the dashboard routes referenced by the frontend scan (the rest of this page are internal or off-screen - a floor, not a ceiling).

Superseded / legacy routes (not documented)

  • None in this area.
