The Merchant Side of the eSewa Miniapp — Feature Guide

For the business person AND the engineer. Each feature: what it is (plain words) → how it works (with the real code path) → diagram → rules & edge cases. Every hop is cited to file:line in the trace docs (03–10) — this guide is the map; those are the survey.

Every API call in this app carries two things: the merchant's login token (JWT) and a one-time 6-digit security code (TOTP, 20-second window). The service checks both with the identity service (IAM) on every single request. Internal service-to-service calls instead use a shared internal password. That's the whole auth story — details in doc 02.

1. Register & log in

What it is. A merchant (or customer) who has an eSewa account opens the miniapp the first time, accepts the terms, and is "registered". From then on they just log in. Their eSewa identity (wallet id) is what identifies them — no separate username/password.

How it works (registration, one time):

  1. App shows terms (fetched from the Website service — out of scope) → user accepts.

  2. App calls IAM POST /api/external/register/ with the eSewa token + the user's external identifier + provider code esewa (doc 03 §5.1).

  3. IAM links/creates the external identity and triggers TMS /api/tenant/external-register/ (doc 08 §5.5), which provisions the merchant's tenant and asks Configuration data-transfer/ to copy the platform's default business rules (chart of accounts, credit settings, fiscal year) into that tenant (doc 09 §6.3).

  4. IAM records a funnel event (onboarding analytics) and Events sends a welcome notification (doc 10 §7.4).

How it works (login, every session):

  1. App calls IAM POST /api/external/token/ (eSewa token + identifier) → gets back an access JWT + refresh JWT (doc 03 §5.2).

  2. The JWT's payload carries: which user, which tenant, merchant/customer type (ESM/ESU), subscribed services, permissions. Every later request sends this JWT + a fresh TOTP code; each service re-verifies with IAM (doc 02 §5).

  3. Token expired? The app auto-refreshes via POST /api/external/token/refresh/ and retries (doc 07 Part B §B.3).

flowchart LR
 A[eSewa app opens miniapp] --> B[Accept terms?]
 B -->|first time| C[IAM register]
 C --> D[TMS creates tenant]
 D --> E[Configuration copies default rules]
 E --> F[Done - logged in]
 B -->|already registered| G[IAM token mint]
 G --> F

Rules & edge cases.

  • The same wallet id can only register once per provider (IAM unique per provider, doc 03 §6).

  • Registration is idempotent: the TMS→Configuration transfer runs once (marker stored in the tenant link, doc 08 §5.5).

  • Known issue: the welcome-notification call hardcodes the wrong module type and can fail silently (doc 10 §11(b)) — registration itself still succeeds.

2. Customers — add, search, edit, delete (no connection needed)

What it is. The merchant keeps a book of customers. A customer can be a plain name+phone ("credit without connection"), or linked to a wallet user ("provider user") so they can later be connected.

How it works:

  1. Add: app → Projectmaster POST /api/miniapp/customer/ {name, mobile?, description, is_provider_user, external_identifier} (doc 06 §5.1). If the merchant ticks "this is a wallet user" and gives the wallet id, a wallet-identity link row is created alongside the customer.

  2. Search/list: GET /api/miniapp/customer/search/ — for each row the backend quietly asks CDXE get-connection/ (internal) whether that customer has an approved connection, and enriches the list (doc 06 §7.2).

  3. Edit: POST /api/miniapp/customer/detail/{id}/ (doc 06 §5.4).

  4. Delete: DELETE /api/miniapp/customer/detail/{id}/ (doc 06 §5.5): the backend first asks Payment "does this customer have a pending payment request?" — if yes, deletion is refused (400). Otherwise it asks Sales to cancel the customer's records and, if it's a wallet user, asks CDXE to terminate the connection — then soft-deletes the customer.

flowchart TD
 A[Add customer] --> B{Wallet user?}
 B -->|no| C[Customer row only]
 B -->|yes| D[Customer + wallet-identity link]
 C --> E[Can extend credit immediately]
 D --> F[Can ALSO send a connection request - section 3]

Rules & edge cases.

  • Credit works fine without a connection — the connection (section 3) only matters for the customer's app seeing the credit and for payment requests to that wallet user.

  • Deletion is blocked while a payment request is pending (doc 06 §5.5); cleanup failures are swallowed (a cleanup task error won't stop the soft-delete — doc 06 §11).

  • "Is this a real wallet user?" validation is a stub in this build: it always answers yes (doc 06 §5.6, §11) — real eSewa user verification isn't wired.

3. Connection requests (merchant → eSewa customer)

What it is. A wallet-linked customer doesn't see the merchant's credit until they're connected. The merchant sends a connection request; the customer approves it in their app.

How it works:

  1. Merchant taps connect → app → CDXE POST /api/miniapp/create-connection/ (doc 05 §5.5).

  2. CDXE checks in parallel: IAM "is that wallet id registered?" + Projectmaster "is that wallet really a customer of this merchant?" (doc 05 §5.5).

  3. CDXE stores the connection as pending with a 5-digit code + a wallet-identity link row, and notifies both sides (doc 05 §7.1).

  4. Customer approves (their app → CDXE approve-reject-connection/{code}/) → connection becomes approved; the customer can now see credit, disputes and payment requests from this merchant. Customer declines → both rows are deleted (doc 05 §7.1).

  5. Merchant lists connections via CDXE get-connection/ / connection/search/; can terminate a connection (connection/terminate/{pk}) — refused while a payment request is pending (doc 05 §5.7).

Rules & edge cases.

  • Connection needs an existing Projectmaster customer with a wallet identity (section 2).

  • Decline is a hard delete — no history (doc 05 §5.6).

  • Terminate keeps history (status=terminated) but is blocked while a payment request is pending (doc 05 §5.7).

4. Credit book — add, edit, delete, view

What it is. A credit record = "customer X owes the merchant Rs Y, payable in N days". This is the heart of the app. The ledger (credit + payments history) and the dashboard totals are all views over it.

How it works:

  1. Add: app → Sales POST /api/miniapp/credit/create/ (multipart: customer, amount, payment term, description, items) (doc 04 §5.2). Sales stores it as a credit record with the customer details embedded (no hard link to Projectmaster), fetches the customer's GL (Account Receivable) mapping from Configuration, and notifies the connected customer via Events + logs the activity.

  2. Edit: POST /api/miniapp/credit/detail/{id}/ (doc 04 §5.4) — editing a disputed credit is how the merchant resolves a dispute (section 7).

  3. Delete: DELETE /api/miniapp/credit/detail/{id}/ (doc 04 §5.4) — only allowed while nothing has been paid against it (remaining == total); deleting also resolves any pending dispute on it.

  4. View: dashboard totals GET credit/overview/; list GET credit/search/; one record GET credit/detail/{id}/; customer's ledger GET credit/ledger/overview/ + GET credit/ledger/ (by customer + date range) (doc 04 §5.1/5.3/5.14/5.15).

  5. Statement: settlement list GET settlement/search/ + detail GET settlement/detail/{id}/ — the statement page also shows the linked payment-request status from Payment (Sales enriches via an internal search call, doc 04 §5.12/5.13; doc 07 §C.3).

flowchart TD
 A[Credit record: customer owes Rs Y] --> B[Edit / Delete]
 A --> C[Settle manually - section 5]
 A --> D[Payment request - section 6]
 A --> E[Customer disputes - section 7]
 C --> F[Ledger + statement]
 D --> F
 E --> B

Rules & edge cases.

  • A credit can only be deleted while fully unpaid; partial payment moves it to settlement history instead (doc 04 §5.4).

  • The customer the credit references is stored as plain data — if the merchant deletes the customer (section 2), Sales' delete-records endpoint cancels the open credits for that customer (doc 04 §5.26).

  • The credit limit/period the merchant set in Profile (section 9) bounds new credits.

5. Manual (offline) settlement

What it is. The customer paid cash / bank transfer / cash at the counter — the merchant records it so the credit is reduced. This is a settlement with no wallet money moving.

How it works:

  1. Merchant selects one or more credit records and how much of each is paid → app → Sales POST /api/miniapp/settlement/manual/create/ {customer, items[{credit, allocated_amount}], total_allocated_amount, payment method/date} (doc 04 §5.11).

  2. Sales creates an approved settlement (a payment row), reduces each credit's outstanding amount, notifies the customer via Events and logs the activity (doc 04 §5.11).

  3. It appears in the statement/transaction history (section 4.5) and in the customer's app (their settlement search).

flowchart LR
 A[Customer paid offline] --> B[Merchant: record settlement]
 B --> C[Sales creates approved settlement]
 C --> D[Credits reduced]
 C --> E[Customer notified]

Rules & edge cases.

  • Allocations must not exceed each credit's remaining amount (validated in the view, doc 04 §5.11).

  • Settlements are never hard-deleted — the system only ever cancels them (doc 04 §5.26 note).

6. Payment requests (merchant asks the customer to pay via wallet)

What it is. Instead of waiting, the merchant sends a payment request to the customer — either for one credit or for the full receivable (all pending credits to that customer). The customer then pays from their eSewa wallet, or declines. The merchant can also cancel a request.

How it works (send):

  1. App → CDXE POST /api/miniapp/payment/request/ {customer, total_allocated_amount, items[], description} (doc 05 §5.14).

  2. CDXE validates the sum and (for connected customers) the approved connection, then calls Sales payment/request/ internally → Sales creates a PENDING settlement — credits are NOT reduced yet → Sales calls Payment payment/request/ (stores the request record, status requested) (doc 04 §5.20; doc 07 A.2).

  3. Events notifies the customer: "merchant X requested Rs Y" (doc 10 §7.3).

How it works (customer pays or declines):

  1. Customer's app → CDXE POST /api/miniapp/payment/request/pay/{id}/ {status: completed + transaction_id, or declined}. Completed requires a signed payload (HMAC over the request, keyed with the shared eSewa key + a 10-digit TOTP — doc 05 §5.15).

  2. CDXE → Payment payment/request/pay/{settlement_id}/ (marks the record completed/declined) → Payment calls Sales payment/request/settle/ (doc 07 A.4, C.1).

  3. Sales finalizes: completed → settlement approved, credits reduced; declined → rejected (credits untouched); cancelled → back to draft (doc 04 §5.21).

How it works (merchant cancels):

  1. App → Payment POST /api/esewa/payment/request/cancel/{id}/ — the only call the app makes straight to the Payment service (federated auth) → Payment marks it cancelled → Sales settles it to draft (doc 07 A.1).

Rules & edge cases.

  • While a request is pending: the customer's credit can't be deleted, the connection can't be terminated, and another request for that customer is blocked (Payment exists/ guard — doc 04/05 §5.7).

  • In this code build the wallet charge behind "completed" is not a live eSewa ePay call — the payment record's status is set by the flow above (mock mode; verdict + evidence in doc 07 §C.5). The frontend's customer-pay function also doesn't yet send the required signature (doc 07 §C.5) — i.e. the customer-side payment UI is not shipped in this checkout.

7. Disputes (customer says "something's off")

What it is. The customer flags a credit (wrong amount, already paid…). The merchant resolves it in one of two ways: edit the credit (fix it) or delete the credit (cancel it). The customer can also withdraw a dispute.

How it works:

  1. Customer raises → CDXE dispute/raise/ → internally Sales dispute/raise/ (guards: credit must be unpaid, have no settlement, no other pending dispute — doc 04 §5.7; doc 05 §5.19).

  2. Merchant sees it in Help & Support; resolving = editing the credit (POST credit/detail/{id}/ → dispute marked resolved, resolution_by_edition) or deleting it (DELETE credit/detail/{id}/?dispute_status=... → credit cancelled, dispute removed, resolution_by_deletion) (doc 04 §5.4).

  3. Customer withdraws → CDXE dispute/cancel/{id}/ → Sales (doc 04 §5.8). Every transition notifies Events.

Rules & edge cases.

  • Disputed credit: can't be settled while a dispute is pending (settlement views exclude it).

  • The raise side is server-side complete, but the customer app's raise button is not wired in this checkout (doc 07 §C.5) — the merchant side (edit/delete resolution) is live.

  • Known code quirk: one delete path writes to the wrong dispute status field, so the resolved flag may not persist (doc 04 §11.7).

8. Notifications & activity

What it is. The bell in the app. Credit added, payment requested, dispute raised, subscription expiring — everything lands here. The merchant can also browse their activity history.

How it works:

  1. Backends push via Events notify-user/ (internal, queued) → a notification row is created per user, gated by the user's notification preferences (doc 10 §7.1/7.2).

  2. App polls GET /api/notification/miniapp/list/ (federated) and can mark read (mark-read/ — note: current implementation marks by user, not by selected ids, doc 10 §11a) and read/update preferences (notification/preference/).

Rules & edge cases. In-app only — no email/SMS/Kafka delivery on the miniapp surface (doc 10 §11). The daily 6:00 AM due-date/overdue reminders for customers come from Sales/CDXE scheduled jobs (doc 04 §8; doc 05 §9 row 20-21).

9. Profile — credit rules & subscription upgrade

What it is. (a) The merchant's own credit policy: max credit limit + payment period (in days) their customers get by default. (b) The merchant's Providhy subscription: buy/upgrade modules and payment period.

How it works (credit rules):

  1. On app start the frontend reads Configuration GET /api/service-configuration/tenant/miniapp/?configuration=master_settings — the credit_settings row holds limit + period (doc 09 §6.1).

  2. Merchant changes them in Profile → POST .../tenant/miniapp/detail/{id}/ — tenant-scoped update; every credit feature reads the same row on the next request (pull-based, no push) (doc 09 §6.2).

How it works (upgrade):

  1. Upgrade page lists modules from the Package service → POST /api/miniapp/subscriptions/initiate/ {payment_period, module_id, subscription_id} on TMS → TMS creates a pending Payment + Subscription and returns a transaction id → (wallet charge — mocked in this build) → POST subscriptions/verify/ {transaction_id} → TMS activates the subscription, creates the tenant's package/module rows, and refreshes the IAM expiry (doc 08 §6.3).

  2. App auto-checks GET subscriptions/status/ after login; Celery jobs send expiry reminders via Events (doc 08 §6.4).

Rules & edge cases.

  • Suspected bug: the upgrade form sends half_yearly/yearly but TMS expects halfyearly/annually — may 400 (doc 08 §10).

  • Verify is mocked by default (ESEWA_MOCK_MODE) and the initiate transaction id is a stub (doc 08 §10) — same mock-mode caveat as section 6.

Appendix B — honest caveats (from the code, this build)

  • No live eSewa ePay integration in these repos: payment records are status rows; the real wallet charge/mock is env-driven (doc 07 §C.5, doc 08 §10).

  • Customer-side actions (approve, pay, self-settle, raise dispute) are built server-side but the customer UI in this checkout is not fully wired — see the Customer-Side doc, appendix.

  • Wallet-user validation is a stub (always "yes") — doc 06 §5.6.

  • A few flagged bugs (payment_period mismatch, mark-read, dispute status field, welcome notification) — each cited in the sections above and in docs 04/07/08/10 §11.
