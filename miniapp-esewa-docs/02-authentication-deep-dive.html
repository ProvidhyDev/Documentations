02 — Federated Identity Authentication: Deep Dive

How a request from the eSewa miniapp becomes "a known user of a known tenant" inside any Providhy service. Audience: technical readers first, but each concept is also explained in plain language. All claims cite source:line. Evidence gathered 2026-11-03.

1. What is "federated identity" here? (plain language)

A federation is an agreement between systems about "who is who". The eSewa miniapp does not run on Providhy's servers and does not know Providhy's user accounts. Instead:

  1. When an eSewa merchant or user first registers in the miniapp, the IAM (Identity & Access Management) service records them as an External Entity: "this phone number, coming from provider 'esewa', maps to this Providhy user account, inside this tenant."
  2. When they log in, IAM issues a signed JWT access token (a tamper-proof digital ticket) that carries everything the other services need to know: user id, tenant id, which services they are subscribed to, their role (merchant ESM or customer ESU), permissions, and whether their subscription is expired.
  3. Every later API call to Sales, TMS, CDXE, Projectmaster, Payment, or Configuration carries that ticket (plus a short-lived OTP code as an extra lock). Each service asks IAM "is this ticket genuine and is the OTP right?", then reads the claims from the ticket and serves the data for only that tenant.

So the miniapp never stores Providhy passwords, and no single service can impersonate anyone: the ticket must be signed by IAM and re-verified against IAM on each request.

3. Two different classes with the same name

IMPORTANT nuance: the codebase contains two distinct implementations named FederatedIdentityAuthentication:

3.1 IAM-internal version (local lookup)

  • File: E:\Work\IAM-Backend\federated_identity\auth_backends.py:10-25
  • How it works:
    1. utils.verify_request_origin(request) must pass (federated_identity\utils.py — see 03-iam doc).
    2. Reads provider_code + external_identifier from the request body.
    3. Looks up ExternalEntity(provider_code, external_identifier) in IAM's own DB.
    4. Returns (the IAM user, tenant_id) or AnonymousUser.
  • Used by: IAM's own federated_identity views (federated_identity\views.py:87, 325) and MiniAppAuthentication (subclass, auth_backends.py:37-41).
  • This is the "resolve an external identity to a user" primitive.

3.2 Service-side version (JWT verify + claims)

  • Copies in each service: Sales\dashboard\auth_backends.py:180, CDXE-REBOOT\dashboard\auth_backends.py:97, ERP-Projectmaster\dashboard\auth_backends.py:166, TMS-service\dashboard\auth_backends.py:147, Payment-Service\dashboard\auth_backends.py:30, Configuration-Service\dashboard\auth_backends.py:102.
  • How it works (Sales copy shown; others identical in substance):
    1. Extract token — helper get_access_token(request, access_token_key="miniAppAccessToken") checks in order: cookie miniAppAccessToken/accessToken → Authorization: Bearer header → request body field miniAppAccessToken/accessToken (E:\Work\Configuration-Service\dashboard\helpers.py:140-168; TMS-service\dashboard\helpers.py:401-433).
    2. Remote verification — validate_token_with_external_iam(token, headers={"X-MINIAPP-TOKEN": ...}) calls POST {IAM_API}/api/external/token/verify/ with the token and forwards the TOTP header (Sales: dashboard\auth_backends.py:218-235). IAM checks signature/expiry AND the TOTP. On IAM unreachable: Sales raises TemporaryServiceUnavailable (auth_backends.py:208-212).
    3. Local decode — TokenBackend(algorithm="HS256").decode(token, verify=False) (auth_backends.py:192): the JWT is re-decoded locally without re-verifying the signature (trust is delegated to IAM's verify call).
    4. Attach claims to the request (auth_backends.py:193-205): user_id, tenant_id, subscribed_services, user_permissions, provider_code, user_type, tenant_root, username, external_identifier, subscription_expired.
    5. Returns (user_id, tenant_id)— note: an *integer id*, not a Django User object. Views/serializers therefore readrequest.useras an id and userequest.` attributes for tenant scoping and role checks.

3.3 JWT mechanics (IAM side)

  • IAM signs with HS256 using a dedicated key: SIGNING_KEY = config("JWT_SIGNING_KEY", default=SECRET_KEY) (E:\Work\IAM-Backend\IAM\settings.py:188). The comment in settings explains: a dedicated key so services can verify miniapp tokens locally without holding IAM's Django SECRET_KEY.
  • Refresh tokens: rotated + blacklisted after rotation; access lifetime = env ACCESS_TOKEN_TIME minutes (settings.py:176-184).
  • Default DRF authentication in IAM: CustomJWTAuthentication (settings.py:144-147); throttling anon 3/sec, user 5/sec (settings.py:140-143).

5. Request anatomy (what a live miniapp request looks like)

POST https://dev-sales-api.providhy.com/api/miniapp/credit/create/
Authorization: Bearer <JWT access>          # issued by IAM external/token/
X-MINIAPP-TOKEN: <6-digit TOTP, 20s step>   # proves possession of shared CUSTOM_KEY
Content-Type: application/json
{
  ...business fields...,
  "provider_code": "esewa",        # (some endpoints still read these for scoping/logging)
  "external_identifier": "<phone>"
}

Server-side processing order for a miniapp endpoint:

  1. DRF authenticator FederatedIdentityAuthentication (service copy) runs → token extracted, IAM verify call (network hop to IAM), claims attached to request, (user_id, tenant_id) returned.
  2. Permission classes (role/subscription/tenant-root) evaluate.
  3. View logic executes with request.user = user id and tenant scoping via tenant_id claim.
  4. Any internal calls to other services use InternalRequestAuthentication on the far side (shared password), not the user's JWT.

6. Security properties & observed weaknesses (as found in code)

# Observation Evidence
1 Token is re-verified against IAM on every request (synchronous network hop). IAM outage = all miniapps fail. Sales auth_backends.py:208-212 (TemporaryServiceUnavailable on connect errors)
2 Local JWT decode uses verify=False — signature trust fully delegated to the IAM verify call. If that call ever 200s on a bad token, forged claims pass. Sales auth_backends.py:192
3 TOTP secret (CUSTOM_KEY) is known to the frontend bundle env; TOTP step is a fixed 20s (short window, but shared secret is not per-user). miniapp-esewa\src\actions\otp.ts:12-22
4 get_access_token accepts the token in cookies or body as well as the header — broader surface than needed. helpers.py:140-168 (Config), TMS helpers.py:401-433
5 Internal service-to-service auth is a single shared password in env (no per-service keys). Sales helper.py:383; TMS auth_backends.py:120-136
6 CORS locked to https://*.domain (Sales settings.py:174-177), cookies secure+SameSite=None (settings.py:169-172).
7 Debug prints of full IAM response (PII-ish) left in auth path. Sales auth_backends.py:227
