03 — IAM-Backend · federated_identity (Federated Identity / Miniapp Auth)

Repo: E:\Work\IAM-Backend · App: federated_identity (Django app inside the IAM service) · DB: iam (dev: iamtest, .env:11) · Public host: https://dev-iam-api.providhy.com (.env:46) Traced 2026-11-03 from production-branch checkout. All line refs are file:line in that checkout.

1. Business overview

federated_identity is the IAM feature that lets users of external payment miniapps (eSewa merchant ESU/ESM users, FonePay, and generic OMS merchants) log into the Providhy ERP without an ERP username/password. An external identity (e.g. an eSewa merchant id) is bound 1:1 to a normal ERP user + tenant (an "external entity"). The app owns:

  • Registration / terms acceptance — when a miniapp user agrees to terms, IAM creates a CustomUser, an ExternalEntity, and a TMS tenant, then hands out ERP JWTs.
  • Login (token mint) — maps external identity to the ERP user and mints ERP access/refresh JWTs containing the claims other services rely on (tenant_id, user_type ESM/ESU, subscribed_services, external_identifier, ...).
  • Token verification proxy — every miniapp business service (Sales, CDXE, Projectmaster, Payment, TMS, Configuration, events) validates the miniapp JWT by calling this app's token/verify/ on each request.
  • Tenant/user lookups + statistics — is-registered, users search/fetch, user-statistics, activity/heatmap analytics, onboarding/funnel metrics for miniapp users.
  • OMS (third-party order systems) integration — onboard a third-party system as a TMS company, issue it an API key, let it mint/verify long-lived merchant JWTs, and auto-register merchant tenants on first order.
  • Funnel tracking — a per-entity onboarding funnel (ESM/ESU stages) with events, dedupe, status denormalization, and cross-service backfill/sync (Celery).

Actors: eSewa/FonePay miniapp frontends (Next.js, E:\Work\miniapp-esewa), the seven ERP miniapp backend services, OMS backends (external, not in E:\Work), IAM ops (clear-cache, funnel migrate), TMS (called, not a caller of this app except token/verify).

3. Authentication & security model

3.1 Non-technical explanation

A miniapp user is first authenticated by the payment provider's own app (eSewa/FonePay). When the user opens the ERP miniapp, the provider passes a one-time app token plus an encrypted envelope of the user's identity (id, phone, name). The frontend sends that envelope to IAM, and IAM checks two things: (1) a fast-changing time code (TOTP, 6 digits, changes every 20 s) computed from a secret both sides share — this proves the request really comes from the legitimate miniapp, not a random website; (2) the encrypted envelope decrypts and the identity inside matches the identifier the client claims. If both pass, IAM finds (or creates, at terms-acceptance) the ERP user and issues normal ERP login tokens. Those ERP tokens then travel to every ERP backend service; each service, on every miniapp request, phones IAM to confirm the token is still valid (and re-checks the time-code header it was given). There is no password, no cookie session of the provider's — trust chains through IAM, and IAM is the single place that knows "eSewa merchant #12345 = ERP user X in tenant Y".

3.2 Technical

Request gate — verify_request_origin (utils.py:78-84). Every miniapp-facing view uses FederatedIdentityAuthentication (auth_backends.py:10-25), whose first step is verify_request_origin(request):

  • Reads header X-MINIAPP-TOKEN. Missing → allowed only if UAT or DEVELOPMENT env flag is set (utils.py:80-83) — a real dev/UAT bypass; otherwise 403 "Invalid origin of request" (auth_backends.py:12-13).
  • Otherwise TOTP.verify(token, valid_window=5) against a module-level pyotp.TOTP built from settings.ESEWA_TOTP_SECRET_KEY (utils.py:67-75; env CUSTOM_KEY_ESEWA, .env:2), TOTP_DIGITS=6, TOTP_INTERVAL=20, TOTP_VALID_WINDOW=5 (settings.py:286-288).
  • The frontend computes the same code client-side: speakeasy.totp({secret: CUSTOM_KEY, encoding:'base32', step:20}) sent on every axios request (miniapp-esewa src/actions/otp.ts:15-21, src/services/api.ts:51-53). The TOTP secret is a client-side env var in the miniapp bundle — the gate authenticates the miniapp app, not the human.
  • Despite the name, no HTTP Origin/Referer is checked.

Identity envelope — token + encrypted_text. Login/register bodies carry token (the provider app token) and encrypted_text (base64 AES-256-ECB/PKCS7 JSON). IAM derives the AES key as the first 32 chars of the provider token, reversed (utils.py:383-394 derive_aes_key_from_token; mirrored by the frontend's cropAndReverse, miniapp-esewa src/shared/utils/app.ts:29-30). aes_ecb_decrypt (utils.py:366-380) must yield JSON whose id or mobileNumber equals the claimed external_identifier (views.py:92-108 register, 330-346 login), else 401 "Invalid request origin". Malformed input returns 401, not 500 (views.py:95-101).

Identity resolution — FederatedIdentityAuthentication (auth_backends.py:10-25). Looks up ExternalEntity by (provider_code, external_identifier); found → (user, user.tenant_id) where user is heimer_auth's CustomUser (auth_backends.py:22-24); not found → (AnonymousUser(), None). Permission HasExternalEntityPermission then requires a non-anonymous user who has an ExternalEntity row (auth_backends.py:28-34) → 403 for not-yet-registered identities. MiniAppAuthentication is an empty subclass kept for miniapp views (auth_backends.py:37-42).

Token mint (access/refresh). helpers.generate_token_with_custom_claims (helpers.py:381-390) = RefreshToken.for_user(user) plus claims; login/registration overwrite/add federated claims (views.py:361-378 login, 160-177 register):

Refresh (external/token/refresh/). RefreshAuthTokenView (views.py:494-513) re-checks verify_request_origin first, then delegates to heimer_auth's CustomTokenRefreshView (views.py:231-260) + FederatedTokenRefreshSerializer (serializers.py:78-96). CustomTokenRefreshSerializer.validate (heimar_auth/serializers.py:195-232): refresh jti must exist in OutstandingToken, user must exist and be active, ROTATE_REFRESH_TOKENS=True + BLACKLIST_AFTER_ROTATION=True (settings.py:189-190) → old refresh blacklisted, new pair generated via helpers.generate_token_with_custom_claims, new access jti saved to Redis. Then the view decodes the new access token (verify=False) and updates user.last_login (views.py:507-512). Observed gap: the refreshed access token only carries tenant_id/is_active/tenant_root/username — FederatedTokenRefreshSerializer.add_custom_fields_to_token (serializers.py:84-95) adds the federated claims but is never called anywhere (grep: only definitions exist), so after a refresh the JWT loses provider_code/user_type/external_identifier/product_code/subscribed_services. (Code-level observation; runtime impact unverified.) Also note refresh passes through the default DRF auth (heimar_auth CustomJWTAuthentication, heimer_auth/auth_backends.py:15-36) which requires a still-valid access token (cookie miniAppAccessToken / Authorization header / body) and enforces the jti-cache check (auth_backends.py:26-31); the view's refresh_token_key="miniAppRefreshToken" attr (views.py:496) is not used by the parent's read path.

Single-active-access enforcement. Every minted access jti is stored per user in Redis db 7 (AuthTokenHandler.save_access_token_jti_to_cache, heimer_auth/auth_token_handler.py:133-150); CustomJWTAuthentication rejects tokens whose jti ≠ cached jti (heimar_auth/auth_backends.py:26-31). New login invalidates the previous access token.

Throttling. LoginRegisterThrottle: 10/min per client IP (scope miniapp_login), keyed by IP deliberately (registration users are anonymous; login identity could be used to lock a merchant out — throttling.py:4-21); RegisterThrottle same rate, separate bucket miniapp_register (throttling.py:24-27). Applied: register (views.py:90), token (views.py:328). OMS mint: AnonRateThrottle (anon 3/sec, settings.py:141, oms_views.py:113).

Cookies on login/register (views.py:179-203 handle_authentication): miniAppAccessToken (max_age=access lifetime) + miniAppRefreshToken (max_age=refresh lifetime), same-site Lax in prod / None otherwise. Frontend axios sends cookies (withCredentials:true, miniapp-esewa src/services/api.ts:28-32).

Audit + activity middleware (wired in MIDDLEWARE, settings.py:43-60). AuthAuditMiddleware (heimar_auth/auth_audit.py:25-50) records every POST to /api/external/token/ as AuthEvent EXTERNAL_LOGIN (auth_audit.py:27) with IP/UA/reason + Prometheus counter iam_auth_events_total. EntityUserActivityTrackingMiddleware (federated_identity/middleware.py:14-20, settings.py:57) runs after the response for /api/external/token/ and /api/external/token/refresh/ and, if request.user is authenticated, calls EntityActivity.record_activity (models.py:184-192) → increments daily active-user counters (Redis, models.py:217-236) and upserts EntityActivitySummary (models.py:360-387).

Internal service calls. InternalRequestAuthentication (heimar_auth/auth_backends.py:111-123): shared password INTERNAL_PASS (env, .env:12) in body or ?password=; request.auth = tenant_id (or None); raises 401 if missing/invalid. Used by all internal endpoints below and by heimer_auth across the platform.

OMS credentials (providhy_auth). API key "pk_." — secret Fernet-encrypted with CUSTOM_KEY (utils.py:390-391, models.py:430) so IAM can re-verify (models.py:435-445, hmac.compare_digest); shown once (models.py:422). Merchant JWT: PyJWT HS256 signed with OMS_TOKEN_SECRET (settings.py:255, defaults to SECRET_KEY), claims typ=merchant, company_id, provider_code, merchant_id, iat, optional exp (providhy_auth/tokens.py:27-57; snapshot source). No exp → never expires; revocation = deactivating the OMSAPIKey row (checked at verify, oms_views.py:91-97).

5.4 POST /api/external/token/refresh/ (RefreshAuthTokenView, views.py:494)

  1. verify_request_origin first (views.py:499-504) → 401 if the TOTP header is bad/missing (401 here, not the usual 403).
  2. Default DRF auth applies (CustomJWTAuthentication, heimer_auth/auth_backends.py:15-36, settings.py:144-147): a still-valid access token must be present (cookie miniAppAccessToken / Authorization header / body) and its jti must match the Redis jti cache, else 401.
  3. CustomTokenRefreshView.post (heimar_auth/views.py:231-260) with FederatedTokenRefreshSerializer (serializers.py:78): refresh jti must exist in OutstandingToken and the user must exist with is_active, else ValidationError → 400.
  4. Rotation (heimar_auth/serializers.py:210-230): old refresh blacklisted (BLACKLIST_AFTER_ROTATION=True, settings.py:182), new refresh+access via helpers.generate_token_with_custom_claims (helpers.py:381-390), new access jti cached.
  5. View decodes the new access (verify=False) and tries to update last_login by filtering username=user_id-claim (views.py:507-510) — the claim is the numeric user id (USER_ID_FIELD="id", settings.py:196), so this lookup matches nothing; last_login is effectively not updated on refresh (code observation, runtime unverified; UPDATE_LAST_LOGIN is also skipped because the custom validate() never calls super()).
  6. 200 {access, refresh} — the refreshed access carries only tenant_id/is_active/tenant_root/username: FederatedTokenRefreshSerializer.add_custom_fields_to_token (serializers.py:84-96) defines the federated claims but is never invoked anywhere (grep: definitions only), so after a refresh the JWT loses provider_code/user_type/external_identifier/product_code/subscribed_services/subscribed_date.
  7. EntityUserActivityTrackingMiddleware (settings.py:57, middleware.py:15) also fires for this path and appends an EntityActivity row.

8. Business walkthroughs

8.1 eSewa merchant onboarding, end to end

  1. The merchant opens the Providhy miniapp inside eSewa. The eSewa app bridges INIT_APP and returns a short-lived app token + scope (miniapp-esewa src/views/home/index.tsx:160-209).
  2. A MERCHANT_DETAIL request returns encryptedData — the merchant's identity JSON AES-256-ECB encrypted under a key derived from the app token (first 32 chars, reversed) (home/index.tsx:86-100; utils/app.ts:18-30; IAM utils.py:383-394).
  3. If the user has not accepted terms, the app posts external/register/: IAM binds the eSewa identity to a brand-new ERP user+tenant (tenant_root admin, no password), creates the tenant in TMS, and issues ERP tokens (views.py:81-316). The merchant sees one ERP dashboard thereafter.
  4. On every later start, external/token/ mints fresh ERP tokens from the same binding (views.py:319-444); the 403 path is what routes the user back to terms.
  5. All subsequent miniapp business calls (credit, connections, payments) go to the ERP services with Bearer + X-MINIAPP-TOKEN; each service re-validates the token against IAM on every request (flow 7.3), so deactivating the user in IAM kills access everywhere within one request.

8.2 eSewa user (customer) flow

An ESU registers the same way (entity_type ESU, no product_code). When the customer initiates a payment to a merchant, the target service resolves both parties via external/is-registered (single and batch modes, views.py:516-611) — e.g. the events service batch-maps external_identifiers to tenant_ids in one call (events/dashboard/views.py:75-80) — then creates the connection/payment records. Activity on login/refresh feeds the analytics endpoints (activities/*) and the funnel (users/funnel/events/), which CRM lists consume through users/ search with funnel_status filters.

8.3 OMS integration, end to end

  1. Ops onboards the third-party order system once: external/oms/onboard/ creates it as a TMS company and returns an API key shown a single time (oms_views.py:38-70).
  2. The third party's backend signs each of its merchants in on its side, then calls external/oms/merchant-token/mint/ with its X-API-Key to get a merchant JWT that never expires (oms_views.py:107-128).
  3. For each order it calls external/oms/merchant/resolve/ to get the merchant's ERP tenant_id; the first call auto-registers the merchant (tenant without package/subscription) (oms_views.py:131-188).
  4. ERP services that need to trust an OMS-issued credential use the shared providhy_auth package, which verifies API keys and merchant JWTs by calling back into IAM's oms/api-key/verify/ and oms/merchant-token/verify/ (providhy_auth/authentication.py:35-88; snapshot source). Deactivating the OMSAPIKey row revokes the system instantly (oms_views.py:91-97).

8.4 Relation to heimer_auth internal registration (api/register/, api/register/v2/)

The classic ERP self-registration — POST /api/register/ (RegisterUser, heimer_auth/views.py:333-423) and /api/register/v2/ (RegisterUserV2, heimer_auth/views.py:427-522) — takes a full company form (username, password, company details, package_id), creates the tenant in TMS via api/tenant/create-tenant[/v2/] (TMS_URL / TMS_URL_V2, helpers.py:31,51), sends an email-verification email, transfers the fiscal year in the Configuration service, and stores a real password. The federated flow creates the SAME shape of object — a normal CustomUser linked to a TMS tenant, visible to every service through tenant_id — but with different mechanics: the identity anchor is ExternalEntity(provider_code, external_identifier) instead of username/email; the user gets an unusable password (serializers.py:28) and no email verification (email_verified is hardcoded true in the token claims, views.py:373,174); the tenant comes from the idempotent TMS external-register endpoint instead of create-tenant (views.py:119-141); and the user is immediately tenant_root. So a federated user is a first-class IAM user/tenant member that simply cannot (and need not) log in with a password — the miniapp tokens are their only credential, and internal ERP endpoints that expect CustomJWTAuthentication behave the same for them once a valid access token exists.

11. Unknowns and unverified

  • Funnel sync targets: SERVICE_APPS (funnel_service.py:189-194) points at api/miniapp/funnel/history|metrics/ (projectmaster, cdxe, sales) and api/esewa/funnel/history|metrics/ (payment); no such routes exist in the current checkouts of those repos (grep across E:Work, 2026-11-03). Until they ship, the 15-minute sync and on-demand backfill record per-service errors; runtime behavior not exercised.
  • providhy_auth: the IAM-Backend working tree contains only pycache for the package; sources were read from E:Work.scratchauditsnapprovidhy-auth (v0.2.0). Version drift vs the installed wheel is unverified.
  • Refreshed tokens drop the federated claims (add_custom_fields_to_token is never called, serializers.py:84-96) and refresh last_login is looked up with username=user_id-integer (views.py:507-510) — both look like latent bugs; runtime impact on services reading claims after a refresh is unverified. Note the dev .env sets ACCESS_TOKEN_TIME=REFRESH_TOKEN_TIME=30 minutes (IAM-Backend/.env:55-56), which makes refresh rare in this config.
  • OMS callers: the actual third-party OMS backends are outside E:Work; the five oms/* endpoints are documented from the IAM side and the shared providhy_auth contract only.
  • eSewa-side contract: the app token + encryptedData come from the eSewa miniapp bridge (requestFromMiniApp INIT_APP / MERCHANT_DETAIL, home/index.tsx:60-243); eSewa's own API is out of scope. The provider token's lifetime/rotation is unknown.
  • TOTP bypass: requests without X-MINIAPP-TOKEN are accepted when UAT or DEVELOPMENT is true (utils.py:80-83); the actual flags in deployed UAT/production envs were not inspected (only the dev .env, where DEVELOPMENT=True, LOCAL=True, PRODUCTION=False).
  • JWT_SIGNING_KEY (settings.py:188) is not defined in this checkout's .env, so SECRET_KEY signs here; whether production sets a dedicated key is unknown (comment says it lets services verify locally).
  • TMS response shape from external-register beyond tenant_id/subscribed_services/fiscal_year depends on TMS serializers (not traced); the register notification context reads subscription_expiry_date from that response (views.py:226-240) — field presence unverified against the TMS serializer.
  • Kafka message payload for activity logs is built in heimer_auth.kafka_functions (not fully traced); only the kafka_data=True hand-off is verified (activity_log.py:37-41).
  • EntityUserActivityTrackingMiddleware would 500 if an authenticated request on the token paths had no ExternalEntity row (models.py:179 uses .get); assumed unreachable because the auth backend only authenticates existing entities.
  • The dev .env contains live-looking secrets (TOTP secrets, DB password, encryption keys) — flagged for the team; do not copy them into other docs.
