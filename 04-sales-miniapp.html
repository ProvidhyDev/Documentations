Sales — Federated Miniapp Documentation

Scope: E:/Work/Sales/miniapp — the credit/sales-ledger surface of the Sales service for the eSewa miniapp (merchant side) and other internal services (customer-facing views via CDXE, settlement callbacks from Payment, customer/ledger lookups from Projectmaster). Evidence base: Sales/miniapp/{urls,views,generics,models,serializers,mixins,filters,utils,tasks}.py, Sales/dashboard/{auth_backends,helper,async_func,choices,pagination,mixins}.py, Sales/core/{urls,settings,celery}.py, Sales/miniapp/migrations/0018_alter_credit_ledger_view.py, Sales/.env. Caller repos: CDXE-REBOOT, ERP-Projectmaster, Payment-Service, miniapp-esewa.

1. Business overview

The Sales miniapp is a trade-credit book for eSewa merchants (ESM) and their connected customers (ESU). A merchant extends credit to a customer on terms (amount, due date, payment term) instead of invoicing goods; the miniapp tracks each credit record's remaining balance, payment status (unpaid / partially paid / fully paid) and due/over-due state.

  • Credit record = a SalesInvoice proxy (unique_id prefix CID-): approved at creation, carries grand_total, remaining_amount, transaction_date (due date), payment_status. No goods/inventory involvement (views.py:91-121).
  • Settlement = a CustomerPayment proxy (unique_id prefix TID-): reduces credit balances. Two flavors: manual (cash/cheque etc., recorded by the merchant, status approved immediately) and payment request (merchant requests the customer to pay via the eSewa wallet; settlement starts pending, becomes approved only when the Payment service reports the eSewa transaction completed; rejected/draft on declined/cancelled) (serializers.py:1327-1370; views.py:1591-1681).
  • Dispute (unique_id prefix CD-): a customer contests a credit via their connected merchant (raised through CDXE). States: issued (default) to resolved (merchant edits the credit = resolution_by_edition, or deletes the credit = resolution_by_deletion) or cancelled (customer withdraws) (choices.py:538-550; views.py:419-513, 1291-1349).
  • Ledger: two Postgres views (credit_ledger_view, credit_ledger_view_customer) union approved credits (+grand_total) and approved settlements (-total_allocated_amount) with a running current_balance per tenant+customer (migrations/0018_alter_credit_ledger_view.py:3-85; models.py:92-134).
  • Notifications: merchant/customer are notified via the Events service on credit create/edit/delete, settlement, payment-request outcomes, dispute resolution, plus daily 00:00 due-date and over-due reminder sweeps (tasks.py:119-353; core/celery.py:47-54).

  • Django 5 + DRF project core (manage.py:11 points to core.settings); root core/urls.py.
  • Apps: miniapp (this surface), sales (sub-apps sales_invoice, customer_payment, ...domain tables), dashboard (shared auth/choices/helper), config_setup, ai_app.

3. Authentication & authorization

Two auth regimes; all 30 endpoints share the single mount api/miniapp/ (section 4), so public / internal / admin is distinguished by WHICH AUTH CLASSES THE VIEW DECLARES, not by mount path.

3.1 Federated (miniapp-browser) auth — FederatedIdentityAuthentication (dashboard/auth_backends.py:180-216)

Opted into by FederatedAuthenticationView (miniapp/generics.py:43-86): authentication_classes = [FederatedIdentityAuthentication], permission_classes = [HasFederatedEntityPermission], default required_user_type = choices.ExternalEntityType.values (generics.py:70); init_subclass forces every subclass to declare required_feature_permission and required_action_permission (generics.py:74-86).

Flow per request (Sales copy):

  1. Token lookup helper.get_access_token(request, access_token_key="miniAppAccessToken") (auth_backends.py:183-185; helper.py:1017-1047): cookie miniAppAccessToken, then Authorization: Bearer , then body field miniAppAccessToken.
  2. POST {IAM}/api/external/token/verify/ with JSON {token: } AND the client's X-MINIAPP-TOKEN TOTP header forwarded (auth_backends.py:188-191, 218-229). TOTP validity is therefore enforced on the IAM side; no TOTP code is computed in Sales.
  3. On 200, the JWT is decoded locally WITHOUT signature verification: TokenBackend("HS256").decode(token, verify=False) (auth_backends.py:192-206). Claims user_id, tenant_id, subscribed_services, user_permissions, provider_code, user_type, tenant_root, username, external_identifier, subscription_expired are placed on the request; returns (user_id, tenant_id) so request.auth = tenant_id.
  4. Failure paths: requests exceptions timeout/ConnectionError to 503 TemporaryServiceUnavailableError (auth_backends.py:208-212, 230-231); HTTP error or exception to AuthenticationFailed 401 (auth_backends.py:214-215, 232-235); missing token to CustomAuthenticationFailed(INVALID_TOKEN) (auth_backends.py:207).

Differences from the canonical IAM copy (SHARED-CONTEXT.md): this Sales copy does NO verify_request_origin origin check and NO local ExternalEntity lookup — it delegates token+TOTP verification to IAM's external verify endpoint and then trusts JWT claims (decoded with verify=False). The canonical MiniAppAuthentication subclass is not present in Sales; the view base references FederatedIdentityAuthentication directly.

3.2 Permission — HasFederatedEntityPermission (dashboard/auth_backends.py:238-247)

Overrides HasPermission.has_permission WITHOUT calling super(): it only checks request.user_type in view.required_user_type (else PermissionDenied / False). Consequences: for miniapp federated views the subscription-expiry check, the IAM user_permissions loop, and the fiscal-year context set by the parent (auth_backends.py:85-100) do NOT run; required_feature_permission / required_action_permission are effectively only validated for presence by init_subclass. Most merchant views restrict to ESEWA_MERCHANT (ESM); ledger views keep the default (all external entity types).

3.3 Internal (service-to-service) auth — shared password

  • InternalRequestAuthentication (auth_backends.py:144-166): reads password, tenant_id, external_identifier, provider_code from POST body (or GET query), sets request.auth = tenant_id, request.external_identifier, request.provider_code; validates password == INTERNAL_PASS via helper.validate_internal_pass (helper.py:383-386), else AuthenticationFailed 401. Returns (None, tenant_id) (anonymous user). Used by views via InternalAuthenticationView (miniapp/generics.py:89-91; permission_classes = []).
  • InternalRequestPermission (auth_backends.py:169-177): same password check applied as a permission (POST body / GET query; other methods denied). Used by plain APIView endpoints that declare no authentication_classes (DRF default auth applies; settings.py:141-144 only adds a production exception handler, so anonymous access is possible — the password is the only gate).
  • InternalSearchView (generics.py:152-211): concrete POST-only search view built on InternalAuthenticationView (q-search mixin; no pagination — plain list response).

5. Endpoint flow traces

Common steps: federated endpoints run the section 3.1 auth chain then the HasFederatedEntityPermission user-type gate; internal endpoints run the password check of section 3.3. Below only view/serializer-specific steps are numbered.

5.1 GET /api/miniapp/credit/overview/ (views.py:43-60)

  • Request: none (query ignored). Auth: federated; ESM only (views.py:47).
  • Flow: build context {tenant_id: request.auth, provider_code} (views.py:51-56); CreditOverviewSerializer computes 3 aggregates (serializers.py:41-77): total_paid = sum(total_allocated_amount) over approved settlements whose items point to approved credits; total_remaining = sum(remaining_amount) over approved CreditRecords; total_over_due = sum(remaining_amount) where transaction_date < today and payment_status in (unpaid, partially_paid) (serializers.py:66-77).
  • DB: CreditRecord (read), CreditSettlement (read).
  • Outbound: IAM token verify (auth only).
  • Errors: 401 (bad token/IAM), 403 (non-ESM), 503 (IAM timeout).

8. Business process walkthroughs

8.1 Sita opens a credit account for her customer (merchant side)

Sita (eSewa merchant) opens the miniapp and goes to Credit. She picks a customer from her customer list, enters the amount she wants to extend and the due date (the due date can be left empty — Sales fills it from the credit period configured for her tenant), and attaches a photo of the purchase if she wants. On save, Sales checks that the customer really belongs to her tenant and is known to the eSewa network, then records the credit as APPROVED with the full amount outstanding. The customer's running balance in the ledger rises by that amount, and if the customer is a registered eSewa user, Sita and the customer both get a "credit created" notification with the amount and the new balance. Later Sita can edit the amount or due date (only while nothing has been paid), or cancel the whole credit (only while it is fully unpaid and never settled) — cancel-with-dispute also closes the dispute.

8.2 Ram pays his credit with the eSewa wallet (customer side)

Ram is Sita's customer. In the miniapp his dashboard shows what he owes across all connected merchants (the totals come from Sales' internal "credit/overview/customer" and "credit/user/search" endpoints, which CDXE fetches on his behalf). He taps "Pay" on the credit, picks how much, and confirms. Behind the scenes CDXE calls Sales' credit/pay endpoint, which verifies the credit belongs to him and that he cannot pay more than is outstanding (pending payment requests count against the balance), records the settlement as approved, reduces the credit's remaining amount, and tells the Payment service that a completed eSewa payment of that amount (with the wallet transaction id) exists for this settlement. Both Sita and Ram are notified of the payment. If he only pays part of the credit, the credit shows "partially paid" until the next payment.

8.3 Sita asks Ram to pay (merchant-initiated payment request)

Instead of waiting, Sita can request payment herself. She selects the credit(s), enters the amount, and confirms — Sales creates a PENDING settlement (the ledger and the credit's remaining amount are NOT touched yet, so the request can still be cancelled) and hands a payment request to the Payment service, which generates the eSewa collect link shown to Ram. When Ram completes the payment in his wallet, the Payment service calls back into Sales (payment/request/settle) with the outcome: completed becomes an APPROVED settlement and the credit is reduced; a declined attempt marks the settlement rejected; a cancelled attempt resets it to draft. Sita sees the request with its live status (requested / completed / declined) in her transaction list, and both parties are notified when it ends.

8.4 Ram disputes the bill

If Ram believes the amount is wrong, he raises a dispute from his miniapp. Sales checks that the credit belongs to his connected merchant, is unpaid, has no active settlement and no earlier pending dispute, then records the dispute in "issued" state — while it is pending, Sita cannot settle that credit. Sita then resolves it by editing the credit to the correct amount (resolution by edition) or, if the credit was recorded in error, by deleting it (resolution by deletion, which cancels the credit). If Ram changes his mind, he simply cancels the dispute. Every resolution is logged in the activity log and the customer is notified.

8.5 Offline (manual) settlement

For cash or bank transfers that never touch the eSewa wallet, Sita records a manual settlement: she picks the customer and the amount (Sales will spread it across the customer's open credits oldest-first, or she can name exact credits), optionally writes a note. Sales approves it immediately, reduces the credits, updates the ledger, and notifies both parties. Manual settlements show up in her transaction list with payment method "manual/offline", distinct from wallet-driven ones.

8.6 The ledger

For any customer, Sita can open the ledger: a chronological list of every credit granted (+amount) and every settlement made (-amount) with the running balance, plus a summary (total given, total received, opening and closing balance for a date range). The numbers come straight from two database views over the approved invoices and approved payments. Every night at midnight Sales sweeps the credits and sends due-date reminders for credits due soon and over-due reminders for unpaid credits past their due date (tasks.py:119-353; core/celery.py:47-54).

11. Unknowns, assumptions & observations

  1. Ledger views are not filtered to miniapp records: credit_ledger_view unions ALL approved SalesInvoice rows and ALL approved CustomerPayment rows in the Sales DB (0018_alter_credit_ledger_view.py:3-85). Miniapp-created records are only distinguishable by unique_id prefixes CID-/TID- (models.py:18-39); the admin overview and the nightly reminder sweeps explicitly filter unique_id startswith CID (views.py:1884; tasks.py:133, 248), but the customer/merchant ledger endpoints do not.
  2. JWT signature: the Sales copy decodes the miniapp JWT locally with verify=False (auth_backends.py:192) after IAM accepted it at /api/external/token/verify/ — the assumption is that IAM validates the signature (and the TOTP header) there. TOTP enforcement itself is not in Sales code (the header is only forwarded, auth_backends.py:188-191).
  3. HasFederatedEntityPermission does not call super() (auth_backends.py:238-247): subscription-expiry, IAM user_permissions and fiscal-year checks of HasPermission (auth_backends.py:85-100) are therefore skipped for all miniapp federated views; only the user_type gate applies. required_feature_permission/required_action_permission are only enforced for presence (generics.py:74-86).
  4. FetchCreditLogsView sets required_feature_permission = ServiceChoices.REPORTING ("PR800") instead of an AllFeatures constant (views.py:955) — likely copy-paste; no practical effect given point 3.
  5. Endpoints #5-8 of section 4.1 (credit/detail/customer, credit/pay, dispute/raise, dispute/cancel) are in the public URL list but use the internal shared password; the browser frontend reaches them only via CDXE (section 10.1). Direct browser calls without the password fail with 401.
  6. Views using permission_classes = [InternalRequestPermission] declare no authentication_classes; DRF default authentication applies and settings only customize the exception handler (settings.py:141-144), so the shared password is the sole gate for 9 internal endpoints.
  7. Code smell (bug, observed): handle_dispute_resolution's resolution-by-deletion path sets dispute.status (not a model field) instead of dispute.dispute_status (views.py:441), so the dispute's persisted status is not set to resolved on that path (only resolution_method is saved, views.py:443-444).
  8. GetCreditRecordForMerchant raises a raw ValueError (HTTP 500) when customer_id is not a list (views.py:650-651).
  9. The ledger overview endpoints check for missing customer_id / customer_identifier AFTER computing aggregates (views.py:1144-1148, 1213-1217).
  10. InitiateTransactionSettlementView maps completed/declined/cancelled to approved/rejected/draft; any other status yields data status None (views.py:1595-1601) — downstream behaviour on an unknown status is untested/unknown.
  11. order_by on the internal search endpoints is taken from the request body and passed to Django order_by (views.py:582, 592) — safe only because callers are trusted internal services with the shared password.
  12. The admin endpoints (section 4.3) have no role/tenant restriction beyond the shared password; admin/credit/overview aggregates across all tenants (views.py:1883-1893).
  13. PayCreditView docstring (views.py:1685-1691) says the settlement must not go through if the payment service fails — matches implementation: settlement creation and the Payment call are in one atomic transaction (views.py:1696; serializers.py:1586-1587).
  14. Frontend constant miniapp/get-credit/ (constants.ts:67) is not served by the Sales miniapp (presumably another service, e.g. Projectmaster) — out of scope.
  15. CreditDispute.entry_by is left null on the raise path (the internal view does not put entry_by into the serializer context, views.py:1300-1305; serializers.py:1209-1215).
