11 — Consolidated ER (cross-service + per-service)

How the miniapp's data lives across 8 databases, and how entities relate across service boundaries. Physical foreign keys exist only inside one service; dotted / LOGICAL links are cross-service correlations by string id (tenant_id, external_identifier, settlement id) — the federation's isolation model in picture form. Per-service field-level detail is in each doc's section 6 (ER).

Reading guide:

  • Identity spine: IAM ExternalEntity (provider + external_identifier) is the root; TMS ExternalTenantLink is what turns an external identity into a tenant; IAM CustomUser.tenant_id is set by TMS at external-register, and every JWT carries that tenant_id.
  • Merchant-customer spine: a PM Customer (+ wallet CustomerIdentityLink) and a CDXE Connection (sender/receiver tenants + ConnectionIdentityLink eSewa ids) are the two halves of "merchant X can lend to wallet user Y". Sales credit records reference the customer by JSON (no FK) — the integrity between Customer and CreditRecord is enforced in code (CDXE/Sales views), not by the database.
  • Money spine: Sales CreditRecord (proxy over SalesInvoice) -> CreditSettlement (proxy over CustomerPayment) -> Payment EsewaPaymentRequest (payment_id = the settlement id). Disputes hang off CreditRecord in Sales.
  • Perimeter: Events rows are keyed by user/submit_user strings (no FK to any identity table); Configuration rows are keyed by tenant_id string.
