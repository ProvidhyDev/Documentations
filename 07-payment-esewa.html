Part A — Payment-Service eSewa app

A.1 Business overview

Payment-Service is a thin, single-purpose microservice on the Providhy federated miniapp surface: it stores eSewa payment-request records (EsewaPaymentRequest) for the eSewa merchant miniapp ("Lenden") and propagates their terminal status to Sales' credit settlements. It does not own credit records, customers, connections, or disputes — those live in Sales / Projectmaster / CDXE (see C.6).

Three facts define the app's shape:

  1. Its only frontend-reachable endpoint is merchant cancellation of a payment request (POST api/esewa/payment/request/cancel/<payment_id>/). All other endpoints are internal S2S (shared-password auth), called by Sales, CDXE, Projectmaster, and TMS (A.10).
  2. There is no eSewa ePay wallet integration in this service's code. No reference to epay.esewa.com.np, no merchant token, no status-URL call anywhere in the repo (verified by grep). The one helper that would call an eSewa URL is hardcoded to a dummy address and is never invoked by any view (A.11). The eSewa/Fonepay merchant payloads for subscription payments live in TMS (TMS-service/dashboard/custom_functions.py:502-541).
  3. The app is the lifecycle record for payment requests (requested -> completed|declined|cancelled; failed exists as a choice). On terminal states it synchronously calls Sales POST /api/miniapp/payment/request/settle/ to update the underlying credit settlement.

A.3 Authentication & authorization

Two DRF auth classes in dashboard/auth_backends.py (Payment-Service's own copy of the federated stack):

1) InternalRequestAuthentication (auth_backends.py:12-27) — used by 6 of 7 esewa endpoints (A.2-A.7):

  • POST: password + tenant_id in body; GET: query params (lines 16-23).
  • Validates password == INTERNAL_PASS (.env:11, helpers.py:81-84, api_links.py:2) — a shared static secret across all services.
  • Returns (True, tenant_id) -> request.auth = tenant_id (line 27). No user, no JWT, no TOTP.

2) FederatedIdentityAuthentication (auth_backends.py:30-67) — used by exactly one endpoint (A.1, cancel):

  1. Token from cookie miniAppAccessToken, else Authorization: Bearer, else body accessToken (helpers.get_access_token, helpers.py:45-72; key set at auth_backends.py:33-35).
  2. POST {IAM}/api/external/token/verify/ with {token}, forwarding the raw X-MINIAPP-TOKEN header (auth_backends.py:37-38,41,125-146) — TOTP verification is delegated to IAM (client-side TOTP: step 20, see B.3).

  4. Raises PermissionError("Your subscription doesn't include cdxe.") when PR2700 (CDXE) is not in subscribed_services (lines 55-56) — a copy-paste leftover from CDXE in this repo's copy (flagged in A.11).

Base view — esewa/generics.py:12-26 FederatedAuthenticationView: auth [FederatedIdentityAuthentication], permissions [HasFederatedEntityPermission]; subclasses must declare required_action_permission + required_feature_permission or ImproperlyConfigured (lines 20-26). FederatedSearchView (generics.py:30-176) is a reusable tenant-scoped GET search template (pagination CustomTransactionPagination, page size 100 — pagination.py:3-5) but no current URL uses it (the search URL is an internal APIView).

Part B — miniapp-esewa frontend

B.1 Business overview

miniapp-esewa ("Lenden") is a wallet/credit-management miniapp that runs inside the eSewa mobile app as a WebView, for eSewa merchants (entity type ESM) and eSewa users (ESU). The merchant experience (what this build wires up): verify customers as eSewa users via the native bridge, establish connections, record credit (dues) with terms, request payment through the customer's eSewa wallet, settle credits manually, review statements and transactions, manage disputes (help & support), notifications, credit-limit settings, and pay for subscription upgrades. All business data (customers, credits, settlements, connections, disputes) lives in the ERP backends — this app holds no data itself (auth session only, in sessionStorage).

B.3 Authentication & login flow (detail)

The miniapp has no username/password form — identity is delegated to the host eSewa app through the WebView bridge.

  1. Root page (app/page.tsx:5 -> src/views/home/index.tsx): on mount, sends bridge request INIT_APP with merchant_identifier = APP_MERCHANT_IDENTIFIER (server action src/actions/identifier.ts:3-7; call at home/index.tsx:194-205). The eSewa app returns {token, scope}; the eSewa app token is stored in sessionStorage["miniAppAuthToken"] (+ "miniAppAuthScope") (home/index.tsx:163-172).
  2. Merchant details — bridge request MERCHANT_DETAIL with that token (home/index.tsx:58-67) returns a JSON blob containing encryptedData (base64) + optional email; stored in sessionStorage["miniAppUserDetails"] (home/index.tsx:73-77).
  3. Decrypt — decryptAES256ECB(encryptedData, cropAndReverse(token)) (home/index.tsx:89-96): AES-256-ECB, PKCS7, key = first 32 chars of the eSewa token, reversed (src/shared/utils/app.ts:18-31). The decrypted JSON's id is the merchant's eSewa identifier (→ external_identifier).
  4. Login — POST {IAM}external/token/ with {token: <eSewa token>, external_identifier: <decrypted id>, encrypted_text: <raw encryptedData blob>, provider_code: "esewa"} (home/index.tsx:86-100, body type auth.ts:32-37). So: token is the eSewa app token (not a Providhy JWT); encrypted_text is passed through to IAM, which decrypts/verifies it server-side (IAM-Backend domain). Response {access, refresh, payload{tenant_id, user_type ESM|ESU, subscribed_services, product_code, tenant_root, username, ...}} (auth.ts:74-97).
  5. Session store — login() writes sessionStorage["user"] = {id, name, email, accessToken, refreshToken, entity_type, payload} and routes to /dashboard (src/context/auth-context.tsx:84-94). On failure (not registered) the app redirects to /terms-conditions (home/index.tsx:129-137, 236-240).
  6. Register (accept terms) — /terms-conditions (src/views/terms-conditions/index.tsx): fetches terms text from GET {LANDING}website/terms/web/?type=esewa_merchant_terms (profile.ts:146-161; the axios interceptor skips the TOTP header for this URL — api.ts:47-49). On accept: bridge GET_PRODUCT for the product code (index.tsx:78-104) then POST {IAM}external/register/ with {token, provider_code, entity_type: "ESM", product_code, encrypted_text, external_identifier, user_details: {username, contact, full_name}} (index.tsx:252-330, body type auth.ts:18-30) → then the same login().
  7. Per-request headers — axios request interceptor (api.ts:34-56): Authorization: Bearer <user.accessToken> (api.ts:8-26) plus X-MINIAPP-TOKEN: <TOTP> where the TOTP is computed by the Next.js server via the getAppOtp server action (api.ts:51-53 → otp.ts:5-24; speakeasy, base32 CUSTOM_KEY, step 20). Skipped for website/terms/web (api.ts:47-49).
  8. Refresh — on 401, axios-auth-refresh calls POST {IAM}external/token/refresh/ {refresh} (api.ts:68-109), updates sessionStorage["user"], retries; on failure clears the session and redirects to /.
  9. Backends validate X-MINIAPP-TOKEN by forwarding it to IAM /api/external/token/verify/ (e.g. Payment-Service dashboard/auth_backends.py:37-41,125-146).

Note: (open)/forms is not a login page — it is a form-component demo (src/views/forms/index.tsx:17-77: name/email/bio/colors/country/datepicker). Login happens at / (home).

7.4 eSewa ePay status verification — verdict: NOT implemented in these repos

The ePay status URL from SHARED-CONTEXT (https://epay.esewa.com.np/api/epay/transaction/status/) appears nowhere in Payment-Service or miniapp-esewa (verified by grep across both repos). What exists instead:

  1. helpers.get_esewa_payment_url() returns a hardcoded dummy http://dummy-api/esewa/payment/url (dashboard/helpers.py:133-141).
  2. EsewaPaymentRequestSerializer.execute_esewa_payment() (serializers.py:104-124) and get_dummy_esewa_payload() (serializers.py:230-252, builds a fake ESW_<uuid> transaction id) are defined but called by no view (verified by grep).
  3. Frontend NEXT_PUBLIC_ESEWA_URL (https://epay.esewa.com.np/api/epay/main/v2/form, .env.example:25) is defined but unused in code (verified by grep).

Verdict (mock-mode finding): in this build the "payment" behind a payment request is a status record, not a live ePay call. The wallet charge happens inside the eSewa app itself (outside both repos); the resulting transaction_id comes back into the system through CDXE's pay call (C.1/7.3). The eSewa/Fonepay merchant integration that IS live (subscription payments) sits in TMS. No merchant token, no ePay client, no status-poll loop in either repo.

C.2 Business walkthroughs

1) Merchant onboarding + login. Aarav opens "Lenden" inside the eSewa app. The WebView fires INIT_APP (home/index.tsx:194-205), receives the eSewa token, then MERCHANT_DETAIL (home/index.tsx:58-67) returns the encrypted merchant blob; the FE decrypts it locally (AES-256-ECB, key derived from the token — app.ts:18-31) and calls IAM login (home/index.tsx:86-100). First time, IAM says "not registered", so the app routes to /terms-conditions: Aarav reads the eSewa merchant terms (fetched from Landing, no TOTP header — api.ts:47-49), taps Accept, the app fetches his product code via the GET_PRODUCT bridge and registers him as an ESM (terms-conditions/index.tsx:252-330), logs in again, and lands on /dashboard with his credit overview, credits, and transactions. From then on every request carries Bearer <JWT> + X-MINIAPP-TOKEN (server-computed TOTP, step 20 — api.ts:34-56, otp.ts:5-24).

2) Requesting payment and paying it back. Aarav owes Sita (a customer) 5,000 from a credit entry. From the dashboard he taps the credit, "Request payment" (dashboard/index.tsx:850-889): the FE POSTs to CDXE miniapp/payment/request/ (payment.ts:31-42); CDXE validates identity/connection and forwards to Sales, which creates a pending credit settlement and records the request in Payment-Service (EsewaPaymentRequest.status=requested, A.2). The FE then pushes a PAYMENT_REQUEST notification to Sita's phone via the eSewa native bridge (es-utils.ts:18-54) and opens /statement?transactionId=.... Sita sees the request in her eSewa app and pays there (wallet charge outside these repos). The completion path — CDXE payment/request/pay/{id}/ -> Payment-Service A.4 -> Sales settle (C.1/7.3) — exists end-to-end in the backends, but no current FE page calls it (transactions.ts:140-153 unused; C.5). Before payment, Aarav can instead cancel: the FE calls Payment-Service directly (the only Payment-Service endpoint the app uses) — cancel-payment-request.tsx:29-63 -> A.1, which requires status requested and settles cancelled in Sales.

3) Disputes (help & support). A customer disputes a credit entry (the raising side, CDXE dispute/raise/, is not wired in the current FE — credit.ts:442-456 unused). On /profile/help-support the merchant sees the disputes list (GET Sales dispute/search/ — help-support/index.tsx:63), opens a dispute for details (GET Sales dispute/detail/{id} — raised-issue-review-credit.tsx:50), and can resolve it by calling DELETE Sales credit/detail/{id}/?dispute_status=...&dispute_id=... (help-support/index.tsx:70-72, credit.ts:503-519), or correct the credit (credit form) or settle it manually (settle-credit-modal).
