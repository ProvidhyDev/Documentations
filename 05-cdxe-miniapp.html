1. Business overview (plain language for a NON-technical reader)

CDXE is the service that links eSewa merchants to their eSewa customers — the "phone book plus handshake" of the eSewa mini-app. A merchant (a shop or business running Providhy's ERP) can invite a customer — a real eSewa wallet user — into their private mini-app; once the customer accepts, the two are "connected". CDXE keeps the list of who is connected to whom and in which state (waiting, connected, declined, terminated).

Why does this matter? Without a connection, the merchant's ERP and the customer's phone app have no agreed relationship. Once connected, the customer can see — in the mobile app — how much credit the merchant has given them, the ledger of transactions, can pay back credit themselves, or raise a dispute if a credit entry looks wrong. The merchant can also send a "payment request" to the customer and see whether it was paid or declined.

One subtlety: CDXE does not store the money or the credit. It stores the relationship. Credit records, ledgers, payments and disputes live in the Sales and Payment services; the customer's identity ("is this really an eSewa wallet user?") lives in IAM and Projectmaster. CDXE sits in front of all of those for the mobile app: it checks the connection exists and is approved, fans out to the right services, merges the answers, and hands the mobile app one clean response. It also forwards every meaningful action (request sent, accepted, payment requested, dispute raised…) to the Events service so both parties get notifications and an activity history.

A second, separate audience uses the same repository: merchants also manage merchant-to-merchant (ERP tenant↔tenant) connections in the web ERP dashboard (the connections app). Those endpoints use ordinary ERP login (IAM-issued JWT for ERP users), not the federated mini-app auth — but they share the same underlying ConnectionRequest table.

3. Authentication & authorization

All 19 public miniapp endpoints opt in through the shared base class (miniapp/generics.py:11-13). The 4 internal endpoints use a different auth: InternalRequestPermission (§3.3). The ERP-side connections app uses IAMAuthenticationBackend (§3.4).

3.1 FederatedIdentityAuthentication — CDXE copy

Implemented in dashboard/auth_backends.py:97-136. It is a divergent copy of the canonical class in IAM-Backend/federated_identity/auth_backends.py:10-25 — the canonical one validates the X-MINIAPP-TOKEN TOTP locally and then looks up ExternalEntity(provider_code, external_identifier) in IAM's own DB. The CDXE copy does neither locally. Its flow:

  1. Extract the access JWT via helpers.get_access_token(request, access_token_key="miniAppAccessToken") (dashboard/auth_backends.py:100-102; dashboard/helpers.py:1047-1074). Lookup order: cookie miniAppAccessToken → Authorization: Bearer <jwt> header → request body field accessToken. (The miniapp frontend sends Authorization: Bearer — miniapp-esewa/src/services/api.ts:34-56.)
  2. Forward the token and the X-MINIAPP-TOKEN header to IAM: POST {IAM_API}/api/external/token/verify/ with JSON {"token": <jwt>} and the X-MINIAPP-TOKEN header (dashboard/auth_backends.py:105-109, dashboard/auth_backends.py:156-171). IAM's VerifyAuthTokenView (IAM-Backend/federated_identity/views.py:447-491, mounted via IAM-Backend/IAM/urls.py:119 + IAM-Backend/federated_identity/urls.py:16) first calls utils.verify_request_origin (IAM-Backend/federated_identity/utils.py:78-84): it verifies X-MINIAPP-TOKEN as a TOTP of secret ESEWA_TOTP_SECRET_KEY (= env CUSTOM_KEY_ESEWA, IAM-Backend/IAM/settings.py:207) with 6 digits, 20-second step, valid window 5 (IAM-Backend/IAM/settings.py:286-288); a missing TOTP header is tolerated only when IAM's own UAT/DEVELOPMENT flags are true (IAM-Backend/federated_identity/utils.py:81-82). The frontend computes this TOTP with speakeasy.totp({secret: process.env.CUSTOM_KEY, encoding: "base32", step: 20}) (default 6 digits) on every request except website/terms/web (miniapp-esewa/src/actions/otp.ts:5-23, miniapp-esewa/src/services/api.ts:47-55).
  3. Non-2xx from IAM → AuthenticationFailed; connection error → TemporaryServiceUnavailableError (dashboard/auth_backends.py:127-136).
  4. CDXE then decodes the JWT itself (TokenBackend("HS256").decode(token, verify=False)) and copies claims onto the request: external_identifier, provider_code, user_type, subscribed_services, user_permissions, tenant_root, username, product_code; returns user_id, tenant_id — so request.user = user_id and request.auth = tenant_id (the tenant) (dashboard/auth_backends.py:110-126).
  5. Requires ServiceChoices.CDXE ("PR2700") in the JWT's subscribed_services, else "Your subscription doesn't include cdxe." (dashboard/auth_backends.py:124-125; dashboard/choices.py:160).

What the CDXE copy does extra vs canonical: it forwards the TOTP to IAM for verification (no local TOTP check, no verify_request_origin call, no ExternalEntity lookup, no AnonymousUser path — any auth failure is a 4xx).

3.2 HasFederatedEntityPermission (permission layer)

dashboard/auth_backends.py:139-153, applied by the base class. Checks, in order:

  1. view.required_app_scope (base default: ExternalProviderChoices.values = ["esewa"], miniapp/generics.py:16; dashboard/choices.py:318-319) must contain the request's provider_code.
  2. view.required_user_type must contain the request's user_type — ESM = eSewa merchant, ESU = eSewa user (dashboard/choices.py:322-324).
  3. Delegates to HasPermission.has_permission (dashboard/auth_backends.py:62-94): if the JWT claim tenant_root is true → allowed immediately (tenant roots skip the remote check). Otherwise it calls GET {IAM_API}/api/internal-check-permissions/?password={INTERNAL_PASS}&user_id={request.user} (dashboard/helpers.py:31; dashboard/auth_backends.py:68-70) and requires the IAM permission list to contain feature_ID == view.required_feature_permission and the view's required_action_permission among that feature's actions (dashboard/auth_backends.py:74-94).

Effective gate per endpoint: valid federated JWT incl. CDXE subscription + TOTP accepted by IAM + provider "esewa" + entity type (ESM/ESU) + feature/action permission (unless tenant root). Feature codes used by the miniapp: PR2701 (CONNECTION, dashboard/choices.py:241), PR2705 (REPORT_SHARING, dashboard/choices.py:251), PR1207 (CUSTOMER_PAYMENT, dashboard/choices.py:235), PR1201 (SALES_INVOICE, dashboard/choices.py:233).

dashboard/auth_backends.py:14-44 — Authorization: Bearer <ERP JWT> → POST {IAM_API}/api/token/verify/ (dashboard/auth_backends.py:47-59), then decodes claims locally; requires CDXE in subscribed_services, email_verified, non-expired subscription; returns user_id, tenant_id. 3.5 SIGNATURE header (payment integrity)

For customer-initiated payment commits the client must send a SIGNATURE header: HMAC-SHA256 over the string merchant_identifier=<m>-total_allocated_amount=<a>-transaction_id=<t> keyed with CUSTOM_KEY_ESEWA + TOTP.now(), where the TOTP is 10 digits, 20-second interval from CDXE's own settings (miniapp/utils.py:19-42; core/settings.py:254-256). Verified in SettleOutstandingCredit.post (miniapp/views.py:869-884) and ApproveDeclinePaymentRequest.post (miniapp/views.py:806-824). CORS allows the X-MINIAPP-TOKEN and SIGNATURE headers (core/settings.py:233-237). Note: the current frontend does not send SIGNATURE anywhere in src/ (no call sites found) — see §11.

8. Business process walkthroughs

  1. A merchant invites a customer into their credit shop. Ramesh, a merchant, opens Sita's profile in the miniapp (her identifier came from the customer he created in Projectmaster) and taps "Send connection request" (miniapp-esewa/src/shared/components/app/send-connection-request.tsx:40 → customer.ts:146). CDXE checks that Sita's identifier really belongs to an eSewa user (IAM) and that she is a verified customer of Ramesh (Projectmaster). If so, CDXE creates a pending connection with a short numeric code and notifies Sita. If the identifier is unknown to both, the request fails with a friendly error.
  2. The customer approves (or declines). Sita sees the request in her app and approves. CDXE flips the connection to approved (declining deletes it). From that moment the two parties can see each other in their respective miniapp views, and Sita can see Ramesh's credit data.
  3. The customer sees her credit and pays it back. In the "Merchants" tab (merchants.ts:76 → connection/search/) Sita lists Ramesh with his current credit balance. She opens the ledger (credit/ledger/) and, if she wants to pay, picks which credit entries to settle, dry-runs it (commit:false) and then commits with a signed request (credit/pay/); Sales executes the settlement. (See §11 — the current frontend build does not yet wire this up.)
  4. The merchant requests a payment. Ramesh can instead request a payment (payment/request/); Sita gets a notification and can complete it (wallet charge via Payment) or decline it (payment/request/pay/{id}/).
  5. Disconnecting. Ramesh can terminate a connection (connection/terminate/{id}/) — CDXE refuses if there is an active payment request between them. Or he deletes Sita as a customer entirely: Projectmaster deletes her, asks Sales to delete her transactions, and asks CDXE to terminate the connection (connection/delete/customer/).
  6. What is "dummy-customer-check"? It is not a CDXE endpoint — it lives in ERP-Projectmaster (ERP-Projectmaster/miniapp/urls.py:17-21, view DummyCustomerCheck, ERP-Projectmaster/miniapp/views.py:255-262): a password-protected stub that always returns is_provider_user: true. It stands in for the real eSewa user-verification API: each repo has an env var ESEWA_USER_CHECK_API that is supposed to point at that API; in Projectmaster's dev env it points at the stub itself (ERP-Projectmaster/.env:49 → http://localhost:1111/api/miniapp/dummy-customer-check/), and the provider-to-URL registry is ERP-Projectmaster/miniapp/registry.py:10-11 (defined but with no call sites found in the PM source). In CDXE's .env the same variable points at a dummyjson URL (E:\Work\CDXE-REBOOT/.env:50) but no CDXE code references it — CDXE verifies customers via IAM is-registered + Projectmaster validate-customer-connection instead (§5.1).

11. Unknowns & assumptions

  • ESEWA_USER_CHECK_API / dummyjson: E:WorkCDXE-REBOOT.env:50 sets it to a dummyjson URL, but no CDXE code references it — the external eSewa user-verification call is not made by CDXE. The equivalent stub endpoint (dummy-customer-check) is in ERP-Projectmaster (ERP-Projectmaster/miniapp/views.py:255-262, registry ERP-Projectmaster/miniapp/registry.py:10-11, PM .env :49); that registry has no call sites found either. Treat the env var as a leftover/planned integration.
  • SIGNATURE flow not wired in frontend: no src/ file sets a SIGNATURE header, and the service functions settleCreditCustomerInitiated / customerInitiatedPaymentPay (credit.ts:394-416), payRequestedPayment (transactions.ts:140-153) and deleteDispute (credit.ts:485-501) have no call sites in views — customer-initiated commit=true payments and the customer-side dispute-cancel / payment-cancel flows appear unshipped in the current UI. deleteDispute additionally targets DELETE api/miniapp/credit/detail/{id}/ which has no DELETE handler in CDXE (would 405).
  • HMAC base-string quirk: SettleOutstandingCredit.generate_string_to_sign (miniapp/views.py:869-884) and ApproveDeclinePaymentRequest.generate_string_to_sign (miniapp/views.py:806-824) build the signed string from body fields merchant_identifier / total_allocated_amount; for payment/request/pay those fields are not declared by MiniappPaymentExecutionSerializer (fields: status, payment_request_id, transaction_id, miniapp/serializers.py:401-402), so unless the client sends undeclared extra fields the signed string is effectively "merchant_identifier=-total_allocated_amount=-transaction_id=...".
  • DeleteCustomerConnection guard: if-not-any check (miniapp/views.py:1083-1093) only 400s when all three fields are missing; a single missing field passes (then matches nothing).
  • multi_tenancy app: source files absent (only stale .pyc), not in INSTALLED_APPS, no references — unused by the miniapp; its (removed) provisioning behavior cannot be documented.
  • total-connections/: no in-repo caller found; assume ops/monitoring.
  • CDXE auth copy diverges from canonical: no local TOTP check, no verify_request_origin, no ExternalEntity lookup; TOTP verification is delegated to IAM (dashboard/auth_backends.py:105-109, 156-171). Whether IAM's UAT/DEVELOPMENT flags (which allow a missing TOTP) are set in a given environment is environment-dependent (IAM .env, not CDXE).
  • TOTP digit split by design: IAM verifies the request TOTP with 6 digits (IAM-Backend/IAM/settings.py:286, matching the frontend speakeasy default); CDXE's 10-digit TOTP (core/settings.py:255) is used only to build the HMAC-SHA256 key for SIGNATURE (miniapp/utils.py:19-24).
  • Frontend .env: only .env.example exists in miniapp-esewa; NEXT_PUBLIC_CDXE=dev-cdxe (hence https://dev-cdxe-api.providhy.com/api/) assumed from the example.
  • Tenant id truncation: ConnectionRequest.sender/receiver are CharField(10); assumes ERP tenant ids fit in 10 chars (TMS tenant ids, e.g. numeric strings).
  • Connection codes: default length 5 (connections/domain.py:8) although the column allows 6; the frontend appends the code from the create-connection response as the URL segment.
  • Connections app list() is intentionally disabled (403, connections/views.py:106-112); ERP list views must use search/ or tenant-search/.
