01 — Full Overview: The eSewa Miniapp on the Providhy ERP Platform

Reverse-engineered from the code on 2026-11-03 (branch checked out in E:\Work). Every service doc (03-10) contains the endpoint-by-endpoint detail; this file is the map of the territory.

1. What is this, in one paragraph

Providhy runs a multi-tenant ERP (sales, purchase, accounting, tenant management, identity, payments, notifications, configuration, master data) as a fleet of Django microservices. On top of it sits a federation for the eSewa miniapp — a wallet-style credit app used by eSewa merchants (entity type ESM) and eSewa customers/wallet users (ESU). The miniapp does not log in with ERP credentials: IAM keeps a table of external entities (provider + external identifier, e.g. a phone number, mapped to an IAM user inside a tenant). Login against IAM mints a short-lived JWT carrying the user's tenant, subscriptions, role and permissions; every subsequent call to the ERP services carries that JWT plus a per-request TOTP code, each service re-validates it with IAM, and then serves only that tenant's data. The miniapp's business is the merchant's credit book: adding customers, extending credit (buy now, pay later), requesting payment through the eSewa wallet, settling, disputing, and managing the merchant's own subscription.

2. Who are the actors (non-technical)

Actor Who What they do in the miniapp
eSewa merchant (ESM) A shop/business with an eSewa merchant account, subscribed to Providhy Sees credit overview, adds customers, creates credit, requests payment, settles, raises/manages disputes, upgrades the subscription, configures credit limit/period
eSewa customer (ESU) A wallet user connected to a merchant Sees what they owe, pays (settlement), responds to payment requests, raises/cancels disputes, sees notifications
Providhy platform (ops/CMS) The SaaS operator Manages packages/modules, sees registration funnel metrics (funnel events, onboarding metrics, activity heatmaps via IAM external API), provisions tenants
eSewa (external) The wallet provider Identity source for registration/login identifiers; in production the payment rail for wallet settlement. NOTE: in this code checkout there is no direct ePay API integration — see 7.1

4. How a request gets through the door (30-second version)

  1. Frontend computes a 6-digit TOTP (shared secret, 20-second window) and adds X-MINIAPP-TOKEN plus the Bearer JWT to every request.
  2. The service's FederatedIdentityAuthentication extracts the JWT (cookie, header, or body), POSTs it to IAM /api/external/token/verify/ forwarding the TOTP header; IAM checks signature, expiry and the TOTP.
  3. The service then decodes the JWT locally (verify=False) and reads the claims: user_id, tenant_id, subscribed_services, user_type (ESM/ESU), provider_code, tenant_root, permissions, subscription_expired.
  4. Permission classes gate by user_type / subscription / tenant_root; the view executes scoped to tenant_id.
  5. Service-to-service calls inside the flow use a different door: a shared internal password (INTERNAL_PASS) plus the tenant id, via InternalRequestAuthentication.

Full mechanism + security notes: doc 02. Per-service variants and their quirks: each doc's section 3.

5. The money flows (what actually happens)

5.1 Registration (one time, per wallet identity)

Wallet user opens the miniapp -> terms page (Website service) -> accept: IAM POST /api/external/register/ with the eSewa token + encrypted identifier + provider code. IAM links/creates the external entity and triggers TMS /api/tenant/external-register/ which provisions the tenant (or links an existing one), creates/links the IAM user, and asks Configuration's data-transfer to copy the platform's default business rules (chart of accounts, config rows, fiscal year, terms) into the tenant. TMS stores the result in ExternalTenantLink (fiscal_year marker makes the transfer idempotent). Funnel events are recorded so the platform can watch onboarding progress.

5.2 Login (each session)

POST /api/external/token/ with the eSewa token + external_identifier + provider_code -> IAM looks up the entity, checks TOTP, returns access+refresh JWT whose payload carries tenant_id, user_type, subscribed_services, product_code, permissions. Frontend stores them in sessionStorage; refresh is automatic on 401.

5.3 Merchant extends credit to a customer

Merchant: add customer in Projectmaster (POST /api/miniapp/customer/) — optionally linking the customer's wallet identity; if the customer is a wallet user, create a connection in CDXE (POST /api/miniapp/create-connection/) — CDXE asks IAM (is the receiver registered?) and Projectmaster (is this wallet a real customer of this merchant?) in parallel, stores Connection(pending)+ConnectionIdentityLink with a 5-digit code, notifies both parties via Events. The customer approves/rejects in their app (approve sets the status; decline cascade-deletes both rows). Then the merchant creates a credit record (Sales ledger, via CDXE or Sales surface) — the customer sees it in their app and can pay.

5.4 Paying / settling credit

Two paths, both ending in the Sales ledger:

  • Merchant-initiated payment request: merchant POSTs payment/request (CDXE) -> Sales creates a PENDING settlement (credits untouched) + a payment request in Payment -> customer sees the request and pays (or declines) -> when the payment reaches a terminal state, Payment (or the customer action) calls Sales payment/request/settle -> settlement becomes approved (credits reduced) / rejected / cancelled. A pending request blocks customer deletion (Projectmaster checks Payment payment/request/exists/).
  • Customer-initiated payment: customer opens the merchant's credit and pays -> CDXE credit/pay with a signed commit (HMAC-SHA256 SIGNATURE over the payload, key CUSTOM_KEY_ESEWA + 10-digit TOTP) -> Sales credit/pay -> Sales creates an APPROVED customer-payment and calls Payment payment/request/ (status completed with the transaction id) -> Events notify. NOTE: the frontend defines these signed flows but no view sends the SIGNATURE header today — doc 05/07 flag this as unshipped.

5.5 Disputes

Customer raises a dispute on a credit (CDXE dispute/raise -> Sales dispute/raise; guards: unpaid, no settlement, no pending dispute). Merchant resolves by editing the credit (resolution_by_edition) or deleting it (resolution_by_deletion); customer can cancel a pending dispute. Every transition notifies Events.

5.6 Subscription lifecycle (merchant's own subscription)

Frontend auto-fetches TMS /api/miniapp/subscriptions/status/ after login. Upgrade page lists modules/packages from the Package service, then TMS subscriptions/initiate (creates Payment + Subscription PENDING; returns a transaction id — in this checkout a random stub, verify is mocked by default), subscriptions/verify (marks paid, activates Subscription, creates TenantPackage/TenantPackageModule if missing, refreshes IAM subscription expiry), subscriptions/cancel (unused in frontend). Celery beat sends expiry reminders via Events. Known mismatch: frontend sends half_yearly/yearly, TMS choices are halfyearly/annually — suspected 400 bug (doc 08 §10).

5.7 Configuration that shapes the credit book

At app boot the frontend reads Configuration /api/service-configuration/tenant/miniapp/?configuration=master_settings — inside it, the credit_settings row (credit limit + credit period) that all credit features honor. Merchant edits it in Profile > Credit management via the federated detail endpoint. Tenant fiscal year / currency / datepicker essence come from Configuration internal endpoints; every customer create fetches the GL mapping (Account Receivable) from Configuration.

7. Key findings a business person should know

  1. The wallet is not (yet) wired to real eSewa payments in this code. Payment-Service stores payment-request records and has no ePay API integration (no epay.esewa.com.np references anywhere, verified). TMS subscription verify is mocked by default (ESEWA_MOCK_MODE). Production may differ via env flags not present in this checkout — doc 07/08 §10.
  2. Two parallel credit surfaces exist. Sales and CDXE both expose credit/pay/dispute/payment-request endpoints for the miniapp. The frontend routes customer-facing credit operations through CDXE (which delegates to Sales' internal ledger endpoints); Sales' direct endpoints are the ledger of record plus merchant-side and internal paths. This looks like an in-flight migration (CDXE-REBOOT) — doc 04/05 §11.
  3. Customer identity is a stub. dummy-customer-check (Projectmaster) always returns is_provider_user:true; the env vars pointing at a real eSewa user-check API are unreferenced leftovers. In this checkout, no service calls the real eSewa verification API — doc 05/06 §11.
  4. Tenant isolation is the core safety model: every miniapp query is scoped by the tenant_id claim; internal calls pass the tenant id explicitly (trusted). One flagged risk: Sales due-date batch jobs read Projectmaster customers with tenant_id=all (cross-tenant) — doc 04/06 §10.
  5. Money-adjacent guards are real: pending payment request blocks customer deletion; dispute guards; settlement lifecycle states; signed (HMAC) commit for customer-initiated settlement — but that signature is not yet sent by the frontend (unshipped) — doc 05.
  6. Suspected bugs found in code (details in each doc's unknowns section): TMS payment_period value mismatch (frontend half_yearly vs TMS halfyearly); IAM trial notification hardcodes module_type=SALES; events mark-read ignores the ids list; Sales dispute deletion writes dispute.status instead of dispute.dispute_status; Configuration tenant/create/configuration/ (non-v1) has no declared auth; events create-export-log/ unauthenticated.
