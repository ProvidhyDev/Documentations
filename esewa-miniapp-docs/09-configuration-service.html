3. Auth mechanism

3.1 FederatedIdentityAuthentication (the two miniapp views)

dashboard/auth_backends.py:102-131 — same design as the TMS copy (doc 08 §3):

  1. JWT via helpers.get_access_token(request, access_token_key= "miniAppAccessToken") (auth_backends.py:105-107; helpers.py:140+) — cookie, Bearer header, or body key.
  2. validate_token_with_external_iam(token, headers={X-MINIAPP-TOKEN: <TOTP>}) (auth_backends.py:110-113, 134-151) POSTs to IAM {IAM_SERVICE}api/external/token/verify/ (auth_backends.py:135) — IAM enforces the TOTP (pyotp, 20 s step, ±5 window, secret CUSTOM_KEY_ESEWA) plus JWT validity before returning 200.
  3. Local decode of the JWT without signature verification (verify=False, auth_backends.py:114) fills request.provider_code/user_type/tenant_root/user_permissions/ subscribed_service/username/external_identifier/subscription_expired (auth_backends.py:115-127). Returns (user_id, tenant_id) → request.auth = tenant_id string (auth_backends.py:128).
  4. On any failure: 401 CustomAuthenticationFailed (auth_backends.py:130-131).

3.2 Other auth/permission classes used by this app

  • IAMAuthenticationConfigBackend (auth_backends.py:54-90): Bearer-style portal JWT validated against IAM api/internal-check-permissions/ (APILinks, helpers.py:39-45,61); sets request.tenant_root, user_permissions, subscribed_service, fiscal_year. Used by the portal tenant configuration views (3, 4, 5, 6, 11, 13, 20) and the miniapp detail view's parent class.
  • HasPermission (auth_backends.py:154-190): 403 when request.subscription_expired (POST only); allow if request.tenant_root; else requires the view's required_feature_permission + required_action_permission to match a grant from IAM api/internal-check-permissions/ (auth_backends.py:172-189). Since delta 0f37ed5 the IAM permission fetch is cached on the view instance (_user_permissions_) so a request that checks several permissions hits IAM only once (auth_backends.py:161-168).
  • Action model change (delta 0f37ed5, choices.py:502-510): the old ADD_EDIT action no longer exists — it was split into separate ADD (choices.py:503) and EDIT (choices.py:504) actions. Views were updated to match: tenant config detail POST now requires EDIT (views.py:358), tenant config status POST requires EDIT (views.py:482), cost-term create/ update/search POST require ADD (cost_term/views.py:37, 91, 158), TDS type create requires ADD and update requires EDIT (tds_type/views.py:77, 97).
  • EbillingPermission (auth_backends.py:237-262): object-level — blocks eBilling tenants from UNIQUE_ID (non-PRODUCT_FLOW), NEGATIVE_INVENTORY, and MASTER_SETTINGS/PRINT_TEMPLATE rows (those are managed server-side for eBilling).
  • InternalRequestPermission / internal password checks: validate_internal_pass (helpers.py:18, 87-89) compares the password field to INTERNAL_PASS; used by views 12, 14(GET), 16, 17, 18, 19, 21, 22 and by the dashboard internal views 27-30 via custom.post_request_data_check_*.

Note on inheritance: the miniapp detail view (431-432) subclasses TenantServiceConfigurationDetailView, which carries the class decorators @permission_classes([HasPermission, EbillingPermission]) (views.py:349-350); the miniapp subclass inherits both permission classes, so the merchant's request must pass HasPermission (tenant_root or CONFIGURATION_SETTINGS permission; not subscription-expired on POST). Since delta 0f37ed5 the merchant's POST additionally needs the EDIT action on the CONFIGURATION_SETTINGS feature (inherited from views.py:356-361) instead of the old ADD_EDIT action.

3.3 TDS type and cost term permission enforcement (delta 0f37ed5)

  • TDS type endpoints (mounted /api/tds/) now enforce HasPermission (tds_type/views.py:131-134): TDSTypeView carries required_feature_permission = CONFIGURATION_SETTINGS (tds_type/views.py:26). initial() runs the request validations before the permission check (tds_type/views.py:42-51); create() checks the ADD action and update (POST .../tds/{pk}/update/) checks the EDIT action via check_providhy_permission (tds_type/views.py:72-74, 76-77, 95-97). This fixes a hole where TDS create/update previously ran no action-level permission check at all.
  • Cost term endpoints keep the same shape but their POST action changed from ADD_EDIT to ADD (cost_term/views.py:37, 91, 158) as part of the action split.
  • New AllFeatures report codes for permission configuration (choices.py:493-498): TRIAL_BALANCE_REPORT PR819, BALANCE_SHEET_REPORT PR820, PROFIT_LOSS_STATEMENT_REPORT PR821, GENERAL_LEDGER_SUMMARY_REPORT PR850, GENERAL_LEDGER_REPORT PR822.
  • New InvalidDataFormat exception (dashboard/exception.py:21-22) with message "{} should be a {}" (dashboard/messages.py:30), raised by the TenantServiceConfigurationSerializer starting_number transform (service_configuration/serializers.py:11-23, 53-62) — see §6.2.

5. How per-tenant service configuration works

  1. Defaults: on first read of any configuration type, DefaultServiceConfiguration rows are created from workflows() (views.py:34-46). Each row = (configuration_type, configuration_status, value-JSON, active_status).
  2. Tenant transfer: when a tenant is created (TMS external-register → data-transfer, §6.3) the default rows are copied into TenantServiceConfiguration for the tenant (dashboard/views.py:1192, transfer.configuration_transfer), plus chart of accounts, fiscal year essence, payment terms, cost terms, TDS types. Since delta 0f37ed5 a request with mini_app: true skips the ERP transfer entirely and sends only the master_settings credit row (falling back to the code default when the platform default row is missing) plus the fiscal year essence (dashboard/views.py:1175-1186, dashboard/data_transfer.py:338-367, defaults.py:206-209).
  3. Portal edit: portal users CRUD tenant rows via the tenant/ endpoints (3-6); each save only updates that tenant's row — no fan-out.
  4. Runtime read: business services read tenant config either by calling the internal expose endpoint (12) or directly through their own api/dashboard/tenant-fy-essence/-style internal calls (e.g. Sales, CDXE, Payment-Service all call tenant-fy-essence, evidence in §9). The miniapp reads via the federated endpoint (1).
  5. Propagation is pull-based: there is no cache invalidation or push event when a row changes; consumers see the new value on their next read. (No kafka/celery push mechanism found in this repo — see §11.)

6. Endpoint traces

6.1 GET /api/service-configuration/tenant/miniapp/ ★ federated

View: TenantServiceConfigurationMiniapp (views.py:345-346) — subclass that only swaps auth to FederatedIdentityAuthentication (346); inherits GET from TenantServiceConfigurationAPIView (views.py:250-342).

Frontend caller: getCreditmanagementSettings (miniapp-esewa/src/services/requests/profile.ts:66-76) called by the ConfigProvider on app boot with ?configuration=master_settings (config-context.tsx:36-50).

Flow (views.py:277-342):

  1. Auth → request.auth = tenant_id (string, §3.1).
  2. configuration_type = request.GET.get("configuration") must be one of ConfigurationTypeChoices, else 400 NOT_FOUND (295-299).
  3. custom.listing_tenant_configurations(tenant_id, configuration_type) (dashboard/custom_functions.py:179-221): queries TenantServiceConfiguration for (tenant_id, configuration_type) ordered by id (204-208), groups rows by configuration_status into a dict (212-219), returns {configuration_type: {<status>: [values...]}, "configuration_type": <type>}. Rows are the raw value-JSON lists (e.g. for master_settings this includes the credit_settings list with credit_limit/credit_period used by the miniapp credit-management page).
  4. Response 200 (338-342). Errors: ValidationError → 400 (328-337); Exception → 500 SERVER_EXCEPTION (338-341).

6.2 GET/POST /api/service-configuration/tenant/miniapp/detail/{pk}/ ★ federated

View: TenantServiceConfigurationMiniappDetailView (views.py:431-432) — auth override only; inherits from TenantServiceConfigurationDetailView (views.py:349-428) with permission_classes [HasPermission, EbillingPermission] (349-350).

Frontend callers:

  • GET — same ConfigProvider flow as 6.1 does not use detail; the credit-management page reads the list endpoint. (detail GET is available but the miniapp currently only uses it implicitly via the list; noted.)
  • POST — updateCreditManagementSettings (profile.ts:78-91): body {value: {credit_limit, credit_period}} to tenant/miniapp/detail/{id}/ where id is the credit_settings row id from the list response (credit-management/index.tsx:72+).

GET flow (views.py:353-401):

  1. Auth + permissions (§3.1, §3.2).
  2. Row lookup by pk (371-375); 404 if missing or tenant mismatch (376-383 — the pk must belong to request.auth's tenant).
  3. EbillingPermission object check (auth_backends.py:237-262) may 403 for eBilling tenants on unique-id / negative-inventory / print-template rows.
  4. Returns the row's value (392-401).

POST flow (views.py:403-428):

  1. Auth + HasPermission (tenant_root or CONFIGURATION_SETTINGS with the EDIT action; subscription_expired → 403 on POST; required action set in initial() at views.py:356-361).
  2. Row lookup by pk, scoped to the tenant (405-411); 404 otherwise.
  3. EbillingPermission object check.
  4. Updates the row: serializer update path (serializers.py:69-76 — UNIQUE_ID non-PRODUCT_FLOW rows are force-kept active) applied to the value fields; save (412-421). Since delta 0f37ed5 the serializer also validates via validate() (serializers.py:53-62): for PURCHASE_FLOW/SALES_FLOW UNIQUE_ID rows the value's starting_number is coerced to int (serializers.py:11-23) and a non-numeric value raises InvalidDataFormat "starting number should be a number" (serializers.py:16-21, dashboard/messages.py:30).

    unverified: which portal screens actually submit a non-numeric starting number — the transform looks like a fix for a reported bad-value case; no frontend evidence in scope.

  5. Response 200 with the updated value (422-428). Errors: 400 INCORRECT_DATA_FORMAT on validation (424-426); 500 on exception.

Effect: the merchant's credit limit/period is written to TenantServiceConfiguration(value-JSON) for their tenant; the miniapp refetches the list (config-context refetchCreditSettings) and the credit features (Credit service / CDXE / Sales) read the same row on their next request — pull-based (§5.5).

Miniapp branch (new in delta 0f37ed5): if request.data.get("mini_app") is True, the view runs only transfer.transfer_credit_settings(tenant_id) (1178) — which creates/updates the tenant's single master_settings credit_settings row (credit_limit/credit_period), using the platform DefaultServiceConfiguration row when present and otherwise the code default CREDIT_SETTINGS_DEFAULT (data_transfer.py:338-367, defaults.py:206-209) — then transfer.transfer_fiscal_essence(tenant_id) (1179, data_transfer.py:408) and returns 200 with the serialized FY data (1180-1186). The ERP CoA/config/terms transfer below is not run for miniapp tenants (code comment at 1176-1177).
  2. transfer_chart_of_account(tenant_id) (1189) — copies default COA accounts into the tenant's dashboard tables (data_transfer.py:15).
  3. transfer.configuration_transfer(tenant_id, coa_ok) (1192) — copies DefaultServiceConfiguration rows into TenantServiceConfiguration for the tenant (the tenant's entire service/module configuration baseline; data_transfer.py:88).
  4. transfer.transfer_fiscal_essence(tenant_id) (1194-1196) — creates the tenant's active TenantFiscalYear (+ currency/datepicker essence) and returns serialized FY data (data_transfer.py:408).

  8. Response 200 {message, data: <serialized FY data>} (1277-1283) — TMS stores data in ExternalTenantLink.fiscal_year as the "transferred" marker. Any failure → 500 SERVER_EXCEPTION (1285).

9. Business process walkthrough (non-technical)

9.1 A new eSewa merchant's configuration appears out of nowhere

When the eSewa wallet first registers a merchant (TMS external-register, doc 08 section 5.5), TMS asks this service's data-transfer endpoint to set up the merchant's company paperwork. Since delta 0f37ed5 the miniapp variant is deliberately lean: with the mini_app flag the service writes just one configuration row — the master_settings credit_settings row carrying the merchant's default credit limit and credit period (taken from the platform default row, or from a hard-coded fallback of credit period 15 / credit limit 100,000 when that default row is missing on older databases) — plus the merchant's fiscal year. The full ERP paperwork (approval workflows, invoice numbering, accounting accounts, payment terms, cost terms, TDS types) is only transferred for regular ERP tenants. From that moment the merchant's company has its own configuration rows. When the merchant then opens the miniapp, the app's startup step quietly calls the federated tenant/miniapp/ endpoint to fetch the master_settings block — inside it sits the credit_settings row: the merchant's default credit limit and credit period (how many days a customer has to pay). Every credit feature in the miniapp reads that same row, so one number is the single source of truth.

9.2 The merchant tightens credit

In Profile > Credit management the merchant sets "no customer may owe more than Rs 50,000, and must pay within 30 days". The miniapp posts the new values to the federated detail endpoint; the service validates the login (merchant, active subscription, permission) and updates only that company's row. There is no push — the next time any credit screen (or the backend credit services) reads the setting, they see the new values. That is what keeps a small merchant's risk rules simple: change it once, it applies everywhere.

10. Unknowns & assumptions

  • POST tenant/create/configuration/ (non-v1) declares no auth class (views.py:1050-1109): it lists all eSewa tenants from TMS and bulk-creates configuration rows; in this checkout nothing protects it beyond DRF defaults. The v1 single-tenant variant has the internal-password check. Flagged as a likely-missing guard (or an admin-only route in practice) — verify in ops.
  • No local callers for ensure-configuration/ (+ bulk) and for expose/ in the eSewa flow (portal-era services likely; those repos not in scope).
  • Pull-based propagation only — no cache invalidation, push event, or cache layer found in this repo; consumers always read fresh rows (section 5.5).
  • The federated detail GET (6.2) has no active frontend caller — only the list endpoint is used at boot; detail is used for POST updates.
  • eBilling tenant config rows (UNIQUE_ID non-PRODUCT_FLOW, NEGATIVE_INVENTORY, MASTER_SETTINGS/PRINT_TEMPLATE) are force-managed server-side (EbillingPermission + serializer force-active) — merchants cannot edit them.
