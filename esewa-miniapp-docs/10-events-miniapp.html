Events — Federated Miniapp Documentation

Scope: The eSewa miniapp surface of the events service — in-app notifications (read/list/mark-read + per-user preference) and miniapp activity logging — in the Django project EMAIL_SERVICE (repo E:/Work/events, DB events). Evidence: E:/Work/events/EMAIL_SERVICE/urls.py, notification_app/{urls,views,models,serializers,registry,tasks}.py, activity_log/{urls,views,models,serializers,registry,tasks}.py, dashboard/{generics,auth_backends,helpers,choices,views,messages,app_links}.py, kafka_consumers/handlers.py, EMAIL_SERVICE/{settings,celery}.py, .env, plus caller repos Sales, CDXE-REBOOT, ERP-Projectmaster, TMS-service, IAM-Backend, frontend miniapp-esewa.

1. Business overview (plain language for a NON-technical reader)

Providhy is a business-management platform with a wallet/credit miniapp for eSewa merchants (ESM) and their customers (ESU). The events service is the platform's shared "noticeboard and diary": it stores the little messages that pop up inside the miniapp ("New Credit Added", "Payment Received", "Overdue Alert") and it keeps a diary of what people did (who created a credit record, who settled a payment, when).

Merchants and customers do not talk to the events service for most of what happens behind the scenes. When a merchant grants a customer credit in the sales system, or a customer pays a payment request, those business services (Sales, CDXE) silently tell the events service "write a notice for this person". Later, when the customer opens the eSewa miniapp, the app asks the events service "what notices do I have?" and shows them, newest first, unread on top.

The events service also lets each person control which kinds of notices they want (payment requests, credit added, overdue alerts, due-date reminders). Turning one off stops that kind of notice from being written. And because the diary (activity log) records every credit/payment/dispute action with names and amounts, a merchant can audit exactly what happened and when — this is also the data behind the platform's audit reports.

Finally, the events service receives some of these "write a notice/diary entry" instructions over the company's internal message bus (Kafka) instead of direct service calls — same result, different wire.

  • DB: Postgres, DB name events (.env DB_NAME="events", settings EMAIL_SERVICE/settings.py:93-102; prometheus engine wrapper django_prometheus.db.backends.postgresql).
  • Apps (settings EMAIL_SERVICE/settings.py:33-51): email_app (out of scope), dashboard (shared helpers/auth), notification_app, activity_log, export_service (out of scope), providhy_kafka (shared Kafka lib), kafka_consumers (in-scope: consumes notification/activity/email topics).
  • Root URL mounts (EMAIL_SERVICE/urls.py:22-29): api/email/ -> email_app, api/ -> dashboard, api/notification/ -> notification_app.urls (line 26), api/activity_log/ -> activity_log.urls (line 27), api/export/ -> export_service. Dev public host: dev-events-api.providhy.com (.env EVENTS_BACKEND_URL).
  • Celery: broker redis://redis:6379/1, result backend django-db (EMAIL_SERVICE/settings.py:179-185); beat schedule in EMAIL_SERVICE/celery.py:17-54 (e.g. send-task-notification daily 06:00 for invoice due-date alerts).
  • Kafka: KAFKA_URL=kafka-crs:9092 (SASL_SSL/SCRAM-SHA-512), KAFKA_ENABLED=True default (EMAIL_SERVICE/settings.py:321-338). Events is a consumer: kafka_consumers/handlers.py:69-70 registers handlers for activity-log and notification creation topics, :50 for email.

3. Authentication & authorization

Two mechanisms are used on the miniapp surface:

3.1 Federated (frontend-facing) — 4 endpoints

Base class FederatedAuthenticationView (dashboard/generics.py:10-14):

  • authentication_classes = [FederatedIdentityAuthentication] (imported from dashboard/auth_backends.py:5, class at auth_backends.py:92-125)
  • required_user_type = choices.ExternalEntityType.values = ["ESM", "ESU"] (dashboard/choices.py:242-244)
  • required_app_scope = choices.ExternalProviderChoices.values = ["esewa"] (dashboard/choices.py:238-240)
  • permission_classes = [HasFederatedEntityPermission] (auth_backends.py:128-143)

Events' copy of FederatedIdentityAuthentication.authenticate (dashboard/auth_backends.py:93-125):

  1. Extracts the JWT via get_access_token(request, access_token_key="miniAppAccessToken") (auth_backends.py:95; helpers.py:141-168) — order: cookie miniAppAccessToken -> Authorization: Bearer -> body field miniAppAccessToken.
  2. Reads the X-MINIAPP-TOKEN header and POSTs {"token": } + that header to IAM at {IAM_API}/api/external/token/verify/ (validate_token_with_external_iam, auth_backends.py:146-162). IAM's VerifyAuthTokenView (IAM-Backend/federated_identity/views.py:447-491) first runs utils.verify_request_origin (views.py:455; utils.py:78-84) which verifies the TOTP (pyotp, secret ESEWA_TOTP_SECRET_KEY, valid_window=settings.TOTP_VALID_WINDOW; missing header tolerated only in UAT/DEVELOPMENT), then validates the JWT via its serializer and returns 200 "Token is valid." — the TOTP is checked by IAM, not by events.
  3. Back in events, the JWT is decoded locally without signature verification (TokenBackend(algorithm="HS256").decode(token, verify=False), auth_backends.py:102); claims are read: user_id, tenant_id, external_identifier, provider_code, user_type, tenant_root, username, subscribed_services, user_permissions (auth_backends.py:103-114) and stashed on the request. These claims are minted by IAM in FederatedTokenRefreshSerializer.add_custom_fields_to_token (IAM-Backend/federated_identity/serializers.py:84-96; username is already get_username()-processed).
  4. Returns (user_id, tenant_id) -> DRF sets request.user = user_id, request.auth = tenant_id (views rely on this, e.g. notification_app/views.py:1017-1018).
  5. Errors: missing token -> 401 INVALID_TOKEN (auth_backends.py:96-97); IAM connection error -> 503 CONNECTION_TIMEOUT (auth_backends.py:116-122); anything else -> 401 via CustomAuthenticationFailed (auth_backends.py:124-125).

Permission layer HasFederatedEntityPermission (auth_backends.py:128-143): request.provider_code must be in required_app_scope (only esewa) and request.user_type in required_user_type (ESM or ESU), else 403 (PermissionError). If a view omits either class attribute, the permission itself raises 403.

Comparison with the canonical IAM implementation (IAM-Backend/federated_identity/auth_backends.py:10-25): the canonical class checks the TOTP origin in the service itself and resolves identity from request-body fields provider_code + external_identifier via a local ExternalEntity DB lookup (no JWT). The events copy instead treats the JWT as the identity carrier, delegates TOTP verification to IAM's verify endpoint, performs no ExternalEntity lookup in events, and adds the provider/user-type permission gate. No other copy-specific protections (no local TOTP check, no permission classes of its own).

Frontend side (miniapp-esewa): every request carries Authorization: Bearer and X-MINIAPP-TOKEN: (src/services/api.ts:34-56); the TOTP is computed server-side in a Next.js action with speakeasy.totp({secret: process.env.CUSTOM_KEY, step: 20}) (src/actions/otp.ts:15-21). (Whether IAM's ESEWA_TOTP_SECRET_KEY equals the frontend CUSTOM_KEY is assumed, not verified in this workspace.)

Endpoints using the federated base class: miniapp/list/, miniapp/mark-read/, preference/, preference// (see section 4.1).

3.2 Internal service-to-service — the "miniapp write" endpoints

InternalAuthenticationBackend (dashboard/auth_backends.py:165-176): accepts password (body or query) which must equal env INTERNAL_PASS (validate_internal_pass, helpers.py:81-84; dev value in .env: wRdDGGjiIQiBswoff2C); optional tenant_id/external_identifier become (request.user, request.auth). No JWT, no TOTP. Used by miniapp/notify-user/, activity_log/miniapp/log-activity/, activity_log/miniapp/list/ (and other internal endpoints) — the frontend never calls them; the eSewa backends (Sales/CDXE/Projectmaster/TMS/IAM celery tasks) do.

5. Per-endpoint flow trace

5.1 GET /api/notification/miniapp/list/ — list the user's in-app notifications

  • Request: query params only: module_type (optional str, must be a MainModule value), page (int), count (int, page size, max 100). The frontend also sends q (notifications.ts:21-24) but the view ignores it.
  • Auth: federated chain (section 3.1) -> request.user = user_id, request.auth = tenant_id, request.external_identifier, request.provider_code = "esewa", request.user_type = ESM/ESU.
  • Flow:
    1. DRF auth: FederatedIdentityAuthentication.authenticate (dashboard/generics.py:11 -> dashboard/auth_backends.py:93-125), incl. IAM verify call.
    2. HasFederatedEntityPermission (auth_backends.py:128-143): provider_code in {esewa}, user_type in {ESM, ESU}.
    3. identifier = request.external_identifier (notification_app/views.py:1017); tenant_id = request.auth (views.py:1018).
    4. Optional module_type validated by validate_choice (views.py:1020; dashboard/views.py:59-67) — raises ValidationError otherwise.
    5. Lookup (views.py:1021-1023): rows where (user = identifier OR user = tenant_id) with submit_user IS NULL, OR (submit_user = identifier OR submit_user = tenant_id).
    6. filter(lookup).order_by("-tag", "-created") (views.py:1025-1027) — see Unknowns: -tag sorts tag=true (read) rows first; documented as coded, intent unverified.
    7. Paginate with CustomPagination (page_size=100, count param, max 100 — dashboard/views.py:35-38; views.py:1029-1030).
    8. Serialize with NotificationChannelSerializer (notification_app/serializers.py:24-27; excludes modified, tenant_id) -> paginated 200 (views.py:1032-1033).
  • DB: reads NotificationChannel (fields of note: user, submit_user, tag, created, message, title, entry_type, entry_id).
  • Outbound calls: IAM POST /api/external/token/verify/ once per request (auth_backends.py:146-162). No eSewa push, no email, no Kafka — this is a pure read of in-app rows.
  • Errors: 401 (bad/missing token or TOTP — auth_backends.py:96-97,124-125; IAM 401 propagates as CustomAuthenticationFailed), 503 (IAM connection timeout, auth_backends.py:116-122), 403 (provider/user-type mismatch, auth_backends.py:136-142), ValidationError for bad module_type (dashboard/views.py:61-62 -> custom exception handler, settings.py:221-224).

5.2 POST /api/notification/miniapp/mark-read/ — mark notifications read/unread

  • Request: JSON body: id (list of notification ids, optional default []), tag (bool, default true = mark read).
  • Auth: federated (same chain); additionally user = helpers.get_username(request.username) (views.py:1041; helpers.py:87-92 — strips the last _-suffixed segment of the JWT username).
  • Flow:
    1. Auth chain (as 5.1).
    2. ids = request.data.get("id", []) (views.py:1038); tag_value = request.data.get("tag", True) (views.py:1039).
    3. identifier = request.external_identifier (views.py:1040); user = get_username(request.username) (views.py:1041).
    4. instances = NotificationChannel.objects.filter(Q(user=identifier, submit_user=None) | Q(submit_user=user)) (views.py:1044-1046) — the id list is not used in the filter.
    5. Guard: if instances.count() != len(ids) -> 404 "Notification not found" (views.py:1047-1051).
    6. instances.update(tag=tag_value) (views.py:1052) — updates all matched rows.
    7. Serialize with NotificationStatusSerializer (serializers.py:30-33; excludes created, modified) -> 200 (views.py:1053-1054).
  • DB: reads + updates NotificationChannel.tag.
  • Outbound calls: IAM verify only.
  • Errors: 404 on count mismatch; 401/403 as in 5.1.
  • Observed inconsistency (code as written): rows created by notify-user/ (5.5) always have submit_user set and user = a sender string, so clause 1 (user=identifier AND submit_user IS NULL) and clause 2 (submit_user=) rarely match those rows — i.e., this endpoint appears to operate on the legacy IAM-user notification shape rather than the miniapp rows. No frontend caller of this endpoint exists in the workspace (see 10/11).

5.3 GET /api/notification/preference/ — get (and auto-seed) notification preferences

  • Request: none (frontend may pass query params; backend ignores them — profile.ts:96-101).
  • Auth: federated -> tenant_id = request.auth, user_id = request.user (views.py:873-874).
  • Flow:
    1. Auth chain.
    2. preferences = NotificationPreference.objects.filter(tenant_id=tenant_id, user=user_id) (views.py:875-877).
    3. If none exist: build one row per NotificationPreferences choice (payment_request, credit_added, credit_overdue, due_date_reminder — choices.py:227-231) with external_identifier = JWT claim, channel="in_app" (choices.py:234-236), enabled=True (views.py:878-892), then bulk_create (views.py:892).
    4. Serialize with NotificationPreferencesSerializer (serializers.py:36-39; excludes created, modified) -> 200 (views.py:893-896).
  • DB: reads, conditionally creates NotificationPreference (unique on tenant_id+user+preference_type+channel, models.py:104-110).
  • Outbound calls: IAM verify only.
  • Errors: 401/403 as in 5.1.

5.4 POST /api/notification/preference// — toggle one preference

  • Request: path pk (int; public-id tokens accepted by PublicIdMiddleware), body {"enabled": bool} (required).
  • Auth: federated.
  • Flow:
    1. Auth chain.
    2. tenant_id, user_id (views.py:899-900).
    3. NotificationPreference.objects.get(pk=pk, tenant_id=tenant_id, user=user_id) (views.py:903-905).
    4. enabled missing/None -> 400 "Request Failed. Try again with valid data" (views.py:906-911).
    5. If value changed: preference.enabled = enabled; preference.external_identifier = request.external_identifier (refreshed from JWT); save() (views.py:913-916).
    6. 200 {"status": "Record updated"} (views.py:917-919).
    7. DoesNotExist -> 404 "Record not found" (views.py:920-924).
  • DB: reads + updates NotificationPreference.enabled/external_identifier.
  • Outbound calls: IAM verify only.
  • Errors: 400, 404, plus auth errors.

5.5 POST /api/notification/miniapp/notify-user/ — write a miniapp notification (internal)

  • Request: JSON body: password (str, required = INTERNAL_PASS), sending_user (str — sender's external_identifier or tenant_id), receiving_user (str — recipient's external_identifier or tenant_id), module_type (str, e.g. sales/cdxe/iam), entry_type (str, e.g. PR1208 credit record), service_type (str, e.g. creation), entry_id (int/public-id, optional), title (str, optional), message (str, optional), message_data (dict, optional — template context), notification_type (str, default basic).
  • Auth: InternalAuthenticationBackend (views.py:928; auth_backends.py:165-176) — password in body/query; plus an explicit second check inside the view (views.py:935-937).
  • Flow:
    1. Backend password check -> 401 on mismatch (auth_backends.py:174-175).
    2. View re-check -> 401 (views.py:935-937); logs the full payload (views.py:938).
    3. Look up (module_type, entry_type, service_type) in registry.mini_app_notification_msg_reg -> (title_template, message_template) and in registry.mini_app_notificaton_preference_reg -> preference_type (views.py:931-932, 952-955, 973-975; registry.py:240-241, 10-239).
    4. If message and title were not both supplied: use the templates; message = message_template.format(**message_data) (views.py:951-967). No template for the triple -> 400 INCORRECT_DATA_FORMAT echoing the request data back (views.py:956-963). Still missing after templating -> 400 (views.py:968-972).
    5. Preference gate: if a preference_type is registered, query NotificationPreference.filter(Q(external_identifier=receiving_user) | Q(tenant_id=receiving_user), preference_type=...) (views.py:983-987). Create the notification only when no row exists or the row is enabled (views.py:989-990); a disabled row suppresses it. If no preference_type is registered for the triple, always create (views.py:980-981).
    6. NotificationChannel.objects.create(user=sending_user, submit_user=receiving_user, module_type=..., service_type=..., entry_type=..., title=..., message=..., notification_type=..., entry_id=...) (views.py:992-1002) — tenant_id is not set (row has tenant_id = NULL); inside a transaction.atomic() (views.py:934).
    7. 200 {"status": "Notification created successfully!"} (views.py:1003-1004).
  • DB: reads NotificationPreference; creates NotificationChannel (fields: user=sender, submit_user=recipient, entry_id typed PublicId, tag default false).
  • Outbound calls: none — no eSewa API push, no email, no Kafka. Delivery to the device is purely via the miniapp polling miniapp/list/.
  • Errors: 401 (password), 400 (template/format; ValidationError handler views.py:1006-1010). Note message_template.format(**message_data) raises KeyError if a placeholder is missing from message_data — unhandled -> 500 (no try around it).

Registered message templates (notification_app/registry.py:10-202): CDXE connection lifecycle (request sent/received/approved/rejected), SALES credit record (due tomorrow, overdue, new credit, credit edited), credit settlement (customer paid, settlement recorded), payment request (created/approved/rejected), credit dispute (raised/cancelled/resolved-by-edition/resolved-by-deletion), IAM subscription lifecycle (trial started/expiring/expired, subscription expiring/expired, upgrade successful, renewal successful). Preference-mapped triples (registry.py:203-239): credit_added, payment_request, due_date_reminder, credit_overdue.

8. Business process walkthrough (non-technical)

8.1 "Maria is a merchant who extends credit to a customer" Maria (an eSewa merchant) opens her miniapp, goes to credit management, and grants her customer Sita NPR 10,000. Her phone sends that to the sales service. Sales books the credit on its own ledger and, at the same moment, queues two background jobs: "send a notice" and "write a diary entry". A few seconds later both jobs arrive at the events service with a shared internal password. Events looks up the standard wording for "credit created" ("... added NPR 10,000 credit — new balance ..."), checks whether Sita still wants that kind of notice (the preference page), and writes a notice row addressed to Sita. It also writes a diary row: "merchant added NPR 10,000 credit against Sita at ". When Sita opens her miniapp, the app asks events "what's my inbox?" and events answers with the new notice. No SMS, no email, no push to eSewa's servers — the notice simply exists in the shared inbox until Sita opens the app (see 5.5/5.7 for the mechanism).

8.2 "Sita pays back" (payment request + settlement) Maria can also request money from Sita. The request is created in the CDXE (connections/data-exchange) service, which tells events to notify Sita ("Maria requested NPR 10,000 from you"). Sita pays inside the miniapp; the payment is processed by the sales service (which coordinates with the eSewa payment backend). Once the payment succeeds, sales tells events "a settlement was approved", and a new notice appears for Maria: "Sita paid NPR 10,000 — new balance ...". Every one of these steps also leaves a diary entry, so Maria's audit trail later reads: request created -> payment approved -> credit settled.

8.3 "The audit diary" Behind every action above, the events service stores a row: who did it (by external identifier), what kind of action, the business document reference, a human-readable sentence, and the timestamp. The same diary feeds the platform's report service (which pulls date-range slices via an internal endpoint) and the tenant data-deletion flow. For eSewa users, the diary rows are written without a tenant stamp (tenant is NULL) and keyed by the user's identifier — that's how the miniapp-facing list endpoint finds exactly "this person's" entries and how a later account deletion can sweep them.

8.4 "Sita turns off payment-request notices" In the miniapp settings, Sita flips "Payment Request" off. Her phone calls events' preference endpoint with her JWT + TOTP; events finds her row (auto-created on first visit, all four types on) and sets that one to disabled. From then on, when CDXE creates a payment request addressed to her, events checks her preference and silently skips writing the notice (5.5, step 5) — the diary entry, however, is still recorded.

11. Unknowns & assumptions

  • activity_log/miniapp/list/ has no caller in this workspace. It requires INTERNAL_PASS, so the frontend cannot call it directly; no backend in E:/Work references the path. Either an out-of-workspace service calls it, or it is legacy. (Verified by grep across all local repos, patterns activity_log/miniapp and miniapp/list.)
  • miniapp/mark-read/ has no frontend caller in miniapp-esewa (grep mark-read/markRead -> none). It exists, is federated-auth, and may be used by another client or be legacy.
  • mark-read filter vs ids (observed, code as written): the view filters by user/submit_user, never by the supplied id list, compares the count of matches to len(ids), then updates all matches (notification_app/views.py:1044-1052). Combined with the fact that notify-user rows always have submit_user set and user = a sender string, this endpoint appears unable to mark miniapp rows read. Flagged as an inconsistency; intent unverified.
  • order_by("-tag", "-created") on miniapp/list puts tag=true (read) rows before unread ones (notification_app/views.py:1026). If "unread on top" was the intent, this is inverted; documented as coded.
  • tenant_id NULL on miniapp rows: notify-user and log-activity never set tenant_id (views.py:992-1002; activity views.py:526-535). Consequences: miniapp/list and mark-read scope purely on user/submit_user strings; tenant-data-deletion must use IAM is-registered/ to find the identifiers to sweep (dashboard/views.py:106-118). Assumed to be by design.
  • JWT decoded with verify=False in the events copy (dashboard/auth_backends.py:102): signature/expiry trust is delegated to IAM's verify call (IAM re-validates via serializer). Assumed safe due to IAM round-trip on every request; noted as a design observation.
  • TOTP secret identity unverified: the frontend computes TOTP from its own CUSTOM_KEY (miniapp-esewa/src/actions/otp.ts:15) while IAM validates against ESEWA_TOTP_SECRET_KEY (IAM-Backend/federated_identity/utils.py:67-71). The two are assumed to be the same value; not comparable from this workspace (IAM's env not inspected for that key).
  • Kafka literal topic names unknown: providhy_kafka (Topics/Actions) is a private package not vendored in E:/Work; only the symbolic names (Topics.ACTIVITY_LOG/NOTIFICATION/EMAIL, Actions.*_CREATED) are evidenced (kafka_consumers/handlers.py:11-70).
  • KAFKA_PRODUCER_SERVICE is empty in events' .env — the events service has no producer gateway configured here; it only consumes. Whether other services actually prefer the Kafka path over the direct HTTP miniapp endpoints (KAFKA_ENABLED flags) is not verifiable from events alone.
  • /api/activity_log/create/ celery arg mismatch (potential bug): send_activity_log.delay passes 9 positional args but the task defines 14 required parameters (activity_log/views.py:175-185 vs activity_log/tasks.py:18-33). Would TypeError in the worker if invoked; no runtime evidence either way.
  • /api/activity_log/create-export-log/: no authentication, and the create omits the NOT NULL module_type (activity_log/views.py:329-335 vs models.py:11-13) -> expected IntegrityError/500 if called. Anomaly, flagged.
  • Caller-side 201 mishandling: Sales/CDXE send_activity_log tasks treat any status != 200 as failure and log an error, yet log-activity returns 201 (Sales/miniapp/tasks.py:107; CDXE-REBOOT/miniapp/tasks.py:94). The log row is still created server-side; only the caller's log line is wrong.
  • IAM notify-user payload hardcodes module_type=SALES (IAM-Backend/federated_identity/tasks.py:49) even though the subscription templates live under the IAM module (events registry.py:145-199). The registry lookup for (sales, PR2502, trial_subscription) does not exist in events' registry, and the IAM call site (views.py:244-254) supplies no title/message — so that IAM call would hit the "no template" 400 path. Flagged as a likely defect (unverified at runtime).
  • get_access_token also accepts a cookie named miniAppAccessToken (helpers.py:157) — no miniapp client was found that sets it; noted, not used.
  • INTERNAL_PASS in plaintext in .env (dev checkout; value differs from the commented sample) — service-to-service auth is a shared secret; noted for the global security doc.
  • Frontend q param on notification list is ignored by the view (notifications.ts:22 vs views.py:1019) — minor.
  • Assumed (not re-verified in this task): IAM login/refresh flows per SHARED-CONTEXT.md; eSewa payment mechanics inside the Payment-Service esewa app (no events references found there).
