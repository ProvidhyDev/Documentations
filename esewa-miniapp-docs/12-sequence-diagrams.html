12 — End-to-End Sequence Diagrams

The cross-service flows the business actually runs, in the order a merchant/customer experiences them. Each diagram is lifted verbatim from the owning service doc (source cited); the per-service docs contain the endpoint-level call maps and file:line evidence for every arrow. Arrows between services are HTTP (sync) unless marked celery (async). TOTP (X-MINIAPP-TOKEN) + JWT verification against IAM happens on every federated request and is shown in detail once (section 3).

1. Login — minting the miniapp token

The wallet hands the miniapp an eSewa token + external identifier; IAM exchanges it for a JWT whose claims (tenant_id, user_type, subscribed_services, permissions) drive every later call. Refresh + 401 handling: doc 07 Part B §B.3.

sequenceDiagram
    participant FE as miniapp-esewa (Next.js)
    participant IAM as IAM /api/external/
    participant REDIS as Redis db 7
    participant KAFKA as Kafka (activity log)
    FE->>FE: compute TOTP from CUSTOM_KEY (speakeasy, step 20) - otp.ts:15-21
    FE->>IAM: POST external/token/ with token, external_identifier, encrypted_text, provider_code + X-MINIAPP-TOKEN
    IAM->>IAM: verify_request_origin TOTP check (utils.py:78-84)
    IAM->>IAM: AES-256-ECB decrypt envelope, id must match external_identifier (views.py:330-346)
    IAM->>IAM: ExternalEntity lookup by provider + identifier (auth_backends.py:18-21)
    IAM->>IAM: mint RefreshToken + custom claims (views.py:361-378)
    IAM->>REDIS: save access jti per user (jti invalidation)
    IAM-->>FE: 200 access, refresh, payload + miniApp cookies
    IAM->>KAFKA: activity log (views.py:417-444)
    Note over IAM: AuthAuditMiddleware records EXTERNAL_LOGIN (auth_audit.py:27), EntityUserActivityTrackingMiddleware appends EntityActivity (middleware.py:15)

Source: doc 03 §7.1

2. First-time registration & tenant provisioning

End to end: terms acceptance -> IAM external-register -> TMS tenant provisioning -> Configuration data-transfer (default rules/COA/FY copied into the tenant) -> ExternalTenantLink marker. The IAM-side half of this flow (token mint at registration, funnel event) is doc 03 §7.2; the Configuration-side transfer is doc 09 §6.3.

sequenceDiagram
    participant W as eSewa Wallet app
    participant F as miniapp-esewa (Next.js)
    participant I as IAM-Backend
    participant T as TMS-service
    participant C as Configuration-Service
    participant P as Package-Service

    W->>F: opens miniapp, provides miniAppAuthToken + merchant identifier
    F->>W: requestFromMiniApp MERCHANT_DETAIL
    W-->>F: encrypted merchant details
    F->>I: POST api/external/register/ (token, provider_code=esewa, entity_type=ESM, encrypted_text, external_identifier, user_details)
    I->>I: AES-decrypt + verify identity match (views.py:262-272)
    I->>T: POST api/tenant/external-register/ (internal password)
    T->>C: POST api/sanitization/form-data/ (name)
    T->>T: Company(esewa) + Tenant ES_xxxxxx (verified, active)
    T->>P: GET api/check-package/ (provider_code, module payment)
    T->>T: TenantPackage + TenantPackageModule + TenantContract
    T->>T: trial CREDIT Subscription + SubscriptionLog (payment_status=credit)
    T->>C: POST api/dashboard/data-transfer/ (row-locked, once per identity)
    C-->>T: fiscal year data
    T-->>I: tenant_id + subscribed_services + fiscal_year
    I->>I: ExternalEntity + CustomUser, funnel ONBOARDED, username_<tenant>
    I-->>F: access/refresh + payload (user_type=ESM, subscribed_services)
    F->>F: stores tokens, redirects to /dashboard

Source: doc 08 §6.1

3. Per-request federated validation (shown once, applies everywhere)

Every miniapp request to any service: JWT + X-MINIAPP-TOKEN -> IAM verify -> local claim decode (verify=False) -> permission gate. Per-service auth variants and their divergences: doc 02 §4, each service doc §3.

sequenceDiagram
    participant FE as miniapp-esewa
    participant SVC as ERP miniapp service (Sales/CDXE/PM/Payment/TMS/Config/events)
    participant IAM as IAM /api/external/token/verify/
    FE->>SVC: miniapp business call + Bearer access + X-MINIAPP-TOKEN + miniApp cookies
    SVC->>SVC: FederatedIdentityAuthentication copy: read token (Sales auth_backends.py:180-215)
    SVC->>IAM: POST external/token/verify/ with token, forwarding X-MINIAPP-TOKEN (Sales auth_backends.py:218-229)
    IAM->>IAM: TOTP check + simplejwt signature/exp check (views.py:455-468)
    IAM-->>SVC: 200 Token is valid (or 401)
    SVC->>SVC: decode JWT verify=False, read claims tenant_id, user_type, external_identifier, subscribed_services (Sales auth_backends.py:192-206)
    SVC-->>FE: business response

Source: doc 03 §7.3

4b. Merchant invites the customer; customer approves (connection)

CDXE stores the relationship (Connection + ConnectionIdentityLink) with a 5-digit code; decline cascade-deletes both rows. The internal validation call into Projectmaster (validate-customer-connection) is traced in doc 06 §7.4.

sequenceDiagram
    participant M as "Merchant (ESM) / miniapp-esewa"
    participant C as "CDXE api/miniapp"
    participant I as "IAM"
    participant P as "Projectmaster"
    participant E as "Events"
    participant U as "Customer (ESU) / miniapp-esewa"
    M->>C: "POST create-connection/ (JWT + X-MINIAPP-TOKEN)"
    C->>I: "POST api/external/token/verify/ (JWT + TOTP header)"
    I-->>C: "200 (TOTP + JWT verified)"
    C->>I: "POST api/external/is-registered/ (customer id)"
    C->>P: "POST api/miniapp/validate-customer-connection/"
    P-->>C: "is_provider_user, customer name/tenant"
    C->>C: "INSERT Connection(pending, 5-digit code) + link"
    C--)E: "notify-user x2 + log-activity (celery)"
    C-->>M: "201 {connection_id: code, ...}"
    Note over E,U: "customer sees the request in-app"
    U->>C: "POST approve-reject-connection/{code}/ {status: approved}"
    C->>P: "POST validate-customer-connection/ (name)"
    C->>I: "POST is-registered/ (merchant id)"
    C->>C: "Connection: approved, code_validated, code cleared"
    C--)E: "notify-user (approved) + log-activity (celery)"
    C-->>U: "200"

6. Customer-initiated settlement (customer pays outstanding credit)

CDXE is the customer-facing proxy (dry-run commit=false -> signed commit=true); the CDXE-internal view of the same flow (HMAC verify step) is doc 05 §7.2. NOTE: the frontend defines the signed flow but does not send the SIGNATURE header in this checkout — flagged unshipped in docs 05 §11 and 07 §C.5.

sequenceDiagram
    participant FE as miniapp-esewa (customer)
    participant CDXE as CDXE
    participant SALES as Sales
    participant PM as Projectmaster
    participant PAY as Payment
    participant EV as Events (celery)
    FE->>CDXE: POST miniapp/credit/pay/ (customer view)
    CDXE->>SALES: POST /api/miniapp/credit/pay/ (internal password)
    SALES->>PM: POST /api/miniapp/customer-check/
    PM-->>SALES: customer data
    SALES->>SALES: settlement APPROVED + items, credits reduced (tx)
    SALES->>PAY: POST /api/esewa/payment/request/ (status completed, transaction_id)
    PAY-->>SALES: 200
    SALES-->>CDXE: 200 {id}
    CDXE-->>FE: 200
    SALES--)EV: notify merchant + customer, activity log
    Note over SALES,PAY: wallet charge itself is executed by Payment/eSewa gateway (outside Sales trace)

Source: doc 04 §7.2

7. Merchant-initiated payment request -> wallet payment -> settlement

The full lifecycle: request (PENDING settlement, credits untouched) -> wallet charge (outside these repos; mock-mode verdict in doc 07 Part C) -> Payment-Service pay -> Sales settle (approved/rejected/draft) -> Events. Customer-side payment request view: doc 10 §7.3; FE/ownership verdict: doc 07 §C.1.

sequenceDiagram
    participant FE as miniapp-esewa (merchant)
    participant CDXE as CDXE
    participant SALES as Sales
    participant PM as Projectmaster
    participant PAY as Payment
    participant ESEWA as eSewa wallet
    participant EV as Events (celery)
    FE->>CDXE: POST miniapp/payment/request/
    CDXE->>SALES: POST /api/miniapp/payment/request/ (internal password)
    SALES->>PM: POST /api/miniapp/customer-check/ (verified provider user)
    PM-->>SALES: customer data
    SALES->>SALES: settlement PENDING + items (credit balances unchanged, tx)
    SALES->>PAY: POST /api/esewa/payment/request/
    PAY-->>CDXE: payment request created (wallet collect link)
    CDXE-->>FE: 201
    ESEWA->>PAY: customer pays (completed, transaction_id)
    PAY->>SALES: POST /api/miniapp/payment/request/settle/ (status completed)
    SALES->>SALES: settlement APPROVED, credit remaining -= allocation (tx)
    SALES-->>PAY: 200
    SALES--)EV: notify merchant + customer, activity log
    Note over PAY,SALES: declined maps to rejected, cancelled maps to draft (views.py:1595-1601)

Source: doc 04 §7.3

8. Dispute lifecycle

Raise (guards: unpaid, no settlement, no pending dispute) -> resolve by credit edit or deletion -> customer cancel; every transition notifies Events. CDXE-facing traces: doc 05 §5 (dispute endpoints).

sequenceDiagram
    participant FE as miniapp-esewa
    participant CDXE as CDXE
    participant SALES as Sales
    participant EV as Events (celery)
    FE->>CDXE: POST miniapp/dispute/raise/
    CDXE->>SALES: POST /api/miniapp/dispute/raise/ (internal password)
    SALES->>SALES: save CreditDispute (issued, CD-)
    SALES-->>FE: 201 {id, amount}
    FE->>SALES: POST /api/miniapp/credit/detail/{id}/ (dispute_data resolved)
    SALES->>SALES: dispute RESOLVED (resolution_by_edition)
    SALES--)EV: notify customer, activity log
    FE->>CDXE: POST miniapp/dispute/cancel/{id}/
    CDXE->>SALES: POST /api/miniapp/dispute/cancel/{id}/ (internal password)
    SALES->>SALES: dispute CANCELLED
    SALES-->>FE: 200

Source: doc 04 §7.4

9. Customer deletion (guarded cross-service cascade)

Pending payment request blocks deletion (Payment exists-check); Sales records + CDXE connection cleaned up; soft delete. CDXE-side termination: doc 05 §7.4.

sequenceDiagram
    autonumber
    participant FE as eSewa miniapp (Next.js)
    participant PM as Projectmaster
    participant PAY as Payment
    participant SALES as Sales
    participant CDXE as CDXE
    participant EV as Events

    FE->>PM: DELETE /api/miniapp/customer/detail/{pk}/
    PM->>PAY: POST /api/esewa/payment/request/exists/ (tenant_id, customer_identifier, provider_code)
    alt payment request in flight
        PAY-->>PM: {"exists": true, ...}
        PM-->>FE: 400 "cannot be deleted right now"
    else no pending payment request
        PAY-->>PM: {"exists": false}
        PM->>SALES: POST /api/miniapp/records/delete/customer/ (tenant_id, customer_identifier)
        SALES-->>PM: ok (errors swallowed per-task)
        opt customer is a provider user
            PM->>CDXE: POST /api/miniapp/connection/delete/customer/ (user_identifier, customer_identifier, provider_code)
            CDXE-->>PM: ok
        end
        PM->>PM: Customer.active_status = "inactive"
        PM->>EV: POST /api/activity_log/miniapp/log-activity/ (service_type=inactive)
        PM-->>FE: 204 No Content
    end

Source: doc 06 §7.3

10. Subscription upgrade (merchant's own subscription)

initiate (PENDING Payment + Subscription) -> verify (activate + TenantPackage/TenantPackageModule + IAM expiry refresh) -> cancel (unused in FE). Frontend/upgrade-page view: doc 07 §C.1 (subscription purchase). Mock-mode + payment_period mismatch caveats: doc 08 §10.

sequenceDiagram
    participant F as miniapp-esewa (UpgradePage)
    participant P as Package-Service
    participant T as TMS-service
    participant E as Events-service

    F->>P: GET miniapp/modules/?service=PR2600
    P-->>F: module list (id)
    F->>P: GET miniapp/modules/{id}/?service=PR2600&payment_period=monthly
    P-->>F: price_break_down + payment_period
    F->>T: POST api/miniapp/subscriptions/initiate/ (payment_period, module_id)
    T->>P: GET api/check-module/ (price and vat)
    T->>T: Payment(pending) + BillItem + Subscription(pending) + SubscriptionLog
    Note over F,T: transaction_id is a random 12-char stub, no gateway call
    F->>T: POST api/miniapp/subscriptions/verify/ (transaction_id)
    T-->>T: mock verify success (ESEWA_MOCK_MODE default true)
    T->>T: Payment paid, Subscription active, TenantPackage+Module created
    T->>E: POST api/notification/miniapp/notify-user/ (celery, async)
    T-->>F: 200 payment_id, transaction_id, amount, module_id
    F->>F: toast "Subscription successful", back to /profile

Source: doc 08 §6.3

    EV->>EV: NotificationChannel filter by identifier/tenant, order by -tag,-created [notification_app/views.py:1021-1027]

12. OMS merchant resolution (first order)

OMS third-party -> IAM merchant-token verify/mint -> merchant resolution; supports the OMS provider_code surface alongside eSewa.

sequenceDiagram
    participant OMS as third-party OMS backend
    participant IAM as IAM /api/external/oms/
    participant TMS as TMS-service
    OMS->>IAM: POST oms/merchant/resolve/ with provider_code, merchant_id, name, contact + shared password
    IAM->>IAM: per-provider row lock, look up entity (oms_views.py:142-160)
    alt first sight
        IAM->>IAM: create CustomUser + ExternalEntity (OMS_MERCHANT, product_code=uuid) (oms_views.py:164-178)

    else already registered
        IAM-->>OMS: 200 tenant_id
