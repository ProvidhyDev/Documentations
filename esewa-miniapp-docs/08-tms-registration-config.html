TMS-service — eSewa Miniapp Registration, Onboarding & Configuration Surface

Federated miniapps documentation, part 08. Scope: the TMS miniapp app, the tenant_management endpoints used in the eSewa miniapp registration/onboarding journey and configuration, and the TMS payment app's role (or lack of one) in miniapp subscription payments. Every other TMS endpoint (portal/CMS tenant management) is out of scope; see SHARED-CONTEXT.md for house rules.

3. Auth mechanism on the miniapp surface

All four public miniapp views and TenantTrakerMiniapp use FederatedIdentityAuthentication (dashboard/auth_backends.py:147-175) plus ExternalUserPermission with required_user_type = "ESM" (Esewa Merchant; auth_backends.py:41-43,166-168,369-371; choices.py:352-354).

Flow (TMS side):

  1. JWT extracted via helpers.get_access_token(request, access_token_key="miniAppAccessToken") (auth_backends.py:154) — from cookie, Bearer header, or request body key miniAppAccessToken (helpers.py:401+). IAM sets the cookie key miniAppAccessToken (IAM-Backend/federated_identity/views.py:196-202, 397-403).
  2. validate_token_with_external_iam(token, headers={X-MINIAPP-TOKEN: <TOTP>}) (auth_backends.py:159-164) POSTs the access token plus the X-MINIAPP-TOKEN header to IAM {IAM_SERVICE}api/external/token/verify/ (auth_backends.py:186-190). IAM's VerifyAuthTokenView (IAM-Backend/federated_identity/views.py:447-491) first enforces verify_request_origin (utils.py:78-84): a missing X-MINIAPP-TOKEN header is only accepted in UAT/DEVELOPMENT; otherwise the TOTP is verified with pyotp (secret = settings.ESEWA_TOTP_SECRET_KEY = CUSTOM_KEY_ESEWA, settings.py:207; 6 digits, interval 20, window ±5, settings.py:286-288). Then the JWT itself is validated.
  3. Back in TMS, the JWT is decoded locally without signature verification (api_key=False, verify=False, auth_backends.py:166-167) purely to populate request fields: user_id, tenant_id, subscribed_services, provider_code, user_type, tenant_root, username, external_identifier, subscription_expired (auth_backends.py:169-174). It returns (user_id, tenant_id) → DRF sets request.user = user_id, request.auth = tenant_id; the views read request.auth as tenant_id (views.py:68).
  4. ExternalUserPermission (auth_backends.py:178-204): rejects with 403 when request.user_type != view.required_user_type (ESM).

Frontend half: every axios request (except website/terms/web/*, api.ts:47-49) gets Authorization: Bearer <access> and a fresh X-MINIAPP-TOKEN computed by speakeasy TOTP with secret process.env.CUSTOM_KEY, step 20 (src/actions/otp.ts:5-24, src/services/api.ts:34-56).

Internal endpoints (5-9, 10) use InternalRequestAuthentication (auth_backends.py:83-106): caller sends tenant_id + shared password == INTERNAL_PASS in the body; request.user/auth = tenant_id.

5. Endpoint traces

5.1 POST /api/miniapp/subscriptions/initiate/

View: InitiateSubscriptionView, miniapp/views.py:38-208. Auth: FederatedIdentityAuthentication (views.py:39), ExternalUserPermission ESM (views.py:40-43).

Request body (frontend auth.ts:181-191): {payment_period: "monthly"|"quarterly"|"half_yearly"|"yearly", module_id?: string, subscription_id?: string}.

  1. tenant_id = request.auth (views.py:68).
  2. InitiateSubscriptionSerializer (serializers.py:12-65): requires tenant_id in context (32-34); subscription_id queryset scoped to the tenant's non-null-module subscriptions (35-37); validate requires module_id or subscription_id (49-54), resolves module via helpers.checked_module(module_id) → outbound GET to Package service {PACKAGE_SERVICE}api/check-module/ (helpers.py:72, 298+) — fetches the module's name/price/vat/services; sets attrs["module_data"] (57-64).
  3. Tenant lookup by tenant_id → 404 if missing (views.py:81-86).
  4. Price: calculate_payment (views.py:45-65): total = module.price × months(payment_period) (choices.py:37-47) + VAT per module.vat (choices.py:61-70); rounded to 2 dp.
  5. Outbound to IAM (views.py:110-124): POST {IAM_SERVICE}api/tenant-user-info/ (helpers.py:144) with {tenant_id, password: INTERNAL_PASS, subscribed_services: [], subscription_expiry: expiry_date, package_upgrade: True} (expiry from choices.get_time_period days, views.py:104-108) — refreshes the user's subscription claims in IAM.
  6. Creates Payment row (views.py:126-138): get_or_create on (tenant_id, transaction_id=module id, subscription_id, product_name=module name, service_type=SUBSCRIPTION, total_amount, payment_status=0 pending). The payment app's tables are used directly, but no payment app view is invoked.
  7. Creates BillItem (views.py:140-147): module_id, quantity 1, rate = module price, amount = sub_total.
  8. Payment "initiation" is a stub (views.py:149-154): EsewaPaymentService.initiate_payment (services.py:70-85) returns a random 12-char alphanumeric transaction_id, the computed amount, and payment_url: None ("Not used for miniapp"). No eSewa ePay API call, no FonePay, no payment-service call.
  9. Creates Subscription + SubscriptionLog (views.py:156-186): Subscription(payment_period, subscription_type=module_addition, subscribe_date=today, expire_date=+period days, price=total, payment_status=PENDING, active_status=ACTIVE, users=1); SubscriptionLog(payment_period, users=1, action=subscription, payment_status=PAID (views.py:181 — note: log says paid while the Subscription row is still pending), price, subscription_type=module_addition, user_id=None).
  10. Response 200 (views.py:188-196): payment_id, transaction_id, amount, module_id.

Error paths: serializer invalid → 400 (views.py:72-73); tenant missing → 404 (84-86); IAM refresh non-200 → 400 "Failed to refresh subscription expiry in IAM" (114-124); any exception → 500 (197-208).

Gateway finding: the miniapp subscription payment does not route through the TMS payment app, eSewa ePay, or FonePay. The real eSewa ePay status check (ESEWA_STATUS_URL) exists only in the payment app for portal flows (§5.9). See §10 unknowns.

5.2 POST /api/miniapp/subscriptions/verify/

View: VerifyPaymentView, miniapp/views.py:211-332. Same auth as initiate (views.py:212-214). Body: {transaction_id} (frontend auth.ts:197-207).

  1. VerifyPaymentSerializer (serializers.py:68-72): transaction_id required; optional amount.
  2. Payment row must exist with that transaction_id and the tenant → 400 if not (views.py:225-231).
  3. Verification call is a stub (views.py:233-235): EsewaPaymentService.verify_payment (services.py:27-68). Behavior is gated by getattr(settings, "ESEWA_MOCK_MODE", True) (services.py:46) — ESEWA_MOCK_MODE is not defined in config/settings.py or .env, so the mock branch is taken by default: returns {success: True, transaction_id, verified_at} without calling eSewa. The non-mock branch (services.py:48-64) would GET ESEWA_VERIFY_URL?merchant_code=...&transaction_uuid=... with an X-API-KEY header, but ESEWA_VERIFY_URL/ESEWA_MERCHANT_CODE are also absent from settings/.env, so that path is dead unless configured externally.
  4. On success (views.py:237-289): sets Payment.payment_status=1 (paid); finds the module's Subscription by (tenant, module_type__module_id) → activates it (active_status=ACTIVE, payment_status=PAID, views.py:254-262); creates the TenantPackage row (views.py:264-271, package "miniapp module", trial=True, active) and TenantPackageModule row (272-280) if missing; updates SubscriptionLog payment_status=PAID (281-289).
  5. Outbound to Events (views.py:291-300): send_notification_task.delay (tasks.py:18-59) POSTs to {EVENTS_SERVICE}api/notification/miniapp/notify-user/ (tasks.py:21, 127-133) with entry_type SUBSCRIPTION_MANAGEMENT, service_type SUBSCRIPTION, receiving_user = provider code (esewa).
  6. Response 200 (views.py:302-311): payment_id, transaction_id, amount, module_id. On verification failure: Payment.payment_status=3 (failed), Subscription.payment_status=FAILED, SubscriptionLog payment_status=FAILED, 400 "Payment verification failed" (views.py:312-332).

5.3 GET /api/miniapp/subscriptions/status/

View: SubscriptionStatusView, miniapp/views.py:335-363. Same auth.

  1. tenant_id = request.auth (345).
  2. Package row: active TenantPackage for tenant (346-350) → serialized with SubscriptionStatusSerializer (serializers.py:80-91: is_active, is_expired, expire_date, remaining_days, payment_status, subscription_type="package", subscription_name).
  3. Module subscription: active Subscription with module_type not null, ordered -id, first (351-354) → same serializer + module_id (serializers.py:101-117).
  4. Response 200 {package: {...}, module: {...}} (355-363). No package → package=null; no module subscription → module=null.

Frontend: auth-context.tsx:75 fetches this on app auth (SunscriptionResponse shape, auth.ts:138-159); the upgrade page reads subscriptionData.module.module_id to pick the module (upgrade/index.tsx:72-88).

5.4 POST /api/miniapp/subscriptions/cancel/

View: CancelSubscriptionView, miniapp/views.py:366-387. Same auth. No serializer (CancelSubscriptionSerializer is empty, serializers.py:75-77). 5.5 POST /api/tenant/external-register/ — tenant provisioning (internal)

View: RegisterExternalEntityView, tenant_management/views.py:4784-4870. Auth: InternalRequestAuthentication (4789). Called by IAM during external registration: IAM-Backend/federated_identity/views.py:119-141 (register_tenant_if_needed; URL built in heimer_auth/helpers.py:52-54, 86-91), invoked from ExternalRegistrationView.post (views.py:293-299).   3. Tenant creation (serializers.py:380-443):
    • name sanitized via outbound POST to Configuration api/sanitization/form-data/ (serializers.py:290-304, helpers.py:167).
    • Company get_or_create for provider_code (399-402).
    • Tenant with tenant_id = generate_unique_tenant_id_with_provider_code (custom_functions.py:48-61): "ES_" + 6-digit number for esewa (prefix map custom_functions.py:28-32); name, email="", contact, verification=VERIFIED, complete=True, active_status=ACTIVE, user_type=genuine_user (404-420).
    • handle_package_creation (421-441): for ESM (ESM check at serializers.py:374-378) → outbound GET to Package api/check-package/ with provider_code + module ["payment"] (helpers.py:71, 268+); then creates TenantPackage + TenantPackageModule rows (306-338) and TenantContracts via helpers.checked_contract → Package api/check-contract/ (helpers.py:73; 340-378). Non-ESM → outbound GET api/package/check-trial-package/ (helpers.py:77) and trial package/modules.
    • handle_subscription_creation (443-477): for the payment module (ESM) creates a trial CREDIT subscription (payment_status=CREDIT, active, expire_date=None, price=0, subscription_type=module_addition, users=1) + SubscriptionLog (action=trial, payment_status=CREDIT); package subscription → ACTIVE with expire_date None, price 0.
  4. Config transfer, once per identity (4821-4835): transfer_configuration_once takes a row lock on the ExternalTenantLink (select_for_update); if fiscal_year is null it calls outbound POST to Configuration api/dashboard/data-transfer/ (custom_functions.py:570-587, helpers.py:161-163, timeout (2,6)) and stores the returned fiscal-year data as the "transferred" marker. What data-transfer does: doc 09 §6.1.
  5. Response 200 (4859-4870): tenant_id + TenantSerializer data (incl. subscribed_services, trial flag, user_range, payment_status). Errors: missing required fields → 400 (4842-4844); serializer errors → 400 with INCORRECT_DATA_FORMAT (4854-4858).

5.6 GET/POST /api/tenant/tour-status/miniapp/

View: TenantTrakerMiniapp (tenant_management/views.py:4085-4086) — subclass of TenantTracker (4019-4082) that only overrides auth to FederatedIdentityAuthentication (4086). The parent implements:

  • GET (4022-4045): tenant by request.auth; with ?tracker_name=X returns that field (4026-4028); otherwise reads tenant.product_tour JSON (default 8 false flags incl. miniapp, helpers.py:219-229) and returns {tour_taken: bool} for the requested take_tour key (must be a valid ProductTour value → else 400). All tours done → true (4037-4038).
  • POST (4061-4082): body {tour_taken: "miniapp"} sets product_tour[tour_taken]=True and saves (4073-4074); without tour_taken it falls back to generic tracker update (4047-4059).

Frontend: getTourStatus (profile.ts:120-131, GET with take_tour='miniapp') and updateTourStatus (profile.ts:133-144, POST {tour_taken:'miniapp'}), used by the dashboard onboarding tour (dashboard/index.tsx:230-234). 404 if tenant missing (4042-4045, 4079-4082).

5.8 Celery beat: subscription lifecycle notifications

config/celery.py:21-64 schedules, daily at 00:00 (crontab minute=0 hour=0): send_trial_expiring_notification_daily (service_type=trial_expiring), send_trial_expired_notification_daily (trial_expired), send_subscription_expiring_notification_daily (subscription_expiring), send_subscription_expired_notification_daily (subscription_expired) — all call miniapp.tasks.send_subscription_notifications (tasks.py:74-171).

Task logic: for the given service_type it selects tenants (e.g. trials expiring within 3 days: tasks.py:77-88; expired trials: 90-102; paid subscriptions expiring within the period: 104-124), chunks by 100 (126-131), and for each tenant POSTs to Events api/notification/miniapp/notify-user/ via send_notification_task (tasks.py:18-59; outbound URL tasks.py:127-133; loop 137-171 with 2 s sleep per chunk). A failed tenant is logged and skipped (139-153).

5.9 payment app (context): where eSewa ePay actually exists

/api/payment/ (config/urls.py:22) hosts the portal/CMS payment flows (payment/urls.py, 28 routes), e.g. test-status/ (PaymentTransactionStatus, payment/views.py:282+), renew-package-payment/, upgrade-package-payment/, credit-payment-internal/ (called by IAM, heimer_auth/helpers.py:96), paid-subscription-internal/ (helpers.py:97-99).

ESEWA_STATUS_URL usage (the only one in the repo, grep-verified): payment/views.py:176 — EsewaPayment.post (views.py:141-208) decodes the base64 eSewa ePay redirect payload, then GETs {ESEWA_STATUS_URL}/?product_code=&total_amount=&transaction_uuid= (settings.py:220; .env ESEWA_STATUS_URL= https://epay.esewa.com.np/api/epay/transaction/status/) and accepts only status "COMPLETE" with both uuid and code (181-191). FonepayPayment (views.py:212-275) validates the HMAC-SHA512 DV with FONEPAY_SECRET_KEY (239-258). These serve the TMS web tenant-portal onboarding/upgrade payments (IAMAuthenticationBackend), not the miniapp.

sequenceDiagram

10. Unknowns & open questions

  1. Who calls the 5 internal miniapp endpoints? No caller in any local repo. Package-service and PMS-service repos are not checked out here. Marked unknown; package service is the most likely consumer.
  2. Real eSewa payment is not wired to the miniapp flow in this code. initiate returns a random stub transaction id (services.py:77-85), verify is mocked by default (services.py:46; ESEWA_MOCK_MODE undefined), and the frontend fires verify immediately after initiate (upgrade/index.tsx:160-175) with no wallet-payment step. Whether production sets ESEWA_MOCK_MODE=false
    • ESEWA_VERIFY_URL externally (UAT/prod .env) is unknown from this checkout.
  3. payment_period mismatch: frontend sends half_yearly / yearly (upgrade/index.tsx:34-48) but TMS PaymentPeriod choices are halfyearly / annually (choices.py:11-17) → 6/12-month selection should 400 at the serializer ChoiceField unless an intermediate layer rewrites it (none found). Flagged as suspected bug.
  4. subscriptions/cancel/ has no known caller.
  5. ESEWA_KEY / ESEWA_SECRET_KEY (settings.py:215-217) are imported in custom_functions.py:15-20 but unused in the miniapp surface; they feed portal payment payload generation (custom.payment_detail).
  6. Whether the TMS/frontend CUSTOM_KEY equals IAM's CUSTOM_KEY_ESEWA is plausible (identical values in the .env files inspected) but IAM's .env is not in this checkout — noted, not verified.
