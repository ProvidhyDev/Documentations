1. Business overview (plain language for a NON-technical reader)

Projectmaster is the "company directory" of the Providhy ERP. For every business (tenant) that uses the platform it keeps the master lists of the people and terms the business deals with: its customers (who it sells to on credit), suppliers, employees, and payment terms (how many days a buyer gets to pay). Everything else in the ERP — sales invoices, credit, payments — hangs off these lists, which is why the service is called "project master".

On top of the normal ERP screens, Projectmaster serves a special, smaller surface for the eSewa miniapp — the wallet/credit app that eSewa merchants (called ESM, eSewa Merchant) use. A merchant who runs a small shop can extend credit to a regular customer ("buy now, pay later"). To do that inside the miniapp, the merchant: adds the customer (name, phone, and optionally a link to that person's eSewa wallet), searches their customer list (with each customer's current credit balance and whether the wallet link is connected), opens a customer to see their balance and the five most recent credit records, edits basic details, or removes the customer. Behind the scenes the app assembles that balance and connection status from sibling services (Sales keeps the credit records, CDXE keeps the "connection" between a merchant and a wallet user, Payment tracks pending payment requests).

The same surface also answers quick yes/no questions from other Providhy services: "for this merchant's company, is this eSewa wallet identifier a real, active customer of theirs (and a wallet user we may connect to)?" Sales asks this when listing or creating credit, CDXE when a connection is requested or approved, and Payment keeps the same check available for payment flows. Those internal questions are protected not by a login token but by a shared service password — an internal, service-to-service channel.

The business value: a merchant's credit book (who they are lending to and how much is owed) is managed in exactly one place, isolated per company, and safely linked to eSewa wallet identities so credit can be settled through the wallet.

3. Authentication & authorization

Mount: single prefix api/miniapp/ (core\urls.py:13). There is no public vs internal URL split; the split is per-view by permission class (3 federated-auth views, 3 internal-password views).

FederatedIdentityAuthentication — local copy at dashboard\auth_backends.py:166-203 (diff vs canonical IAM-Backend\federated_identity\auth_backends.py):

  1. Token extraction: helper.get_access_token(request, access_token_key="miniAppAccessToken") (auth_backends.py:169-171; helper.py:361-390) — checks, in order: cookie miniAppAccessToken → Authorization: Bearer <jwt> header → JSON body field miniAppAccessToken.
  2. Outbound verification: POST {IAM_API}/api/external/token/verify/ with {token} and the X-MINIAPP-TOKEN header forwarded (auth_backends.py:174-178, 206-219). IAM validates the token and the TOTP. This repo performs NO local TOTP check (no speakeasy/TOTP code anywhere — grep totp|speakeasy hits only core\settings.py:162 and auth_backends.py:176); TOTP verification happens on the IAM side (IAM internals out of scope).
  3. The JWT is decoded without signature verification (TokenBackend(algorithm="HS256").decode(token, verify=False), auth_backends.py:179) and its claims are trusted after step 2: user_id, tenant_id, subscribed_services, user_permissions, provider_code, user_type, tenant_root, username, product_code, external_identifier, subscription_expired (auth_backends.py:180-193) → attached to the request; returns (user_id, tenant_id) (auth_backends.py:194), so request.user = user_id, request.auth = tenant_id.
  4. Failures: IAM connection timeout/error → TemporaryServiceUnavailableError (auth_backends.py:196-200; a plain Exception, exception.py:9-12 — unhandled by DRF since the EXCEPTION_HANDLER config is commented out, core\settings.py:91-94 → Django 500); anything else → CustomAuthenticationFailed = HTTP 401 (auth_backends.py:202-203, exception.py:4-6).

Permission classes:

  • HasFederatedEntityPermission (auth_backends.py:222-229), used by all three public miniapp views:
    1. request.user_type must equal the view's required_user_type — all three views require ESM (eSewa Merchant) (views.py:23, 84, 215; choices.py:349-351).
    2. Delegates to HasPermission (auth_backends.py:123-154): POST + subscription_expired → PermissionError (125-126); tenant_root users are allowed without a call (127-128); otherwise GET {IAM_API}api/internal-check-permissions/?password=<INTERNAL_PASS>&user_id=<user_id> (auth_backends.py:131-133; helper.py:71) and the response must contain the view's required_feature_permission PR301 "Customer Creation" (views.py:21,82,213; choices.py:113) with the required action: add for create (views.py:22), edit for edit/detail (views.py:83) and view for search (views.py:214; action codes dashboard\choices.py:270-274). IAM call failure → TemporaryServiceUnavailableError (134-135).
    3. Permission split (2026-11-05): the old combined action add_edit no longer exists in ActionChoices — it is split into ADD = "add" and EDIT = "edit" (choices.py:270-274). Every view that checked add_edit now checks add on the create path and edit on the update path (see §4.4 and the flow notes); IAM must grant the two actions separately going forward.
  • InternalRequestPermission (auth_backends.py:157-163), used by the three internal views: static shared password — POST compares request.data["password"], GET compares request.GET["password"] against INTERNAL_PASS (helper.py:125-128, 33; .env:11). No authentication_classes is set on these views and no REST_FRAMEWORK default exists (core\settings.py:91-94 commented out), so they run as anonymous + shared secret; there is no per-tenant authorization beyond the tenant_id the caller puts in the body.
  • Inline password checks (2026-11-05): the new get-all party endpoints do NOT use InternalRequestPermission; they verify the body's password themselves with helper.validate_internal_pass and return 401 on mismatch — CustomerGetALLAPIView (customer/views.py:556-568), SupplierGetALLAPIView (supplier/views.py:560-577, declared AllowAny via a permisson_classes typo), EmployeGetALLAPIView (employee/views.py:264-278, AllowAny). ListPaymentTermTenantView uses the class (payment_term/views.py:683-684). Same trust model as above: shared secret + caller-supplied tenant_id, no per-tenant authorization.

Tenant scoping: tenant_id from the JWT (request.auth) is injected into the filterset data (dashboard\mixins.py:21-23) and into every serializer context (views.py:30,109,229); every Customer query also filters customer_identity__provider_code = request.provider_code (views.py:93, 299; filters.py:22-24) and excludes active_status = "inactive" (filters.py:26-27; views.py:94, 300). MiniAppFilterMixin injects provider_code into the filterset kwargs (miniapp\mixins.py:11-21); FilteredAPIViewMixin adds tenant_id + fiscal-year date bounds (dashboard\mixins.py:14-45; the date bounds are unused by CustomerFilterSet).

Which endpoints use what: all 5 federated endpoints (create/search/detail×3) use FederatedIdentityAuthentication + HasFederatedEntityPermission (views.py:19-23, 80-84, 211-215); the 3 internal endpoints use only InternalRequestPermission (views.py:256, 274, 324). No endpoint in the miniapp app uses different/extra auth. The domain-app internal endpoints added in the 2026-11-05 sync use the inline shared-password pattern (§4.4).

8. Business process walkthrough (non-technical)

8.1 Bikash, a merchant, adds a customer and watches the credit book

Bikash runs a hardware shop and lends tools to regular customers before they pay. In his eSewa miniapp he opens "Customers" and adds "Sita's Kitchen" — a name, the customer's phone number, and, because Sita also has an eSewa wallet, he pastes Sita's wallet ID so the two accounts are linked. The system (Projectmaster) first checks that his login is a genuine eSewa merchant belonging to his company, and that his company's subscription allows creating customers. It stores the customer under his company alone — other companies in the platform can never see or touch this record — and, because the company has an "accounts receivable" default configured, it quietly tags the customer with the right accounting account so later invoices post correctly. A short activity note ("Bikash created customer Sita's Kitchen") is written to the company's activity log.

From then on, the customer list shows Sita's Kitchen with two live numbers assembled from other services: the credit balance (from the Sales service, which owns the credit records) and the connection status (from CDXE, which manages the link between Bikash and Sita's wallet). Bikash can filter the list by "connected", "pending", or "offline" customers, search by name or phone, and tap a customer to see the last five credit entries and the outstanding unpaid amounts. He may correct the name or add a note, but the phone number and the wallet link are fixed once set.

8.2 Sita gets "connected" to Bikash — a cross-company handshake

For Sita's wallet to settle credit through the miniapp, a connection must exist between Bikash (the merchant) and Sita (the wallet user). When Bikash sends the connection request, the connection service (CDXE) does not trust the name alone: it asks Projectmaster, "in Bikash's company, is this wallet ID a real, active customer of his, and is it flagged as a wallet user?" Projectmaster answers from its customer-identity table. Only if the answer is yes (or the receiver is already a registered platform user) does the connection proceed, and both sides get notified. Later, when Sita approves or declines the request, CDXE asks Projectmaster the same question once more to fetch the customer's name for the notification. In plain terms: Projectmaster is the referee that confirms "this wallet really belongs to a customer of this shop" before any money link is created.

8.3 Removing a customer safely

When a customer relationship ends, Bikash deletes the customer from the miniapp. The system first asks the Payment service whether any payment request is still in flight for that customer — if so, deletion is refused with a clear message, because the money flow would dangle. Otherwise it asks Sales to clean up the customer's miniapp transaction records, and — only if the customer was a linked wallet user — asks CDXE to remove the connection. After that, the customer is marked inactive (not physically erased, so historical records stay consistent) and an activity note is written. Because each company's records are isolated by tenant, Bikash can only ever delete his own customers; a customer that belongs to another company or another provider simply doesn't exist to him.

11. Unknowns & assumptions

  • dummy-customer-check has no discoverable caller. The endpoint always returns {"is_provider_user": true} (views.py:258-262) — a stub. check_user_url_registry (miniapp\registry.py:10-12) is defined but referenced nowhere in this checkout, and the ESEWA_USER_CHECK_API env var (.env:49) is not read by any view. The CDXE-REBOOT repo has its own ESEWA_USER_CHECK_API (.env:50, pointing at a dummyjson.com URL) that is likewise unreferenced by code. Inferred: the design intent is "service X asks Projectmaster whether an external identifier is a real eSewa user"; the actual consumer is unverified.
  • TOTP verification location: this service forwards X-MINIAPP-TOKEN to IAM's /api/external/token/verify/ (auth_backends.py:174-178, 206-219) and decodes the JWT with verify=False (line 179). Whether/how IAM validates the TOTP and the signature is out of scope (IAM tracer's document) — assumed enforced there.
  • JWT trust model: after IAM verification, all claims (tenant_id, provider_code, user_type, external_identifier, …) are taken from the unsigned local decode (auth_backends.py:179-194). This is by design but means every security property rests on the IAM verify call + network trust.
  • Internal endpoints authorize by shared secret only (auth_backends.py:157-163, INTERNAL_PASS .env:11); the caller-supplied tenant_id is trusted verbatim (e.g. customer-check with tenant_id="all" spans all tenants — views.py:331, serializers.py:446-454). Whether that exposure is acceptable is a design judgment, not something the code answers.
  • Delete cleanup failures are swallowed: task_runner converts per-task exceptions to {"error": ...} (helper.py:313-314), so the customer is soft-deleted even if the Sales/CDXE/Payment calls failed (inferred risk, not a documented behavior).
  • Celery is nominal: send_activity_log is a shared_task but invoked inline (views.py:61,143,200), no broker/worker is configured in core\settings.py or Dockerfile. Whether a separate worker deployment exists in the cluster is unknown from this repo.
  • task_runner is sequential, not concurrent, and the a*-named helpers are synchronous despite httpx.Client type hints (helper.py:303-315, async_func.py:26-212). A commented-out async runner exists (async_func.py:215-223, helper.py:318-331).
  • Search-view edge case: if CustomerFilterSet is invalid, filter_queryset returns None (dashboard\mixins.py:56-58) and the view passes it straight to the serializer (views.py:222); the resulting behavior (DRF error/500) was not executed and is unverified.
  • q filter: optional (only applied when present); passing an empty q raises a bare Exception (filters.py:16-20) → unhandled 500 (inferred from the code path).
  • Frontend GET detail URL lacks a trailing slash (customer.ts:98) → relies on Django's APPEND_SLASH 301 redirect (verified by reading the URL strings; redirect behavior is Django default, not repo code).
  • messages.py defines RECORD_NOT_FOUND twice (line 6 "Record not found" and line 25 "Record not found."); the later binding (line 25) is the value actually served.
  • customer-check return_data mechanism was a suspected bug (serializer.data with no instance) — verified NOT a bug in installed DRF 3.18.3: the data property falls back to to_representation(self.validated_data) (.venv\...\rest_framework\serializers.py:249-255), matching the overridden to_representation (serializers.py:443-467).
  • Sales payment_term/GL handling in miniapp create: gl_mapping is only auto-set from the Configuration service's "Account Receivable" entry (serializers.py:108-126); if the tenant has no such configuration the customer is created with gl_mapping=null (code path verified; the accounting consequences are outside this repo).
  • entry_by username mangling: helper.get_username strips the last _segment from the JWT username (helper.py:196-201) — presumably to normalize name_suffix style identities; the exact convention is inferred.
  • skip_mobile_validation (serializers.py:37-41) is set but never read in this serializer (observation).
  • mcp_tools app listed in the shared-context repo map does not exist in this checkout (verified by directory listing).
  • transfer-payment-term has no declared authentication (2026-11-05): DefaultPaymentTermView carries no auth/permission class and the global REST_FRAMEWORK block is commented out (core\settings.py:92), so DRF defaults (anonymous + AllowAny) apply — a bulk, multi-tenant, write-capable endpoint reachable without credentials at the service level.
