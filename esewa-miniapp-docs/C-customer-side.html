The Customer (eSewa User) Side — Feature Guide

For the business person AND the engineer. The customer app runs inside the eSewa wallet app — it is NOT in the miniapp-esewa repo (verified on the production branch: that repo contains only the merchant UI). Everything in this guide is the customer-facing backend surface the wallet app calls, traced from the code (docs 03–10). Where a flow is not wired anywhere yet, it says so honestly.

Identity: a customer is an eSewa wallet user (entity type ESU). Their wallet id is their login. They only see a merchant's credit data after the merchant connected them (section 2).

Every call carries the customer's JWT + a fresh 6-digit TOTP code, verified by each service against IAM (doc 02). Internal hops between services use the shared internal password.

1. Register & log in

What it is. Same door as the merchant: first time → accept terms → registered; after that → login. Their eSewa identity (wallet id) is the account.

How it works:

  1. Wallet app → IAM POST /api/external/register/ (eSewa token + wallet id + provider esewa) — one time; IAM links the identity, TMS provisions/links the tenant side, Configuration copies default rules (docs 03 §5.1, 08 §5.5, 09 §6.3).
  2. Login → IAM POST /api/external/token/ → JWT (user, tenant, type ESU, permissions) + refresh (doc 03 §5.2).
  3. Auto-refresh on expiry via POST /api/external/token/refresh/ (doc 07 Part B §B.3).

Rules & edge cases. Same as merchant (M-doc §1): unique per provider, idempotent provisioning, funnel event + welcome notification recorded.

2. Connection requests (merchant invites, customer decides)

What it is. When a merchant sends a connection request, the customer gets an in-app notification. Approving it is what unlocks seeing the merchant's credit, disputes and payment requests.

How it works:

  1. Merchant side creates the pending connection with a 5-digit code (CDXE — merchant guide §3).
  2. Customer opens the request → wallet app → CDXE POST /api/miniapp/approve-reject-connection/{code}/ (doc 05 §5.6):
    • Approve: connection becomes approved (code validated, code cleared), both sides notified.
    • Decline: both connection rows are deleted — the invitation disappears, nothing is stored.
  3. Customer lists their merchants: CDXE GET /api/miniapp/connection/search/ (their connections) and GET /api/miniapp/merchant/detail/{pk} (merchant info incl. outstanding credit owed — internally enriched from the Sales ledger, doc 05 §5.16/§5.4).

 participant M as Merchant

 M->>C: create-connection (pending + code)
 C--)U: notification: merchant X wants to connect

Rules & edge cases.

  • No connection = no credit visibility. The customer's app only surfaces merchants they approved.
  • Decline is a hard delete (no history) — doc 05 §5.6.
  • If the merchant later terminates the connection, it becomes terminated (history kept) — doc 05 §5.7.

3. See my credit

What it is. Everything the customer owes: per-merchant totals, each credit entry, the running ledger (credits + payments) and statements.

How it works (all via CDXE, which pulls live data from Sales internally):

  1. My credits (for a merchant): CDXE GET /api/miniapp/get-credit/ — the customer's credit records for connected merchants (internally: Sales credit/user/search/ + credit/detail/customer/ over the connected merchant tenant ids — doc 05 §5.8).
  2. Totals: GET /api/miniapp/credit/overview/ (outstanding, paid) (doc 05 §5.12).
  3. Ledger: GET /api/miniapp/credit/ledger/ + /credit/ledger/overview/ (by connection + dates) (doc 05 §5.10/5.11).
  4. One credit entry: GET /api/miniapp/credit/detail/{id}/ (doc 05 §5.13).
  5. Statements/history: GET /api/miniapp/settlement/search/ + /detail/{id}/ (doc 05 §5.17/5.18).

 A[My merchants] --> B[Credits list]
 B --> C[Credit entry]
 A --> D[Totals / ledger / statements]
 B --> E[Pay - sections 5 and 6]
 C --> E
 B --> F[Dispute - section 4]

Rules & edge cases.

  • All reads are scoped by the approved connections of this customer (CDXE manager get_connected_merchant_tenant_ids — doc 05 §3/§6) — a customer can never see another customer's numbers.
  • Data lives in Sales; CDXE is the customer-facing proxy (merchant side reads Sales directly — merchant guide §4).

4. Raise an issue (dispute)

What it is. The customer flags a credit entry — wrong amount, already paid, not their purchase. The merchant then fixes (edits) or cancels (deletes) the credit (merchant guide §7).

How it works:

  1. Raise → wallet app → CDXE POST /api/miniapp/dispute/raise/ → internally Sales POST /api/miniapp/dispute/raise/ (doc 05 §5.19 → doc 04 §5.7).
  2. Sales guards: the credit must be unpaid, have no settlement yet, and have no other pending dispute — otherwise 400 (doc 04 §5.7).
  3. List/detail: CDXE dispute/search/ + dispute/detail/{id}/ (internally Sales customer variants, doc 04 §5.27/5.28).
  4. Withdraw: CDXE POST /api/miniapp/dispute/cancel/{id}/ (doc 04 §5.8).
  5. Merchant resolution (edit/delete) updates the dispute to resolved — the customer sees the result via their credit list/detail again; every step notifies Events.

 Disputed --> UnpaidCredit: customer withdraws

Rules & edge cases.

  • While a dispute is pending the credit can't be settled (either side).
  • The server side is complete and live; the customer-side raise UI belongs to the wallet app, not the miniapp-esewa repo (doc 07 §C.5).
  • Known code quirk: one dispute-delete path writes the wrong status field (resolved flag may not persist) — doc 04 §11.7.

5. Payment requests (merchant asks, customer pays or declines)

What it is. The merchant sends a pay request (for one credit or the full amount owed). The customer gets a notification and chooses: pay from the eSewa wallet or decline.

How it works (customer side):

  1. Request arrives (created merchant-side — merchant guide §6); customer is notified by Events (doc 10 §7.3).
  2. Customer opens it → wallet app → CDXE POST /api/miniapp/payment/request/pay/{id}/ with status completed + wallet transaction_id (or declined). For completed, the payload must carry a signature — HMAC-SHA256 over the request keyed with the shared eSewa key + a 10-digit TOTP (doc 05 §5.15, miniapp/utils.py:19-42).
  3. CDXE → Payment POST /api/esewa/payment/request/pay/{settlement_id}/ (marks the record completed/declined; guards: must be requested, must belong to a merchant connected to this customer — doc 07 A.4).
  4. Payment → Sales POST /api/miniapp/payment/request/settle/ (doc 07 C.1; doc 04 §5.21):
    • completed → settlement approved, the credit(s) reduced → customer sees it in their ledger/statement;
    • declined → rejected, credits untouched;
    • (merchant cancel → draft — customer just sees the request disappear, merchant guide §6).
sequenceDiagram
 participant U as Customer (wallet app)
 participant C as CDXE
 participant P as Payment
 participant S as Sales
 participant E as Events
 U->>C: payment/request/pay/{id} (completed + txn id + SIGNATURE)
 C->>C: verify HMAC signature
 C->>P: payment/request/pay/{settlement_id}
 P->>S: payment/request/settle (completed)
 S->>S: settlement approved, credits reduced
 C--)E: notify both sides
 Note over U,S: declined = same path -> rejected, credits untouched

Rules & edge cases.

  • One pending request per customer at a time (blocks delete/terminate on the merchant side — doc 05 §5.7).
  • In this code build the wallet charge itself is mocked (no live ePay call in these repos — doc 07 §C.5); the flow above is exactly what happens around it.
  • The miniapp-esewa repo contains the customer pay function (payRequestedPayment) but it is not wired to any page and doesn't produce the signature — evidence the customer UI lives in the wallet app, not this repo (doc 07 §B.5/§C.5).

6. Settle by myself (customer-initiated payment)

What it is. Without waiting for a request, the customer can pay on their own: (a) one specific credit in full or part, or (b) anything pending with a chosen merchant — the payment is allocated across that merchant's open credits.

How it works (both variants are the same call with different allocations):

  1. Customer picks a merchant + amount → wallet app → CDXE POST /api/miniapp/credit/pay/ with merchant_identifier, total_allocated_amount, and items (credit id + allocated amount per entry) (doc 05 §5.9).
    • variant (a): items = the single credit;
    • variant (b): items = that merchant's open credits (the app allocates the amount across them).
  2. CDXE first does a dry run (commit=false) — validates sums + the approved connection, and answers: Validation successful. Ready to commit. (doc 05 §7.2).
  3. Then the real commit (commit=true) with the SIGNATURE header (HMAC, same scheme as section 5) → CDXE → Sales POST /api/miniapp/credit/pay/ (doc 04 §5.6).
  4. Sales creates an approved settlement in one atomic step: reduces the credits, records the payment, and registers the completed request with Payment (transaction id from the wallet) (doc 04 §5.6).
  5. Events notifies the merchant that the customer paid (doc 10 §7.2).
flowchart TD
 A[Customer picks merchant + amount] --> B[Dry run commit=false]
 B -->|invalid| X[Error - nothing changed]
 B -->|OK Ready to commit| C[Commit commit=true + SIGNATURE]
 C --> D[Sales: approved settlement]
 D --> E[Selected credits reduced]
 D --> F[Payment record completed]
 D --> G[Merchant notified]

Rules & edge cases.

  • Only connected merchants can be paid this way; only credits that are unpaid and not in dispute qualify.
  • The signature check means the wallet must be the one committing — a plain app without the shared key can't forge a payment (doc 05 §3).
  • This flow's frontend functions exist in miniapp-esewa (settleCreditCustomerInitiated, customerInitiatedPaymentPay) but are exported, unused stubs — again pointing to the wallet app as the real client (doc 07 §B.5).

7. Notifications

What it is. The bell: connection requests, credits added, payment requests, payment results, dispute outcomes, due-date reminders.

How it works:

  1. Backends push via Events notify-user/ (internal, queued, per user, gated by the customer's notification preferences) (doc 10 §7.1).
  2. Wallet app polls GET /api/notification/miniapp/list/ (federated) and can mark read / change preferences (mark-read/, notification/preference/) (doc 10 §4/§5).

Rules & edge cases. In-app only (no email/SMS) — doc 10 §11. Daily 6:00 AM due-date/overdue reminders for the customer's credits are generated by Sales/CDXE scheduled jobs (doc 04 §8; doc 05 §9).

Appendix B — honest caveats

  • The customer UI is not in any repo we have: miniapp-esewa (production branch, verified 2026-11-04) contains only merchant pages; the customer app ships inside the eSewa wallet app. This document therefore describes the backend contract the wallet app implements.
  • In the merchant repo, all customer-side request functions are exported but unused (no page sends them, and the SIGNATURE header is never produced by that repo) — consistent with the wallet app being the real caller (doc 07 §B.5/§C.5).
  • Mock ePay: no live eSewa ePay integration in the backend repos of this build — wallet charges are status records / env-mocked (doc 07 §C.5).
  • Dispute-status field quirk on one delete path (doc 04 §11.7); mark-read implementation quirk (doc 10 §11a).
